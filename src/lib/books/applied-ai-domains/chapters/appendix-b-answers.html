Chapter 58 — The Physical AI Landscape & Embodiment

Exercise 58.1 [W]. Sense (turning raw sensor signal into a useful representation of the world) is covered by Chapter 59. Plan (deciding what to do next given that representation) is covered by Chapters 60-61. Act (turning a decision into motor commands) is covered by Chapter 63.

Exercise 58.2 [W]. At equilibrium, the proportional term kp * error must exactly balance the constant bias force for the system to hold still. If the error were zero, there would be no counter-force at all, and the bias force would immediately push the system away from zero again, so a nonzero error is required just to generate the counter-force needed to stay in place. This is structural, not a tuning failure; only the integral term, which keeps accumulating regardless of how small the current error is, can eventually cancel it.

Exercise 58.3 [A]. A smaller ki (0.5 vs. 2.0) means the integral term accumulates counter-force more slowly, so the steady-state error would be expected to land somewhere between the full-PID result (-0.0016) and the P-only result (0.3857), closer to zero than P-only because there is still some integral action working to cancel the offset, but not as tight as ki=2.0 because it takes longer for the accumulated integral to build up enough counter-force to fully cancel the bias.

Exercise 58.5 [E]. Tuning directly on hardware skips the cheap, safe iteration simulation provides. Every bad gain choice during tuning is a real collision or a real fall, not a discarded simulation run. It also means starting from scratch with no prior estimate of reasonable gains, which is slower in practice than tuning roughly in simulation first and refining on hardware. Concrete risk: a kp set too high during live tuning can cause violent oscillation that damages the actuator or the arm itself before anyone can cut power.

Exercise 58.6 [E]. With no obstacles and a fixed task, the extra flexibility a 7th DOF provides, avoiding awkward configurations or obstacles for the same end-effector pose, has no work to do. The 6-DOF arm is exactly sufficient to reach any position and orientation the task requires, is cheaper to build, and has a control/planning problem with a unique (or at most doubly-valued) solution per target pose rather than the infinite family of solutions a redundant 7-DOF arm introduces, a strictly simpler problem for no lost capability given the constraints.

Exercise 58.7 [R]. Discussion only, no single answer. Closed-form inverse kinematics relies on being able to solve a system of trigonometric equations symbolically, which is tractable for 2 (and with effort, 3) links because the equations stay low-dimensional and the geometry is simple enough to enumerate the small number of solution branches (elbow-up/elbow-down) by hand. Past that, the equations become a coupled nonlinear system with no general closed-form solution, and the number of solution branches can grow or become degenerate (redundant arms have infinitely many). Numerical methods (e.g. Jacobian-based iterative solvers) trade an exact symbolic answer for an iteratively-refined numerical one that scales to arbitrary link counts.

Exercise 58.8 [W]. High-level planning (10 Hz) only needs to reconsider its decision a few times a second because the situation it’s reasoning about, which task to do next, changes slowly. Manipulator joint control (500 Hz) is holding a physical system stable against continuous disturbances (gravity, contact forces, its own momentum) that must be corrected many times per second or the system diverges, the same open-loop-vs-closed-loop argument from this chapter, applied to loop rate rather than control strategy: a slow correction on a fast-changing physical quantity is effectively no correction at all.

Chapter 59 — Perception for Physical AI

Exercise 59.1 [W]. In order of increasing compute cost: object detection (cheapest sufficient choice for “is there an obstacle in this general area?”, e.g. a mobile robot’s coarse obstacle check), semantic segmentation (cheapest sufficient choice for “which pixels are drivable floor?” where individual object identity doesn’t matter), instance segmentation (necessary when a robot must pick up this specific object among several of the same class, e.g. “grasp this cup, not that one”).

LiDAR measures depth directly by timing a reflected laser pulse per point, which needs no texture or visual correspondence at all. It works identically on a blank wall as on a textured one.

Exercise 59.5 [E]. Skipping calibration means using the lens’s millimetre focal length instead of the calibrated pixel focal length the depth formula actually requires. The two aren’t interchangeable, and using the wrong one produces a depth map that’s systematically wrong by a constant scale factor, not just noisier. Concretely: every recovered depth will be off by the ratio between the true calibrated pixel focal length and whatever pixel-equivalent was guessed from the datasheet, and there’s no way to tell from the output alone that it’s wrong. The map will still look plausible, just incorrect, which is worse than an obviously broken result.

Exercise 59.6 [E]. Against shipping it: a 2% accuracy gain rarely survives contact with a control loop that now has 3x less budget left for the actual control computation. If the slower model’s p99 no longer fits inside the loop’s period (Chapter 58), the robot is acting on stale information some fraction of the time, and a stale-but-plausible perception can be worse than a slightly-less-accurate but timely one. Unless the accuracy gain addresses a specific, costly failure mode the current model has and the new p99 still fits comfortably inside the latency budget with margin, the latency regression should block the change.

Exercise 59.7 [R]. Discussion only, no single answer. A false-positive loop closure tells the SLAM system two poses are the same place when they aren’t, and because pose graph optimization treats loop closure edges as hard constraints to satisfy, a wrong one doesn’t just fail to help. It actively warps the rest of the map to be consistent with a false constraint, potentially folding two distant, genuinely different locations into the same point on the map. This chapter’s brief mention of loop closure as “recognition and correction” doesn’t cover that the correction step has no way to distinguish a correct match from a confident wrong one without additional consistency checks (e.g. requiring geometric agreement across several nearby poses, not just one).

Exercise 59.8 [W]. This isn’t a contradiction because the two sensors’ errors are independent. The camera’s noise and the IMU’s noise don’t correlate, so when they’re combined with inverse-variance weighting, the combined estimate’s variance is provably lower than either individual variance (the harmonic-mean-like combination of independent variances is always smaller than the smaller of the two). The fused RMSE beating even the better sensor isn’t an artifact of this particular run; it’s the mathematical guarantee that motivates fusion in the first place, whenever the independence assumption genuinely holds.

Chapter 60 — World Models & Predictive Learning

Exercise 60.1 [W]. Pixel-space generative models predict the next frame, pixel by pixel. Latent/representation predictors (JEPA family) predict the next embedding. Explicit dynamics models predict the next state in a hand-defined state space.

Exercise 60.2 [W]. Context encoder, target encoder, predictor. The context encoder is the only one receiving gradients directly during training. The target encoder updates only via EMA, with no gradient of its own, and the predictor is trained via the loss between its output and the target encoder’s output.

Exercise 60.3 [A]. A dashboard tracking only loss would see the collapsed run’s loss (0.000003) as dramatically better than the healthy run’s (0.000833) and flag it as the superior model. Loss alone has no way to distinguish “learned to predict accurately” from “learned to output nearly the same value regardless of input,” since both produce a very small prediction error once the target itself has collapsed to near-constant. Procedure 60.3’s variance check adds exactly the missing information: it measures whether the embeddings themselves carry meaningful spread across different inputs (0.00540 for the healthy run vs. 0.00039 for the collapsed run, roughly 14x smaller). A low loss with a collapsed embedding spread reveals the low loss is cheap and meaningless, not evidence of good prediction.

Exercise 60.4 [A]. The variance check (Procedure 60.3) catches representation collapse: the model mapping every input to nearly the same embedding, making prediction trivially easy. The mean-baseline check catches a different failure mode: even with genuine, non-collapsed variance in the embeddings, the predictor itself could still be ignoring its context input and just learning to output the batch’s average target embedding, which is a different kind of shortcut that a variance check alone wouldn’t necessarily catch (the target encoder’s embeddings could have healthy spread while the predictor still cheats by ignoring context and outputting something close to the mean target). Both checks are necessary because they isolate different components: variance checks the encoder/representations; the mean-baseline check specifically verifies the predictor is actually using its input rather than only the target distribution’s central tendency.

Exercise 60.5 [E]. “Before celebrating, check the embedding variance directly, not just the loss. This chapter’s own Worked Example showed a collapsed run’s loss dropping to 0.000003, nearly 300x lower than a healthy run’s 0.000833, while its embedding spread was about 14x smaller, meaning it had learned to output nearly the same value for every input rather than actually learning to predict. An unusually fast, unusually low loss on a joint-embedding model is specifically the symptom to be suspicious of, not celebrate, until the variance check confirms it isn’t collapse.”

Exercise 60.6 [E]. With only a 5% mask ratio, nearly all of an image’s patches remain visible, so the predictor could learn to simply copy or lightly interpolate from the small number of masked patches’ immediate visible neighbours. Spatially adjacent patches in a real image are often nearly identical or smoothly varying, so a near-complete context lets the predictor solve the task through local copying/interpolation rather than genuinely understanding the scene’s broader structure. At a 50% mask ratio, entire regions can be hidden with no immediately-adjacent visible patch to copy from, forcing the predictor to actually use higher-level structural understanding (object shape, scene layout) to make a reasonable prediction, since simple local copying is no longer sufficient.

Exercise 60.7 [R]. VICReg doesn’t need a second encoder because it prevents collapse through an explicit loss term rather than an architectural asymmetry: it directly penalises any embedding dimension whose variance across the batch falls below a threshold, making the trivial “collapse everything to one point” solution actively costly to the loss function rather than architecturally hard to reach. JEPA and BYOL instead rely on the EMA target encoder’s slow, gradient-free updates to prevent the target from collapsing in lockstep with the online network, an architectural mechanism. VICReg substitutes a direct mathematical penalty for that architectural trick, so there’s no need for two separately-updated networks at all. A single encoder trained with the variance (and covariance) regularisation term added to its loss is sufficient.

Chapter 61 — Vision-Language-Action Models

Exercise 61.1 [W]. A transformer predicting the next language token and a transformer predicting the next action token are doing the same underlying computation. If an action can be represented as a discrete token from a fixed vocabulary, “predict what to do next” becomes just another instance of autoregressive next-token prediction, identical in mechanism to how a chatbot predicts the next word.

Exercise 61.2 [W]. Discrete action tokens (RT-2): reuses the entire LLM stack unchanged, but loses precision to binning. Open-weight discrete backbones (OpenVLA): same precision trade-off, but inspectable/fine-tunable by anyone. Continuous action heads (π0): full continuous precision, better for smooth/fast or multi-modal-solution tasks, but requires a separate action-generation mechanism bolted onto the VLM.

Exercise 61.3 [A]. The image-scrambled condition (0.278) falling below the majority-class baseline (0.316) is more informative than merely “lower than instruction-scrambled” because it shows the model is actively worse than a trivial always-guess-the-common-answer strategy when denied correct visual input, meaning its instruction-only guesses are actively miscalibrated, not just uninformed. Being merely lower than the other scrambled condition wouldn’t by itself establish this; only comparing against the baseline reveals that visual grounding isn’t just helpful here, its absence makes the model’s guesses actively counterproductive relative to a naive baseline.

Exercise 61.4 [A]. The loss curve alone (converging to 0.0001) only proves the model fit its training objective well. It cannot distinguish between “the model learned to use both image and instruction correctly” and “the model found a shortcut using only one modality (or memorized training examples) that happens to also minimize loss.” The full-accuracy-vs-scrambled comparison specifically proves genuine dual-modality dependence: since scrambling either modality independently causes a measurable accuracy drop below the full-accuracy condition, the model cannot be ignoring either one. A model that ignored the instruction entirely would show no accuracy change when the instruction is scrambled, and this pattern is absent from the measured results.

Exercise 61.5 [E]. “A converged training loss only tells us the model fit its training objective. It doesn’t tell us whether the model is genuinely using both the visual input and the language instruction, or has found a shortcut that relies mostly on one. Before considering this ready to deploy, run a modality-ablation check like this chapter’s Worked Example: scramble the image and the instruction independently and confirm accuracy drops meaningfully in both cases, ideally compared against a majority-class baseline, since a model that’s secretly ignoring one modality would show a perfect loss curve but fail unpredictably in deployment whenever that ignored modality actually matters.”

Exercise 61.6 [E]. With only 32 bins across the gripper’s full closure range, each bin represents a fairly coarse chunk of the physical closure distance. For a task like picking up a fragile object (an egg, a piece of fruit) where the correct grip force needs to fall within a narrow window (enough to hold securely, not enough to crush), the nearest available bin might apply meaningfully too much or too little force. The visible failure mode would be inconsistent task success: the object is crushed on some attempts (bin rounds up to too much force) and dropped on others (bin rounds down to too little), even though the model’s higher-level decision, “grasp this object,” was correct, because the actual executed force came from an imprecise discretisation grid rather than a genuine modeling failure.

Exercise 61.7 [R]. A discrete token vocabulary must commit to one specific bin per action dimension per prediction. Even if two different grasp approaches (e.g., approaching from the left versus the right) are equally valid, the model’s autoregressive token-by-token generation forces it toward one particular sequence of tokens, and averaging or blending between the two valid options during training can produce a token sequence that represents neither option well (a blurry compromise rather than a clean choice). A continuous flow-matching or diffusion head instead models a full probability distribution over the continuous action space directly, and can represent genuinely multi-modal distributions (two separate high-probability regions corresponding to the two valid grasps). At inference time, sampling from this distribution naturally picks one of the valid modes cleanly, rather than averaging between them the way a poorly-calibrated discrete-token approach risks doing.

Chapter 62 — Simulation with Isaac Sim & Isaac Lab

Exercise 62.1 [W]. Physics accuracy, rendering fidelity, speed/parallelism. Rendering fidelity matters “not at all” for a policy that only observes joint angles and velocities, since it never receives any visual input for photorealism to affect.

Exercise 62.2 [W]. Isaac Sim is the underlying simulation/rendering platform (physics engine, rendering); Isaac Lab is a robot-learning framework built on top of it that wraps scenes as standardised RL environments and runs thousands of parallel instances on one GPU. Isaac Lab is the one to use for training a policy at scale, since its parallelism is what makes large-scale RL training throughput practical.

Exercise 62.3 [A]. The full-range comparison (0.6485 vs. 0.4937) could in principle be explained by the domain-randomized controller simply being “better tuned overall” in a way that trades away performance at any single specific point. A skeptic could argue the fixed-config controller still wins where it was actually designed to win, and the average result is just an artifact of testing outside its intended range. The unloaded-mass comparison closes that exact loophole: it evaluates both controllers at the ONE condition the fixed-config controller was specifically designed for, with no “unfair range” objection available, and domain-randomized STILL wins (0.410 vs. 0.462), proving the earlier result isn’t merely “fixed-config wins on its home turf but loses badly elsewhere,” it’s “domain-randomized wins essentially everywhere, including home turf.”

Exercise 62.4 [A]. Overshoot represents how far past the target position/setpoint the arm’s actual position swings before settling. Physically, the arm moves further than commanded before correcting back, a direct consequence of a controller’s gains being poorly matched to the actual mass being moved (heavier unexpected payload = more momentum than the controller “expects,” causing it to overcorrect). A 20.54% overshoot in a real deployment is a safety concern because the arm’s end effector could swing significantly past its intended position, risking collision with nearby objects, people, or the workpiece itself, especially in tight tolerances or shared human-robot workspaces where that extra swing wasn’t accounted for.

Exercise 62.5 [E]. “This chapter’s own measured result shows the opposite: a controller tuned across a realistic payload-mass range beat the perfectly-matched single-condition controller even AT that exact matched condition (cost 0.410 vs. 0.462 at mass=1.0), not just elsewhere in the range. Tuning narrowly for one expected condition risks the controller learning to exploit that specific condition’s quirks in a way that doesn’t generalize even when the deployment conditions are close to, but not exactly, what was assumed, so a range-robust tuning approach is worth testing even when the target condition seems well known.”

Exercise 62.6 [E]. Evidence justifying adding friction as a second randomized parameter would be: real-hardware validation testing (Procedure 62.1 step 3) showing worse-than-simulated performance specifically traceable to friction mismatches (e.g. slippage or drag not predicted by the single-parameter-randomized simulation), or a documented, well-founded uncertainty about the actual friction coefficients of the real deployment surface/joints that wasn’t captured by mass randomization alone. In either case, concrete evidence that mass randomization alone left a real, measurable sim-to-real gap traceable to friction specifically, rather than simply adding more parameters preemptively without evidence they matter for this task.

Exercise 62.7 [R]. MuJoCo’s MJX reimplements MuJoCo’s physics in JAX, enabling the same kind of GPU-parallel simulation (many environment instances run simultaneously as batched array operations) that Isaac Lab provides, but built on JAX’s functional, differentiable-programming ecosystem rather than Isaac Sim’s Omniverse/USD/PhysX stack. This means MJX can run on a GPU without requiring an NVIDIA Isaac licence or the heavier Omniverse platform, and integrates naturally with JAX-based RL research code. A learner without an Isaac licence gains GPU-parallel simulation throughput (thousands of environments at once, the key advantage over single-instance CPU MuJoCo) using an entirely open-source stack, at the cost of MuJoCo’s simpler, non-photorealistic rendering compared to Isaac Sim’s ray-traced visuals.

Chapter 63 — Learning Robot Policies

Exercise 63.1 [W]. Reinforcement learning needs a reward function and no demonstrations. Imitation learning / behaviour cloning needs demonstrations and no reward function. VLA fine-tuning needs a small amount of task-specific data (demonstrations, or preference data) and can optionally combine with either a reward function or plain imitation.

Exercise 63.2 [W]. A neural network always outputs something for any input, whether or not that input resembles anything it was trained on. There’s no built-in mechanism for it to recognise “this state is unlike anything I’ve seen” and respond with hesitation or a refusal. The cloned policy was fit only to states near the origin, so outside that region it’s extrapolating with no signal telling it the extrapolation is unreliable, and it outputs a confident (and wrong) action exactly as smoothly as it outputs a confident (and right) one in-distribution.

Exercise 63.3 [A]. A True result would mean the demonstrations themselves had, at some point, come within the 1.2-unit obstacle-avoidance trigger radius, i.e. the expert’s obstacle-repulsion behaviour actually fired during at least one demonstration, leaking some avoidance signal into the training data. That would contaminate the distribution-shift test: the cloned policy might then perform better than expected out-of-distribution not because imitation learning generalises well, but because a sliver of avoidance behaviour was accidentally present in training after all. Checking for False first ensures the subsequent 0/40 result is a clean measurement of distribution shift, not an artifact of leaked training signal.

Exercise 63.4 [A]. The first DAgger iteration rolls out the current (already-trained, already-failing) behaviour-cloning policy from a range of starting states, including states near the obstacle where it currently fails, and records exactly the states it visits. It then queries the scripted expert (not the cloned policy) for the correct action at each of those visited states, and adds those (state, expert-action) pairs to the training set before retraining. This directly targets the 0/40 failure because the new corrections come from precisely the region the current policy gets wrong, its own drift, rather than from more demonstrations near the origin, which the policy already handles correctly and gains nothing further from.

Exercise 63.5 [E]. RL being “more general” than imitation learning isn’t automatic. It only generalises across whatever distribution the training reward and environment actually cover, and it needs a correct, well-shaped reward function to get there, which is often harder to build than it looks. If you already have good demonstrations, skipping them for RL trades a cheap, sample-efficient path for many thousands of trial-and-error episodes and a reward-design problem with its own failure modes (reward hacking, sparse-reward stalling). Concrete cost: reward mis-specification can produce a policy that scores well but does something visibly wrong, and that failure is often harder to diagnose than a demonstration-coverage gap.

Exercise 63.6 [E]. This is reward hacking: the reward (forward velocity) is being maximised by a degenerate behaviour (repeated forward falls) that technically satisfies the metric without doing the intended task (walking). The fix is not tuning the learning rate or architecture. It’s inspecting the trained policy’s actual behaviour directly, not just watching the reward curve, and then tightening or adding reward terms to close the loophole (e.g. penalising loss of balance or excessive impact force alongside the velocity reward).

Exercise 63.7 [R]. Discussion only, no single answer. The “no-regret online learning” framing casts DAgger’s guarantee formally: because each iteration retrains on an aggregated dataset that includes corrections at the actual states the current policy visits, the sequence of policies produced behaves like an online learner competing against the best fixed policy in hindsight, and standard no-regret bounds then give a guarantee on cumulative future performance rather than just an intuition that “it should help.” The pseudocode conveys the mechanical fix; the formal framing explains why iterating it converges rather than just plausibly improving things, and gives a way to reason about how many iterations are enough.

Exercise 63.8 [W]. A pretrained VLA checkpoint already carries broad visual and instruction-following competence from its internet-scale pretraining, so fine-tuning it on a small teleoperated dataset only needs to teach the new task’s specifics, not general perception or language understanding from zero. Training a policy from scratch has none of that prior competence to draw on, so it would need a much larger demonstration set (or a fully-specified reward and many RL episodes) to reach comparable generalisation. Route 3 is the cheaper path precisely because the “do you need broad generalisation” and “can you afford a large model at inference” conditions both favour it here (a household-manipulation VLA implies broad generalisation is exactly the goal).

Chapter 64 — Edge Compute & IoT Networking

Exercise 64.1 [W]. The deciding question: can this decision tolerate the latency, reliability, and bandwidth cost of a cloud round-trip? (a) A robot’s obstacle-avoidance check cannot. It’s a time-critical control-loop decision that must run on the edge. (b) A monthly fleet-wide performance dashboard easily can. It’s not time-critical and benefits from centralized aggregation, so it belongs in the cloud.

Exercise 64.2 [W]. The three axes are power, range, and bandwidth/latency. LoRaWAN sacrifices bandwidth (very low) specifically to achieve long range (kilometres) at very low power. The radio physics trade-off is that transmitting reliably over long distances at low power requires a much narrower, slower signal than short-range high-bandwidth protocols like BLE use.

Exercise 64.3 [A]. Quantization’s size reduction follows directly from the arithmetic of storing fewer bits per weight (e.g. FP32 → INT8 is mechanically a 4x reduction before any measurement). It’s essentially guaranteed by construction. Latency, by contrast, depends on whether the actual runtime and hardware have optimized kernels for the lower-precision operations; on a generic CPU without such optimized paths, INT8 operations can be slower than native FP32 paths, which is a property of the software/hardware stack, not of the arithmetic itself.

Exercise 64.4 [A]. A real deployment decision should be based on the actual on-device latency of the model that will actually run in production, which is the quantized model, since that’s the one being deployed for its size benefit. Using the FP32 model’s latency would answer a question (“how fast would the model I’m not shipping be”) irrelevant to the real deployment; this chapter’s own finding that quantization can make a model smaller and slower is exactly why the deployed model’s own measured number, not an assumption transferred from a different model, is the only trustworthy figure.

Exercise 64.5 [E]. “A cloud round-trip typically costs tens of milliseconds mean latency with a long tail, which this chapter’s own measurement showed causes deadline misses against a 20ms control-loop budget. Running perception in the cloud for this robot would mean the decision routinely arrives after the control loop already needed it, which isn’t a ‘bigger GPU is better’ trade-off, it’s an outright miss.”

Exercise 64.6 [E]. Likely cause (Procedure 64.3): unstructured pruning was used, and the deployment runtime doesn’t exploit sparse weight structure. Per the compression comparison table, unstructured pruning’s speed-up is “only if runtime exploits sparsity.” Fix: either switch to structured pruning (removes whole channels/filters, benefits standard dense kernels) or use a runtime/library with genuine sparse-matrix support.

Exercise 64.7 [R]. Discussion only. Combining pruning, quantization, and Huffman coding compounds their savings multiplicatively rather than requiring a choice between them. Pruning removes redundant connections, quantization reduces bits per remaining weight, and Huffman coding further compresses the resulting (now more skewed) weight-value distribution losslessly. Applying all three together achieves compression ratios well beyond what any single technique reaches alone, which is the paper’s central point.

Exercise 64.8 [W]. Procedure 64.1 points to LoRaWAN: it’s the only protocol in the comparison combining very-low power (multi-year battery life) with long range (kilometres). MQTT and CoAP don’t inherently provide multi-kilometre range without additional network infrastructure, and BLE’s range is limited to metres. None of the other three protocols satisfy both the distance and battery-life constraints simultaneously the way LoRaWAN’s radio design is specifically built for.

Chapter 65 — Deployment, Fleets & Safety

Exercise 65.1 [W]. Never let one thing be the only thing standing between a decision and a bad outcome. Every safeguard should be an independent layer that can catch what the layer before it missed. A safety monitor consulting the policy’s own confidence score would violate this because it would no longer be independent. A policy that fails confidently (exactly the failure mode this chapter names) would report high confidence on its own wrong decision, and a monitor trusting that confidence score would fail to catch exactly the case it exists to catch.

Exercise 65.2 [W]. A training simulator deliberately covers a distribution of possible realities (via domain randomization) so a trained policy generalises; a digital twin is a virtual replica of one specific real asset, kept in sync with that asset’s actual sensor data, for monitoring and diagnosing that exact device. Domain randomization applies to the training simulator, not the digital twin. Accuracy to one specific reality is the digital twin’s entire point, the opposite of domain randomization’s goal.

Exercise 65.3 [A]. Reporting only “collisions dropped from 11/40 to 0/40” without also noting task success stayed at 0/40 in both conditions risks the misleading impression that the safety monitor “fixed” the robot or made it more capable, when in fact the underlying policy is exactly as bad at the task as before; the monitor only prevented that badness from producing collisions. Reporting both numbers together makes clear that a safety layer bounds damage without improving capability, which is precisely this chapter’s central distinction between “fixing the problem” and “bounding the damage while the problem gets fixed properly.”

Exercise 65.4 [A]. 200 / 10 = 20x blast-radius reduction. Scenario B’s canary success rate (0.542) fell well below the threshold-adjusted baseline expectation (0.85 × 0.922 ≈ 0.784), triggering staged_rollout’s halt condition. The canary group’s measured performance was low enough, relative to the pre-update baseline, to signal a real regression rather than normal variation, which is exactly the evidence needed to stop the rollout before the remaining 190 devices received the same bad update.

Exercise 65.5 [E]. “This chapter’s own Worked Example shows exactly why that’s premature: the safety monitor eliminated all collisions, but the underlying policy’s task-success rate stayed at 0/40, completely unchanged. A safety net bounds damage; it doesn’t fix the capability gap that made the dangerous behavior possible in the first place. The actual policy work (better or more demonstrations, a DAgger-style fix) is still an open problem, and calling the project ‘safety complete’ risks shipping a robot that safely fails at its job forever rather than fixing why it fails.”

Exercise 65.6 [E]. A fleet running frequent, low-risk software updates (e.g. minor logging or telemetry improvements) with a rollback threshold set too strictly could see legitimately good updates repeatedly blocked by normal performance variance across the canary group. Each blocked update requires manual investigation and re-deployment, consuming engineering time and delaying genuinely beneficial fixes (security patches, bug fixes) from ever reaching the fleet, which is a real operational cost even though no dangerous update was ever actually deployed.

Exercise 65.7 [R]. Speed and Separation Monitoring requires a robot to continuously reduce its speed as a human approaches, rather than operating at full speed until a hard boundary is crossed and then stopping abruptly. This is a distinct, additional layer from an emergency-stop button because it acts proactively and continuously (reducing risk exposure well before any critical threshold is reached) rather than reactively and only at one hard boundary. If the continuous speed-reduction layer fails or is insufficient, the emergency-stop remains as a separate, independent final layer, exactly the defense-in-depth principle from this chapter’s Motivation: multiple independent layers, each catching what the layer before it might miss, rather than relying on a single hard-stop mechanism as the only safeguard.

Chapter 68 — CNN Fundamentals

Exercise 68.1 [W]. Translation equivariance: if the input shifts, the output shifts correspondingly. Translation invariance: the output doesn’t change when the input shifts. Convolution alone provides equivariance; invariance requires pooling (or similar) applied afterward.

Exercise 68.2 [W]. (8 + 2*0 - 3) // 1 + 1 = 6. This differs from the “same”-padding case (output 8) because no padding is added, so the kernel can’t be centered on the border pixels. The output shrinks by kernel_size - 1 = 2 pixels total (1 lost from each side) compared to same-padding, which pads exactly enough to keep the output the same size as the input.

Exercise 68.3 [A]. The two conditions’ mean±std ranges (0.874 ± 0.016, i.e. roughly 0.858-0.890, and 0.866 ± 0.013, i.e. roughly 0.853-0.879) overlap substantially. This overlap means the observed difference is well within what random seed variation alone would produce, so “augmentation didn’t help” (a null result) is the honest conclusion. Claiming “augmentation made it slightly worse” would be over-interpreting noise as a real, directional effect that the data doesn’t actually support at this level of measurement precision.

Exercise 68.4 [A]. Weight sharing means the same small kernel (e.g. 9 weights for a 3x3 kernel) is applied at every spatial position in the image, rather than each position needing its own independent set of weights. A fully-connected layer processing the same image would need one weight per (input pixel, output unit) pair. The CNN instead reuses roughly 1,900 weights total across every position the kernels slide over, because the assumption “an edge looks the same regardless of where it appears” lets one learned detector serve the whole image instead of needing a separately-learned detector per position, which is exactly why ~1,900 parameters is enough to reach 94.4% accuracy where a comparably-sized fully-connected network would need vastly more.

Exercise 68.5 [E]. “Before assuming that pipeline helps, check whether flips make sense for X-rays specifically. Many anatomical structures have a canonical left/right orientation that a horizontal flip would violate, and colour jitter is largely meaningless for grayscale medical imagery. Beyond label-preservation, this chapter’s own augmentation experiment showed that even a ‘safe’ augmentation’s strength has to be calibrated to the image’s actual scale and resolution. A default tuned for large natural photos measurably didn’t help on much smaller images, so the pipeline needs to be measured on this specific dataset, not assumed to transfer.”

Exercise 68.6 [E]. Before assuming the bug is in the model architecture (wrong layer types, wrong activation choice, etc.), explicitly compute the expected output size through every conv/pool layer in sequence using the output-size formula, and compare that computed flatten dimension against what the first fully-connected layer was actually declared with. A shape-mismatch error is very often simply an arithmetic mistake in this calculation (e.g. forgetting a pooling layer halves the spatial size) rather than a deeper design flaw, and checking this first is much faster than debugging the architecture’s logic.

Exercise 68.7 [R]. In a plain (no skip connections) deep CNN, the gradient of the loss with respect to an early layer’s weights is computed via the chain rule as a product of many per-layer partial derivatives, one for each layer between that early layer and the output. If each of these per-layer factors is somewhat less than 1 (which is common with saturating activations or certain weight initialisations), multiplying many such factors together causes the product to shrink exponentially with depth, so by the time the gradient signal reaches the earliest layers, it has become vanishingly small, and those layers barely update during training despite technically receiving a gradient, effectively becoming untrainable once the network is deep enough.

Chapter 69 — ResNet & Deep Architectures

Exercise 69.1 [W]. F(x) + x instead of H(x) directly. Because the derivative of F(x) + x with respect to x always includes a +1 term (from differentiating the identity x path), the total gradient can never be driven to exactly zero purely by the multiplicative chain through F, unlike a plain block where the gradient is a pure product of per-layer terms that can shrink toward zero.

Exercise 69.3 [A]. The dramatic epoch-10 gap (plain 0.687 vs. residual 0.998, with both networks identical in size and training budget) suggests vanishing gradients do most of their damage early in training, when weights are still far from a good solution and need large, informative gradient updates to move efficiently. The plain network’s early layers are receiving a severely attenuated signal at exactly the point where a strong signal matters most for making rapid initial progress. The plain network does eventually make substantial progress (0.981 by epoch 60), suggesting some gradient signal does get through over many epochs, just far less efficiently than the residual network’s direct path provides from the start.

Exercise 69.4 [A]. Fine-tuning’s larger trainable-parameter count (8,398,858, versus feature extraction’s 5,130) becomes a liability rather than an advantage specifically because the target dataset is small relative to that capacity. With only a limited number of target examples, a network with millions of trainable parameters has enough freedom to fit noise and idiosyncrasies in the small training set rather than learning genuinely generalizable patterns, producing worse held-out test accuracy despite (or because of) its larger capacity. Feature extraction’s much smaller trainable-parameter count (only the new head) is far less prone to this overfitting, which is why it outperforms fine-tuning here even though fine-tuning nominally has “more information” (unfrozen backbone weights) available to adapt.

Exercise 69.5 [E]. “This chapter’s own Worked Example measured the opposite on a domain visually different from ImageNet: a from-scratch model with only 3,658 parameters, fewer than the feature-extraction head alone, reached 0.842 test accuracy, beating both feature extraction (0.633) and fine-tuning (0.561). Pretrained features only help to the extent they’re relevant to the target domain, and fine-tuning’s larger capacity is actively risky on small target datasets. The right move is testing all three approaches on your specific task, not defaulting to fine-tuning as a rule.”

Exercise 69.6 [E]. If a residual stage doubles the channel count between blocks (a common pattern in deeper ResNet variants, e.g. going from 64 to 128 channels between stages), the identity shortcut x has 64 channels while the block’s output F(x) has 128 channels. These shapes cannot be added directly. The projection-shortcut variant is required here: a 1x1 convolution on the shortcut path maps the 64-channel input to 128 channels (and can also apply a matching stride if the block also downsamples spatially), so the shapes align for the final addition.

Exercise 69.7 [R]. Scaling only one axis (e.g. depth alone) tends to hit diminishing returns because a network that’s very deep but proportionally narrow, or high-resolution but shallow, wastes some of its added compute on a dimension that isn’t the actual bottleneck for that architecture. A very deep but narrow network may lack the channel capacity to represent enough distinct features per layer, regardless of how many layers it has. Compound scaling increases depth, width, and resolution together in a balanced ratio because a network processing higher-resolution input genuinely benefits from more layers (to grow the receptive field enough to cover the larger image) and more channels (to capture the finer-grained detail the higher resolution provides) simultaneously. Scaling all three in a fixed, empirically-tuned ratio avoids compute being spent on one axis while another remains the limiting factor.

Chapter 70 — Object Detection & Segmentation

Exercise 70.1 [W]. Detection: predicts a set of bounding boxes, each with a class label and confidence score, localising objects to rectangles. Segmentation: predicts a label for every individual pixel, producing a full mask. Both keep spatial location information that whole-image classification discards entirely (a single label with no “where”).

Exercise 70.2 [W]. ResNet’s skip connections add two paths at the SAME resolution to fix vanishing gradients, letting a block default to the identity function. U-Net’s skip connections concatenate (not add) features from DIFFERENT stages, early fine-detail encoder features and later coarse decoder features, to reinject spatial detail lost during downsampling. Same “shortcut” shape, different mechanism and different problem.

Exercise 70.3 [A]. “100% above 0.5” alone doesn’t reveal how much above 0.5. Conversely, mean IoU alone doesn’t reveal whether that average is pulled up by a few excellent detections while some images fail the correctness threshold entirely; “100% above 0.5” confirms every single image individually cleared the bar, not just the average. Together they rule out both failure modes a single number alone could hide.

Exercise 70.6 [E]. If a detector correctly identifies a cat and a dog standing close together with genuinely overlapping bounding boxes, running NMS across all classes at once would treat the dog’s high-confidence box as a suppressor of the cat’s box (or vice versa, whichever has lower confidence) purely because their boxes overlap above the IoU threshold, incorrectly discarding one of the two genuinely-correct, different-class detections. Running NMS separately within each class only compares cat-boxes against other cat-boxes and dog-boxes against other dog-boxes, so the legitimately overlapping but differently-classed detections never suppress each other.

Exercise 70.7 [R]. A single “IoU > 0.5” threshold treats every detection above that line as equally “correct,” collapsing a barely-passing 0.51 IoU detection and a nearly-perfect 0.95 IoU detection into the same pass/fail bucket, hiding real differences in localisation quality. mAP averaged across multiple IoU thresholds (typically 0.5 to 0.95 in COCO’s convention) instead rewards a detector more for tighter, more precise boxes, since a detector that only clears the loosest threshold (0.5) but fails stricter ones (0.75, 0.9) scores lower under mAP than a detector whose boxes are consistently tight enough to clear even the strict thresholds, giving a much finer-grained, more complete picture of localisation quality than one binary threshold provides.

Chapter 72 — Generative Foundations: Autoencoders, VAEs & GANs

Exercise 72.1 [W]. A plain autoencoder’s latent space has no constraint pulling it toward any particular shape. The measured latent statistics show it can have gaps, uneven density, and arbitrary location, unlike a regularised N(0,1) target. Drawing a random point from N(0,1)N(0,1)N(0,1) and decoding it therefore has no guarantee of landing in a region the decoder ever saw during training, so the output is unpredictable, potentially nonsensical, rather than a plausible new sample.

Exercise 72.2 [W]. The reparameterisation trick solves differentiability: direct sampling from Normal(mu, std) involves a random draw that has no gradient with respect to mu/std, so backpropagation cannot flow through it. Rewriting the sample as mu + eps * std with eps drawn separately isolates the non-differentiable randomness into eps alone, leaving z a differentiable function of the learned parameters mu and std. This is what makes end-to-end training possible.

Exercise 72.3 [A]. Setting BETA=5.0 weights the KL term five times more heavily relative to reconstruction. Reconstruction quality should visibly degrade (blurrier, more generic outputs) compared to BETA=1.0, since more of the loss budget is being spent forcing regularisation than rewarding accurate reconstruction.

Exercise 72.4 [A]. Even genuinely identical distributions produce nonzero FID when estimated from finite, different samples (sampling noise in the mean/covariance estimates). For it to approach zero, the dataset would need to grow much larger (reducing estimation variance) or the two splits would need to become the same images (which would defeat the sanity-check’s purpose).

FID is expected to be monotonically ordered (real-vs-real lowest, degraded next, pure noise highest), and a violation of that ordering points to an error in the feature extraction, covariance computation, or sqrtm step, not a genuine finding about the images.

Chapter 76 — Graph Theory Fundamentals

Exercise 76.1 [W]. BFS explores nodes in strict order of increasing distance from the source, using a queue that processes all nodes at distance kkk before adding any at distance k+1k+1k+1. So by the time a node is first dequeued (reached), every shorter possible path to it has already been exhausted without success, guaranteeing the path found is the fewest-hops path.

Exercise 76.2 [W]. Degree centrality: how many direct connections a node has. Betweenness centrality: how much shortest-path traffic between other node pairs flows through this node. PageRank: how much a node is linked to by other well-linked nodes, recursively.

Exercise 76.3 [A]. Answer depends on the specific microservice graph’s structure and weights as defined in the chapter. The mechanical step is running nx.shortest_path (unweighted, fewest-hops) and nx.dijkstra_path (weighted) between api_gateway and payment_service and comparing both the hop count and the actual node sequence. They agree when the fewest-hops route also happens to be the cheapest-weighted route; they can diverge when a longer-hop-count path has lower total edge weight than a shorter one.

Exercise 76.4 [A]. The most damaging single-node failure by betweenness centrality alone is whichever node the output table ranks highest on that specific column, typically a node sitting on many shortest paths between otherwise-disconnected parts of the graph (a structural bridge/bottleneck). This can differ from the highest-PageRank node because PageRank rewards being linked to by important nodes (an endpoint of importance), while betweenness rewards sitting between other nodes on their shortest paths (a routing bottleneck). A node can be a critical routing chokepoint without itself being heavily linked-to, and vice versa.

Exercise 76.5 [A]. Per this chapter’s discussion of Louvain’s stochastic step, re-running with a different seed is more likely to change community membership (which specific nodes land in which cluster, especially borderline nodes) than the overall number of communities detected. Louvain’s greedy local-optimization order is randomized by seed, which can shift ambiguous nodes between adjacent communities, while the broader structural division into roughly that many communities tends to be more stable across seeds for a graph with reasonably clear community structure.

Exercise 76.6 [E]. “There typically isn’t one single point of failure. A database node failing usually means direct, catastrophic data-layer outage, while an order_service node with high betweenness centrality failing disrupts many paths between other services without necessarily being the most-connected node itself. The honest answer depends on which failure mode you’re actually worried about: direct dependency loss (check degree/direct connections) versus routing disruption (check betweenness). Worth computing both before naming one node.”

Exercise 76.7 [E]. “At 50 million edges queried by three concurrent applications, Amazon Neptune (managed, scales past in-memory limits, handles concurrent query load) is the right recommendation over in-memory networkx, which won’t hold a graph that size and has no built-in concurrency handling. If the graph were instead 5,000 edges queried by one internal script, in-memory networkx is simpler, cheaper, and sufficient. The crossover is really about scale (fits in memory?) and concurrent access needs (multiple simultaneous querying applications?), not an inherent superiority of either approach.”

Exercise 76.8 [R]. Discussion only. The chapter’s Worked Example flags one specific karate-club member (historically member 9 in most published analyses of this dataset) as a case where the algorithmically-detected community assignment disagrees with the real-world club split Zachary recorded. A plausible real-world explanation not visible from graph structure alone: that member may have had genuine social or logistical ties pulling toward one faction (e.g. friendship, geographic proximity) while formally affiliating with the other faction for unrelated reasons (e.g. deference to the instructor, administrative convenience), exactly the kind of context edges in a pure interaction graph can’t encode.

Chapter 77 — Graph Data Modeling & Databases

Exercise 77.1 [W]. A property graph attaches key/value properties directly to nodes and edges. An RDF triple is an atomic (subject, predicate, object) fact, with no exceptions for what kind of information it represents. RDF needs reification: treating an edge itself as a subject so additional triples can attach to it, because a plain triple has no attribute slots of its own; property graphs attach edge properties directly with no extra mechanism needed.

Exercise 77.2 [W]. 30/12 = 2.5x. The expansion is caused by RDF’s insistence that every node property (which was a single direct field in the property graph) becomes its own separate triple, with no shortcut for attaching multiple properties to one entity in a single record.

Exercise 77.3 [A]. Cypher’s MATCH (a)-[:OWNS]->(b) syntax visually mirrors the graph pattern being searched for. Arrows in the query point the same direction as the relationship being matched, so a two- or three-hop pattern reads almost like a diagram of the graph shape itself, letting one line of Cypher capture what would otherwise be several traversal steps. SPARQL’s flat WHERE { ?a ex:OWNS ?b } triple-pattern syntax has no such visual correspondence. Connecting multiple triple patterns via shared variables requires more explicit lines to express the same multi-hop shape, which is exactly why it needed roughly double Cypher’s line count (6 vs. 3) for this chapter’s identical query.

Exercise 77.4 [A]. All else being equal, converting from a property-graph representation to RDF would be expected to roughly 2.5x the number of stored facts (triples) that need to be indexed and stored. This directly increases index size, storage footprint, and potentially query planning complexity, since a triple store now has 2.5x as many atomic facts to search through and join across compared to the property graph’s more compact per-entity attribute storage.

Exercise 77.5 [E]. “Per this chapter’s decision framework, RDF’s advantages are specifically interoperability with external ontologies and formal RDFS/OWL inference, neither of which this vendor-management graph currently needs. Meanwhile, this chapter’s own measurement showed RDF costs roughly 2.5x more stored facts for the same graph and needs about twice the query length for the same multi-hop question versus Cypher. ‘Future-proofing’ without a concrete near-term interoperability need is paying a real, measured cost now for a benefit that may never materialize. Worth revisiting only if a genuine cross-organisation RDF interoperability requirement actually appears.”

Exercise 77.6 [E]. If Acme Corp PURCHASES_FROM Contoso Bolts were recorded once for 2023 with annual_spend_usd=250000 and then recorded again for 2024 with annual_spend_usd=310000 using a plain nx.DiGraph, the second add_edge call would silently overwrite the first edge’s properties entirely. The 2023 purchase record (and its annual_spend_usd=250000 value) would be lost, leaving only the 2024 figure, with no error or warning that historical data had been silently discarded. A MultiDiGraph instead keeps both edges as separate records between the same node pair, preserving the full purchase history.

Exercise 77.7 [R]. RDF’s uniform triple structure means every fact, regardless of domain, has the exact same shape: (subject, predicate, object). So a single inference rule engine can apply a transitivity rule like “if X OWNS Y and Y OWNS Z, then X INDIRECTLY_OWNS Z” mechanically across ANY RDF dataset without needing to know anything domain-specific about what OWNS “really” represents structurally, since every relationship is stored identically. A property graph’s non-uniformity (properties attached differently to nodes versus edges, different edge types potentially structured differently) means a generic inference engine would need to understand each graph’s specific schema/structure before applying a transitivity rule, making uniform, cross-dataset formal inference much harder to implement generically compared to RDF’s one-shape-fits-all approach.

Chapter 78 — Knowledge Graph Construction

Exercise 78.1 [W]. Entity recognition, relation extraction, validation. Validation can only remove predictions (drop triples that fail a consistency check), never add new ones.

Exercise 78.2 [W]. Entities: precision 1.000, recall 1.000. Raw relations: precision 0.800, recall 0.571. The two tasks measured so differently because entity extraction only needs to recognise that a capitalised span with a known suffix is an entity, while relation extraction additionally needs to get phrase boundaries exactly right (subject and object spans), which is a harder, more error-prone problem, as shown by the “Jane Doe previously” boundary bug.

Exercise 78.3 [A]. Precision improving while recall stays exactly flat is the expected signature of a validation-only fix because validation’s only possible action is removing bad predictions. Removing a false positive (like the malformed “Jane Doe previously” triple) directly improves precision (fewer wrong predictions among those kept) without touching which correct facts were ever produced in the first place, which is what recall measures. A different pattern, both precision AND recall improving, would imply the intervention did something beyond filtering: either producing new correct predictions (which validation alone structurally cannot do) or correcting a previously wrong prediction into a right one, neither of which a pure consistency check can accomplish.

Exercise 78.4 [A]. Final recall (0.857) stays below 1.000 because the earlier ("Jane Doe previously", "WORKED_AT", "Initech") boundary error is still uncorrected. That triple was dropped by validation (fixing precision) but the correct ("Jane Doe", "WORKED_AT", "Initech") fact was never produced by any stage of the pipeline, since neither validation nor the LLM extraction pass (which only reprocessed the ONE sentence with the missed passive-voice/implicit relation) ever revisited that specific extraction. The LLM step’s improvement is scoped to the sentence it targeted; it has no mechanism to notice or fix a different, earlier mistake elsewhere in the pipeline.

Exercise 78.5 [E]. “This chapter’s own pipeline trace shows precision and recall are controlled by different, independent parts of the extraction pipeline. Validation raised precision from 0.800 to 1.000 while recall stayed flat at 0.571, meaning a third of the true relationships in the corpus were still missing from the graph even after precision hit 100%. A ‘100% precision’ claim says every kept prediction is correct, but says nothing about how many correct facts were never extracted in the first place. The graph could still be substantially incomplete even while being fully accurate on what it does contain.”

Exercise 78.6 [E]. An LLM could plausibly extract a relation like ("Acme Corp", "WORKED_AT", "Globex Inc"): grammatically and semantically plausible-sounding text, but structurally invalid under the domain/range schema, since WORKED_AT requires a PERSON subject and Acme Corp is typed as ORG, not PERSON. Procedure 78.2’s validation check would catch this by looking up Acme Corp’s known entity type and comparing it against WORKED_AT’s expected subject type (PERSON), rejecting the triple regardless of how confident or fluent the LLM’s phrasing was, exactly the same mechanism that caught the rule-based extractor’s boundary error, applied without favouritism to the extraction source.

Exercise 78.7 [R]. A learned embedding-based approach (e.g. representing entities and relations as vectors and scoring candidate triples by a learned compatibility function) doesn’t rely on discrete text-span boundaries at all. Instead of extracting exact character spans from a sentence (where “Jane Doe previously” vs. “Jane Doe” is a hard, brittle boundary decision), it could learn to recognise “Jane Doe” as the correct entity by its similarity to other known PERSON entities in embedding space, sidestepping the specific brittle-regex-boundary failure mode entirely. This comes at the cost of needing substantial training data to learn good embeddings and losing the rule-based approach’s complete auditability. A learned model’s “why did it choose this boundary” is much harder to inspect directly than a regex pattern’s explicit failure.

Chapter 79 — Graph Neural Networks

Exercise 79.1 [W]. Each node updates its own representation by aggregating its neighbours’ representations, then applying a learned transformation. A 2-layer GCN’s “field of view” is limited to nodes within 2 hops: its output for any node has only ever been influenced by that node’s direct neighbours and its neighbours’ neighbours, nothing further.

Exercise 79.2 [W]. GCN, node2vec, TransE. node2vec and TransE both require no labels during training: they are fully unsupervised, learning purely from graph structure (random walks for node2vec, the h + r ≈ t constraint for TransE).

Exercise 79.3 [A]. Since the input features were the identity matrix (every node given only a one-hot marker of its own identity, no real attribute information whatsoever), any predictive signal the model used to correctly classify 29 of 30 unlabelled test nodes could only have come from the graph’s connectivity pattern itself, propagated outward from the 4 labelled nodes through repeated neighbourhood aggregation. This directly proves that graph structure alone, with zero node attributes, carries enough signal to recover the correct faction labels for the overwhelming majority of nodes.

Exercise 79.4 [A]. Reporting 94.12% alone doesn’t establish whether that number is actually good. Without a comparison point, a reader has no way to know if 94.12% represents strong structural signal or is simply what any reasonable embedding (even a poor or random one) would achieve on this particular graph. The random-embedding baseline (54.90%), embeddings with no learned structure at all, just random vectors, establishes the floor: since node2vec’s 94.12% is dramatically above that floor, the result demonstrates real, learned structural signal, not an artifact of how the evaluation itself is set up.

Exercise 79.6 [E]. Consider the query 'Acme Corp OWNED_BY ?' from the Worked Example, where the top-3 predictions were ['Zenith Holdings', 'Orion Group', 'Acme Corp'] with the correct answer (Zenith Holdings) ranking first in this specific case, but imagine a different query where the correct answer ranked 2nd or 3rd instead of 1st. Hits@3 (which was a perfect 1.0000 across the whole evaluation set) captures that “close, and practically still useful” case that Hits@1 would discard entirely, which matters a great deal for any real system where a human reviews a shortlist rather than blindly trusting only the single top prediction.

Exercise 79.7 [R]. The h + r ≈ t constraint forces a single shared vector r (e.g. for OWNED_BY) to, when added to a given head entity’s vector h, land close to exactly one point in embedding space. If a company h genuinely has two different owners t1 and t2, satisfying the constraint would require h + r to be simultaneously close to both t1 and t2. But h + r is one fixed point, and it can only be close to both t1 and t2 if those two tail entities are themselves already close together in embedding space (which they generally have no independent reason to be, since they’re different, unrelated entities). This is a genuine geometric contradiction for a true 1-to-many relation, not merely a training difficulty. No amount of additional training resolves it, which is exactly why TransE structurally cannot represent this class of relation well, motivating successor models like RotatE that use richer geometric operations than simple vector addition.

Chapter 80 — GraphRAG & LLM Retrieval

Exercise 80.1 [W]. Vector similarity measures how alike two pieces of text read semantically, based on co-occurrence patterns learned during embedding training. It has no mechanism for representing a specific, factual, structural relationship like “shares a parent company with” unless that exact relationship happens to be spelled out in text near both entities. A graph edge encodes that connection explicitly and deterministically, independent of whether any passage ever states it in similar-reading language.

The three one-hop lookups: (1) finding an entity’s direct neighbors/relationships, using G.neighbors(node) or G.edges(node, data=True); (2) filtering those neighbors by relationship type (e.g. only OWNS or PURCHASES_FROM edges), using edge attribute filtering on the same call; (3) following the resulting neighbor set one hop further, repeating the same G.neighbors()/G.edges() pattern on the new node set.

Chapter 81 — Graph-Based Agentic Reasoning

Exercise 81.1 [W]. A fixed pipeline commits to a shape (how many hops, in what order) before it sees the data; an agent loop commits to nothing but a stopping rule, deciding after every step whether to continue based on what’s been found so far.

Exercise 81.2 [W]. A hop budget alone only caps how many rounds the loop runs. On a cyclic graph, without a visited set, the same nodes would keep being re-added to the frontier every round (since they’re still reachable), wasting rounds re-exploring identical ground rather than making genuine progress, and only stopping because the round counter eventually hits its ceiling. The visited set is what makes each node explored exactly once regardless of cycles, which is what actually gives the loop correct, non-redundant termination behaviour rather than just an eventual stop.

Exercise 81.3 [A]. The third result proves the adaptive loop’s advantage comes specifically from its control structure (deciding when to stop), not from a smarter underlying traversal algorithm. The exact same agentic_search code, using the identical get_neighbors primitive, found the match when given room (max_hops=6) and failed to find it when given too little room (max_hops=2). Since nothing about the algorithm itself changed between these two runs, only the stopping-condition parameter, this isolates the advantage entirely to the control structure/stopping decision rather than any algorithmic sophistication.

Exercise 81.4 [A]. The real vendor relationship (Cascade Textiles) sits exactly at hop 3 from the flagged entity, and Chapter 80’s pipeline design was structurally limited to checking 2 hops: a flagged entity’s owner, then that owner’s other direct holdings (the “siblings”), with no mechanism to look one layer further. A hop budget of exactly 2 on the adaptive loop reproduces this same structural limit numerically: both approaches stop examining the graph at the same depth, so both miss a fact that only becomes visible at depth 3, for the identical underlying reason: insufficient traversal depth, whether hard-coded into the function’s shape or set as a tunable parameter.

Exercise 81.5 [E]. “Setting max_hops very high risks exactly the ‘too loose’ failure mode this chapter’s Trade-offs section describes. On a large, densely-connected real graph, the search could explore a huge fraction of all reachable nodes before concluding there’s no answer, which is slow and, if that exploration feeds a downstream LLM prompt, risks flooding it with irrelevant context. The right hop budget should be set based on the actual expected depth of real answers in your domain, not maximized ‘just in case.’ Measure what depth real answers tend to sit at, the way this chapter’s Worked Example did, rather than guessing high.”

Exercise 81.6 [E]. If the target-set check only ran once, after all max_hops iterations completed, the loop would lose its early-stopping behavior entirely. It would always run the full number of hops regardless of whether a match was found early, wasting compute on unnecessary further exploration after a match already exists. More seriously, if visited tracking or frontier updates depend on the early-return behavior in the actual implementation (e.g., a match at hop 1 stops accumulation and returns a clean single match), running the check only at the end could also mean multiple matches from different hops get conflated together, or that the reported “hop” at which the match was found becomes wrong/undefined, since the loop no longer records which specific hop actually produced the qualifying result.

Exercise 81.7 [R]. Book 2’s Agentic AI chapter’s step-limit guardrail exists to prevent a general tool-calling agent from retrying or looping indefinitely on ambiguous or unsatisfying results, with max_steps as the safety ceiling and a distinct “step_limit_reached” status as the outcome. This chapter’s max_hops is a domain-specific instance of exactly that same pattern, applied to graph BFS-style traversal specifically rather than arbitrary tool calls. The key difference is that graph traversal has a natural, meaningful unit of progress (a “hop,” i.e., one level of neighbourhood expansion) that maps directly onto the budget parameter, whereas a general agent’s “step” could be any heterogeneous tool call with no shared notion of depth or progress across different tool types, making the graph-specific version’s stopping condition (“found the target in the frontier”) more concrete and directly checkable than a general agent’s more open-ended “have I achieved the goal” judgment.

Chapter 82 — Evaluating & Deploying Graph-LLM Systems

Exercise 82.1 [W]. Context recall: the fraction of ground-truth facts present in the retrieved context. Context precision: the fraction of retrieved chunks/entities that are relevant. Both can be computed here without any generation step because they’re defined purely in terms of what was retrieved versus what should have been retrieved. No downstream generated answer is needed to compute either metric, only the retrieval output and a ground-truth reference.

Exercise 82.2 [W]. Single-hop: vector-RAG 0.333/1.000, GraphRAG 0.333/1.000 (exact tie). Multi-hop: vector-RAG 0.167/0.312, GraphRAG 0.778/1.000 (GraphRAG far ahead). Pattern: GraphRAG matches vector-RAG exactly where vector-RAG already works (single-hop) and wins by roughly an order of magnitude on precision where it doesn’t (multi-hop).

Exercise 82.3 [A]. The 0.0 recall on single-hop questions was diagnosed as a harness bug, not a genuine finding, because GraphRAG was being scored using ONLY the multi-hop pattern-matching function (a tool never designed to answer single-hop questions) rather than being given the appropriate direct entity-lookup tool a real graph-RAG system would actually use for that question shape. Exercise 82.4 [A]. Vector-RAG’s cost is constant (16 operations) because it always scores every passage against the query regardless of graph/dataset structure. This scales with the total number of passages, not with any particular question’s complexity. GraphRAG’s cost (3.8 average) varies with the local graph structure near the anchor entity, specifically, how many neighbours/hops need to be examined to answer a given question. On a production graph with millions of nodes, a highly-connected anchor entity (e.g., a large corporation with thousands of subsidiaries or vendors) could require examining a traversal fan-out far larger than 16, while vector-RAG’s constant-per-query cost wouldn’t change with graph size at all. The comparison measured here could straightforwardly invert at larger, differently-shaped graphs, which is exactly why “GraphRAG is cheaper” can’t be generalized past the specific 9-node graph it was measured on.

Exercise 82.5 [E]. “This chapter’s own benchmark explicitly says the traversal-speed measurement doesn’t test the actual reasons production systems migrate to a managed graph database: concurrent query load from many simultaneous users, a graph too large to fit in one process’s memory, durability/backup guarantees, and access control, none of which a single-process timing loop can show. ‘Fast enough for one process, one query at a time’ and ‘ready for production’ are different claims, and this benchmark only answers the first one.”

Exercise 82.6 [E]. To distinguish a system failure from a benchmark ground-truth error for the Solaris Energy question, check whether the intended answer pattern actually exists in the graph as constructed. Trace the specific entities and relationships the question implies should connect, and verify that path is genuinely present. In this chapter’s case, that check revealed the graph had Solaris Energy purchasing directly from the flagged vendor (a one-hop fact), not from a sibling vendor sharing a parent with the flagged one (the intended two-hop fact), meaning no valid two-hop answer existed for the question as worded, which is a benchmark construction error, not a retrieval system failure, and the fix was adding a genuine third vendor to the graph so the intended pattern actually existed.

Exercise 82.7 [R]. A full RAGAS evaluation adds faithfulness (is every claim in the generated answer supported by the retrieved context?) and answer relevance (does the generated answer actually address the question asked?) on top of retrieval-only precision/recall. This chapter’s retrieval-only evaluation can confirm the right facts were retrieved, but it cannot catch a generation-stage failure where the LLM ignores good retrieved context and hallucinates an unsupported answer anyway, or where the LLM produces a technically-faithful-but-off-topic response that doesn’t actually address what was asked. Both failure modes require actually running the generation step and checking its output against the retrieved context, which a purely retrieval-focused evaluation like this chapter’s structurally cannot surface.

Exercise 83.3 [A]. The two results are consistent, not contradictory, because the claim being tested is about the shape of the pattern (GraphRAG ties or modestly beats vector-RAG on single-hop, substantially beats it on multi-hop) rather than about any specific numeric value being reproduced exactly. Exercise 83.4 [A]. An unanswerable-question check that emerges independently (designed fresh for a new domain without reference to the earlier chapters’ specific question) is stronger evidence of a generally good benchmark-design habit than reusing the identical question would be, because independent re-derivation shows the practice (“always include a no-valid-answer case”) was internalized as a principle rather than mechanically copied. If the exact same question had simply been copied over, it would only show the specific test case transferred, not that the underlying design discipline generalizes to genuinely new benchmark construction. The independent reappearance is evidence about the methodology, not just about one recurring test case.

Exercise 83.5 [E]. “The earlier chapters validated GraphRAG’s advantage on one specific graph, built and tuned by the same person who wrote the extraction and retrieval code. That’s exactly the scenario where a pipeline could quietly work only because it was (even unintentionally) shaped around that one example’s quirks. Building a second benchmark on genuinely new data, with a different domain’s entities, relations, and question shapes, is the only way to distinguish ‘this technique generally works’ from ‘this technique works on the example we happened to build it against.’ That’s not redundant, it’s the entire point of a capstone.”
