Chapter 76 treated a graph as a mathematical object: nodes, edges, and the algorithms that walk them. Real systems need more than that: nodes and relationships that carry rich attributes (“this company was acquired in 2018,” “this vendor’s annual spend is $250,000”), a way to store millions of them durably, and a query language other engineers can read without re-deriving traversal code from scratch. This chapter is about the representations, property graphs and RDF triples, and the databases built around each, so a graph theory algorithm has somewhere real to live.

77.1 Motivation

There are two dominant ways to put attributes onto a graph. A property graph attaches key/value properties directly to nodes and edges: a node just has a type and an industry; an edge just has a since date. An RDF triple store refuses that shortcut: everything, without exception, is a (subject, predicate, object) triple. A node’s “property” is really just another triple; an edge with its own properties needs reification: treating the edge itself as a subject so additional triples can attach to it, because a plain triple has no attribute slots of its own. Worked Example 77 below converts the same small graph into both forms and measures the structural cost of RDF’s uniformity directly.

77.2 Exposition

77.2.1 Property Graphs: Optimise for the Common Case

Most real-world graph queries want to filter or aggregate on node/edge attributes (“vendors with annual_spend_usd > 100000”), and a property graph makes that a direct field lookup: no extra hop, no reification. The cost is conceptual non-uniformity: nodes, edges, and their properties are three different kinds of thing, each with different rules, which makes property graphs slightly less amenable to generic, cross-domain reasoning than RDF’s single uniform shape.

77.2.2 RDF: Optimise for Uniformity and Standardised Reasoning

RDF’s insistence that everything is a triple is exactly what makes it interoperable at web scale. The same triple format can describe a company, a chemical compound, or a Wikipedia page, and standard ontologies (RDFS, OWL) can define formal inference rules that apply uniformly across any RDF dataset, because there’s only one shape of fact to reason about. That uniformity is also RDF’s cost, and Worked Example 77 measures exactly how much.

77.2.3 Why the Query Languages Look So Different

Cypher’s MATCH (a)-[:OWNS]->(b) syntax is deliberately drawn to look like the pattern it searches for: arrows point the way relationships do, directly mirroring the property graph’s shape. SPARQL’s WHERE { ?a ex:OWNS ?b } is a flat list of triple patterns connected by shared variables, equally expressive, but the graph shape has to be reconstructed mentally rather than read off the query’s punctuation. Worked Example 77 measures both against a hand-written Python/networkx traversal directly, quantifying how much traversal machinery a declarative query engine handles internally versus what a hand-rolled traversal has to write and maintain.

77.3 Trade-offs and Limits

Property graphs win on query ergonomics for attribute-heavy, domain-specific graphs, most enterprise use cases: vendor networks, org charts, recommendation graphs. RDF triple stores win when interoperability across datasets and formal, standards-based inference matter more than raw query convenience: biomedical ontologies, linked open data, regulatory taxonomies that need to interoperate with other organisations’ RDF data. networkx is in-memory, single-process, and has no query language of its own. Every traversal is Python written and maintained by hand, exactly right for learning mechanisms and genuinely small graphs, and exactly wrong once a graph needs to persist, scale past what fits in one process’s memory, or be queried by more than one application. Neo4j (property graph, Cypher) and Amazon Neptune (both property graph and RDF, Gremlin/openCypher/SPARQL) are the production answers.

77.4 Procedures

Procedure 77.1 (Model a Many-to-Many Relationship as a Property Graph). When to use: two entity types that can each relate to many of the other.

Common mistake: using a plain nx.DiGraph when two nodes might need more than one relationship type between them, or the same relationship type recorded twice with different properties: DiGraph silently overwrites the earlier edge instead of adding a second one.

Procedure 77.2 (Translate the Same Query Across networkx, Cypher, and SPARQL). When to use: moving a graph query from a prototype to its production target, or reading someone else’s query in an unfamiliar language.

77.5 Worked Example

A 6-node, 6-edge company/vendor property graph, converted to RDF triple form:

Representation Count
Property graph elements (nodes + edges) 12
RDF triples 30

12 graph elements became 30 triples: a 2.5x expansion, the direct structural price of RDF’s total uniformity. Every node property that was a direct field lookup in the property graph (Acme Corp’s type, industry, compliance_flag) becomes its own separate triple, and each edge’s own properties require reification. This factor isn’t a fluke of this particular example. It’s what “everything is a triple, no exceptions” costs structurally, confirmed by counting, not asserted.

Approach Lines needed
networkx traversal (hand-written Python) 11

Cypher took roughly a third the lines of the hand-written networkx Python (3 vs. 11), a real, measured difference in how much traversal machinery is written and maintained by hand versus delegated to a query engine’s internal indexing and planning. SPARQL, while still shorter than the hand-rolled Python (6 vs. 10-11), needs roughly twice Cypher’s line count for the equivalent query: a direct, measured instance of Exposition’s claim that SPARQL’s flat triple-pattern syntax requires reconstructing the graph shape mentally rather than reading it off the query’s arrows, the way Cypher’s syntax does.

77.6 History and Further Reading

Robinson, Webber & Eifrem’s “Graph Databases” (Robinson et al. 2015) (O’Reilly) is the standard property-graph-and-Cypher reference. The W3C RDF 1.1 Concepts and Abstract Syntax is the formal RDF specification. Hogan et al.’s “Knowledge Graphs” (Hogan et al. 2021) (ACM Computing Surveys) covers both property-graph and RDF traditions broadly. Kleppmann & Riccomini’s Designing Data-Intensive Applications (Kleppmann and Riccomini 2026), Chapter 3, covers the same property-graph-versus-RDF territory from the data-modelling side, including two query languages this chapter doesn’t build (Datalog and GraphQL) and SQL’s own support for graph queries, worth reading as the wider data-systems context this chapter’s graph-specific comparison sits inside.

77.9 Mental Model

A property graph is a graph where nodes and edges are allowed to carry their own labelled bag of attributes, the way a company org chart gets naturally sketched on a whiteboard. An RDF triple store insists on breaking everything down to atomic subject-predicate-object facts, the way a database-normalisation purist would insist every table have exactly one kind of row. Neither is “more correct.” They’re two different bets about whether uniformity or ergonomics matters more for the data at hand. This chapter’s Worked Example turned that bet into a number: 2.5x more facts, for the uniformity RDF buys.
