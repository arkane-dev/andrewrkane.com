Chapter 76 and Chapter 77 both assumed a graph already existed: hand-built, six nodes, six edges, ready to traverse or query. Real knowledge graphs don’t start that way. They start as unstructured text: contracts, news articles, support tickets, internal wikis. Something has to read that text and decide what the nodes, edges, and their types actually are, before either earlier chapter’s techniques have anything to operate on. This chapter is that something.

78.1 Motivation

Knowledge graph construction from text is a pipeline, not a single step: entity recognition (what things are mentioned?), relation extraction (how are they connected?), then validation (is what got extracted actually consistent with a schema?). Each stage can fail independently, in different ways, for different reasons. Worked Example 78 below builds a pipeline plain enough to see exactly where and why each stage’s mistakes happen, rather than treating “extraction accuracy” as one number.

78.2 Exposition

78.2.1 Rule-Based Extraction Is Cheap, Transparent, and Brittle: All Three at Once

A regex-based extractor costs nothing to run and its failures are fully explainable. Worked Example 78 hits a real bug where “Jane Doe previously worked at Initech” extracts the subject as “Jane Doe previously” instead of “Jane Doe,” because the non-greedy regex group had no way to know the adverb “previously” wasn’t part of a name. There was no other literal boundary for it to stop at. That’s not a contrived failure; it’s the generic failure mode of pattern matching that has no model of sentence structure. Entity extraction and relation extraction are two genuinely different problems with different measured difficulty, as Worked Example 78 shows directly: entity extraction (recognising that a capitalised span is an entity) is measurably easier than relation extraction (getting phrase boundaries right).

78.2.2 Ontology Validation Fixes Precision, Not Recall: and That Split Is the Point

A small ontology (allowed entity types, plus a domain/range constraint per relation: WORKED_AT must run from a PERSON to an ORG) allows catching bad extractions by checking consistency, without touching the extractor that produced them. Validation can only delete predictions; it has no mechanism to conjure the correct fact the extractor never produced correctly in the first place. Precision and recall are genuinely controlled by different parts of the pipeline, and Worked Example 78 is direct, measured proof of that split, not an assertion.

78.2.3 LLM-as-Extractor: Handling What Rules Structurally Can’t

Some sentences use passive voice or an implicit relation that no regex pattern targets at all: not a near-miss, a complete miss, because no pattern was even written for that shape of sentence. An LLM handles this differently: given a prompt describing the target schema (entity types, an ALL_CAPS_SNAKE_CASE predicate convention, subjects/objects restricted to extracted entities), it can return structured JSON that a small parser validates and converts into typed objects. Worked Example 78 adds the resulting facts to the validated set and measures the recall gain directly: real, measured progress, not a clean sweep to perfect recall, because the LLM step only reprocesses the sentence it targets; an earlier mistake elsewhere in the pipeline is still sitting there, uncorrected, because nothing revisited it.

78.3 Trade-offs and Limits

Rules are free, instant, and fully auditable: the regex can be read and its behaviour fully explained. They also only work for sentence shapes someone anticipated. An LLM handles novel phrasing without new patterns being written, at the cost of a per-call price, latency, and a parsing/validation step that has to defend against malformed or hallucinated JSON. Validation catches consistency errors, not missing facts. A domain/range ontology check is a precision tool; if recall is the problem, either a better extractor for that specific gap or a different extraction strategy entirely is needed, and validation alone will never get there. A small, fixed ontology (bounded entity/relation types) is exactly right for a bounded domain where the entities and relationships of interest are known in advance; an open-domain extractor with no fixed schema is a different, harder problem, useful when the relevant relationships aren’t yet known, but with much weaker validation guarantees, since there’s no fixed domain/range to check against.

78.4 Procedures

Procedure 78.1 (Extract Entities with Rule-Based Heuristics). When to use: a bounded domain where entity naming conventions are consistent (capitalisation, known suffixes).

Procedure 78.2 (Validate Extracted Triples Against a Small Ontology). When to use: after any extraction pass, rule-based or LLM, before trusting the resulting graph.

Common mistake: treating a validation pass as a fix for low recall. It can only remove bad triples, never add correct ones the extractor missed.

Procedure 78.3 (Extract with an LLM for Sentence Shapes Rules Can’t Handle). When to use: a specific, identified extraction gap that no reasonable amount of additional regex patterns would close.

Common mistake: trusting LLM output without the same validation pass applied to rule-based output. An LLM extraction needs a consistency check before being trusted, not automatic faith because a bigger model produced it.

78.5 Worked Example

A rule-based extractor (Procedure 78.1) run on a small corpus of six sentences, evaluated against a hand-labelled gold standard:

Stage Predicted Correct Gold Precision Recall
Entities 7 7 7 1.000 1.000

A clean sweep for entities: the suffix-based heuristic genuinely worked on this corpus. Relation extraction, the same corpus, a harder problem:

Stage Predicted Correct Gold Precision Recall
Relations (raw) 5 4 7 0.800 0.571

A measurably worse result from the same corpus and the same general extraction approach, because relations require getting phrase boundaries right, not just recognising that a capitalised span is an entity. The wrong prediction, ("Jane Doe previously", "WORKED_AT", "Initech"), is exactly the boundary bug Exposition describes.

Stage Predicted Correct Precision Recall
Relations, raw 5 4 0.800 0.571
Relations, post-validation 4 4 1.000 0.571 (unchanged)

Validation dropped the malformed triple automatically. "Jane Doe previously" was never in the known entity set, and precision jumped to a clean 1.000. Recall stayed at exactly 0.571, unchanged, confirming Exposition’s claim precisely: validation can only delete predictions, and the correct ("Jane Doe", "WORKED_AT", "Initech") fact the extractor should have produced never appeared, so no amount of validation recovers it.

Stage Predicted Correct Precision Recall
Rule-based + validation 4 4 1.000 0.571
+ LLM extraction on the missed sentence 6 6 1.000 0.857

Recall rises from 0.571 to 0.857: real, measured progress, not a clean sweep to 1.000, because the LLM step only reprocessed the one sentence it targeted (passive voice, implicit “partner of” relation with no matching regex pattern at all); the earlier WORKED_AT boundary mistake is still sitting there, permanently lost to the raw extractor’s error, uncorrected because nothing revisited it. The complete trace across the whole pipeline (1.000/1.000 entities, 0.800/0.571 → 1.000/0.571 → 1.000/0.857 relations) is Mental Model’s claim made fully numeric: precision and recall move independently, and each pipeline stage’s contribution is visible, not inferred.

The final constructed graph: 8 nodes, 6 edges, ready for Chapter 77’s traversal and query techniques to operate on. This is the object neither this chapter’s preceding chapters, nor any downstream graph technique, could have started with directly from raw text.

78.6 History and Further Reading

Grishman & Sundheim’s “Message Understanding Conference-6: A Brief History” (Grishman and Sundheim 1996) is the origin of NER/relation-extraction evaluation as a task, including precision/recall as the standard metrics used throughout this chapter. Edge et al.’s “From Local to Global: A Graph RAG Approach to Query-Focused Summarization” (Edge et al. 2024) uses LLM-based extraction (this chapter’s Procedure 78.3, at production scale) as the first stage of a GraphRAG pipeline.

78.7 How This Connects

This chapter builds on Chapter 76 and Chapter 77 (the property graph this chapter builds uses the exact same networkx node/edge conventions). It enables Chapter 79 (a graph needs to exist, with typed nodes and edges, before embeddings can be learned over it) and Chapter 80 (GraphRAG retrieves from exactly this kind of constructed graph: the whole retrieval pipeline is only as good as the graph this chapter’s techniques built). It’s often confused with assuming “we used an LLM to extract it” means the graph is now reliable. This chapter’s validation step exists precisely because LLM output, like rule-based output, needs a consistency check before being trusted, not automatic faith because a bigger model produced it.

78.9 Mental Model

Building a knowledge graph from text is not “run an extractor, get a graph.” It’s “run an extractor, measure exactly what it got right and wrong, add a validation layer that fixes what it can fix (consistency), and add a different technique for what it structurally cannot (novel sentence shapes).” Precision and recall move independently through that pipeline, and this chapter’s numbers (1.000/1.000 entities, 0.800/0.571 → 1.000/0.571 → 1.000/0.857 relations) are the concrete trace of exactly where and why, stage by stage, rather than one opaque “extraction accuracy” figure.
