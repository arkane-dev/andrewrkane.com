Book 2, Chapter 31 (Retrieval-Augmented Generation (RAG)) covered the standard RAG recipe: embed a chunk, embed a query, retrieve whatever is textually or semantically closest, hand it to an LLM. That works well when the answer to a question sits inside one passage. It works badly, often silently badly, when the answer only exists as a relationship spanning multiple passages, because vector similarity has no notion of “connected to,” only “reads alike.” Chapter 76 of this track gave traversal and shortest-path algorithms; Chapter 77 gave a place to store a richly-attributed graph; Chapter 78 gave a way to build one from text. This chapter is where those three pieces combine into a retrieval strategy that succeeds precisely where flat vector RAG structurally cannot.

80.1 Motivation

Vector search asks “what reads alike?” Graph traversal asks “what’s connected?” These are different questions, and a lot of genuinely useful questions are the second kind: “which vendor shares a parent company with a vendor flagged for a compliance issue” has no single sentence that states the answer. It emerges only once three separate facts are connected: entity A was flagged, A’s parent is P, P also owns entity B. GraphRAG’s answer is: don’t rank passages by text similarity for this kind of question. Build a graph, anchor on the entity the question is about, and traverse.

80.2 Exposition

80.2.1 Entity-Centric Retrieval Starts From a Thing, Not a Query String

Flat vector RAG turns the whole query into one embedding and searches for nearby chunks. Entity-centric retrieval instead identifies the specific entities the question concerns (“a vendor that was flagged,” “Acme Corp’s vendors”) and starts traversal from those entities in the graph, using exact graph lookups (in_edges, out_edges) instead of approximate textual similarity. The graphrag_multihop_answer function built in this chapter does exactly this: find flagged vendors, walk to their owner, walk to the owner’s other holdings, filter by Acme’s actual vendor list.

80.2.2 Multi-Hop Traversal Is Chapter 76’s Machinery, Reused

There is no new algorithm here. owners_of, siblings_owned_by, and vendors_of are each a one-hop graph query, chained together exactly the way breadth-first search explores one layer at a time. GraphRAG’s “multi-hop retrieval” is not a different kind of computation from ordinary graph traversal; it’s the same traversal idea, aimed at answering a specific factual question instead of computing a general graph property.

80.2.3 The Measured Comparison: A Genuine, Not Cherry-Picked, Failure

This chapter’s tutorial measured, rather than asserted, the difference. On a genuinely multi-hop question, a flat TF-IDF baseline’s top-3 retrieved passages never mentioned the answer entity at all, because the passage naming that entity as the connecting vendor shares almost no vocabulary with the query’s specific words (“flagged,” “parent,” “compliance”). Graph traversal, by contrast, found the exact two-hop chain deterministically, because it never depended on textual overlap in the first place. Crucially, the same worked example also ran a control query whose answer sits in one sentence. There, flat vector RAG’s top-ranked passage stated the answer directly. This is the honest, load-bearing point: GraphRAG isn’t a strictly better retrieval method. It’s the right tool for a specific shape of question (multi-hop, relationship-dependent), and flat vector RAG remains perfectly adequate, often simpler and cheaper, for single-hop, fact-lookup questions.

80.2.4 Community Summarisation Answers a Different Kind of Question Again

A specific two-hop path answers “does X relate to Y.” Some questions are broader, “summarise this vendor’s risk exposure,” and don’t have one specific path as the answer; they need a cluster. Louvain community detection (Chapter 76) run directly on the ownership/purchasing graph finds natural clusters, and a natural-language summary can be built entirely from real graph facts, assembled by string formatting: no LLM call, no hallucination risk, the same “compute it exactly, don’t ask a model to recall it” principle that graph algorithms embody generally.

80.2.5 The Graph-Grounded Prompt Makes the Traversal’s Output Auditable

The final prompt this chapter constructs states the derived multi-hop fact explicitly as a fact, not as raw source text the model has to re-derive: Northwind Ltd -OWNED_BY-> Meridian Holdings, Meridian Holdings -OWNS-> Fenwick Supplies. This is a meaningfully different object to hand a generation step than three separate, unconnected sentences. It’s the answer to the connecting question, computed and stated, with every hop individually inspectable and auditable, rather than left for the LLM to (maybe, silently) infer from concatenated context.

80.3 Trade-offs and Limits

GraphRAG requires a knowledge graph to already exist (the extraction work of Chapter 78), requires knowing which entities a question concerns (not always obvious from an arbitrary natural-language query), and adds engineering complexity a flat vector index doesn’t have. Flat vector RAG requires none of that setup, and, as this chapter’s control-query result showed, is entirely sufficient when the answer lives in one passage. Reach for GraphRAG specifically when questions in a domain are relationship-shaped, not by default.

Multi-hop traversal depth is a real design decision. This chapter’s traversal was fixed at exactly two hops because that’s what the worked scenario needed. A production system has to decide how many hops to traverse before stopping. Too few and the answer is missed, exactly as flat vector RAG missed it here; too many and the pipeline retrieves an explosion of loosely-related context, reintroducing the “too much irrelevant material” problem RAG exists to avoid in the first place. Community summarisation trades precision for coverage: a specific traversal path is a precise, auditable answer to a specific question, while a community summary covers more ground but is a coarser artefact, useful for “tell me about this cluster” questions, wrong for “what specifically connects X and Y.”

80.4 Procedures

Procedure 80.1 (Anchor Retrieval on Named Entities, Not the Query String). When to use: the question concerns specific, identifiable entities rather than a general topic.

Why this matters: identifying “Northwind Ltd” as the anchor entity via a node attribute check, not a text search, is what lets every subsequent step be an exact graph lookup instead of an approximate similarity search.

Procedure 80.2 (Run a Fixed-Depth Multi-Hop Traversal). When to use: the question is a specific relationship between two entities, and the hop count needed is known in advance.

Common mistake: hard-coding the hop count without checking whether the domain’s real questions need more or fewer hops. See Chapter 81 for what happens when the required depth isn’t known in advance.

Procedure 80.3 (Detect and Summarise a Graph Community). When to use: the question is about a cluster or neighbourhood rather than one specific pair of entities.

Why this matters: the summary text is assembled entirely from real graph facts via string formatting: zero hallucination risk, because nothing in the summary wasn’t already a verified graph fact. An LLM can be used to phrase the final sentence more fluently, but should not be the source of the facts themselves.

Procedure 80.4 (Construct a Graph-Grounded Prompt). When to use: handing a traversal’s output to a generation step.

Why this matters: stating the derived relationship as an explicit fact rather than handing over raw source sentences means the LLM doesn’t have to silently re-derive the connection itself. The traversal already did that, and every hop is independently checkable against the graph.

80.5 Worked Example

The tutorial notebook behind this chapter builds ten short text passages describing a network of companies, vendors, and a compliance flag, then asks: “Which of Acme Corp’s vendors shares a parent company with a vendor that was flagged for a compliance issue?” The gold answer, worked out by hand from the corpus: Northwind Ltd was flagged; its parent is Meridian Holdings; Meridian Holdings also owns Fenwick Supplies; Acme Corp purchases from Fenwick Supplies. So Fenwick Supplies is the answer, reached via two hops and confirmed against a third fact. No single passage states this.

A flat TF-IDF vector-RAG baseline (the same retrieval mechanism as production RAG: rank passages by similarity to the query, with TF-IDF standing in for a real embedding model) retrieved, at top-3: “Meridian Holdings is a Zurich-based holding company” (score 0.321), “Globex Materials is independently owned with no parent” (score 0.249), and “Northwind Ltd was flagged” (score 0.236). Fenwick Supplies is never mentioned at all. TF-IDF ranked the one passage that actually names Fenwick as Meridian’s other subsidiary below three passages sharing more surface vocabulary with the query (“holding company,” “parent,” “flagged”) despite two of them being irrelevant to the actual answer.

Listing 80.2, run against the same graph, found the match deterministically:

MATCH FOUND:
   Northwind Ltd -OWNED_BY-> Meridian Holdings
   Meridian Holdings -OWNS-> Fenwick Supplies
   Acme Corp -PURCHASES_FROM-> Fenwick Supplies
   => Fenwick Supplies shares parent Meridian Holdings
      with flagged vendor Northwind Ltd

A control query, “how much does Acme Corp spend annually with Fenwick Supplies?”, checked that this isn’t a strawman comparison: there, the flat vector-RAG baseline’s top-ranked passage (score 0.551) directly stated “$180,000 annually,” the correct answer. GraphRAG isn’t being compared against a deliberately weak baseline; vector RAG is simply the wrong tool for one specific shape of question, and the right tool for another.

Community detection (Listing 80.3) on the same graph found three communities: {Fenwick Supplies, Meridian Holdings, Northwind Ltd}, {Acme Corp, Globex Materials}, and {Atlas Group, Solaris Energy, Voltix Components}. Summarising the first produced, entirely from string-formatted graph facts:

Community summary (Meridian Holdings cluster):
  Meridian Holdings owns 2 member(s) of this community:
  Northwind Ltd, Fenwick Supplies.
  Northwind Ltd was flagged for environmental violations in 2024.

The graph-grounded prompt (Listing 80.4) states the three-hop chain explicitly, and a simulated LLM response (no live endpoint in this chapter’s worked example: the prompt text and one realistic response are both real, but the response is hardcoded and clearly labelled as simulated) correctly names Fenwick Supplies and repeats the supporting chain verbatim. The measured comparison: on the multi-hop query, vector-RAG’s top-3 never states the answer entity together with the flag condition (False); GraphRAG’s traversal finds and states the chain explicitly (True). On the control query, vector-RAG’s top passage directly states the answer (True). GraphRAG isn’t needed there at all.

80.7 History and Further Reading

Edge et al.’s “From Local to Global: A Graph RAG Approach to Query-Focused Summarization” (Edge et al. 2024) is the paper that popularised the term “GraphRAG,” including LLM-based extraction and community-based summarisation at production scale: the same community-summarisation idea built at toy scale in this chapter. Blondel et al.’s “Fast Unfolding of Communities in Large Networks” (Blondel et al. 2008) is the Louvain algorithm this chapter’s community detection step reuses from Chapter 76. Microsoft Research’s GraphRAG project documentation is a production-oriented reference implementation of the same ideas at much larger scale. Book 2, Chapter 31 (Retrieval-Augmented Generation (RAG)) is the flat vector-RAG baseline this chapter measured against throughout.

This chapter builds on Chapter 76 (traversal and community detection, reused directly, not reimplemented), Chapter 77 (the property-graph model this chapter’s graph uses), Chapter 78 (this chapter assumes a graph like the one that construction pipeline would produce), and Chapter 79 (learned embeddings are a common way to do entity-centric retrieval at a scale where exact traversal alone becomes expensive). It connects to Book 2, Chapter 31 (RAG): GraphRAG is not a replacement for that chapter’s architecture, it’s an additional retrieval strategy layered alongside it. Production systems frequently run both and route a query to whichever fits its shape. It’s often confused with “GraphRAG is always better than vector RAG.” This chapter’s own control-query result is the direct counterexample worth keeping in mind for the rest of this track.

80.10 Mental Model

Vector RAG answers “what does this remind me of?” Graph traversal answers “what is this actually connected to?” A multi-hop question needs the second question asked, explicitly, one hop at a time, and no amount of better embeddings changes that, because the connection was never encoded as text similarity in the first place. This chapter’s numbers are the direct, measured proof: flat retrieval missed the answer entity entirely; traversal found it, deterministically, in three inspectable hops.
