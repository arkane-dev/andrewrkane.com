Chapter 80 built a genuinely good retrieval pipeline, but a fixed one. Its multi-hop function checked exactly two hops because that’s what its worked example needed, and nothing about the function’s shape adapts if the real answer sits three hops away, or one. In production, the right hop count usually isn’t known in advance: questions about a procurement graph, a citation network, or an organisational hierarchy vary in how many relationships they need to traverse. This chapter asks: what if, instead of writing one fixed traversal function per question shape, an agent were given the traversal primitives as callable tools and allowed to decide, one call at a time, how far to go?

81.1 Motivation

A fixed pipeline commits to a shape before it sees the data. An agent loop commits to nothing but a stopping rule. Chapter 80’s function is, structurally, nested loops (flagged entities, then owners, then siblings): a shape baked in at write time. This chapter’s agentic_search is one loop that calls the same one-hop get_neighbors primitive repeatedly, checking after every call whether it’s found what it’s looking for, and only going further if it hasn’t. The traversal algorithm underneath, one-hop graph lookups, hasn’t changed at all; Chapter 76 and Chapter 80 already provide that. What’s changed is the control structure wrapped around it. Worked Example 81 below measures exactly what that control-structure change buys, and what it doesn’t.

81.2 Exposition

81.2.1 The Measured Failure a Fixed Pipeline Actually Has

Worked Example 81 reuses Chapter 80’s exact fixed_2hop_pipeline function, unmodified, on a graph where a real vendor relationship exists three ownership hops from a flagged company. The fixed pipeline returns nothing, because it only ever checks a flagged entity’s owner’s direct other holdings, and the sibling one level up isn’t itself a vendor. The actual vendor is invisible to a function that was never written to look past the first sibling layer.

81.2.2 The Adaptive Loop’s Advantage Is a Stopping Condition, Not a Smarter Algorithm

agentic_search calls get_neighbors on the current frontier, checks whether anything new is in the target set, and only expands the frontier again if it isn’t. There’s no new graph algorithm here. BFS from a start node, hop by hop, is the same idea Chapter 76 used for shortest paths. The genuinely new piece is deciding when to stop dynamically, based on what’s been found so far, rather than deciding it in advance.

81.2.3 Adaptivity Has a Real Limit, Measured Directly

Worked Example 81 doesn’t stop at the success case. Re-running the same search with a tighter hop budget reproduces the fixed pipeline’s exact blind spot. The loop gives up one hop too early, for the same underlying reason: nothing at that depth matched. This is the honest, load-bearing finding of this chapter: an adaptive loop isn’t magic. Its advantage over a fixed pipeline is a tunable ceiling instead of a hard-coded one. Set that ceiling too tight, and the result is back to the fixed pipeline’s exact failure mode, just configurable instead of baked in.

81.2.4 Why the Visited Set, Not Just the Hop Budget, Prevents Infinite Loops

A hop budget alone caps how many rounds the loop runs, but on a graph with a cycle (a cross-holding structure where an entity ultimately owns a stake back into part of its own ownership chain), an unguarded frontier-expansion step would keep re-adding the same nodes every round. The visited set is what actually stops that: each node is explored exactly once, regardless of how many times it’s reachable. The hop budget is a safety ceiling on top of that; it’s not what makes the loop correct.

81.3 Trade-offs and Limits

A fixed pipeline is simpler, faster (no repeated stopping-condition checks), and structurally cannot loop forever, but it’s blind to anything outside the shape it was written for. An adaptive loop generalises to questions whose hop count varies, at the cost of needing an explicit stopping condition and a hop-budget decision that genuinely matters and can be gotten wrong, as Worked Example 81 measures directly. Choosing a hop budget is a real design decision, not a formality: too tight, and the agent silently gives up before finding real answers, the same silent-failure character Chapter 80 found in flat vector RAG, just relocated to a different parameter; too loose on a large, densely-connected real-world graph, and the agent risks exploring a large fraction of the graph before concluding there’s no answer, which is slow and can retrieve an explosion of irrelevant context if that exploration also feeds a downstream prompt. This chapter’s “agent” is a deterministic rule-based function, not a real language model deciding what to call next. It’s appropriate for demonstrating the control-structure difference clearly and reproducibly, but a real Bedrock Agents or tool-calling-LLM deployment would have the model itself make the “keep going or stop” decision, more flexible but also less predictable than this chapter’s fixed BFS-with-early-stop policy.

81.4 Procedures

Procedure 81.1 (Implement an Adaptive Frontier-Expansion Search). When to use: any multi-hop graph question where the right hop count isn’t known in advance.

Common mistake: relying on the hop budget alone to prevent infinite loops on a cyclic graph. Without the visited set, a cycle causes the same nodes to be re-added to the frontier every round, and the loop only terminates because max_hops eventually runs out, wastefully re-exploring the same nodes many times over.

Procedure 81.2 (Choose a Hop Budget Deliberately, Not by Default). When to use: setting max_hops for a new graph or question domain.

81.9 Mental Model

A fixed pipeline is a script: it runs the same steps regardless of what it finds along the way. An agent loop is a policy: after every tool call, it looks at the result and decides what to do next. This chapter’s numbers are the direct, measured proof of the difference: reused unmodified, the fixed pipeline found nothing on a 3-hop scenario; the policy, given room to keep going, found it at hop 3, and, given too little room, failed in exactly the same way the fixed pipeline did. Adaptivity is not a free upgrade; it’s a different, tunable trade-off, and this chapter measured both sides of that trade honestly.
