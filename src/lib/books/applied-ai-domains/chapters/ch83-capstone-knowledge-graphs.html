Every chapter in this book’s knowledge-graphs section (Chapters 76 through 82) taught its lesson on the same procurement/ownership scenario (Meridian Holdings, Acme Corp, Fenwick Supplies, and their vendor relationships). That repetition was deliberate: reusing one familiar graph kept each chapter’s specific lesson isolated and easy to follow. But it leaves an important question unanswered: does any of this generalise past the one example used to teach it, or did the pipeline only ever work because the data was hand-tuned to make it work? This capstone, the final chapter of the entire book series, answers that directly, by building the entire pipeline (extraction, construction, traversal, retrieval, evaluation) on a domain none of the earlier chapters ever touched: a small network of AI research papers and their citations.

83.1 Motivation

Reproducing the same shape of result on new data is stronger evidence than a good result on familiar data. This capstone’s numbers are not identical to Chapter 82’s: different graph, different questions, different specific precision/recall values. What matters is that the pattern is the same: single-hop questions are answered well by both retrieval methods, with GraphRAG holding a modest edge, while multi-hop questions show a real, substantial GraphRAG advantage. That’s the same shape of result Chapter 80 and Chapter 82 found on a completely different graph, exactly what would be expected if the underlying claim (“GraphRAG helps specifically with relationship-shaped questions”) is a real property of the methods, not an artefact of one convenient dataset.

83.2 Exposition

83.2.1 Extraction Had to Be Genuinely Validated, Not Assumed

This capstone’s knowledge graph (13 entities, 15 edges) was built from 12 short text passages using the same rule-based extraction discipline Chapter 78 established: every single AUTHORED_BY/CITES edge traces back to a specific source passage, checked by hand, not asserted. This matters more here than in Chapter 78, because this is genuinely new data the extraction logic was never tuned against. If the extraction approach only worked by accident on Chapter 78’s specific examples, it would have shown up here as edges that don’t actually match what the text says. It didn’t.

83.2.2 The Traversal Function Needed Zero Changes

Chapter 81’s adaptive BFS-style traversal was reused for this capstone’s citation_chain_search completely unmodified: same algorithm, applied to a CITES relation instead of an OWNS relation, on an entirely different graph. That it worked without modification is itself informative: the traversal logic was never actually specific to ownership hierarchies, just to the general shape “follow a directed relation outward, hop by hop, with a stopping condition.” A capstone is a good place to discover that a piece of code was more general than its original chapter’s framing suggested.

83.2.3 The “No Valid Answer” Case Reappeared, Independently

Chapter 80 and Chapter 82 each included one question with no valid multi-hop answer, to check both methods correctly report “not found” instead of fabricating a spurious match. This capstone’s benchmark included one too: a citation-chain question about a paper with no outgoing CITES edges in this corpus, so no chain exists, and the traversal correctly stopped at the starting node rather than inventing a path. This wasn’t copied from the earlier chapters’ specific question. It emerged naturally from designing an honest benchmark on new data, a small, genuine confirmation that “always include an unanswerable question” is a generally good benchmark-design habit, not a one-off trick for this book’s specific graph.

83.3 Trade-offs and Limits

A capstone on new data costs more than reusing the familiar example. Building a second domain from scratch (new corpus, new entities, new benchmark questions, new gold labels to get right) took real additional work compared to just re-running Chapter 82’s exact pipeline again. That cost bought something a repeat run couldn’t: confidence the result isn’t an artefact of one dataset’s specific quirks. Six questions is still a small benchmark. Like Chapter 82’s eight, this capstone’s six questions are enough to demonstrate the methodology and produce an honest result, not enough to be a rigorous statistical claim. A real production decision should run this same precision/recall-by-type approach over dozens-to-hundreds of questions drawn from actual usage, on whichever domain is actually being deployed to.

83.4 Procedures

Procedure 83.1 (Validate Extraction Against Source Text Before Trusting a New-Domain Graph). When to use: any time extraction techniques are applied to genuinely new data they weren’t originally tuned against.

Procedure 83.2 (Reuse Prior Pipeline Code Unmodified as a Generalisation Test). When to use: validating that a technique built for one domain wasn’t secretly overfit to that domain’s specific shape.

Procedure 83.3 (Include a “No Valid Answer” Question in Every Retrieval Benchmark). When to use: any benchmark comparing retrieval methods, on any domain.

This wasn’t a question copied from an earlier chapter’s specific benchmark; it emerged naturally from designing an honest benchmark on genuinely new data, confirming Procedure 83.3’s practice generalises rather than being a one-off trick tied to the procurement graph’s specific structure.
