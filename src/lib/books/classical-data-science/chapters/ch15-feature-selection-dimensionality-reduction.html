Feature engineering fills a dataset with columns. This chapter is about admitting that not all of them are useful. One-hot encoding, interaction terms, datetime extraction: you’ve done it all. A modelling table can carry hundreds of columns. Past a point, more columns stop helping and start hurting. Models overfit. Training slows. Distance-based methods stop behaving sensibly. Two different operations both go by the name “dimensionality reduction,” which invites confusion rather than avoiding it. Feature selection keeps a subset of the original columns, so “income” stays income. Feature extraction builds a smaller number of new columns that are blends of the originals, trading interpretability for compactness. Both exist to fight the same enemy: the curse of dimensionality. Knowing which one a given situation needs matters as much as knowing how to run either.

15.1 Motivation

Module 14’s feature engineering deliberately produces more candidate columns than a model needs. The theory is that it’s cheaper to generate too much signal and prune it than to under-engineer and miss something. That pruning step is this chapter. Without it, a model trained on hundreds of largely redundant or irrelevant features doesn’t just run slower. It performs worse. It has more surface area on which to fit noise instead of signal. The goal is a feature set that is as small as it can be, without discarding anything that helps. Get there by keeping the best of what already exists (selection), or by compressing everything into fewer, denser dimensions (extraction).

15.2 Exposition

15.2.1 The Curse of Dimensionality

Three things get worse as the number of features grows. Distances stop being informative. In high dimensions, the ratio between the nearest and farthest neighbour’s distance shrinks towards 1. “Nearest” stops meaning much for the algorithms that depend on it: KNN, K-Means, anything built on Euclidean or cosine similarity. The data becomes sparse relative to the space. Keeping the same density of training examples per unit volume requires the number of examples to grow exponentially with the number of dimensions. With 20 features and a modest sample size, the data is a thin cloud in a mostly empty 20-dimensional space. Overfitting risk rises. More features means more ways to fit noise rather than signal, especially with a fixed number of rows. 500 features and 1,000 rows gives a model enormous freedom to memorise the training set rather than learn from it. There’s also a practical cost, independent of any statistical concerns: more features means more compute, more memory, and slower training.

The sparsity claim is easy to say and easy to underestimate, so it’s worth making concrete with numbers. Picture a cube of jelly, one unit of length on each side, with a million tiny balls suspended in it. One ball per data point. Say the cube has 3 dimensions: three features, each ranging over that unit of length. A million evenly-spaced balls sit roughly 1/1,000,0003=1/1001/\sqrt[3]{1{,}000{,}000} = 1/1001/31,000,000​=1/100 of the cube’s side apart from their nearest neighbours. That’s close enough that “nearest” means something. Now stretch that same cube into 20 dimensions. One axis per feature. Keep the same million balls. The average spacing between a ball and its nearest neighbour becomes 1/1,000,00020≈1/1.995≈0.5011/\sqrt[20]{1{,}000{,}000} \approx 1/1.995 \approx 0.5011/201,000,000​≈1/1.995≈0.501: roughly half the entire length of the cube’s side. The same million points that felt dense in 3 dimensions are, in 20 dimensions, spaced about as far apart as two points picked at random. No amount of data collection closes that gap. Matching the 3-dimensional spacing of 1/1001/1001/100 in 20 dimensions would need 10020=1040100^{20} = 10^{40}10020=1040 balls, about 103410^{34}1034 times the million we started with. This is the curse. Adding dimensions doesn’t make a dataset a little sparser. It makes it exponentially, catastrophically sparser, for a fixed number of examples.

15.2.2 Feature Selection: Filter, Wrapper, Embedded

Selection methods fall into three families, distinguished by how they decide which features matter.

Filter methods score each feature independently of any model, then keep the top scorers:

  • Variance threshold drops near-constant features, which carry no signal for any model.
  • Correlation with the target keeps features most linearly related to y. It’s cheap but blind to non-linear relationships, so a feature with a perfect U-shaped relationship to the target scores near-zero linear correlation and gets wrongly discarded.
  • Mutual information measures any dependency, linear or not, between a feature and the target. Slower than correlation, but far more reliable at catching non-linear signal.

Filters are fast (score everything once, sort, cut) but they ignore how features interact with each other and with whatever model will consume them.

Wrapper methods use the downstream model’s own performance to decide what to keep, searching over subsets directly rather than scoring features in isolation. Recursive Feature Elimination (RFE) trains the model, ranks features by importance or coefficient magnitude, drops the weakest, and repeats until reaching a target count. This directly optimises for what matters: model performance. But it’s expensive. It retrains the model repeatedly. And the resulting subset is specific to whichever model did the selecting.

Embedded methods get selection for free as a side effect of training a model that has sparsity or importance built in. L1 regularisation (Lasso) drives some coefficients exactly to zero, building selection into the loss function (Chapter 18 covers regularisation in depth). Tree-based importances (Random Forest, gradient-boosted trees) naturally produce a feature ranking as a byproduct of how often and how effectively each feature was used for splitting. Embedded methods are usually the best default in practice: they give selection signal without a separate search loop. But the importance scores can be biased towards high-cardinality or correlated features. Treat them as a hint, nothing more.

15.2.3 Feature Extraction: PCA

Principal Component Analysis doesn’t select features. It constructs new ones. The idea: find the direction in feature space along which the data varies most, call that the first principal component. Find the next direction (orthogonal to the first) that captures the most remaining variance. Repeat. Mathematically this is an eigendecomposition of the feature covariance matrix. If Σ\SigmaΣ is the covariance matrix of the standardised features, PCA finds its eigenvectors and eigenvalues:

Σv=λv\Sigma v = \lambda vΣv=λv

Each eigenvector vvv is a principal component (a direction in feature space) and its eigenvalue λ\lambdaλ is the amount of variance captured along that direction. Sorting components by eigenvalue, largest first, and keeping the top kkk gives the kkk-dimensional linear subspace that preserves the most variance possible for that value of kkk. In practice, a dataset almost never needs every original dimension to explain the bulk of its variance. Ten correlated features might contain only three or four independent “directions” of information. PCA finds them.

Standardise features before applying PCA. Variance is scale-dependent, and PCA chooses directions of maximum variance. A feature measured in dollars (range: thousands) will dominate the variance calculation over one measured in years (range: tens), purely because of its scale, not because it’s more informative. There are no right answers here, only trade-offs. With PCA the trade-off is interpretability. Component 1 is something like 0.31×income−0.22×age+0.18×tenure+…0.31 \times \text{income} - 0.22 \times \text{age} + 0.18 \times \text{tenure} + \dots0.31×income−0.22×age+0.18×tenure+…: a blend rather than a concept. Say a prediction needs to be explained in terms of a specific original variable, for a regulator, or a customer. Tree-based feature importance on the raw features is the better fit.

15.2.4 A Note on Kernel PCA

PCA assumes the informative structure in the data is linear: one direction, or a few, that variance stretches along. When it isn’t, kernel PCA applies the same kernel trick Chapter 11 introduces for Support Vector Machines. It implicitly maps the data into a higher-dimensional space via a kernel function, then runs ordinary PCA there. Kernel PCA is a different tool, not a drop-in upgrade. The resulting components are harder to interpret. There’s no simple way back to the original feature space, the way ordinary PCA has. The choice of kernel and its parameters becomes its own modelling decision. It’s worth reaching for when a scatter plot, or a failed linear PCA, suggests the real structure curves through feature space rather than sitting along a straight line.

15.2.5 t-SNE and UMAP: Visualisation, Not Modelling Features

t-SNE and UMAP are non-linear dimensionality reduction techniques. They’re almost always used to compress data to 2 or 3 dimensions for visualisation, rather than as inputs to a downstream model. Both preserve local neighbourhood structure, meaning points close together in the original high-dimensional space should stay close together in the embedding, rather than PCA’s global objective of maximising total variance. This makes them better at revealing cluster structure visually. PCA can smear well-separated real clusters together if the axis of maximum variance doesn’t align with what separates them. t-SNE or UMAP will usually recover more of that separation, though not always cleanly.

Figure 15.1 is the honest picture, not the idealised one. PCA’s top component chases the noisy nuisance dimension, since it has by far the largest variance. Two of the three clusters (purple and teal) merge into a single smeared mass, while the third (yellow) stays visibly apart. Silhouette score: 0.0073, close to the 0 that means “no cluster structure visible at all.” UMAP does better, but “better” here means partial, not perfect. Yellow separates cleanly, and purple and teal pull apart along most of their length, though they still touch where the embedding curls back on itself. Silhouette score 0.0774, roughly ten times higher than PCA’s: a real and measured improvement, not a clean sweep.

t-SNE, run on the same data with its default settings, is the surprise: 0.0033, worse than PCA, not better. That’s not a bug in the method. t-SNE builds its neighbourhood graph from distances measured in the original feature space, the same space where the noise dimension’s huge scale already dominates every pairwise distance. A method built to preserve local neighbourhoods still inherits whatever those neighbourhoods look like in the raw data, noise dimension included, unless something else, a smaller perplexity, a prior scaling step, counteracts it. Rerunning with perplexity=12 instead of the default 30 gives 0.107, better than UMAP, on the exact same data. That swing, from worse-than-PCA to better-than-UMAP on one hyperparameter change, is the sensitivity this chapter’s Trade-offs section warns about, made concrete.

The moral isn’t “UMAP is better than PCA,” and it isn’t “t-SNE and UMAP always fix this” either. PCA’s global-variance objective can be actively misled by a single noisy, high-variance column that has nothing to do with the structure that matters. A local-structure method recovers some of what PCA lost, but only if its own settings are tuned to the data, and a default configuration is no guarantee of that. That’s exactly why it’s worth looking at the real picture, with real numbers, instead of assuming the textbook one.

There are three separate reasons their output shouldn’t feed a model, though. First: both are typically non-parametric in their classic form. There’s no simple transform() for new data with the same guarantee as the fitted embedding. UMAP supports transform() with caveats, while classic t-SNE does not, without retraining on the combined dataset. Second: distances between clusters in the embedding aren’t meaningful. Only local neighbourhood structure within a cluster is preserved reliably, so two clusters that look far apart aren’t necessarily “more different” than two that look close. Third: both are stochastic and sensitive to hyperparameters (perplexity for t-SNE; n_neighbors and min_dist for UMAP). Rerunning with a different seed or parameter can meaningfully change the layout. That’s fine for a one-off exploratory plot, but a poor foundation for a reproducible production feature. Use t-SNE and UMAP to look at data: check whether classes separate, spot outlier clusters, sanity-check a clustering result from Chapter 19. Use PCA, or regular feature selection, when reduced dimensions need to feed a model.

15.3 Trade-offs and Limits

Selection preserves interpretability and is safe to defend to a stakeholder (“we use income and tenure”). Extraction squeezes out more redundancy but gives up that interpretability entirely. Filters are cheap and model-agnostic, but ignore feature interactions. Wrappers are thorough, but expensive and specific to whichever model did the searching. Embedded methods are the best per-cost trade-off for most tabular problems, and are the reasonable place to start. Between PCA and t-SNE/UMAP: PCA is linear, deterministic, and reversible. An approximation of the original data can be reconstructed from it, which makes it suitable both for visualisation and as a preprocessing step for a downstream model. t-SNE and UMAP are non-linear and much better for visual cluster discovery, but they’re the wrong tool whenever reduced features need to be deployed and explained.

It’s also worth asking whether this chapter’s machinery is needed at all. Tree-based models (Random Forest, XGBoost, LightGBM) are relatively robust to irrelevant features. They won’t split on features that don’t help. Feature selection matters most for linear models, distance-based models (KNN, K-Means), and any case where training cost or interpretability is a real constraint. It is not a required step before training.

15.4 Procedures

Procedure 15.1 (Drop Low-Variance and Highly Correlated Features). When to use: as a first, cheap pass before any modelling, to remove features that are almost constant or redundant with another feature.

Common mistake: running VarianceThreshold on unscaled data. A feature ranging 0-1,000,000 will always look “high variance” even if it’s useless, while a feature ranging 0-1 might get dropped even if it’s highly predictive. Scale first, or reserve variance thresholding for features already on comparable scales such as one-hot encoded columns.

Procedure 15.2 (Select Features by Mutual Information). When to use: a fast, non-linear-aware ranking of features against the target, without training a full model.

Common mistake: computing mutual information, or any selection statistic, on the full dataset before the train/test split: that leaks test-set information into the feature-selection decision. Fit the selector on the training fold only, then apply the same selected columns to the test set.

Procedure 15.3 (Run Recursive Feature Elimination). When to use: finding the feature subset that most helps a specific model, when retraining it repeatedly is affordable.

Common mistake: using a slow model (a deep neural network, a large XGBoost ensemble) inside RFE. Each elimination step retrains from scratch, so runtime multiplies by the number of features removed. Use a fast, well-regularised model for the search; it’s not being deployed, only used to rank features.

Procedure 15.4 (Use Tree-Based Feature Importance for Selection). When to use: a tree ensemble is already in use, or affordable to fit, and selection is wanted essentially for free.

Common mistake: trusting importance rankings blindly when features are highly correlated. Tree models split arbitrarily between two near-identical correlated features, diluting importance across both and making each look less important than a single, non-redundant version would. Decorrelate first (Procedure 15.1) if this matters.

Procedure 15.5 (Choose the Number of PCA Components). When to use: after deciding PCA is appropriate (linear structure, a need for a reproducible transform) before fitting the final model.

Common mistake: fitting PCA on training and test data combined “to get a stable transform”: this leaks test-set variance structure into the transform. Fit on training data only, and call .transform(), never .fit_transform(), on the test set.

Procedure 15.6 (Interpret PCA Loadings). When to use: explaining, even approximately, what a principal component “means.”

A large positive or negative loading means that feature strongly drives the component: the sign indicates direction only, not importance. If PC1 loads heavily and positively on income, credit_limit, and spend, it’s roughly “overall financial scale,” but that’s a rough label, not a rigorous claim.

The tutorial notebook builds a synthetic classification dataset with 50 features: 10 truly informative, 10 redundant (linear combinations of the informative ones), and 30 pure noise. It then runs every selection and extraction technique against it and compares downstream Random Forest accuracy and fit time. A baseline using all 50 features scores:

Running the full comparison on a 1,500-row training split (2,000 samples, 25% held out, random_state=42 throughout) produces:

The pattern matches what this chapter’s Trade-offs section predicts. RFECV and the embedded Random Forest importance method don’t just match the 50-feature baseline, they beat it, using roughly half the columns and shedding noise features that were otherwise available for the model to overfit on. The mutual-information filter and PCA extraction both trail the baseline slightly here. PCA’s 37-component result is a reminder. Sometimes real informative structure is spread across many original dimensions, not just redundancy to compress. Then extraction can lose a little relative to a wrapper method that gets to see actual downstream accuracy during selection. Mutual information’s top-15 list: feature_0, feature_5, feature_6, feature_7, feature_9, feature_18, feature_23, feature_25, feature_26, feature_37, feature_38, feature_43, feature_45, feature_48, feature_49. It draws heavily from the first 20 columns, which is exactly where make_classification places the informative and redundant features, confirming the filter is finding real signal rather than noise.

On the extraction side, fit PCA() with no component limit on the scaled 50-feature training set and read the cumulative explained-variance curve. 37 components are needed to reach 95% of the variance. Not a dramatic compression. 20 of the 50 features carry genuine signal, and PCA still has to represent all of that spread-out structure, without the pure-noise columns contributing meaningfully.

The second half of the notebook switches from modelling to pure visualisation. It loads the classic 64-pixel handwritten-digits dataset (1,797 samples, 10 classes) and compares PCA, t-SNE, and UMAP as they each compress it to 2D. Timing the three on this machine: PCA runs in 0.05s, t-SNE in 1.54s, and UMAP in 8.58s. PCA’s near-instant linear projection against two much slower non-linear methods is exactly the relative-speed ordering this chapter’s Exposition describes. Visually, plotting each embedding coloured by true digit class, PCA produces a reasonable but often overlapping scatter, since it optimises for global variance rather than class separation. t-SNE and UMAP never see the labels, yet typically produce much tighter, more visually distinct clusters per digit. Both are explicitly preserving local neighbourhood structure rather than total spread.

15.10 Mental Model

Feature engineering fills a toolbox. Feature selection and dimensionality reduction decide which tools are needed for the job in front of you. Selection removes tools that won’t be used. Extraction welds several overlapping tools down into one multi-purpose one. Both exist because a toolbox that’s overflowing slows everything down, hurting more than it helps.
