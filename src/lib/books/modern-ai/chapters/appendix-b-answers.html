Chapter 21 — Responsible AI & Data Governance

Exercise 21.1 [W]. A demographic group column that’s excluded from training can still be discriminated against through proxy variables: other features (zip code, name, browsing history) that happen to correlate strongly with the excluded attribute. The model has no way to “know” it’s using a proxy. It just finds whatever pattern in the available features predicts the historically biased label best. If a proxy carries that signal, the model uses it exactly as it would use any other predictive feature.

Exercise 21.2 [W]. (a) Equal Opportunity: missing a qualified applicant (false negative) is explicitly the harm being minimised. (b) Equalised Odds: both false positives and false negatives carrying real cost is exactly equalised odds’ target condition (equal TPR and FPR across groups).

Exercise 21.3 [A]. With proxies: Group A 0.828 − Group B 0.147 = 0.681 (68.1 percentage points). Without proxies: Group A 0.577 − Group B 0.588 = −0.011 (about 1.1 percentage points, in the opposite direction, and effectively noise). The gap changed dramatically, from 68 points to near zero. The overall selection rate level also shifted, roughly 48-58% combined, versus the widely split 82.8%/14.7%. But the far more consequential change is the near-total collapse of the gap between groups, not the modest shift in overall level.

Exercise 21.4 [A]. A TPR of 0.880 for Group A means 88% of truly qualified Group A candidates are correctly identified as hires. A TPR of 0.183 for Group B means only 18.3% of truly qualified Group B candidates are. In plain terms: an equally qualified Group B candidate has roughly a 1-in-5 chance of being correctly recognised as hireable, versus roughly 9-in-10 for an equally qualified Group A candidate. That’s nearly a 5x gap in the odds of a qualified person from each group actually being selected.

Exercise 21.5 [E]. “Not collecting race or gender directly doesn’t prevent discrimination through proxies. This chapter’s own measured example shows a model with neither attribute in its feature list still producing a Disparate Impact Ratio of 0.177, entirely through zip code and first name standing in for the excluded attribute. The right check isn’t ‘did we collect the protected attribute.’ It’s a fairness audit on the model’s actual outputs across whatever demographic groups matter here.”

Exercise 21.6 [E]. “A blanket rule removes genuinely useful signal along with the bias. For a logistics model, commute time legitimately correlates with delivery performance regardless of who lives where. Removing zip code entirely could hurt accuracy for no fairness benefit, if it isn’t actually acting as a demographic proxy in that context. The better approach is auditing each candidate feature’s actual correlation with the sensitive attribute and its actual contribution to any measured disparity, as this chapter’s before/after removal comparison did, rather than assuming every feature that could be a proxy is one in every application.”

Exercise 21.7 [R]. Discussion only. Demographic parity and equalised odds become mutually exclusive specifically when the true base rates of the outcome differ between groups, e.g. if Group A and Group B genuinely have different underlying qualification rates in the population. Satisfying equal selection rates (demographic parity) while the true positive rate must also be equal (equalised odds) is only simultaneously achievable when the groups’ true positive rates in the data already match. That’s rarely the case when historical bias has shaped the labels themselves, as in this chapter’s hiring example, where Group B’s true hire rate was deliberately lowered by construction.

Exercise 23.7 [R]. Discussion only. Past the critical batch size, decode latency stops being memory-bandwidth-bound and becomes compute-bound instead. Further increasing batch size starts trading off against per-token latency directly, instead of being nearly free the way it was below the critical batch size. This differs from the memory-bandwidth-bound regime this chapter’s formulas describe, where the whole point of batching is exploiting slack compute capacity while memory bandwidth is the bottleneck. Past the critical batch size, that slack is gone.

Chapter 24 — MLOps & CI/CD for ML

Exercise 24.1 [W]. Traditional software only has code that changes between releases. The same input always produces the same output for a given code version, so checking “does the code still work” (tests passing) is sufficient. ML systems have code, data, and learned parameters all changing independently. The same code can produce a worse model if the training data shifts, or if hyperparameters change, neither of which a code-only test suite would catch. That’s why data validity and model quality need their own separate checks.

Exercise 24.2 [W]. Shadow deployment. It validates the new model against real production traffic patterns while producing zero risk to actual users, since predictions are only logged, never served. That makes it the right choice before any user is exposed to a costly-if-wrong fraud model’s decisions.

Exercise 24.3 [A]. A gate checking only candidate_f1 >= 0.5 would pass the Gradient Boosting candidate outright, since 0.9660 comfortably clears 0.5. Procedure 24.3’s actual gate adds the second condition: comparing against the current production metric (0.9722). 0.9660 is below 0.9722, so the “regression vs. production” check fires and correctly rejects it despite easily clearing the absolute bar.

Exercise 24.4 [A]. gate_candidate(0.9660, 0.9722, min_f1=0.5, tolerance=0.01): the absolute check passes (0.9660 ≥ 0.5). The regression check compares 0.96600.96600.9660 against 0.9722−0.01=0.96120.9722 - 0.01 = 0.96120.9722−0.01=0.9612. Since 0.9660≥0.96120.9660 \geq 0.96120.9660≥0.9612, no regression is flagged either. With a 0.01 tolerance, the Gradient Boosting candidate would pass. A small tolerance band is enough to let a candidate through that’s marginally, but not meaningfully, below the incumbent. This illustrates why the tolerance parameter itself is a real design decision, not just a technicality.

Exercise 24.5 [E]. The most likely bug is the gate comparing against a stale, cached production metric captured at pipeline-definition time, rather than querying the registry live at gate-check time. If the “production” number used in the comparison was hardcoded or fetched once and never refreshed, a genuinely worse candidate could pass simply because it’s being compared against an outdated (possibly already-superseded or incorrect) baseline number instead of the actual current production metric.

Exercise 24.6 [E]. “Tracking every run gives you the logging and comparison half of the picture. You can see what was tried. But MLOps is specifically about automating the promotion and deployment decision based on that logged data. Does a new model get gated, tested, and shipped automatically, or does someone still manually decide and push it? Tracking is necessary but not sufficient. Without the gate and pipeline automation this chapter covers, you still have the exact failure mode from the Motivation: a manually-pushed regression that nobody caught.”

Exercise 24.7 [R]. Discussion only. Shadow deployment’s named limitation is that it validates prediction quality but not real-world business impact. Since shadow predictions are never actually served to users, there’s no way to observe how the new model’s decisions would have changed user behaviour, conversion, or other downstream business metrics that only manifest when real users actually see and react to the new model’s outputs. Canary is recommended as the more common default specifically because it exposes the new model to a small slice of real consequences, catching business-impact problems shadow mode structurally cannot detect, while still limiting the blast radius if something goes wrong.

Chapter 25 — Monitoring

Exercise 25.1 [W]. Data drift is a shift in P(X)P(X)P(X) while P(y∣X)P(y \mid X)P(y∣X) stays fixed. The inputs look different, but the rule mapping inputs to the true label hasn’t changed. That means it’s visible directly in the input features, with no need for a label at all. Comparing a reference sample of x1 against a current sample and computing PSI or a KS statistic detects it immediately. Concept drift is the opposite. P(y∣X)P(y \mid X)P(y∣X) itself changes, the same inputs now genuinely map to a different true output, which by construction leaves no trace in the marginal distribution of XXX. There is nothing unusual to see in the inputs, because nothing about the inputs changed. Only the relationship changed, and the only way to observe a broken relationship is to compare predictions against actual outcomes, i.e. labels. This is why the two failure modes need different detection machinery: PSI/KS on features for data drift, and rolling performance metrics against ground truth (with whatever label lag that entails) for concept drift. One can’t substitute for the other, because they’re measuring genuinely different quantities.

Exercise 25.2 [W]. In periods 3-4, accuracy moved only trivially: 0.776 and 0.777, essentially indistinguishable from the quiet-period baseline of ~0.76-0.78, even though x1 and x2 shifted by 0.8 and then 1.4 standard deviations. A monitoring system that only tracked accuracy would have seen nothing worth flagging across those two periods, because the model’s learned relationship still held even as it extrapolated into a less-familiar region of feature space. The substantial input shift caused no proportional harm to predictive performance. PSI, by contrast, is computed directly from the input distributions and doesn’t need performance to move to register a signal. It caught the shift immediately and dramatically (0.736 and 0.640 in period 3, climbing to 1.878 and 1.935 in period 4), well before there was any accuracy-based reason for concern. This is exactly the leading-indicator property the Exposition describes. Data drift is detectable before, or even in the complete absence of, a performance impact, which an accuracy-only monitor is structurally unable to see.

Exercise 25.3 [A]. Running Listing 25.1 with period 0’s x1 values as expected and period 5’s x1 values as actual reproduces the table’s reported value of 0.016, essentially the same order of magnitude as the quiet-period noise floor (0.021, 0.028 in periods 1-2), and nowhere close to the 0.10 “moderate shift” threshold. This is exactly what the tutorial’s design predicts, not a detection failure, because period 5 was constructed to leave the input distribution of x1 completely untouched. Only the sign of the coefficient relating x1 to the label was flipped. Since PSI is a function purely of the two x1 samples’ bucketed distributions, and those distributions are statistically identical between period 0 and period 5 by construction, a near-zero PSI is the correct, expected output. The tool is doing exactly what it’s supposed to do: reporting that the inputs didn’t move, which is true.

Exercise 25.4 [A]. Walking max_psi=0.30, accuracy_drop=0.02 through Listing 25.5’s classify function: the first check, accuracy_drop > ACCURACY_DROP_RETRAIN (0.02 > 0.05), is false, so it does not return 'RETRAIN'. The second check, max_psi > PSI_ALERT (0.30 > 0.25), is true, so the function returns 'INVESTIGATE'. This is the conservative choice rather than the aggressive one, because PSI alone, even a fairly large PSI of 0.30, is only an indirect proxy for drift, per the Trade-offs table, and the accuracy drop of 0.02 is well under the 0.05 threshold that would confirm real harm. Retraining is expensive and carries its own risk (a new model version that could behave worse), so the decision rule deliberately withholds that action until performance evidence confirms the input shift actually mattered. This exactly mirrors what happened with periods 3-4 in the Worked Example: elevated PSI, unconfirmed performance impact, INVESTIGATE rather than RETRAIN.

Exercise 25.5 [E]. Per this chapter’s triage checklist, two explanations should be ruled out before recommending a retrain. First, a pipeline bug rather than real drift. Check whether transaction_amount’s volume or null rate changed abruptly around the same time the PSI spike appeared, since a broken upstream feature source (a currency conversion step failing, a new payment provider sending amounts in a different unit) can produce a large PSI reading that has nothing to do with genuine customer behaviour change. Second, whether the shift coincides with a known, already-understood business event: a product launch, a new merchant category going live, a marketing campaign driving a different customer mix. In that case the drift is real but expected, and doesn’t by itself indicate the model’s relationship between transaction amount and fraud has broken, only that the input distribution has moved into a region the model may or may not still generalise well to. Only after ruling out both would input drift alone, still without confirmed labels, justify escalating past INVESTIGATE.

Exercise 25.6 [E]. A usable proxy is early engagement decline: a drop in login frequency, feature usage, or session count over a short rolling window (7-14 days) relative to each customer’s own recent baseline, monitored as an aggregate rate across the customer base rather than waiting for the 30-day confirmed-churn label. If the proxy’s population-level rate shifts meaningfully compared to its historical range, that’s a much faster signal that something about customer behaviour or the product experience has changed than waiting a full month for confirmed churn outcomes. The risk: engagement decline is a proxy, not the label itself, and the relationship between “engagement dropped” and “customer actually churned” can itself drift. A seasonal dip (e.g. a product used mainly during a school term going quiet over summer) could trigger the proxy without any actual increase in churn, producing a false alarm and, if acted on by retraining, potentially degrading the model on a false premise rather than a real one.

Exercise 25.7 [R]. Discussion only, no single answer. Reasoning from Listing 25.1’s implementation: bucket edges are computed once, from expected’s percentiles (np.unique(np.percentile(expected, breakpoints))), and then np.histogram(actual, edges) is used to bin the current sample into those same, fixed edges. np.histogram places any value below the first edge or above the last edge into neither bin. Those out-of-range values simply don’t get counted in actual_counts at all, rather than being forced into the nearest bucket. If production values fall entirely outside the reference range, the extreme buckets nearest that edge would show actual_pct collapsing toward the zero-replacement floor (1e-4) while whichever bucket happens to still catch some mass dominates. If all actual values fall outside every bucket edge, every actual_counts bin is zero, actual_counts.sum() is zero, and actual_pct = actual_counts / actual_counts.sum() divides by zero, producing NaNs rather than a large, meaningful PSI. That’s a real gap in the implementation, since the case that most obviously represents a severe drift (production data occupying a completely different range) is exactly where the function is likely to break rather than report a maximal score. Contrast this with chi-squared for categorical data, which explicitly reindexes and fills unseen categories with a small floor value rather than silently dropping them. The numeric PSI implementation would benefit from an analogous explicit clamp of out-of-range values into the nearest edge bucket, instead of dropping them from the histogram.

Chapter 27 — NLP Fundamentals

Exercise 27.1 [W]. TF-IDF(word, doc) = TF(word, doc) × IDF(word), where IDF(word) = log(N / df(word)). A word appearing in every one of the N documents has df = N, so IDF = log(N/N) = log(1) = 0, and any TF value multiplied by zero is zero. The word contributes nothing to the document’s vector, regardless of how often it appears within any single document.

Exercise 27.2 [W]. Call .fit_transform() only on training data. It learns the vocabulary and IDF table, then transforms in one step. Call .transform() only on test/new data, reusing the vocabulary and IDF already learned from training. Calling .fit_transform() on test data re-learns a new vocabulary/IDF from the test set itself, which leaks test-set statistics into the pipeline and typically also produces a differently-shaped matrix than the one the trained classifier expects.

Exercise 27.3 [A]. TF-IDF outperformed mean-pooled GloVe-50 here (0.9074 vs. 0.8327 macro-F1) because this task’s discriminating signal is specific vocabulary. Words like nhl, orbit, 3d, doctor are highly diagnostic of their category, and TF-IDF preserves each of these as its own dimension with a large weight. Mean-pooling averages a document’s ~200 word vectors into one 50-dimensional point, so the three or four topic-defining words get diluted by the other ~196 generic words in the average. The ranking would likely flip on a task needing genuine semantic similarity across different vocabulary, e.g. matching “the patient had a myocardial infarction” to “the patient suffered a heart attack,” where TF-IDF sees zero word overlap but embeddings correctly see near-identical meaning.

Exercise 27.4 [A]. The gap between queen (0.861) and the next result, daughter (0.768), is a substantial 0.093 in cosine similarity. For a 50-dimensional space where most word pairs have much smaller similarity gaps, this is a wide margin, suggesting the analogy is largely unambiguous. The arithmetic result sits clearly closer to queen than to any of the four next-nearest words, rather than being a near-tie the model got lucky on.

Exercise 27.5 [E]. “This chapter’s Worked Example measured the opposite on a real classification task. TF-IDF scored 0.9074 macro-F1 versus embeddings’ 0.8327 on the same 20 Newsgroups split. Embeddings do capture semantic similarity that TF-IDF can’t, which matters enormously for retrieval and paraphrase-matching tasks. But ‘captures meaning’ isn’t the same as ‘wins on every task.’ When the actual signal is specific, discriminating vocabulary rather than paraphrase-level similarity, TF-IDF’s sparse exact-word representation can be the stronger choice. The only way to know which applies is to measure both on the actual task.”

Exercise 27.6 [E]. If a document happens to contain zero tokens from the embedding vocabulary (e.g., it’s mostly numbers, code, or a language the embedding table wasn’t trained on), doc_embedding silently returns an all-zero vector, indistinguishable from any other document that legitimately embeds near the origin. A classifier trained on data containing several such zero-vector documents effectively learns “the zero vector means class X” if those particular documents happen to skew toward one class, a spurious pattern with nothing to do with content. Detecting it: count how many training documents produce an all-zero embedding before training, and flag or route to a fallback representation (e.g., TF-IDF) any document whose vocabulary coverage is below a chosen threshold.

Exercise 27.7 [R]. FastText represents each word as the sum of vectors for its character n-grams (subwords) rather than one atomic vector per whole word. “Unhappiness”, even if never seen as a complete token during training, decomposes into subwords like “un”, “happi”, “ness” that likely were seen inside other training words (e.g., “unhappy”, “happiness”, “sadness”). FastText can compose a reasonable vector from those learned subword pieces. GloVe and Word2Vec store one fixed vector per whole word learned during training. A word absent from the training vocabulary simply has no vector at all, with no mechanism to construct one from its parts.

Chapter 28 — Intro to Neural Networks

Exercise 28.1 [W]. output = σ(w₁x₁ + w₂x₂ + ... + wₙxₙ + b). Without a nonlinear σ, each layer is just a linear (affine) transformation, and the composition of any number of linear transformations is itself a single linear transformation. A ten-layer network with no activations computes exactly the same class of function as a one-layer network, gaining nothing from the extra depth.

Exercise 28.2 [W]. Dropout, weight decay, and early stopping. model.eval() disables dropout at inference time (dropout is only active when the model is in .train() mode).

Exercise 28.3 [A]. An early-stopping implementation should save the weights from epoch 43, where validation loss was at its minimum (0.0725). That is the point at which the model generalised best to unseen data. Saving the epoch-149 weights would be wrong despite epoch 149 having the lowest training loss (0.0016), because the low training loss at that point reflects memorisation of training-set noise, not improved generalisation. Validation loss had already risen to 0.1054 by then, meaning the model got measurably worse on data it hadn’t memorised even as it looked better on data it had.

Exercise 28.4 [A]. Breast Cancer Wisconsin’s 30 features are cleanly linearly-separable enough that even a 785-parameter network (or, by extension, a plain logistic regression) can find a near-optimal decision boundary. There isn’t enough genuine complexity in the underlying pattern for extra capacity to exploit at convergence, so all three configurations converge to essentially the same test-set decision boundary. The overfitting difference is only visible mid-training, in how each configuration’s validation loss evolves before reaching that shared endpoint, not in the endpoint itself.

Exercise 28.5 [E]. “This chapter’s Worked Example trained a 73,985-parameter network on only 426 examples, over 170 parameters per training example, and its validation loss rose for the second two-thirds of training even while training loss kept falling. More parameters gave that model more capacity to memorise noise, not more genuine skill. The 785-parameter network reached the same test F1. Bigger only helps when there’s enough data and genuine complexity in the task to use that capacity for signal rather than memorisation.”

Exercise 28.6 [E]. Without optimizer.zero_grad(), PyTorch’s default behavior is to accumulate gradients into .grad across every .backward() call rather than replacing them. By epoch 150, each parameter’s gradient would be the sum of all 150 individual epochs’ gradients rather than any single epoch’s gradient, causing wildly oversized weight updates. This wouldn’t raise an error, because gradient accumulation is a legitimate, deliberately-used PyTorch feature (for simulating larger batch sizes on limited memory). The code runs to completion, but training diverges or produces nonsensical loss values, which looks like a hyperparameter problem rather than a missing line of code.

Exercise 28.7 [R]. The Universal Approximation Theorem guarantees that a sufficiently wide single-hidden-layer network exists that approximates any continuous function arbitrarily well. It says nothing about whether gradient descent, starting from a random initialisation and running a finite number of steps, will actually find that network’s weights. In practice, gradient descent finds a local (not necessarily global) minimum of the loss landscape, and the “sufficiently wide” network the theorem requires may need more neurons than are practical to train. The theorem is an existence proof, not a construction or training-convergence guarantee. That’s why architecture design and optimisation research remain necessary even though the theorem has been known since 1989.

Chapter 29 — Training a Transformer Model

Exercise 29.1 [W]. score(i, j) = softmax(Qᵢ · Kⱼ / √d_k). The √d_k term prevents the dot products Qᵢ · Kⱼ from growing large as d_k increases, which would otherwise push softmax into a near-one-hot regime with vanishing gradients everywhere except the single largest score.

Exercise 29.2 [W]. Encoder-only (e.g. BERT), decoder-only (e.g. GPT-2), encoder-decoder (e.g. T5). Encoder-only models cannot generate text. They see full bidirectional context, which is well-suited to classification/understanding tasks but incompatible with left-to-right generation.

Exercise 29.3 [A]. Layer 4 attending to “animal” with weight 0.1688 versus 0.0289 to “street” (averaged across all 12 heads) indicates that coreference-relevant information has been built up by the middle-to-later layers of the network. Earlier layers (0–1) show much weaker and less consistent differentiation (0.0364 vs 0.0462 at layer 0, actually favoring “street” slightly). Checking multiple layers was necessary because attention patterns are not uniform across depth. A single layer chosen arbitrarily (especially an early one) could have shown the opposite or a null result, giving a misleading impression that the model doesn’t encode this resolution at all.

Exercise 29.4 [A]. 12 × 32 × 4096² = 12 × 32 × 16,777,216 = 6,442,450,944 ≈ 6.44B. Adding vocab×d_model with vocab=32,000: 32,000 × 4096 = 131,072,000 ≈ 0.13B, giving a total of roughly 6.57B parameters. That’s consistent with the chapter’s claim that this configuration lands “in the right ballpark for a 7B model” once minor terms are included.

Exercise 29.5 [E]. “DistilBERT was pretrained purely with a masked-language-modelling objective, predicting randomly masked tokens from context, with no coreference-specific labels or task anywhere in its training. The attention pattern favoring ‘animal’ over ‘street’ for ‘it’ emerged as a side effect of learning to predict masked words well, which requires implicitly tracking what pronouns refer to. It’s a learned regularity, not an explicitly trained capability.”

Exercise 29.6 [E]. Formula-only (no embedding term) gives 84,934,656 against an actual 124,439,808, an error of (84,934,656 - 124,439,808) / 124,439,808 ≈ -31.7%, a far larger error than the -0.73% achieved once the embedding term is added. The embedding term matters more for GPT-2 small specifically because its vocabulary (50,257 tokens) is large relative to its total parameter count (124M). The embedding matrix alone (50,257 × 768 ≈ 38.6M) is nearly a third of the whole model. A much larger model (e.g. a 70B-parameter model) has a similarly-sized vocabulary but a vastly larger 12·L·d² term, so the same embedding matrix becomes a negligible fraction of the total, and the formula-only estimate would be accurate even without adding it.

Exercise 29.7 [R]. Sliding-window attention restricts each token to attending only within a fixed-size local window (e.g. the nearest 512 tokens) rather than the entire sequence, reducing complexity from O(n²) to O(n·w) where w is the window size. What it gives up: a token far outside the window has no direct attention path to it in a single layer. Long-range dependencies must instead propagate indirectly across multiple stacked layers (each layer’s window effectively “reaches” a bit further than the last), which is a weaker and less direct mechanism than the original architecture’s ability for any token to attend to any other token in one step.

Chapter 30 — Prompt Engineering

Exercise 30.1 [W]. A zero-shot version simply instructs: “Classify the following IT helpdesk ticket as hardware, software, or network.” A few-shot version adds 2-3 labelled examples spanning the categories before the real ticket. “My laptop won’t connect to the VPN” is genuinely ambiguous (VPN client software issue vs. network connectivity vs. occasionally a hardware NIC problem). Few-shot is more likely to handle it consistently, since worked examples can show how to break exactly this kind of tie, whereas zero-shot relies entirely on the model’s own prior judgment call.

Exercise 30.2 [W]. Discussion depends on the specific problems, but the pattern holds: any problem requiring more than one arithmetic operation applied in sequence (e.g. “a train travels at X for Y hours, then Z for W hours, what’s the total distance”) benefits from CoT, because direct-answer prompting has nowhere to write down the intermediate per-leg distances before summing them. The model must hold that intermediate value in an implicit internal state rather than as an explicit token it can condition on.

Exercise 30.3 [A]. Feeding back the previous attempt’s parse error (e.g. “missing required field ‘deal_value_usd’”) gives the model a concrete, specific correction target instead of a blind re-ask. This should improve retry success because the model can directly address the stated failure rather than resampling from the same distribution that produced the first failure with no new information.

Exercise 30.4 [A]. Schema: {"company_name": "string", "deal_stage": "string", "deal_value_usd": "number"}. company_name and deal_stage should be marked required (a sales call transcript should reliably mention both). deal_value_usd is more defensible as optional, since not every call transcript states a concrete dollar figure, and forcing it as required risks the model hallucinating a plausible-looking number rather than reporting it’s genuinely absent.

Exercise 30.5 [E]. Self-consistency multiplies cost and latency by N (5-way here), which is very likely incompatible with a 2-second customer-facing latency budget. 5 sequential or even parallel generations plus a vote step will typically blow that budget. Self-consistency is better suited to backend, non-latency-sensitive, high-stakes reasoning tasks (e.g. an offline batch job scoring loan applications) where accuracy matters more than response time.

Exercise 30.6 [E]. The risk is prompt injection. Retrieved ticket text is untrusted input, and embedding it in the same string as system instructions gives an attacker who controls ticket content a channel to inject text like “ignore previous instructions.” The concrete fix is to keep system instructions in a dedicated system parameter (separate from user/retrieved content) wherever the API supports it, and to never let the retrieved text alone trigger high-stakes actions without a validation step.

Exercise 30.7 [R]. Discussion only. The reported finding is that CoT’s accuracy benefit over direct-answer prompting emerges mainly at larger model scales and is small or absent in smaller models. Below some threshold, models may not yet have the latent capability CoT elicits, only the surface pattern of “write more text before an answer” without the reasoning benefit. This implies CoT prompting on a small locally-hosted model may add latency and cost without a matching accuracy gain, and should be validated empirically on that specific model rather than assumed to transfer from results on frontier-scale models.

Exercise 30.8 [R]. Discussion only. Both are forms of position bias: a judgment (a next-token probability distribution, or an LLM-as-judge comparison) shifting based on the order items appear in, rather than their actual content. They likely share the same underlying root cause (transformers attending more strongly to certain positions, particularly recency in-context), but manifest differently. This chapter’s version anchors generation toward whichever example format appeared most recently in the prompt, while Chapter 32’s version biases a judgment toward whichever candidate answer is shown first or second in a pairwise comparison. Treating them as the same underlying phenomenon with different symptoms is defensible. Treating them as identical failure modes requiring identical fixes is not, since the mitigations differ (example ordering/balance here, response-order randomization there).

Chapter 31 — Retrieval-Augmented Generation (RAG)

Exercise 31.1 [W]. Online steps, in order: (1) embed the user’s query, (2) retrieve the closest chunks from the vector store, (3) augment: build a prompt from the retrieved chunks plus the query, (4) generate: send the augmented prompt to an LLM. Chunking and embedding the document store happen only once, offline, during indexing.

Exercise 31.2 [W]. Always embed queries and documents with the exact same model, pinned to the same version. If violated, e.g. a document store embedded with one model version but queries embedded with a newer version, the two sets of vectors no longer live in a comparable space, and similarity scores become meaningless even though the code runs without error.

Exercise 31.3 [A]. Ranking the correct document lower (say, second or third) still leaves useful signal. A system could return the top-3 and the answer would likely be present. “0.0000 for every document” means there is no signal at all. Every document is exactly tied, so whichever one gets selected as “top-1” is an artifact of sort-stability or array order, not of any actual relevance judgment. A system built on this retrieval would confidently hand the LLM an arbitrary, equally-irrelevant-looking document and prompt it to answer from that. The failure is silent and looks identical to a successful retrieval from the outside.

Exercise 31.4 [A]. With min_similarity=0.3 and TF-IDF’s measured scores all at 0.0000, every candidate falls below the threshold, so build_prompt would return the “no relevant context found” fallback path, telling the LLM to answer from general knowledge and say so, rather than handing it an irrelevant document dressed up as ground truth. This is the safer failure mode. A naive prompt builder without the threshold check would take whatever TF-IDF ranked “first” (an arbitrary tie-broken choice) and present it to the LLM as retrieved context, risking a confidently wrong answer grounded in unrelated text: worse than an honest “I don’t have relevant context for this.”

Exercise 31.5 [E]. “Weekly fine-tuning solves staleness at a real infrastructure and cost burden. Every retrain needs a training run, evaluation, and redeployment, for information that might only have changed in a handful of documents. It also doesn’t give auditability. A fine-tuned model can’t show which specific document a fact came from, while RAG can cite the exact retrieved passage. And fine-tuning is genuinely good at changing behavior or style, not at being a fact database. Updating documentation weekly via fine-tuning is solving a retrieval problem with a much more expensive and less transparent tool.”

Exercise 31.6 [E]. If a genuinely complete idea spans three sentences and only the first and last are captured by neighboring chunks (with overlap_sentences=1 carrying only the single boundary sentence forward), the middle content could still end up split awkwardly if the max_words cutoff falls inside that three-sentence span. Increasing overlap_sentences to 2 or 3 would carry more of the preceding context forward into the next chunk, though at the cost of more redundant embedded content and higher storage/embedding cost.

Exercise 31.7 [R]. “Approximate” in ANN search means the search is not guaranteed to return the exact true k-nearest-neighbours. It can occasionally miss a genuinely close vector or include one that’s slightly further than the true top-k, in exchange for turning what would be an O(n) exhaustive scan into something close to O(log n). At millions-of-chunks scale, this trade is usually acceptable, because RAG retrieval already tolerates some imprecision by design. Reranking (Procedure mentioned in Trade-offs) and threshold filtering are already built to catch and correct for a retrieval step that isn’t perfectly precise, so ANN’s small accuracy cost rarely changes the end-to-end answer quality, while the latency win is often the difference between a usable and unusable production system.

Chapter 32 — LLM Evaluation

Exercise 32.1 [W]. Classical evaluation assumes there is a single correct answer (ground-truth label) to compare a prediction against. This fails for open-ended text generation because two completely different sentences can both be excellent answers, and a nearly-identical sentence can be a terrible answer if it changes one key fact. There is no single string to diff against.

Exercise 32.2 [W]. Position bias: mitigated by scoring both A/B orderings and only trusting a verdict that agrees across both. Verbosity bias: mitigated by explicit “do not reward length” rubric instructions and post-hoc correlation checks between length and score. Self-preference bias: mitigated by using a judge model from a different family than the model(s) being evaluated, validated periodically against human scores.

Exercise 32.3 [A]. A ROUGE-threshold gate would have passed the opposite-meaning candidate (F1=0.947, comfortably above almost any reasonable threshold) while potentially failing the faithful paraphrase (F1=0.308, likely below a typical threshold). For a medical or safety-related answering system, this means the gate would happily ship a response that is the factual opposite of correct, and dangerous if acted upon, while blocking a completely correct answer purely because it used different words. The gate would be actively selecting for the wrong outputs, worse than having no automated gate at all in this specific dimension.

Exercise 32.4 [A]. Precision dropped further than recall because the verbose candidate contains most of the reference’s content (high recall: the reference’s words are “found” somewhere in the long candidate) but pads that content with many extra filler words not in the reference (low precision: most of the candidate’s own words don’t match anything in the reference). This directly mirrors Procedure 32.3’s length-bias check. A judge or metric that doesn’t specifically penalise unnecessary length will see the high-recall signal and score the verbose answer well, without any correction for the precision cost of all that padding, exactly the mechanism that produces verbosity bias in an LLM judge, just visible here in a purely lexical metric instead.

Exercise 32.5 [E]. “This chapter’s Worked Example scored a factually correct paraphrase at 0.308 and a factually opposite, potentially dangerous answer at 0.947 using the exact same reference-based ROUGE metric. The free metric isn’t measuring correctness, it’s measuring word overlap, and those two things diverge sharply and unpredictably. ‘Free’ evaluation that ranks a wrong answer above a right one isn’t a cost saving. It’s a broken signal that would need a second, more reliable method to catch what it misses.”

Exercise 32.6 [E]. Collapsing “A wins one order, B wins the other” into “TIE” loses the information about which specific comparisons were unstable versus genuinely settled. At scale, treating a systematic pattern of position-sensitive disagreement (e.g., always occurring on a particular category of question) as generic noise indistinguishable from a real tie would hide a rubric or judge weakness that’s specific to that category, when a closer look might reveal the judge is actually unreliable on a whole class of comparisons rather than randomly inconsistent.

Exercise 32.7 [R]. Example: two raters rate 100 responses as “helpful” or “not helpful.” If 85 of the 100 responses are genuinely helpful and both raters lean toward rating almost everything “helpful” independent of actual quality (say, each rates 90% of responses as helpful), percent agreement can be high (e.g. both say “helpful” on 78 of the 100, both say “not helpful” on 3, giving 81% raw agreement) purely from both raters sharing a strong bias toward the majority label, not from genuine shared judgment on the harder cases. Kappa corrects for this by subtracting out the agreement expected by chance given each rater’s marginal label distribution. A low kappa despite high percent agreement reveals that the raters aren’t actually discriminating between good and bad responses. They’re both just defaulting to the common label most of the time, meaning the task’s rating guidelines likely need sharper, more discriminating criteria before the scores are trustworthy.

Chapter 33 — Continuous Pretraining

Exercise 33.1 [W]. CPT changes what the model knows (self-supervised next-token prediction on domain text, no behaviour change). IFT changes how the model behaves (supervised training on instruction-response pairs, communication style not knowledge). RAG changes what the model can look up (external retrieval at inference time, weights never change).

Exercise 33.2 [W]. C ≈ 6 · N · D: N is the model’s parameter count, D is the number of training tokens processed. The 6 combines roughly 2 FLOPs/parameter/token for the forward pass and roughly 4 for the backward pass (backward does about twice the work of forward).

Exercise 33.3 [A]. Procedure 33.1’s own thresholds classify a ratio below 1.2 as “base model handles the domain well enough, try prompting/IFT first,” and the measured 0.84x falls well under that threshold, so the test recommends against CPT entirely (and the direction is even more extreme than “well enough,” since legal text was actually easier for the model than general text). This would surprise someone who assumed legal language’s superficial unfamiliarity (Latin phrases, unusual syntax) implies statistical unpredictability to a language model. But the underlying reason is that highly templated, formulaic legal boilerplate is common across the public web (contracts, ToS pages) and therefore well-represented in GPT-2’s pretraining data, even though it reads as specialised to a human.

Exercise 33.4 [A]. 1.99 / 0.27 ≈ 7.4x memory reduction. This is larger than the “3-4x” figure Exposition cites for bigger models because LoRA’s memory cost has two components: the frozen base model (2 bytes/param, fixed regardless of scale) and the trainable adapters (16 bytes/param × a small fraction of N). At small scale, the frozen-base term is tiny in absolute terms, so LoRA’s total memory is dominated almost entirely by the adapter term, which is a very small fraction of the full 16-bytes/param figure. That produces a larger relative reduction than at bigger scale, where the frozen base term itself becomes large enough to matter more in the LoRA-vs-full comparison.

Exercise 33.5 [E]. “Before committing CPT budget, run Procedure 33.1’s domain gap test directly against your engineering wiki text versus general text. This chapter’s Worked Example showed that a domain that feels highly specialised (legal contract language) can actually score lower perplexity than everyday sentences, because formulaic or repetitive text is often well-represented in a model’s pretraining data regardless of how unfamiliar it looks to a person. ‘Feels specialised’ and ‘is statistically unfamiliar to the model’ are different claims, and only the second one justifies CPT.”

Exercise 33.6 [E]. Running quality filtering before deduplication means every duplicate copy of a document gets filtered (language ID, length, perplexity, domain classification) redundantly. If a document appears 50 times in the raw corpus, quality filtering runs 50 separate times on functionally identical text, wasting that much compute on redundant filtering work before deduplication ever removes the duplicates. Running deduplication first means the 50 copies collapse to one before any filtering compute is spent, so filtering only ever processes each unique document once.

Exercise 33.7 [R]. Manually picking a single fixed domain-mixing ratio (e.g. 85% domain / 15% general) applies the same static blend throughout training regardless of how the model’s performance on each type of data evolves. DoReMi instead learns the mixing ratios by training a small proxy model to find domain weights that minimize worst-case loss across domains, then applies those learned weights to the larger training run. It treats the mixture ratio itself as something to be optimized empirically per-domain-set rather than fixed by an intuition-based percentage, which can better balance domains with very different intrinsic difficulty or size than a single hand-picked ratio would.

Chapter 34 — Instruction Fine-Tuning

Exercise 34.1 [W]. The three parts: system prompt, user message, assistant response. Loss is computed only on the assistant response. The model isn’t penalised for how it represents the system prompt or user message, only for how well it produces the correct response given them.

Exercise 34.2 [W]. W·x + B·A·x. W (the base model’s original weight matrix) is frozen. A and B (the low-rank adapter matrices) are the only trained parameters.

Exercise 34.3 [A]. The trainable-parameter percentage falling inside the expected 0.1–1% range confirms that target_modules=["c_attn"] correctly matched real layers in the model and that LoRA is doing what it’s supposed to: adapting a small slice of the architecture rather than accidentally leaving the base model fully trainable or matching nothing at all. A figure of 40% would indicate target_modules matched far more of the model than intended (or LoRA wasn’t actually restricting training to adapters), effectively defeating LoRA’s entire memory/compute advantage while still reporting as “using LoRA”: exactly the kind of silent misconfiguration the print_trainable_parameters() sanity check exists to catch before an expensive training run.

Exercise 34.4 [A]. The genuine generalisation is producing “Lisbon,” the correct answer to a question about a country (Portugal) that never appeared in any of the six training examples, meaning the model correctly extended the learned instruction-response pattern to a held-out case. The training-set-size artifact is the trailing repetition, “Response: Lisbon. Response: Portugal.”, a malformed continuation pattern not present in any training example, which is exactly the kind of instability six examples (far below even LIMA’s 1,000-example floor) would be expected to produce. Both can be true simultaneously because they reflect different aspects of what was learned. The semantic mapping (country → capital) generalised well from a small, consistent pattern, while the precise boundary of “when to stop generating” is a subtler formatting behavior that needed more examples to stabilise.

Exercise 34.5 [E]. “IFT teaches a model how to communicate, not new fixed facts. It memorises poorly, and any facts baked in this way go stale the moment next quarter’s results are released. For quarterly financial results specifically, use RAG (Chapter 31): index the actual results documents and let the model retrieve and cite them at query time. That’s also auditable. You can show exactly which document backed an answer, which a fine-tuned model’s baked-in ‘knowledge’ cannot.”

Exercise 34.6 [E]. A team could fine-tune a model using a hand-written prompt template that superficially resembles the model’s expected chat format (e.g., manually writing [INST]...[/INST] tags) and pass all training-time tests, since the training loop only checks that loss decreases on the hand-formatted examples. If the exact special tokens, whitespace, or tag placement differ even slightly from what tokenizer.apply_chat_template() produces at serving time, the served model receives inputs formatted differently from what it was trained on. That degrades output quality in production even though every training-time unit test (which never exercised the actual serving-time template) passed cleanly.

Exercise 34.7 [R]. Quantising only the frozen base weights to 4-bit while keeping LoRA adapters in higher precision (fp16/bf16) is reasonable because the base weights are never updated during training. They only need enough precision to produce a reasonably accurate forward pass, and 4-bit NF4 quantisation is specifically designed to preserve the statistical distribution of pretrained weights well enough for this. The LoRA adapters, by contrast, are exactly the parameters receiving gradient updates. Keeping them in higher precision avoids compounding quantisation error with the optimizer’s own numerical sensitivity (small updates to already-quantized low-precision values would lose meaningful signal), so the precision budget is spent where training actually happens rather than uniformly across parameters that never change.

Chapter 35 — Reinforcement Learning & RLHF

Exercise 35.1 [W]. For an LLM trained with RLHF, the “action” is emitting the next token (or, at a coarser grain, the whole response), and the “reward” is a scalar score assigned to the full response by a reward model. The reward is assigned to the whole response rather than to each token because there is no reliable way to judge whether an individual token, in isolation, was “good.” Quality (helpfulness, coherence, tone) is a property of the completed response, not of any single token in it. A token that looks poor in isolation might be a necessary step toward a strong overall answer.

Exercise 35.2 [W]. The Bradley-Terry loss, −log⁡σ(r(chosen)−r(rejected))-\log \sigma(r(\text{chosen}) - r(\text{rejected}))−logσ(r(chosen)−r(rejected)), is minimised as the gap between the two scores grows, regardless of where that gap sits on the number line. It never appears in a form that compares either score against a fixed target value. If the loss instead demanded a specific value per response (e.g. a mean-squared-error loss against hand-assigned scores of 1.0 and 0.0), the reward model would need genuinely calibrated absolute scores from annotators, which is a much harder and more expensive labelling task than a simple pairwise preference. And the model’s outputs would no longer be free to occupy whatever numeric range best separates good from bad, the way the chapter’s worked example showed both chosen and rejected scores landing in a shared negative range while still ranking correctly.

Exercise 35.3 [A]. Discussion only, no single answer. A representative example set for, say, a legal-summary domain: chosen responses that name the correct governing clause and cite it plainly, rejected responses that give a vague gist without citation, following the chapter’s Worked Example pattern of complete-and-cited versus terse-and-unsupported.

Exercise 35.4 [A]. In Listing 35.3, at step 0 the policy and reference model are literally the same weights (the reference is initialised as a frozen copy of the starting policy). Therefore sequence_logprob(policy, prompt, response) and sequence_logprob(reference, prompt, response) return identical values for any response, so chosen_term = logp_chosen_policy - logp_chosen_ref = 0 and rejected_term = 0 as well, making chosen_term - rejected_term = 0. The margin is algebraically forced to zero regardless of which preference pairs are used, because no gradient step has yet moved the policy away from the reference.

Exercise 35.5 [E]. The likely cause is beta set too low. The KL leash is too loose, so the policy has wandered far enough from the reference model to start exploiting the reward model’s blind spots (reward hacking), which manifests as the repetitive text the reviewer noticed even as the (proxy) preference margin keeps climbing. The specific change to try first, per Procedure 35.5, is raising beta (e.g. from 0.1 to 0.2 or 0.5) to tighten the constraint back toward the reference model, then re-checking actual generations rather than the margin alone.

Exercise 35.6 [E]. Both PPO-based RLHF and DPO need an SFT model to serve two roles at once: the starting point for the policy being optimised, and the frozen reference model that anchors the KL penalty (explicit in PPO, folded into DPO’s loss). Skipping SFT means preference-tuning would start from, and be anchored to, a base model that has never learned to follow instructions at all, so the “reference” behaviour being preserved is not a sensible baseline to preserve, and the preference pairs (which assume instruction-following completions) would be out of distribution for what the base model naturally produces.

Exercise 35.7 [R]. Discussion only, no single answer, since it requires reading the DPO paper. Expect an answer to identify that the key step is recognising the KL-constrained reward-maximisation objective has a known closed-form optimal policy (a Boltzmann-like distribution over the reward), which lets the reward function be expressed algebraically in terms of the optimal policy and the reference policy. Substituting that expression back into the Bradley-Terry loss cancels the explicit reward model out entirely, leaving a loss defined purely on the policy’s own log-probabilities.

Exercise 35.8 [R]. Discussion only, no single answer. Consider: overfitting is a mismatch between training-set performance and true generalisation, caused by fitting noise specific to the training data. The “alignment tax” is a measurable drop in a preference-tuned model’s performance on general capability benchmarks it wasn’t tuned on, relative to the SFT checkpoint it started from. They share the shape of “optimizing for one objective costs performance on another,” but overfitting is about a model learning spurious training-specific patterns, while the alignment tax is about a model’s capacity or behaviour genuinely shifting toward the preference-tuning objective (helpfulness, tone, safety) at some cost to unrelated capabilities. It’s worth arguing whether that’s better framed as a capacity trade-off than as noise-fitting.

Chapter 36 — Agentic AI & Agent Patterns

Exercise 36.1 [W]. observe → reason → act → observe (result of that act) → reason → act → ... → stop. A single prompt call is just reason → act, executed exactly once. An agent runs the full loop repeatedly, with the model deciding when to stop rather than stopping automatically after one turn.

Exercise 36.2 [W]. step_limit_reached should be a distinct, explicit return value, not an exception or a silent cutoff. Treating it as a silent cutoff would make it impossible for downstream code or a human reviewer to distinguish “the agent found the answer” from “the agent ran out of steps and the true answer is unknown.” The two cases look identical without an explicit status flag, risking a partial or non-answer being treated as a confirmed result.

Exercise 36.3 [A]. Without Procedure 36.2’s guardrail, the scripted policy shown in Listing 36.4 would call flaky_search("population of Atlantis") indefinitely. It retries unconditionally whenever the observation contains “No definitive result,” and that observation never changes across calls, so there is no condition inside the policy itself that would ever cause it to stop. This is exactly the “infinite or near-infinite loop” failure mode from Failure Modes. A tool returning an ambiguous, unsatisfying result with no built-in escape causes indefinite retrying rather than the model (or here, the scripted policy) giving up.

Exercise 36.4 [A]. Mental Model’s three-place debugging list is: a missing or wrong tool, a missing stopping condition, or an early error that compounded uncaught. The two Worked Example trajectories used identical loop code, identical tool implementations, and differed only in the tool’s returned observation. The calculator’s clean numeric result satisfied the policy’s stopping condition on step 1, while flaky_search’s unsatisfying result never did. This demonstrates that the failure originated specifically at the “missing stopping condition” layer (the ambiguous observation gave the policy no way to recognize it should stop) rather than a tool being wrong or an early error compounding: a useful isolation when debugging a real trajectory, since it points directly at reviewing what conditions the policy/model treats as “done.”

Exercise 36.5 [E]. “Before splitting into five agents, is there concrete evidence the single agent’s context or tool surface has actually become a bottleneck? Has it hit context limits, or do the three tools genuinely require distinct specialised reasoning that’s getting muddled in one system prompt? This chapter’s guidance is to default to one agent and only add more with demonstrated need, because multi-agent systems multiply latency, token cost, and the number of places a failure can occur. Five agents sounds more sophisticated, but a single well-scoped agent outperforms multi-agent setups on most tasks people reach for one on.”

Exercise 36.6 [E]. Legitimately demonstrated: the loop mechanics themselves. How the step counter increments, how the trajectory is logged, how the step_limit_reached status triggers precisely at max_steps, and how an unconditional retry policy genuinely exhausts the guardrail rather than stopping early. This is real, measured, reproducible behaviour of the actual guardrail code. NOT legitimately demonstrated: anything about how a real LLM would actually decide whether to retry. A real model might recognize “No definitive result found. Sources disagree.” as a signal to try a different query, rephrase, ask a clarifying question, or give up gracefully with a caveat, none of which the deterministic scripted policy is capable of, since it has no actual judgment, only a fixed rule.

Exercise 36.7 [R]. Debate/critique is well-suited to catching a plausible-but-wrong answer that “sounds right” on a single pass but doesn’t survive scrutiny, e.g., a subtly incorrect calculation or a claim that omits a caveat a careful reviewer would flag, since a single-pass agent has no mechanism to second-guess its own output once generated, while a critique step specifically prompts a second agent (or role) to look for exactly this kind of flaw. The roughly-doubled cost can be worth it specifically for high-stakes outputs where a subtle, hard-to-catch error would be expensive if it shipped uncaught. The cost of a second pass is small relative to the cost of a wrong answer reaching production undetected.

Chapter 37 — Capstone Project

Exercise 37.1 [W]. The four elements: Business Question, Success Criteria, Out of Scope, Stakeholder. “Build a model to predict pump failure” states a task, not a business question. It’s missing all four elements: why the prediction matters (business question, properly framed), what counts as good enough (success criteria with a cost-justified threshold), what’s deliberately excluded (out of scope), and who uses the output (stakeholder).

Exercise 37.2 [W]. Deployment and monitoring. Per Motivation, cutting these under time pressure means the stages that most distinguish a data scientist from a Kaggle-style notebook exercise get dropped first: exactly the stages that demonstrate a model was built to production standard rather than existing only as a validation-set metric in a notebook cell.

Exercise 37.3 [A]. The cross-validation standard deviations (0.0617 for LR, 0.0402 for RF) describe the spread of recall scores across the 5 folds for each model individually. Both are small relative to the 0.4069 gap between the two means (0.7241 vs. 0.3172). If the gap between models were smaller than roughly the sum of their standard deviations, it would be plausible that fold-to-fold noise alone explains the difference. Here the gap is roughly 6-7x the larger of the two standard deviations, meaning the models’ recall distributions barely overlap across folds. This is the same logic Chapter 13’s cross-validation chapter uses to distinguish a genuine model-selection signal from noise: look at the spread, not just the point estimate, before trusting a comparison.

Exercise 37.4 [A]. A single PSI value with nothing to compare it against can’t distinguish “the check is working correctly and detected a real shift” from “the check always reports a high number regardless of input,” or conversely “the check never reports a high number regardless of input.” Either failure mode would look identical to a correctly-functioning check if only one batch were ever tested. Testing against both a genuinely-drifted batch (0.4704, correctly flagged as major) and a no-drift control batch drawn from the same distribution as training (0.0482, correctly not flagged) demonstrates the check discriminates in both directions. It doesn’t just always fire, and it doesn’t just never fire. That’s the minimum evidence needed to trust it as a real monitoring signal rather than a check that happens to look plausible.

Exercise 37.5 [E]. “Five tuned architectures and a strong CV F1 score demonstrate real modelling skill, but per this chapter’s rubric, that’s only one dimension of a capstone. Modelling is often over-invested in relative to its real payoff (Procedure 37.2’s effort allocation caps it at 25%), while deployment and monitoring, entirely missing here, are worth 30% combined and are the stages that prove the model could actually be used, not just scored. A modest single model with real deployment and monitoring code demonstrates more of this book’s stated goal than five well-tuned models that only exist as notebook cells.”

Exercise 37.6 [E]. Fraud/anomaly detection on financial transactions: here, a false positive (flagging a legitimate transaction as fraud) has a real cost, blocked legitimate purchases, customer friction, support burden, while a missed fraud case, though costly, is often one of many transactions and may be partially recoverable through other controls (chargebacks, insurance). A model tuned to minimize false alarms even at the cost of missing more fraud cases could be the right choice if the business’s actual cost structure makes “don’t annoy legitimate customers” the dominant concern: the opposite trade-off from this chapter’s predictive-maintenance example, where a missed failure (unplanned downtime, safety risk) dominates the cost of an extra inspection.

Exercise 37.7 [R]. A plausible fairness-adjacent question: if runtime_hours or maintenance history correlates with which facility or region a pump is deployed in, a model trained to prioritize inspection resources based on predicted failure risk could systematically under-prioritize maintenance in facilities with less complete sensor logging (more missing vibration readings) purely due to data quality differences rather than genuine risk differences, effectively deprioritizing maintenance where monitoring infrastructure is already weakest. Naming this explicitly in the “Out of Scope” section, even without solving it, is better practice than silent omission, because it tells a future reader (or the practitioner’s future self) that the question was considered and consciously deferred, rather than leaving it ambiguous whether it was missed entirely. That’s the same distinction Chapter 21’s governance chapter draws between an unexamined blind spot and a documented, deliberate scope boundary.
