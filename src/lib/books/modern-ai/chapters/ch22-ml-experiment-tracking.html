Fifty experiments over two weeks: tweaked hyperparameters, different feature sets, two model architectures tried. The last run gets 87% accuracy, but there’s no record of which combination of parameters produced it. A run’s output folder gets deleted by accident. A colleague asks which model is in production and whether it can be reproduced, and there’s no good answer. This is the default state of untracked ML work. It’s one of the leading causes of ML projects failing to reach production. Experiment tracking fixes it by making every run a first-class, logged, reproducible, queryable artefact.

22.1 Motivation

An ML experiment is a run of code that takes inputs (data, hyperparameters, code version) and produces outputs (a trained model, metrics, plots). Experiment tracking records both sides of that equation, persistently and automatically. A previous result can be reproduced exactly. Dozens of runs can be compared on any metric at once. A production model can be traced back to the exact training run that produced it. Colleagues can see what’s already been tried, rather than re-discovering it. It’s version control for models. Git tracks code changes. MLflow tracks experiment changes.

22.2 Exposition

22.2.1 What to Track

Six categories matter. Parameters: learning rate, max_depth, n_estimators. Metrics: accuracy, F1, RMSE, ideally per epoch or iteration, not just the final value. Artefacts: the model file, feature importance plot, confusion matrix. Code version: the git commit hash at training time. Data version: dataset hash or versioned S3 path. Environment: Python and library versions. Missing any one of these breaks full reproducibility. MLflow’s autolog() captures the first four automatically. Data versioning is handled separately (Chapter 24 covers this).

22.2.2 MLflow Components

MLflow has four integrated pieces. Tracking is the core logging layer. Every run lives inside an experiment (a logical grouping), carrying parameters, metrics, and artefacts that can be sorted, filtered, and plotted side by side in the UI. Projects is a packaging convention, an MLproject file specifying entry point, parameters, and environment, for running ML code reproducibly on any machine. Models is a standard save format. Any model saved this way loads back with mlflow.pyfunc.load_model(), regardless of whether it was originally sklearn, XGBoost, or PyTorch. The Model Registry is a central catalogue with an explicit lifecycle, None → Staging → Production → Archived. It’s the promotion gate between experimentation and deployment, answering “which model is in production right now, and what run produced it?” with a definitive, auditable trail.

22.2.3 Weights & Biases

W&B is MLflow’s main alternative, with a stronger deep-learning focus and a hosted cloud dashboard rather than a self-hosted tracking server. For most enterprise and Solutions Architect contexts, MLflow remains the default. It’s open source. It runs on any infrastructure. It has tight SageMaker integration via a managed tracking server that requires no server management at all.

22.3 Trade-offs and Limits

Tracking doesn’t solve data versioning. MLflow records which data path was used, not whether the data at that path later changed underneath the run. DVC or S3 versioning covers that separately. It adds a small logging overhead per call, which matters for very tight training loops (per-batch logging at millisecond scale needs to be selective about frequency). What’s lost by skipping it entirely is larger: reproducibility of deleted or forgotten runs, organisational memory about what was already tried, and, in regulated industries, the ability to explain which model made a specific decision. That can be a legal requirement, not just good practice.

22.4 Procedures

Procedure 22.1 (Start MLflow Tracking in a Script). When to use: every model training run.

Procedure 22.2 (Log Parameters, Metrics, and Artefacts). When to use: inside a with mlflow.start_run() block.

Procedure 22.3 (Use Autolog for Quick Sweeps). When to use: rapid experimentation where custom logging isn’t needed.

Procedure 22.4 (Compare Experiments Programmatically). When to use: finding the best run after a sweep, without opening the UI.

Procedure 22.5 (Register and Promote a Model). When to use: a run produces a model good enough for production.

Common mistake: leaving autolog() enabled after a sweep finishes. It silently captures every subsequent training call, cluttering the experiment with unintended runs.

22.5 Worked Example

Sweeping four Random Forest configurations (n_estimators in {50, 200}, max_depth in {3, 6}) on the Breast Cancer Wisconsin dataset, each logged as its own MLflow run against a local SQLite-backed tracking store:

Measured F1 across the sweep: n_estimators=50, max_depth=3 → 0.9583; n_estimators=50, max_depth=6 → 0.9655; n_estimators=200, max_depth=3 → 0.9655; n_estimators=200, max_depth=6 → 0.9583. Two configurations tie for the best score (0.9655) despite using very different amounts of compute. 50 trees at depth 6 matches 200 trees at depth 3 exactly on this metric. That’s a genuinely useful thing to discover from a tracked sweep rather than assume, since “more trees” alone doesn’t explain the ranking here.

Querying the tracking store back programmatically, without opening any UI, confirms the same ranking:

This returns the two 0.9655 runs (n_estimators=200/max_depth=3 and n_estimators=50/max_depth=6) tied at the top, followed by the two 0.9583 runs: exactly the four logged results, sorted, queryable as an ordinary DataFrame months after the sweep ran, with every parameter that produced each score still attached. This is the entire point of tracking made concrete. Nothing about “which config won” depends on anyone’s memory of running the sweep.

22.7 How This Connects

This chapter builds on every prior modelling chapter. Tracking is the wrapper around all of them, not a technique specific to one model type. It enables Chapter 24’s MLOps, where the model registry is the literal handoff point between data science and production. It’s often confused with Chapter 25’s monitoring: tracking is training-time observability (what happened while building the model), monitoring is inference-time observability (what’s happening while the model serves live traffic). Both are needed. Neither substitutes for the other.

22.9 Mental Model

An untracked experiment is like writing code without ever committing to Git. It works fine until the moment there’s a need to go back, and by then it’s gone. Experiment tracking is the git commit for ML runs: every run should be a commit. The model registry is the main branch. Only promoted, reviewed models live there. Everything else stays a candidate until someone explicitly says otherwise.
