A model that exists only in a Jupyter notebook is a science project. Its predictions are available only to whoever runs that notebook, on that machine, by hand. For a model to create value it needs to be reachable by other systems: an application, a pipeline, a customer. On demand, at scale, reliably. Deployment moves a model from an experiment environment into a production one. Serving answers prediction requests from that environment usefully. Solutions Architects are often the people who design this layer. Understanding the trade-offs between deployment patterns is one of the most immediately practical skills in this book.

23.1 Motivation

A deployed model is a function that takes inputs and returns outputs, the same thing it did in training, now reachable via a network call, a file system, or a queue. The deployment pattern determines how that function gets called. Real-time inference answers synchronously in milliseconds to seconds. Batch inference runs on a schedule over a large dataset and stores results for later. Streaming inference processes events continuously as they arrive. Async inference queues a request and returns the result separately once ready. Choosing the wrong pattern for a use case is a common, expensive mistake. It’s one an SA who understands the trade-offs can save a customer real money on.

23.2 Exposition

23.2.1 Deployment Patterns

Real-time inference wraps the model in an HTTP endpoint. Applications POST feature values and get predictions back in the response. Latency matters directly. A checkout recommendation needs to answer in under 100ms, or the moment is lost. The endpoint has to stay running 24/7 even during quiet periods, which is expensive for low-traffic models. Batch inference runs a scheduled job over millions of rows at once with no live endpoint at all. It’s appropriate whenever hours-old predictions are acceptable (nightly churn scoring, daily email personalisation). It’s dramatically cheaper, since compute only runs while the job runs. Streaming inference processes events from Kafka or Kinesis one at a time or in micro-batches, combining real-time freshness with batch-like throughput. IoT anomaly detection and clickstream scoring are typical cases. Async inference queues a request, processes it when capacity allows, and lets the caller poll or receive a callback. It’s well suited to long-running inference like document processing or LLM generation over long text. SageMaker’s async inference scales to zero when idle.

23.2.2 Model Serialisation

Before a model can be served, it has to be saved in a form another process can load. For tabular sklearn/XGBoost models staying in Python, joblib is the default. For cross-language serving (Java, C++, Rust, edge devices), ONNX is framework-independent. For neural network weights, safetensors is the modern standard, safe to load from untrusted sources unlike pickle. Whichever format, the full pipeline, preprocessing and model together, needs saving, not the estimator alone. Saving the model without its scaler or encoder forces that logic to be reimplemented by hand at serving time: a classic source of train/serve skew.

23.2.3 Serving Frameworks

FastAPI is the current standard for building ML APIs in Python: async, fast, with automatic OpenAPI docs and pydantic request validation, though the team owns the server and scaling. mlflow models serve spins up a FastAPI server directly from a registered model with zero code, good for internal tools. BentoML adds packaging and containerisation on top, for teams wanting a fuller managed serving layer without hand-writing Kubernetes configs. SageMaker Endpoints are the managed option. A model artefact goes in, and SageMaker handles the server, load balancing, auto-scaling, and monitoring: the recommended default for most AWS production deployments.

23.2.4 Estimating Capacity for Transformer/LLM Inference

Everything above applies to any model type, but transformer/LLM inference has a fairly precise capacity answer, built on the parameter-count formula from Chapter 29 (N≈12⋅nlayers⋅dmodel2N \approx 12 \cdot n_{layers} \cdot d_{model}^2N≈12⋅nlayers​⋅dmodel2​). Generation has two phases with opposite bottlenecks. Prefill (processing the prompt) processes all prompt tokens in parallel in one forward pass. It’s compute-bound, costing roughly 2N2N2N FLOPs per prompt token. Decode (generating each new token) produces tokens one at a time. Each step must read the entire model’s weights from GPU memory: memory-bandwidth-bound, not compute-bound. That’s why autoregressive generation feels slow even on GPUs with enormous FLOPs budgets. A full weight-read is paid for every single token. The time per token at batch size 1 is approximately (2×N×bytes_per_param)/memory_bandwidth(2 \times N \times \text{bytes\_per\_param}) / \text{memory\_bandwidth}(2×N×bytes_per_param)/memory_bandwidth. Batching amortises that same weight-read across more tokens simultaneously, moving decode from memory-bound toward compute-bound as batch size grows. That’s why LLM-serving frameworks (vLLM, TGI, TensorRT-LLM) exist largely to batch efficiently, rather than to speed up any single request.

The KV cache, cached Key/Value vectors for every token already seen, avoids recomputing attention over the whole prompt at each step. It grows linearly with both context length and batch size: kv_cache_bytes≈2×nlayers×dmodel×seq_len×batch_size×bytes_per_param\text{kv\_cache\_bytes} \approx 2 \times n_{layers} \times d_{model} \times \text{seq\_len} \times \text{batch\_size} \times \text{bytes\_per\_param}kv_cache_bytes≈2×nlayers​×dmodel​×seq_len×batch_size×bytes_per_param. Unlike the fixed model weights, the KV cache can dwarf them at long context or high concurrency. It’s usually the KV cache term, not the weights, that caps the maximum batch size or context length a given GPU can actually serve.

23.2.5 Shrinking the Model: Distillation, Quantisation, Pruning

Every number in the capacity formulas above scales with NNN, the parameter count, and with bytes-per-parameter. Three standard techniques attack one or the other directly, instead of accepting the capacity a model ships with.

Quantisation reduces bytes-per-parameter: storing weights in 8-bit or 4-bit integers instead of 16- or 32-bit floats. Since decode is memory-bandwidth-bound, halving bytes-per-parameter roughly halves decode time at batch size 1, on top of halving the memory the weights occupy. Quality loss is usually small at 8-bit and noticeable but often acceptable at 4-bit. Post-training quantisation (no retraining needed) is the cheapest capacity win available for a model that’s already trained.

Pruning removes weights (or whole attention heads, or whole layers) that contribute little to the model’s output, shrinking NNN directly. Unstructured pruning (zeroing individual weights) needs specialised sparse kernels to realise a real speedup. Structured pruning (removing whole heads or layers) loses more accuracy per parameter removed, but runs fast on ordinary hardware, since the resulting model is smaller, not sparse.

Distillation trains an entirely smaller “student” model to mimic a larger “teacher” model’s outputs, rather than editing the teacher directly. The student learns from the teacher’s full output distribution (soft labels), not just the teacher’s final answer. That carries more signal per training example than training the student from scratch on the original labels would. A well-distilled student can retain most of a much larger teacher’s task performance at a fraction of the parameter count. That’s why distilled models are common as the default choice when serving cost matters more than squeezing out the last point of accuracy.

None of the three are mutually exclusive. A distilled student can be quantised and pruned again, stacking capacity savings. The formulas above show why. Parameter count and bytes-per-parameter are two independent multipliers on decode time and memory, so cutting either compounds with cutting the other.

23.2.6 Containers and Reproducibility

A Docker container packages a model, its dependencies, and its runtime into a portable unit that runs identically anywhere. Without containers, “it works on my machine” is the most common deployment failure. Every SageMaker endpoint runs inside a container, either a built-in AWS-provided one or a custom Dockerfile.

23.3 Trade-offs and Limits

Pattern Latency Cost Best use case
Real-time endpoint Milliseconds High (always-on) Interactive apps, fraud checks, chatbots
Batch Transform Hours Low (pay-per-run) Nightly scoring, reports
Async Inference Seconds-minutes Low (scale-to-zero) Long-running inference, LLM/document processing
Streaming Milliseconds-seconds Medium Continuous event scoring

The most common mistake is building a real-time endpoint for a use case that’s actually batch. If predictions are consumed in a daily report, a 24/7 endpoint is pure waste. Batch Transform typically costs 10-100x less for the identical workload.

23.4 Procedures

Procedure 23.1 (Serialise a Model Safely). When to use: immediately after training, before any serving code is written.

Common mistake: saving with pickle.dump and loading in a different Python minor version. Pickle and joblib serialise a reference to the class definition, not a self-contained copy, so a version mismatch can load silently and produce different predictions, or fail outright.

Procedure 23.2 (Build a Minimal FastAPI Inference Endpoint). When to use: a real-time endpoint is needed and there’s no managed serving layer yet.

Common mistake: loading the model inside the predict function instead of at module load time. This re-reads the file from disk on every request, adding tens of milliseconds and hammering the filesystem under load.

Procedure 23.3 (Choose Between Real-Time and Batch). When to use: at design time, before building anything.

Procedure 23.4 (Estimate LLM Serving Capacity). When to use: before picking an instance type for an LLM endpoint. Sizing off “the model file is 14GB, a 24GB GPU is fine” ignores the KV cache and will OOM under real concurrent traffic.

Common mistake: raising batch size to increase throughput without checking the KV cache still fits. This is the most common cause of an endpoint that works fine in testing (batch size 1) and OOMs under real concurrent load, since KV cache memory scales linearly with batch size while weight memory stays fixed.

23.7 How This Connects

This chapter builds on Chapter 22’s experiment tracking. Deployment happens from the model registry, not from an arbitrary notebook state. It enables Chapter 24’s MLOps, where deployment is one automated step in a CI/CD pipeline, and Chapter 25’s monitoring, which can only observe a model that’s actually deployed. It’s often confused with training itself. Training produces the model, serving uses it. The two are entirely separate systems with different uptime requirements and scaling profiles. A training job failing overnight and an inference endpoint going down at 2pm are different emergencies with different on-call implications.

23.9 Mental Model

A deployed model is a microservice. It has a contract (input schema, output schema), an SLA (latency, uptime), and operational requirements (logging, health checks, version management). Treat it like infrastructure, not like a notebook cell that happens to be running somewhere. The same questions asked about any API apply here without exception: what happens when it goes down, how does it scale, who owns it.
