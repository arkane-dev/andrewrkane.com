A model gets deployed and works. Six weeks later, someone retrains it with a small data fix, tests it manually on their laptop, and pushes the new version straight to production. It quietly performs worse than the old one, because nobody wrote a test that would have caught the regression. A month after that, a different engineer can’t figure out which data, code, and hyperparameters actually produced the model currently serving customers. None of this is a deployment problem. Chapter 23 solved how to serve a model. This is a process problem. How does every change to a model get tested, reviewed, versioned, and made reversible before it reaches production, automatically, every time, without depending on someone remembering to be careful?

24.1 Motivation

Regular CI/CD asks one question at each gate: does the code still work? ML CI/CD has to ask three. Does the code still work? Is the data still valid: no schema drift, no unexpected nulls, sane value ranges? Is the model still good enough, measured against a held-out set, and critically, compared against the model currently in production, not just an absolute bar? A pipeline checking only code correctness will happily ship a model trained on corrupted data, or one that’s technically deployable but meaningfully worse than what’s already live. MLOps pipelines gate on all three, because ML systems have three things that change: code, data, and model parameters. Traditional software only has one.

24.2 Exposition

24.2.1 The Model Registry as the Central Object

The model registry (introduced in Chapter 22) is what MLOps is built around. Every trained version is registered with the metrics it achieved, the code commit and data version that produced it, and a stage: Staging → Production → Archived. The registry turns “which model is live?” from a question someone has to remember into a query. It’s the gate itself. Nothing reaches Production without being registered, and in a well-built pipeline, nothing is promoted without passing automated checks first.

24.2.2 CI for ML: What Gets Tested

Data validation tests assert incoming data matches expectations: required columns present, dtypes correct, value ranges sane, no unexpected null-rate spike. They catch upstream pipeline breakages before they silently degrade a retrained model. Model performance regression tests evaluate a candidate on a fixed, versioned test set and assert its metric clears both a fixed minimum and the metric of the model currently in production. The second comparison is what prevents silent regressions, since a model can clear an absolute threshold and still be worse than what it’s replacing. Integration tests for the serving pipeline check the code path itself, separate from model quality. Does the serialized model load? Does the API return the expected schema? Does it survive a malformed request without crashing? Training-serving skew is a specific, common bug where feature engineering differs even slightly between the training and inference code paths. The model looks great in evaluation and performs badly in production, because live data was transformed differently than training data was. The fix is a single shared, versioned feature-engineering pipeline (Chapter 14’s sklearn.Pipeline pattern) used by both training and serving, never two separate reimplementations.

24.2.3 CD for ML: Deployment Strategies

Once a model passes CI, CD decides how it reaches production traffic. Blue-green deploys the new model fully alongside the old one and switches all traffic at once: fast rollback, but no gradual signal before the switch. Canary sends a small percentage of live traffic to the new model, ramping up gradually if metrics hold: slower, but catches problems before they affect everyone. Shadow (dark launch) sends the new model a copy of live traffic and logs its predictions without ever serving them to users: zero production risk, but validates prediction quality only, not real-world business impact. Rolling updates instances one at a time, a middle ground common in Kubernetes deployments. The right strategy scales with how expensive a bad prediction is. A recommendation engine can tolerate canary. A fraud or medical-triage model often needs shadow validation first.

24.2.4 The Training Pipeline as Versioned Code

A notebook is fine for developing a model. It’s a bad place to run production training, since notebooks execute cells out of order, hide state, and aren’t easily invoked by a scheduler or CI system. MLOps moves training logic out of the notebook into versioned, tested code: a CLI script with load_data(), build_pipeline(), train(), evaluate(), main(). It’s runnable identically by a human, a CI job, or a scheduler, unit-testable, and reviewable in a pull request like any other code change.

24.3 Trade-offs and Limits

Approach Effort Catches Best for
No pipeline, manual retrain/deploy None Nothing automatically Prototypes, single-person projects
CI tests only (code + data) Low-medium Code bugs, data schema breaks Early-stage teams
CI + model performance gate Medium The above + silent quality regressions Most production teams
Full CI/CD + canary/shadow deploy High The above + real-world impact before full rollout High-stakes or high-traffic models

Building the full pipeline has real cost: infrastructure, maintenance, slower time-to-ship for small changes. The right investment level scales with how expensive a bad model in production actually is, not with team size alone.

24.4 Procedures

Procedure 24.1 (Set Up a Real MLflow Model Registry). When to use: moving past a local/prototype registry to a real shared tracking server.

Common mistake: forgetting archive_existing_versions=True. Without it, two versions can end up simultaneously marked Production, defeating the registry’s core purpose of having exactly one answer to “what’s live?”

Procedure 24.2 (Write a Data Validation Test). When to use: the first stage of any training pipeline, before a single row is used to fit anything.

Procedure 24.3 (Write a Model Performance Gate). When to use: after training a candidate, before it’s allowed to register as Production.

Common mistake: gating only on an absolute threshold. A model can clear F1 > 0.5 and still be considerably worse than what’s already serving traffic. Always compare against the current production metric too.

24.5 Worked Example

Register the Breast Cancer Wisconsin dataset’s strongest simple model, a logistic regression pipeline, as the “production” baseline. Then run three increasingly sophisticated candidates through Procedure 24.3’s gate:

Measured: the production logistic regression reaches F1 = 0.9722, an unusually strong baseline on this dataset. All three candidates score respectably on their own terms (weak RF 0.9510, tuned RF 0.9583, Gradient Boosting 0.9660). But every one of them fails Procedure 24.3’s gate, because every one scores below the incumbent’s 0.9722. Each individually looks like a perfectly good model. F1 above 0.95 would pass most absolute thresholds without a second thought. The gate rejects all three anyway, exactly as designed. This is the “silent regression” failure mode from the Exposition made concrete. Without the production-comparison check, any one of these three could have shipped as an “improvement” that was actually a downgrade, since an absolute-threshold-only gate (Procedure 24.3 without its second condition) would have passed the Gradient Boosting candidate outright at F1=0.9660.

Getting a model that actually clears this particular bar would need genuinely better tuning: Chapter 17’s hyperparameter search, or Chapter 12’s ensemble stacking, applied specifically against this dataset’s strong logistic-regression baseline. Not trying a fancier-sounding algorithm and assuming it wins. The gate doesn’t care which algorithm is more sophisticated. It cares whether the number went up.

24.9 Mental Model

Think of the model registry as main in Git, and every candidate model as a pull request. CI is the automated checks that must pass before merge: here, data validation and performance gates instead of tests and linting. CD is what happens after merge: deployment. The discipline is identical to modern software engineering. Only the specific checks differ, because a model can be syntactically perfect, deploy cleanly, and still be a worse model. That’s exactly what this chapter’s Worked Example demonstrated, with three candidates that all “worked” and all still failed the gate.
