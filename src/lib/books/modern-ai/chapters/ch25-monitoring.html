A model that has just been deployed is, in one sense, already out of date. The moment training finishes, the world keeps moving and the model does not. Customers change, seasons change, competitors launch new products, upstream pipelines get “improved,” and fraud patterns adapt specifically because a model is now watching for them. None of this shows up as a bug. The code is correct, the infrastructure is healthy, the model is doing exactly what it was trained to do. The problem is that the world it was trained on no longer exists. Monitoring is the discipline of noticing that gap before it costs the business money. This chapter builds the statistical tools and decision rules that do the noticing.

25.1 Motivation

A model learns a fixed function: a mapping from inputs to outputs, frozen at the moment training finished. Production traffic is not frozen. Every change that happens after deployment falls into one of three buckets. The distribution of inputs shifts while the true relationship between inputs and outputs stays the same (data drift). The relationship itself changes even though the inputs look normal (concept drift). Or the distribution of the model’s own outputs shifts, which can be a downstream symptom of either of the above, or of a silently broken input pipeline (label/prediction drift). These three failure modes require different detection strategies, arrive on different timescales, and demand different responses. Conflating them is one of the most common mistakes in production ML monitoring.

25.2 Exposition

25.2.1 Data Drift (Covariate Shift)

Formally, data drift is when P(X)P(X)P(X) changes but P(y∣X)P(y \mid X)P(y∣X) stays fixed. The features arriving in production no longer look like the features the model trained on, but the underlying relationship between those features and the label hasn’t moved. A loan approval model trained mostly on applicants aged 25-45 starts seeing a wave of applicants aged 60+ after a new partnership launches. The relationship between income, credit history, and default risk hasn’t changed, but the model is now extrapolating into a region of feature space it saw far less of during training, where its predictions are less reliable. Data drift is a leading indicator. It often shows up before performance visibly degrades, which is exactly what makes it useful. But it is not a guarantee of harm. If the model generalises well into the new region, performance might not move at all: a distinction this chapter’s Worked Example makes concrete with real numbers.

25.2.2 Concept Drift

Formally, concept drift is when P(y∣X)P(y \mid X)P(y∣X) changes: the same input now maps to a different, real output. This is the dangerous failure mode, because the inputs can look completely normal while the model is silently wrong. A fraud model trained before a new fraud technique emerges will see the same transaction pattern that used to be safe now behaving as a common attack vector. A demand forecasting model trained before a competitor cuts prices will see the same seasonal pattern stop predicting the same sales volume. Concept drift cannot be detected by watching the inputs alone. There is nothing to see in XXX. It requires either ground-truth labels, usually lagged, or a strong proxy for correctness.

25.2.3 Label / Prediction Drift

This is drift in the distribution of what the model outputs. For example, the fraction of transactions flagged as fraud suddenly doubles. It is a symptom, not a root cause. It can be produced by data drift, by concept drift, or, very commonly in practice, by a broken upstream feature pipeline silently sending null or default values. Monitoring prediction distributions is cheap, requires no labels at all, and often catches pipeline bugs faster than it catches genuine drift.

25.2.4 Detecting Drift Without Labels

Because inputs are always available immediately, drift detection tests compare a reference distribution, usually the training set, or a recent known-good production window, against a current window of live traffic.

Population Stability Index (PSI) buckets both distributions using the same bin edges, usually deciles of the reference distribution, then measures how much probability mass has shifted between buckets:

PSI=∑i(actual_pcti−expected_pcti)×ln⁡ ⁣(actual_pctiexpected_pcti)\text{PSI} = \sum_i (\text{actual\_pct}_i - \text{expected\_pct}_i) \times \ln\!\left(\frac{\text{actual\_pct}_i}{\text{expected\_pct}_i}\right)PSI=i∑​(actual_pcti​−expected_pcti​)×ln(expected_pcti​actual_pcti​​)

PSI is popular in industry, especially in credit risk where it originated, because it is simple, interpretable, and has widely agreed thresholds. Below 0.10 is no significant shift. 0.10-0.25 is a moderate shift worth logging. Above 0.25 is a significant shift worth investigating. Its main weakness is sensitivity to bucket choice. It is also less statistically rigorous than a proper hypothesis test. It has a deep connection to the KL divergence covered earlier in the course. PSI is a symmetrised, discretised cousin of KL divergence, both measuring “how far is this distribution from that one” with the same log-ratio-of-probabilities shape.

The Kolmogorov-Smirnov (KS) test is a nonparametric statistical test that measures the maximum distance between two empirical cumulative distribution functions, with a p-value indicating how likely that distance is under the null hypothesis that both samples come from the same distribution:

DKS=max⁡x∣Fexpected(x)−Factual(x)∣D_{KS} = \max_x \left| F_{\text{expected}}(x) - F_{\text{actual}}(x) \right|DKS​=xmax​∣Fexpected​(x)−Factual​(x)∣

The KS test is more statistically principled than PSI. But the p-value shrinks automatically as window size grows. With enough production traffic, even trivially small, harmless shifts become “statistically significant.” In practice, teams often report the KS statistic itself, a plain effect-size number bounded between 0 and 1, rather than relying on the p-value once sample sizes get large.

The chi-squared test is the categorical-feature equivalent, comparing observed versus expected category frequencies between reference and current windows for features like country, device_type, or plan_tier. It carries the same interpretation caveat as KS at large sample sizes.

25.2.5 Performance Monitoring (When You Have Labels)

When ground-truth labels do become available, even weeks or months later, direct performance monitoring is the gold standard, because it measures the thing that actually matters rather than a proxy. The same evaluation metrics used at training time, accuracy, AUC, precision/recall, calibration, get tracked over a rolling window and compared against the model’s baseline performance at launch. The complication is label lag. A loan default model might not know whether a loan defaulted for 12-24 months. A fraud model’s confirmed chargeback might take 60-90 days. Performance monitoring is therefore inherently reactive. It tells you a problem existed some time ago, not that one exists right now. This is why input drift monitoring, fast but indirect, and performance monitoring, slow but direct, are used together rather than as substitutes for each other.

25.2.6 Retraining Trigger Strategies

Once drift can be detected and performance decay measured, a policy is needed for when to act. Scheduled retraining retrains on a fixed cadence regardless of detected drift. It’s simple and predictable in cost, but it wastes compute when nothing has changed and reacts too slowly when something has. Drift-triggered retraining fires automatically when a drift metric crosses a threshold. It’s fast to react, but it risks retraining on noise if thresholds are too sensitive, and cannot catch concept drift on its own, since concept drift produces no input-side signal at all. Performance-triggered retraining fires when a monitored performance metric drops below a threshold. It’s directly tied to business impact, but bottlenecked by label lag. The pattern most teams converge on in practice is hybrid. Drift signals trigger an investigation, not an automatic retrain. Confirmed performance drops, or a strong business-metric proxy, trigger the actual retrain.

25.3 Trade-offs and Limits

Approach Speed Directness Risk
Input drift (PSI/KS) Fast (immediate) Indirect: proxy for harm Misses concept drift entirely; can false-alarm on harmless shifts
Performance monitoring Slow (label-lag bound) Direct: measures actual harm Confirms the problem only after it already happened
Prediction distribution monitoring Fast (immediate) Indirect: symptom, not cause Can’t distinguish drift from a broken pipeline without further digging
Scheduled retraining N/A N/A Wastes compute on stable periods; too slow for sudden shifts

The practical answer most teams converge on is to monitor everything cheaply and continuously, inputs, predictions, but gate expensive actions, retraining and paging on-call, behind confirmed performance signals wherever label lag allows it. Data drift and concept drift are frequently used interchangeably in casual conversation. But they require different detection strategies (input statistics versus labelled performance) and imply different fixes. Data drift might just need a wider training distribution. Concept drift means the old labels are no longer even true, and no amount of re-sampling the same relationship will fix it.

25.4 Procedures

Procedure 25.1 (Compute PSI for a Numeric Feature). When to use: comparing a live production window against a reference distribution, usually the training set, to check for data drift.

Common mistake: recomputing bucket edges from actual instead of always using expected’s edges. If both sides define their own bins, the two sides are no longer comparing the same buckets, and the PSI value becomes meaningless.

Procedure 25.2 (Run a KS Test for Drift). When to use: a statistically principled alternative or complement to PSI for a continuous feature.

Watch out for large sample sizes: with tens of thousands of production rows or more, the p-value shrinks toward zero even for tiny, harmless distribution shifts. Track the statistic itself as the primary signal once windows get large, and treat the p-value as informational rather than as the alert trigger.

Procedure 25.3 (Monitor Categorical Feature Drift). When to use: features like country, device_type, or plan_tier, anything that isn’t numeric.

Common mistake: a brand-new category appearing in production, e.g. a new plan_tier launched last week, will always register as significant drift. That is often a real and useful signal that the feature encoding pipeline needs to handle it, not a false alarm to suppress.

Procedure 25.4 (Track Performance With Label Lag). When to use: ground-truth labels exist, but arrive days, weeks, or months after the prediction was made.

Two signs performance monitoring itself needs attention: a metric drops only in the most recent window (check n before reacting, it may just be a small-sample artifact), or metrics look fine but the volume of labelled feedback has dropped sharply, meaning the label pipeline may be broken and silently blinding the monitor.

Procedure 25.5 (Set Layered Alert Thresholds and a Retraining Trigger). When to use: turning raw drift and performance numbers into actionable decisions without causing alert fatigue.

Rule of thumb: require an alert to persist across two consecutive windows before paging. This alone eliminates most single-window noise pages. Also alert on the trend (is PSI climbing steadily over the last several windows) in addition to the instantaneous value, to catch slow drift that never crosses a static threshold sharply. Before acting on any alert, triage in order. Did feature volume or nullness change abruptly? That’s a pipeline bug, not real drift: fix upstream, don’t retrain. Did the alert coincide with a known business event? That’s likely real drift, worth retraining. Is only one feature drifting while others are stable? Check that feature’s upstream source specifically. Has accuracy actually dropped, or only the input distribution? Input drift without a performance drop often needs no action at all.

25.5 Worked Example

The tutorial trains a baseline logistic regression on three numeric features (x1, x2, x3) simulating a binary classifier, credit approval, churn, or fraud, then simulates six weeks of production traffic against it. Periods 0-2 are quiet weeks matching the training distribution. Periods 3-4 introduce data drift. The mean of x1 and x2 shifts by 0.8 and then 1.4 standard deviations, while x3 never moves (a stable control feature) and the true coefficients relating features to label stay fixed. Period 5 introduces concept drift. The input distribution is untouched, but the sign of the x1 and x2 coefficients flips. The same inputs now genuinely map to a different label.

The baseline model trained on 3,000 rows reaches accuracy 0.788 and AUC 0.862 on its own training data. Evaluated directly against each production period:

Period What happens Accuracy AUC
0 Launch week, matches training 0.781 0.857
1 Quiet week 0.762 0.854
2 Quiet week 0.771 0.862
3 Data drift begins (shift = 0.8) 0.776 0.869
4 Data drift continues (shift = 1.4) 0.777 0.856
5 Concept drift (coefficients flip) 0.254 0.170

Periods 3-4 barely move accuracy or AUC at all, despite a substantial shift in the input distribution. The model is extrapolating into a less-familiar region, but the relationship it learned still holds there. Period 5 collapses to 0.254 accuracy and 0.170 AUC, worse than a coin flip, because the model is now confidently applying a relationship that has been inverted.

Running Listing 25.1 and Listing 25.2 with period 0 as the reference distribution against all six periods produces:

Period x1 PSI x2 PSI x3 PSI (stable)
0 0.000 0.000 0.000
1 0.021 0.015 0.013

3 0.736 0.640 0.018

Periods 3-4 light up clearly on x1/x2 PSI: 0.736 and 0.640 in period 3, climbing to 1.878 and 1.935 in period 4, both far past the 0.25 “significant shift” threshold, while x3 stays flat throughout. Period 5’s PSI values (0.016, 0.021) are indistinguishable from the quiet periods 1-2, because the input distribution genuinely never moved. This is the core empirical result of this chapter: input drift detection is structurally blind to concept drift. A monitoring system watching only PSI would flag periods 3-4 loudly and period 5 not at all: exactly backwards from where the actual harm occurred.

Simulating a two-period label lag (Listing 25.4’s pattern) and applying Procedure 25.5’s decision rule to each period’s max PSI and confirmed accuracy drop:

Period Max PSI Accuracy Decision
0 0.000 0.781 OK
1 0.021 0.762 OK
2 0.035 0.771 OK
3 0.736 0.776 INVESTIGATE: input drift, performance not yet confirmed
4 1.934 0.778 INVESTIGATE: input drift, performance not yet confirmed
5 0.021 0.254 RETRAIN: confirmed performance drop

Periods 3-4 land on INVESTIGATE rather than RETRAIN. PSI is elevated, but accuracy hasn’t confirmed real harm, and in this simulation it never will, because data drift alone didn’t break the relationship the model learned. An automatic retrain triggered by PSI alone would have burned compute and introduced retraining risk for no benefit. Period 5 escalates to RETRAIN once its lagged accuracy comes in, even though its PSI never crossed any threshold at all. The gap between the drift-score alarm (or lack of one) and the confirmed performance drop is exactly the two-period label lag built into the simulation. It is the central operational fact this chapter is about. What can be acted on today (input drift) is not the same as what confirms whether that action was needed (lagged performance).

25.10 Mental Model

A deployed model is a weather forecaster trained on last year’s climate and then locked in a room with no windows. Input drift monitoring is checking the barometric pressure readings coming into the room. If they look unusual compared to what the forecaster trained on, that’s a warning sign, even before knowing whether the forecasts themselves are wrong. Performance monitoring is checking the forecasts against what the weather actually did: the only way to know for certain, but often unavailable until the day is already over. Neither replaces the other. A good monitoring system runs both, all the time.
