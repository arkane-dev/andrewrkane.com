Over the previous chapters, pieces of an ML platform got built by hand: a training loop, an experiment tracker (Chapter 22), a deployment layer (Chapter 23), a monitoring loop (Chapter 25). Each piece works individually. Stitching them together, securing them, scaling them, and keeping them running at 2am when a fraud model needs to answer in 80ms is a different job entirely. It’s infrastructure engineering, and the same undifferentiated heavy lifting every company doing ML eventually has to solve. A managed ML platform exists to take that lifting off the table. This chapter doesn’t teach a new ML concept. It teaches how everything already learned maps onto AWS’s managed platform, and how to advise a customer on when that trade is actually worth it.

26.1 Motivation

Every capability built from Chapter 16 onward has both an open-source implementation (what was actually built in this book) and a managed AWS equivalent. Local Jupyter maps to SageMaker Studio. A training script on a laptop maps to SageMaker Training Jobs. Self-hosted MLflow maps to SageMaker’s managed MLflow and Model Registry. FastAPI-plus-Docker maps to SageMaker Endpoints and Batch Transform. Hand-rolled drift checks map to SageMaker Model Monitor. This chapter fills in that right-hand column: what each managed service actually is, what it costs in money and lock-in, and when an SA should recommend it over the open-source path.

26.2 Exposition

26.2.1 S3: The Foundation

Everything in the AWS ML stack sits on S3. Training data, model artefacts, pipeline outputs, feature store offline data: all of it lives in S3, referenced by URI, and SageMaker reads and writes there directly rather than moving data into some proprietary store. This matters directly for the lock-in conversation. Data stays in a standard, portable format even if the compute layer later moves off SageMaker.

26.2.2 SageMaker: The ML Compute and Orchestration Layer

Studio is a hosted JupyterLab-like IDE, replacing “a data scientist’s laptop” with a governed, access-controlled, auto-provisioned environment. It’s Chapter 6’s Python ecosystem, hosted, nothing conceptually new. Training Jobs replace python train.py run locally. A training script gets packaged, pointed at S3 data, given an instance type, and SageMaker provisions the machine, runs the script, streams logs, and tears the machine down when finished. It’s billed per second of actual training time, not for an idle instance. Processing Jobs apply the same managed, scaled-out pattern to data cleaning and feature engineering. Pipelines is SageMaker’s answer to Chapter 24’s CI/CD-for-ML problem: a versioned, re-runnable DAG of process-train-evaluate-conditionally-register steps, narrower and more opinionated than a general orchestrator like Airflow specifically because it only orchestrates ML steps. Model Registry is the same concept as Chapter 22’s MLflow registry, natively wired into Pipelines and Endpoints so approving a model version can directly trigger deployment. Endpoints and Batch Transform are Chapter 23’s real-time and batch inference patterns, managed. A container and model artefact go in, and SageMaker supplies the always-on HTTP service or the scheduled batch job. Feature Store solves training/serving skew directly. The same feature computation logic feeds both a low-latency online store for real-time inference and an S3-backed offline store for training, so train-time and serve-time features can never quietly diverge.

26.2.3 Bedrock: Managed Foundation Models

Bedrock is a different kind of service. It’s not about training and deploying your own models, but calling someone else’s pretrained foundation models (Claude, Titan, Llama, and others) through one unified API, with no infrastructure to manage and no weights to host. It’s the managed alternative to hosting your own transformer, in the same shape as SageMaker Endpoints being the managed alternative to a hand-hosted FastAPI service. The trade-off is identical too: control over model internals traded for zero infrastructure and a per-token bill instead of a GPU bill.

26.2.4 Advising a Customer: The Actual SA Judgment Call

This is the real skill. “Should we use SageMaker or build on open source?” has an honest answer of “it depends.” An SA earns their keep making that concrete across four axes. Team size and platform maturity: a five-person DS team with no MLOps engineer benefits enormously from a managed surface, while a fifty-person platform team with existing Kubernetes expertise may already have better tooling. Multi-cloud or portability requirements: a hard cloud-agnostic requirement rules SageMaker out entirely, since its Pipelines, Registry, and Endpoints don’t run anywhere but AWS. Cost model: per-second managed billing is often cheaper than a team’s fully-loaded cost of running equivalent infrastructure at low-to-variable volume, but self-managed clusters can win at very high, steady-state volume. Existing AWS footprint: a customer already deep in AWS’s IAM/VPC/S3 ecosystem gets much faster time-to-value than one starting integration from zero on another cloud. There is rarely a universally correct answer. Only a correct answer for this customer’s specific constraints.

26.3 Trade-offs and Limits

Dimension AWS-managed Open-source, self-hosted
Time to first production model Fast: infra pre-built Slower: build and secure the platform first
Operational burden Low: AWS patches/scales/monitors High: the team owns uptime, security, upgrades
Cost at low/variable volume Often cheaper (pay-per-use) Often more expensive (idle infra, dedicated staff)
Cost at very high, steady volume Can be more expensive Can be cheaper at scale
Portability Locked to AWS Portable to any cloud or on-prem
Customisation depth Bounded by what’s exposed Unlimited: full control of every layer

26.4 Procedures

Procedure 26.1 (Set Up a Least-Privilege IAM Role for SageMaker). When to use: before running anything on SageMaker.

Common mistake: attaching AmazonSageMakerFullAccess to every role for convenience. It grants far more than a training job needs. Fine for a personal sandbox, not fine for a shared or production account.

Procedure 26.2 (Launch a SageMaker Training Job in Script Mode). When to use: running an existing training script on managed, right-sized compute instead of a laptop.

Procedure 26.3 (Deploy and Invoke a Real-Time Endpoint). When to use: a use case needing millisecond-scale responses.

Common mistake: leaving a real-time endpoint running after a demo. Unlike Training Jobs (billed per second of actual compute), endpoints bill continuously whether called or not.

Procedure 26.4 (Call a Foundation Model via Bedrock). When to use: a managed foundation model call is needed rather than self-hosting.

Common mistake: forgetting Bedrock model access must be explicitly enabled per-model in the console before the first call. An AccessDeniedException on an otherwise-correct IAM policy usually means the model itself isn’t enabled for the account/region yet.

26.5 Worked Example

Applying this chapter’s four-axis advising framework to two contrasting hypothetical customers makes the “it depends” answer concrete rather than evasive.

Customer A: a 6-person data science team at a Series B startup, no dedicated MLOps engineer, already running its product on AWS (RDS, S3, existing IAM setup), no regulatory requirement for multi-cloud. Scoring the four axes: team size/maturity strongly favours managed, since every hour not spent operating Airflow is an hour spent on models, and there’s no one to operate it. Portability requirements are absent, removing the strongest argument for open-source. Cost model favours managed at this team’s low, variable training volume. Existing AWS footprint means most of the integration work is already done. All four axes point the same direction. SageMaker is close to an unambiguous recommendation here.

Customer B: a 60-person ML platform team at a large financial institution, existing Kubernetes expertise, a regulatory requirement to remain multi-cloud-capable for disaster-recovery purposes, and steady-state training volume large enough that dedicated GPU clusters are already partially amortised. Scoring the same four axes: team size/maturity favours self-hosting, since the team likely already has better tooling than a generic managed surface. The multi-cloud requirement rules SageMaker out structurally. Pipelines, Registry, and Endpoints don’t run anywhere but AWS, so this axis alone can decide the question regardless of the other three. Cost model at this volume plausibly favours self-managed clusters. Existing footprint is a wash, since the team is deliberately not AWS-exclusive. Here the axes don’t just lean the other way. One of them (portability) is a hard constraint that overrides the others entirely. The right answer isn’t “weigh four factors.” It’s “check whether any single factor is a hard constraint before weighing the rest.”

This is the actual shape of the SA judgment call. Not a scorecard averaged across four dimensions, but a check for hard constraints first, then a genuine trade-off analysis for whatever’s left.

A customer can run entirely on AWS (EC2, S3, RDS) without touching any SageMaker service at all. SageMaker is AWS’s opinionated ML platform, not a synonym for doing ML on AWS.

26.9 Mental Model

Everything from Chapter 16 onward is a recipe learned from scratch: every ingredient, every step, understood directly. SageMaker is a well-equipped commercial kitchen. Same recipe, but someone else bought, installed, and maintains the ovens. The recipe still has to be known, and it is, by this point. SageMaker just removes the burden of running the kitchen. Whether renting that kitchen is worth it depends entirely on how often the cooking happens and how much not doing the dishes is actually worth.
