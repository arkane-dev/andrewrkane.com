Once a transformer is trained (Chapter 29), the question a Solutions Architect faces daily isn’t “how do I train a model” but “how do I get this frozen model to do a specific task, reliably, without retraining it.” Fine-tuning (Chapter 34) is one answer, but it costs data, compute, and iteration time. Prompting is the other: steering a frozen model’s behaviour purely through the text fed into it, with no weight updates, at the cost of a single API call. This chapter turns prompting from trial-and-error guesswork into an engineering discipline: zero-shot and few-shot framing, chain-of-thought reasoning, and two different strengths of guarantee for structured output.

30.1 Motivation

A large language model is, mechanically, a function that maps a sequence of tokens to a probability distribution over the next token. Generation is sampling from that distribution, appending the result, and repeating. A prompt is nothing more than the input sequence that distribution is conditioned on. Every token in it can, via self-attention, influence every token the model is about to generate. There is no separate “instruction-following module” bolted onto the transformer. Instruction-following is a learned behaviour, trained in during pretraining and alignment, so that certain textual patterns reliably steer generation in predictable directions. Prompt engineering, then, is not programming the model in the traditional sense. It’s constructing a context that makes the correct completion the most probable next tokens, given everything the model learned during training. Getting this right is the cheapest lever a Solutions Architect has for improving an LLM application, and it should almost always be pulled before fine-tuning enters the conversation.

30.2 Exposition

30.2.1 In-Context Learning: Zero-Shot vs. Few-Shot

Zero-shot prompting gives the model only a natural-language instruction, “classify this message as billing, technical, or account,” and relies entirely on the model’s prior knowledge of what “classify” and the category names mean. Few-shot prompting adds worked examples directly in the prompt before the real input. This is in-context learning. The model conditions its next-token predictions on a handful of concrete input→output demonstrations sitting in its context window, not just on an instruction. The mechanism isn’t fully understood, but the leading account is that pretraining exposes models to enough structurally similar patterns, worked examples, analogies, templates, that the model develops a general-purpose “pattern completion” capability, and few-shot examples invoke it.

Few-shot examples aren’t free. They cost context length (latency and money), and they anchor the model’s behaviour, sometimes too strongly. A model can over-fit to superficial patterns in the examples, such as always predicting whichever category the majority of the examples used. Good few-shot sets are class-balanced, include at least one genuinely ambiguous case so the model sees how ties should be broken, and place the strongest, clearest example last, closest to the real input. Recency has a measurable effect on which example dominates.

30.2.2 Chain-of-Thought: Buying the Model Time to Think

Every token a decoder-only model generates is produced by the same fixed amount of computation: one forward pass through a fixed number of layers. If a problem genuinely requires multiple reasoning steps, asking for the final answer directly forces the model to do all of that reasoning silently, compressed into the hidden state that produces a single output token. That’s fragile. Chain-of-thought (CoT) prompting asks the model to write out its reasoning before committing to a final answer. This isn’t just a presentation choice. It materially increases the computation available to solve the problem, because each generated reasoning token becomes part of the context for the next one. The model can “see” its own intermediate result when generating the next step, rather than holding everything in an implicit internal state. This is why CoT helps disproportionately on multi-step arithmetic, logic, and planning tasks, and helps little on tasks that were already a single lookup or classification. Reserving it for genuinely multi-step problems avoids paying for output tokens with no accuracy benefit.

A stronger variant, self-consistency, samples several independent CoT reasoning paths for the same problem and takes a majority vote over the final answers. It costs N×N\timesN× the tokens of a single CoT call but measurably improves reliability on harder problems, since it’s less likely that every one of NNN independent reasoning paths makes the same mistake.

30.2.3 Structured Output: Constraining a Fundamentally Unstructured Process

Text generation is, by default, unstructured. The model can emit any token sequence. Production systems need to parse the output programmatically, which means the output has to reliably match a schema. Two families of technique exist, differing in the strength of guarantee they offer:

  • Schema-in-prompt. Describe the desired JSON shape in natural language, ask the model to comply, and validate plus retry on failure. This works because instruction-following, including “comply with this output format,” is itself a learned behaviour, but it is probabilistic compliance, not a guarantee. Models occasionally wrap JSON in markdown fences, add a trailing sentence, or drop a required key despite explicit instructions.
  • Constrained decoding / native tool calling. Rather than hoping the model complies, the serving system restricts which tokens are even eligible to be sampled at each generation step, so the output is provably valid against a schema. Or, in the tool-calling case, the API packages a structured “tool call” object directly, validated server-side. This moves the guarantee from the model’s behaviour to the serving infrastructure, which is why production systems that need structured output almost always prefer tool calling over schema-in-prompt whenever the provider supports it.

30.2.4 Prompt Brittleness and Prompt Injection

Because prompts work by shifting a learned probability distribution rather than executing deterministic logic, small changes in wording, example order, or even whitespace can measurably change outputs. This isn’t a bug to be embarrassed about. It’s the direct consequence of prompting being a soft, statistical steering mechanism rather than a programming language. The engineering response mirrors how any other probabilistic system is managed. Version prompts as named constants (never inline strings scattered through a codebase). Test them against a held-out labelled set before shipping a change (Chapter 32 formalises this). Prefer techniques like tool calling that constrain the output space wherever the requirement allows it.

A related and higher-stakes concern is prompt injection: untrusted input, a user message, or a retrieved document in a RAG pipeline (Chapter 31), that contains text designed to override or hijack the model’s instructions (“ignore previous instructions and…”). Treat this the same way any other untrusted-input boundary is treated in software engineering. Never treat user-supplied text as trustworthy instructions. Keep system instructions in a dedicated system parameter separate from user content where the API supports it. For high-stakes actions (sending money, deleting data, calling other tools), never let model output alone trigger the action. Require a validation step or human confirmation outside the model’s control.

30.3 Trade-offs and Limits

Few-shot vs. zero-shot: few-shot usually improves accuracy and consistency, at the cost of more input tokens and the risk of over-anchoring to the examples’ incidental patterns. Start zero-shot on any new task. Add few-shot only once zero-shot proves inconsistent or the output format needs to match a very specific convention.

Chain-of-thought vs. direct answer: CoT improves accuracy on genuinely multi-step tasks, at the cost of more output tokens and slower responses. Using it on trivial tasks is pure overhead with no accuracy benefit, and can occasionally hurt by giving the model room to talk itself into an overcomplicated wrong answer.

Schema-in-prompt vs. tool calling: schema-in-prompt works with any model and is easy to prototype, but compliance is probabilistic. Always validate and handle failure. Tool calling gives a much stronger guarantee but requires provider support and a bit more setup, defining the schema as a first-class object rather than prose.

Prompting vs. fine-tuning: prompting steers a frozen model at inference time. Cheap, instant, but limited by context length and the model’s existing capabilities. Fine-tuning (Chapter 34) changes the model’s weights and can teach genuinely new behaviours, but costs data, compute, and iteration time. Most production systems reach the prompting ceiling first and only fine-tune once it’s clearly been hit.

30.4 Procedures

Procedure 30.1 (Write a Zero-Shot Prompt). When to use: the first attempt at any new task, or when no representative examples exist yet.

A zero-shot prompt works well when it has an explicit task verb (“classify”, “extract”, “summarise”), enumerated output options (preventing free-form drift), an explicit output-format constraint, and the task framing placed before the input, with the input last. Common mistake: burying the actual instruction in the middle of a long prompt, or after the input data. Instruction-following degrades when the instruction is far from where generation begins.

Procedure 30.2 (Add Few-Shot Examples). When to use: zero-shot is inconsistent, ambiguous, or the output format needs to match a specific convention.

Start with 3-5 examples; more cost context length with diminishing returns past roughly 8-10 for most classification-style tasks. Common mistake: using examples that are all “easy” cases, leaving the model no signal for the hard cases it will actually see in production.

Procedure 30.3 (Elicit Chain-of-Thought Reasoning). When to use: multi-step arithmetic, logic puzzles, planning tasks, or anything where the answer depends on an intermediate computed value.

Common mistake: asking for chain-of-thought on tasks that don’t need it: single-step lookups, simple classification. It adds latency and cost with no accuracy benefit.

Procedure 30.4 (Force Structured Output via Schema-in-Prompt, with Validation). When to use: downstream code needs to parse the model’s output programmatically and native tool calling isn’t available.

Common mistake: not validating at all: treating “the model usually returns valid JSON” as “the model always returns valid JSON.” Malformed output will happen. Always wrap parsing in a try/except with a defined fallback or retry.

Procedure 30.5 (Use Native Tool Calling for a Stronger Guarantee). When to use: the provider supports tool/function calling. Prefer this over Procedure 30.4 whenever it’s available.

Procedure 30.6 (Version and A/B Test a Prompt Before Shipping). When to use: before shipping any prompt change to production. Treat prompts as code, not throwaway strings.

Chapter 32 (LLM Evaluation) covers this formally, with proper metrics and statistical rigour. This is the minimum viable version. Never ship a prompt change that hasn’t been measured against a held-out set.

30.5 Worked Example

The tutorial notebook behind this chapter runs four experiments against a live Claude model (claude-haiku-4-5), comparing techniques head-to-head rather than describing them in the abstract.

The first experiment classifies five customer support messages, deliberately including one ambiguous case (“I was charged twice this month and my login also stopped working after that”), under both Listing 30.1 and Listing 30.2, using the exact same five messages for both runs so the only variable is the presence of three worked examples. Because this technique compares live model output, the specific labels vary by run. The diagnostic the notebook is built around is whether the ambiguous message’s classification changes between the two prompts. A change indicates the few-shot examples shifted the model’s tie-breaking behaviour, which is the effect in-context learning is supposed to produce.

The second experiment is fully deterministic in its ground truth, which makes it the sharper worked example. Four arithmetic word problems are scored under direct-answer and chain-of-thought prompting, using an exact-match tolerance of 0.1 against known correct answers:

Problem Correct answer
120 apples, sell 35% in the morning, sell 28 more in the afternoon. How many remain? 50
Train travels 60 km in hour 1, then speed +20% for 2 more hours. Total distance? 204.0
Sara has 3× Tom’s stickers; together 48. How many does Tom have? 12
Tank filled by pipe A in 6h, pipe B in 3h. Time if both run together? 2.0

The train and tank problems are the ones most likely to separate the two prompting styles, since both require carrying an intermediate computed value (the increased speed; the combined fill rate) into a second step, exactly the case Listing 30.3’s mechanism (each reasoning token becomes context for the next) is designed to help with. Direct-answer prompting has to produce that intermediate result silently, in one hidden state, with nowhere to write it down.

The third experiment applies Listing 30.4 to a genuinely mixed product review (praises the bass and battery life, criticises Bluetooth reliability and case build quality) and asserts two structural properties on the result, isinstance(result["issues"], list) and 1 <= result["rating_estimate"] <= 5, which is the validation half of Procedure 30.4 made concrete rather than just described. The fourth experiment re-runs the same review through Listing 30.5 and returns a tool_call.input dict that arrives pre-validated against the JSON Schema, with no fence-stripping logic required: the direct illustration of why production systems prefer the stronger guarantee whenever a provider supports it.

30.7 History and Further Reading

Brown et al.’s “Language Models are Few-Shot Learners” is where in-context learning was first characterised at scale, the GPT-3 paper this chapter’s Exposition draws on directly (Brown et al. 2020). Wei et al.’s “Chain-of-Thought Prompting Elicits Reasoning in Large Language Models” is the original CoT paper and documents the scaling behaviour: CoT helps more as models get larger (Wei et al. 2022). Yao et al.’s “ReAct: Synergizing Reasoning and Acting in Language Models” extends CoT with interleaved tool use, the natural next step past this chapter’s structured-output procedures (Yao et al. 2023). Burkov’s Hundred-Page Language Models Book, Section 5.7, covers prompt engineering as a direct extension of how LLMs are trained and sampled, useful context for why certain prompting techniques work at all (Burkov 2025). Anthropic’s own prompt engineering documentation is worth keeping open alongside this chapter for practical, model-specific guidance that complements the general theory here.

30.8 How This Connects

This chapter builds directly on Chapter 29. Self-attention and autoregressive generation are the mechanism prompts act through, and nothing here works without that architecture underneath it. It enables Chapter 31, where the retrieved context in a RAG pipeline is itself a prompt-engineering problem (how retrieved chunks are formatted strongly affects generation quality), and Chapter 32, which formalises how to test prompt quality with real metrics instead of eyeballing a handful of examples. It is often confused with fine-tuning. The distinction that matters is that prompting steers a frozen model at inference time, while fine-tuning changes what the model’s weights actually encode.

30.10 Mental Model

A prompt is a lever on a probability distribution, not a command. Zero-shot pulls that lever with instruction alone. Few-shot pulls it with demonstration. Chain-of-thought gives the model room to pull the lever gradually, one reasoning step at a time, instead of in one blind yank. Structured-output techniques don’t change the lever. They change how tightly the output is checked, or constrained, against a schema afterward, ranging from “hope and validate” to “the platform guarantees it.”
