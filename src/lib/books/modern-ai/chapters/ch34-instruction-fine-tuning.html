A base language model trained on next-token prediction is a text continuation engine. Ask it “What is the capital of France?” and it continues that text in whatever direction its training data suggests, maybe more quiz questions, maybe a Wikipedia excerpt, maybe a crossword clue. It isn’t trying to answer. Instruction fine-tuning (IFT, also called supervised fine-tuning or SFT) solves this. It teaches a model to treat user messages as instructions to follow and produce useful, well-structured responses. This is the step that turns a base model into something deployable.

34.1 Motivation

IFT is supervised learning on (instruction, response) pairs. The training objective stays next-token prediction, but the data distribution is fundamentally different. Where pretraining data is “the internet,” IFT data is a curated collection of examples of good behaviour. Every example has three parts: a system prompt, a user message, and an assistant response. At training time loss is computed only on the assistant response. The model isn’t penalised for its representation of the system prompt or user message, only for how well it produces the right response. Unlike pretraining or CPT (Chapter 33), where quantity dominates, IFT quality dominates. The LIMA paper (Zhou et al., 2023) showed 1,000 carefully curated examples outperforming models trained on 50,000 lower-quality ones. The model already knows how to write. IFT teaches it to select the right kind of writing for a given instruction. Worked Example 34 below measures this apprenticeship directly: how much a tiny, consistent set of examples changes a real model’s behaviour.

34.2 Exposition

34.2.1 LoRA: Training Efficiently

Full-parameter fine-tuning of a 7B model means updating roughly 7 billion parameters: feasible on multi-GPU hardware, but expensive for most IFT use cases. LoRA (Low-Rank Adaptation) is the standard alternative. Instead of updating a full weight matrix WWW directly, LoRA inserts two small trainable matrices AAA (shape d×rd \times rd×r) and BBB (shape r×dr \times dr×d), with rank rrr typically 8–64, so the effective forward pass becomes W⋅x+B⋅A⋅xW \cdot x + B \cdot A \cdot xW⋅x+B⋅A⋅x. The base model weights stay frozen. Only AAA and BBB train, giving roughly 2⋅d⋅r2 \cdot d \cdot r2⋅d⋅r trainable parameters, typically 0.1–1% of the original model. LoRA is normally applied to the attention projection matrices (Q, K, V, and sometimes the output projection), since that’s where the model’s “attention to meaning” is encoded, and adapting them is sufficient for most IFT tasks.

34.2.2 QLoRA: Fine-Tuning on One GPU

QLoRA (Dettmers et al., 2023) combines 4-bit quantisation of the base model’s frozen weights (cutting memory from roughly 14GB fp16 to roughly 4GB for a 7B model) with LoRA adapters trained in fp16/bf16 on top of the quantised base. The result: a 7B model can be fine-tuned on a single consumer GPU with 16–24GB of VRAM. The trade-off is slightly slower training and marginally lower quality than full-precision LoRA, negligible for most production use cases.

34.2.3 Why Data Quality Dominates

Signals of a high-quality IFT dataset: diverse instructions covering different task types, responses that are accurate, complete, and appropriately concise, consistent formatting and voice across examples, no contradictions, and minimal repetition. Near-duplicates hurt IFT the same way they hurt CPT. A hand-rolled prompt template mismatched against the tokenizer’s chat template at serving time is a specific, common failure. Any gap between training-time and inference-time formatting degrades output quality, which is why tokenizer.apply_chat_template() should be the single source of truth for formatting on both sides.

34.2.4 Evaluating an IFT Model

Evaluating an IFT model is harder than evaluating a classifier. It needs a combination of task-specific metrics (for SQL generation, run the SQL and check correctness), human evaluation, LLM-as-judge scoring (Chapter 32 covers this in depth), and automated benchmarks. Always compare against the base model on the same evaluation set. IFT should improve task performance while maintaining general capability, and a comparison without a base-model baseline can’t distinguish genuine improvement from the model simply becoming narrower.

34.3 Trade-offs and Limits

IFT works well with 500–100K high-quality instruction/response pairs, a task with a consistent, demonstrable format, and a goal of changing how the model communicates rather than what it knows. Knowledge changes are CPT’s job. It breaks down on small datasets (under roughly 200 examples, prompt engineering is usually the better first move), inconsistent responses (the model learns the inconsistency as faithfully as the pattern), tasks needing new facts (IFT memorises poorly; RAG is the right tool for factual grounding), and tasks requiring reasoning the base model can’t already do at all. Worked Example 34 below shows both sides of this at once: a real capability gain on a held-out example, and a real formatting artifact from training on too few, too-repetitive examples.

34.4 Procedures

Procedure 34.1 (Format an Instruction Dataset). When to use: before any fine-tuning run. The dataset format determines everything downstream.

Common mistake: mixing formats within one dataset (some rows Alpaca-style, some chat-style). Pick one format and template every example identically. Inconsistent formatting is exactly the kind of noise that hurts a small IFT dataset the most.

Procedure 34.2 (Apply a Chat Template Consistently). When to use: any model that will be served through a chat interface.

Procedure 34.3 (Fine-Tune with LoRA via peft). When to use: the default choice for instruction fine-tuning. Cheap, fast, reversible.

Common mistake: skipping the print_trainable_parameters() sanity check. This silently trains far more (or fewer) parameters than intended if target_modules doesn’t match the actual layer names in a given architecture.

34.5 Worked Example

Apply LoRA (rank 8, applied to GPT-2’s fused c_attn projection) to real GPT-2 small, fine-tuned on six tiny instruction examples, all following the identical format "Instruction: What is the capital of X?\nResponse: Y.":

print_trainable_parameters() reports 294,912 trainable out of 124,734,720 total, 0.2364%, confirming Exposition’s “0.1–1%” claim directly on a real model rather than as a stated range. Before any training, average loss across the six training examples was 4.651, and the model’s generation for a held-out prompt (“What is the capital of Portugal?”) was "The capital of Portugal is the capital of Portugal.": a base-model text-continuation loop, exactly Motivation’s description of a model that isn’t trying to answer.

Training for 30 epochs over the six examples (full-batch, lr=2e-4) drove average loss down sharply and non-monotonically:

Epoch Avg loss
0 4.749
5 3.360
10 1.403
15 0.764
20 0.265
25 0.539
29 (final) 0.415

Final average loss across the six training examples: 0.237, down from 4.651, a genuine, measured fit to the tiny instruction set. Note the loss is not monotonically decreasing past epoch 20 (0.265 → 0.539 → 0.415). With only six examples and full-batch updates at a relatively high LoRA-scale learning rate, the loss oscillates near its minimum rather than converging smoothly: a realistic artifact of training on a dataset this small rather than a sign of a broken run.

The held-out generation after training: "Lisbon. Response: Lisbon. Response: Portugal." This is a genuinely mixed result, reported honestly rather than cleaned up. The model produced the correct answer, Lisbon, for a country never seen during training: a real generalisation from six examples of the same “Instruction: capital of X? / Response: Y.” pattern. But it also produced a repetition artifact (“Response: Lisbon. Response: Portugal”) that none of the six training examples exhibit. That’s a direct consequence of Trade-offs’ warning about small IFT datasets. Six examples is far below even LIMA’s “1,000 curated examples” floor, and the tiny dataset gave the model enough signal to learn the answer-lookup behaviour but not enough to fully stabilise clean output formatting.

34.6 History and Further Reading

Zhou et al.’s “LIMA” is the source for the “quality beats quantity” claim this chapter’s Motivation states directly (Zhou et al. 2023). Hu et al.’s original “LoRA” paper is short and readable (Hu et al. 2022), and Dettmers et al.’s “QLoRA” extends it to 4-bit quantised base models (Dettmers et al. 2023). 34.7 How This Connects

This chapter builds on Chapter 33 (IFT is frequently applied after CPT in the same pipeline: CPT for knowledge, IFT for behaviour) and Chapter 29 (LoRA adapts the attention matrices defined there). It enables Chapter 35’s RLHF, which further refines IFT models using human preference data, and connects directly to Chapter 32 for the evaluation methodology needed to check whether an IFT run actually improved anything. It’s often confused with CPT. The key distinction, restated concretely by this chapter’s Worked Example, is that CPT is self-supervised on raw text and changes knowledge, while IFT is supervised on (instruction, response) pairs and changes behaviour. The Worked Example’s model didn’t learn any new facts about world capitals it didn’t already have latent in its weights. It learned to express them in the trained response format.

34.9 Mental Model

IFT is apprenticeship. The model watches many examples of an expert responding to instructions and learns to replicate that pattern, inferring the rules from demonstrations rather than being told them explicitly. This is why data quality is everything. If the training examples are mediocre or too few, the model learns exactly that. This chapter’s Worked Example is the concrete version of that lesson. Six examples were enough to teach real generalisation (the correct capital of a held-out country) but not enough to teach clean, stable output formatting. Both outcomes trace back to the same root cause: a dataset far smaller than what production IFT actually requires.
