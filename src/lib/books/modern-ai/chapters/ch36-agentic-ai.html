Prompting (Chapter 30), retrieval (Chapter 31), and evaluation (Chapter 32) all assume a fixed shape: one prompt in, one response out. That’s enough for classification, extraction, or question-answering over retrieved context. It isn’t enough for “book me a flight and email me the confirmation,” “debug this failing test and fix it,” or “research this topic across ten sources and write a summary”: tasks needing an unknown, task-dependent number of steps, decided at run time based on what happens after each step. An agent is what results when a model decides its own next action rather than following a script written in advance.

36.1 Motivation

The defining loop of an agent is observe → reason → act → observe (the result of that act) → reason → act → ... → stop. Compare this to a single prompt call, which is just reason → act executed once. An agent runs that loop repeatedly, and critically, the model itself decides when to stop, which action to take next, and how to interpret each observation. Tools and stopping conditions are supplied, judgment calls in between are not. This isn’t a new capability bolted onto an LLM. It’s tool calling (Chapter 30) and autoregressive generation (Chapter 29) run in a loop, where each tool’s result becomes new context for the next generation step. Worked Example 36 below builds and runs this loop directly, with real executable tools and a real step-limit guardrail, to make the mechanics concrete rather than diagrammatic.

36.2 Exposition

36.2.1 The ReAct Pattern

ReAct (Reason + Act) is the foundational pattern nearly every agent implementation reduces to. Instead of silently deciding on an action, the model is asked to think out loud before acting: chain-of-thought applied specifically to action selection. A typical turn: Thought: I need X before I can compute Y. Action: search("X"). Observation: <result>. Thought: now I can compute Y. Action: calculator(...). Observation: <result>. Final Answer: .... Writing the “Thought” step before each action gives the model a place to make its plan explicit in tokens it can condition on, rather than deciding silently with no way to correct course. Modern tool-calling APIs formalise this loop at the API level. The model’s text output is its reasoning trace, its tool_use blocks are its actions. But the underlying pattern is identical to the original ReAct paper’s plain-text scratchpad.

36.2.2 Tool Use as the Only Way an Agent Acts

An agent has no capabilities beyond the tools it’s given. The model cannot “just go look something up.” It can only emit a request to call a function with arguments in a defined schema, finding out what happened only when that function runs and returns a result. This means an agent’s capability surface, and its blast radius if something goes wrong, is entirely bounded by which tools it has access to. A calculator tool can at worst return a wrong number. A tool that deletes files or sends money can at worst do that for real. Tool scoping is therefore the primary safety control, not an implementation detail.

36.2.3 Memory: Short-Term vs. Long-Term

Short-term memory is just the context window: the running transcript of thoughts, actions, and observations accumulated in the loop so far. It’s free but bounded. A long-running agent eventually fills its context window and must summarise, discard old steps, or stop. Long-term memory, information persisting across separate agent runs, or too large for any context window, is where RAG (Chapter 31) becomes directly relevant: a search_memory tool backed by a vector store, indexed over the agent’s own past interactions rather than a static document set. From the model’s point of view, “recall something learned three days ago” and “retrieve a relevant support ticket” are the same operation: a tool call returning text to reason over.

36.2.4 Planning and Multi-Agent Orchestration

Two broad planning strategies exist. Iterative (ReAct-style) decides one action at a time, adapting naturally to surprising observations but risking wandering across many steps. Plan-and-execute writes a full multi-step plan up front, more predictable and reviewable but less adaptive mid-execution if an early assumption turns out wrong. Multi-agent orchestration splits responsibility across agents with narrower toolsets, sequential handoff, supervisor/worker, or debate/critique patterns, but multiplies latency, token cost, and the number of places a failure can occur. A single well-scoped agent with a good toolset outperforms a multi-agent system on most tasks people reach for one on. Default to one agent. Add more only when a single agent’s context or tool surface has demonstrably become the bottleneck.

36.2.5 Failure Modes to Expect

Infinite or near-infinite loops: a tool returning ambiguous or unsatisfying results can make the model retry indefinitely rather than giving up, which is why every agent loop needs a hard step limit, treated as a distinct explicit outcome rather than a silent timeout. Tool misuse: the model can call a tool with plausible-looking but wrong arguments, or the wrong tool entirely. Narrow, well-described schemas reduce this but nothing eliminates it. Compounding errors: a wrong observation early in a trajectory becomes part of the context for every subsequent step, so the error compounds rather than staying contained. Cost and latency blowup: every step is a full model call, so a ten-step trajectory costs roughly ten times a single prompt call. Worked Example 36 demonstrates the first of these, the infinite-retry failure mode, directly and measurably.

36.3 Trade-offs and Limits

Start with one agent and the smallest tool set that solves the task. Only split into multiple agents with concrete evidence (context overload, genuinely distinct specialisations) that one agent isn’t enough. Plan-and-execute is easier to put a human checkpoint in front of. Iterative ReAct adapts better mid-task but is harder to review before it runs. A hand-rolled loop is fully transparent with zero dependencies, at the cost of rebuilding common infrastructure (retries, tracing, multi-agent routing) from scratch. Frameworks (LangGraph, CrewAI) provide that infrastructure for free, at the cost of an abstraction layer between the developer and what’s actually sent to the model. Worth it once the infrastructure is genuinely needed, overkill for a single well-scoped agent.

36.4 Procedures

Procedure 36.1 (Define a Tool Schema for an Agent). When to use: every time an agent is given a new capability.

Common mistake: writing a description that explains what the function does but not when to use it. The model chooses between tools from the description text, and a missing triggering condition is a missing signal, not a cosmetic gap.

Procedure 36.2 (Implement a Step-Limit Guardrail). When to use: every agent loop, no exceptions.

Key idea: treat step_limit_reached as a distinct return value, not an exception or silent cutoff. Downstream code and any human reviewer needs to tell “the agent answered” apart from “the agent ran out of steps and the answer is unknown.”

Procedure 36.3 (Add a Human-in-the-Loop Approval Checkpoint). When to use: before any tool call with real-world side effects: sending an email, making a purchase, deleting data, deploying code.

36.5 Worked Example

No hosted LLM API is used in this Worked Example. Instead, the loop mechanics from Procedure 36.2 are run with a small, fully deterministic scripted policy standing in for the model’s decisions, so every step is real, reproducible, and measured rather than a fabricated transcript of what an LLM “would” say. Two real tools back it: a calculator (genuine arithmetic evaluation) and a flaky_search tool deliberately built to return an ambiguous, unsatisfying result for one specific query, modelling Exposition’s “tool returns ambiguous results” failure mode directly.

Run against max_steps=6, the loop’s real, logged trajectory:

Step Action Observation
1 flaky_search("population of Atlantis") “No definitive result found. Sources disagree.”
2 flaky_search("population of Atlantis") “No definitive result found. Sources disagree.”
3 flaky_search("population of Atlantis") “No definitive result found. Sources disagree.”
4 flaky_search("population of Atlantis") “No definitive result found. Sources disagree.”
5 flaky_search("population of Atlantis") “No definitive result found. Sources disagree.”
6 flaky_search("population of Atlantis") “No definitive result found. Sources disagree.”

Final status: step_limit_reached, with all 6 of max_steps=6 consumed and 6 real calls made to flaky_search. This is Procedure 36.2’s guardrail doing exactly its job. The scripted policy never gives up on the ambiguous result, exactly matching Exposition’s warning that “a tool that returns ambiguous or unsatisfying results can make the model retry indefinitely rather than giving up.” The hard step limit is what turns an unbounded retry loop into a bounded, explicitly-flagged failure instead of a silent hang. Without the guardrail, this exact policy would call flaky_search forever.

36.7 How This Connects

This chapter builds on Chapter 30’s tool/function-calling mechanics (the mechanism every agent action goes through) and Chapter 31 (the standard pattern for an agent’s long-term memory). It enables Chapter 37’s capstone, which may combine an agent loop with earlier chapters into a single project. It’s often confused with “agentic” meaning any tool call. A single tool call inside an otherwise fixed pipeline is tool-augmented generation, not an agent. What makes something agentic is the loop: the model deciding its own next step based on the result of its previous one, potentially many times, until it decides it’s done.

36.9 Mental Model

An agent is a prompt-and-tools loop, not a new kind of model. Everything it can do is bounded by the tools it’s handed. Everything it does with those tools is governed by the same reasoning-in-context mechanism from Chapter 30, run more than once. Every agent failure traces back to one of three places: a missing or wrong tool, a missing stopping condition, or an early error that compounded because nothing caught it. This chapter’s Worked Example isolated the second of these directly and measurably. The same loop code produced a clean 1-step success and a guardrail-triggered 6-step failure, with the only difference being whether a stopping condition (a clean tool result) was ever reached.
