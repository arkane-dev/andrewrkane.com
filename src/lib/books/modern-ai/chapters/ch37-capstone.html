Every module up to this point taught one skill in isolation, on a dataset chosen to make that skill’s lesson land cleanly. That’s the right way to learn a technique. It’s the wrong way to learn whether a data science project can actually be run end to end. Real projects don’t arrive labelled “this is a Chapter 12 problem.” They arrive as a vague business question, a messy dataset, and a stakeholder who wants an answer. Deciding which of this book’s techniques actually apply, in what order, and how far to take each one, is itself the skill this capstone chapter is built to exercise. Not a 37th technique, but the first project where nothing tells you which chapter you’re in.

37.1 Motivation

A capstone is a single, self-contained project exercising the full lifecycle from Chapter 10, problem framing through monitoring, on a problem scoped by the practitioner, using techniques selected from across this book. Two things distinguish it from every prior chapter’s Worked Example. The dataset and problem are chosen, not handed over (dataset and problem selection is itself a core skill no worked example can teach with a pre-cleaned dataset). And the applicable techniques must be recognised, not assumed (a chapter on regularisation assumes regularisation is needed; a real project first requires noticing that overfitting is happening at all). This chapter’s own Worked Example below is built the same way: a synthetic-but-realistically-messy predictive maintenance problem, run through the full lifecycle rather than one isolated technique.

37.2 Exposition

37.2.1 Scoping: The Skill Most Learners Underrate

The single most common way capstones fail isn’t a modelling mistake. It’s scope. Two failure directions recur. Too ambitious: “predict customer churn, deploy it, and build a full monitoring dashboard with automated retraining” is a team’s quarter, not an individual project. Attempting all of it usually means every stage gets done shallowly, and deployment/monitoring (the stages that most distinguish a data scientist from a notebook exercise) get cut first under time pressure. Too safe: picking an already-clean, famous, heavily-solved dataset avoids the hardest and most realistic parts of the job, data cleaning and problem framing, and proves only that .fit() can be called, not that the job can be done. The fix for both: scope so every lifecycle stage gets a real, if modest, version. A small model correctly deployed and monitored beats a sophisticated model that only exists as a notebook cell.

37.2.2 Why a Capstone Deliberately Doesn’t Specify a Dataset

Every other chapter in this book picked a dataset in advance, because the chapter was teaching one isolated technique and a curated dataset kept the lesson clean. A real practitioner will never be handed a curated dataset. They’ll be handed whatever a customer’s systems produce: inconsistent, undocumented, partially missing. The first job is deciding whether the data can even support the business question being asked. This chapter’s Worked Example deliberately injects realistic mess (missing sensor readings, sensor-glitch outliers) into an otherwise clean synthetic dataset, for exactly this reason.

37.2.3 Deployment and Monitoring Are Not Optional Extensions

It’s tempting to treat model training as “the real work” and deployment/monitoring as polish added if time permits. A model that exists only in a notebook has not been built to production standard, and production standard is this book’s premise throughout. Chapter 23 and Chapter 25 exist precisely because a validation-set metric alone demonstrates only half the lifecycle. Carrying a capstone project through both, even in miniature, is what demonstrates full-lifecycle competency rather than isolated modelling skill. This chapter’s Worked Example includes a real monitoring check (a PSI drift test) precisely to keep this stage from being theoretical.

37.2.4 An Optional GenAI Extension

Chapters 30–36’s techniques apply to a genuinely different class of problem than the classical-ML chapters. Most classical capstone projects (tabular prediction, classification, forecasting) have no natural place for a prompt, a retrieval pipeline, or an agent, and forcing one in is a scoping mistake in the other direction. If a project’s problem statement is a natural fit (a support-ticket triage system that both classifies tickets and drafts a suggested response using RAG over a knowledge base), extending into Chapters 30–32 demonstrates the book’s full breadth. If it isn’t a natural fit, a rigorous classical-ML capstone that nails deployment and monitoring is complete on its own.

37.3 Trade-offs and Limits

Breadth versus depth: a capstone lightly touching every chapter demonstrates breadth but nothing deeply. A capstone going deep on 8–10 well-chosen techniques while handling the rest competently demonstrates the judgment a real project requires: knowing where the hard problem actually is and spending time there. Prefer depth. A novel problem versus a well-trodden one: a completely novel problem is the most honest test of the full lifecycle, including the parts hardest to fake (problem framing, data cleaning). A well-known dataset with a realistic deployment/monitoring angle bolted on is faster to scope and still exercises the production-lifecycle chapters meaningfully. Either is legitimate. An unscoped novel problem with no fallback if the data turns out unusable is the risky combination to avoid.

37.4 Procedures

Procedure 37.1 (Write a Capstone Problem Statement). When to use: before any modelling. Revisit Chapter 2’s problem-framing techniques directly.

Common mistake: writing “build a model to predict X” as the whole problem statement. That’s a task description, not a business question. It’s missing why the prediction matters and what a good-enough answer looks like.

Procedure 37.2 (Scope Effort Across the Lifecycle). When to use: immediately after picking a problem, before diving into any one stage.

Common mistake: spending 70% of a project’s time iterating on model architecture, then running out of time for deployment and monitoring. A modest, actually-deployed-and-monitored model demonstrates more of this book’s premise than a highly tuned model that only exists in a notebook.

Procedure 37.3 (Present Results to a Non-Technical Stakeholder). When to use: writing a capstone’s final summary. The audience is explicitly not another data scientist.

Common mistake: leading with a raw metric like ROC-AUC. A non-technical stakeholder has no intuition for 0.87. Translate it into what it means for their decision instead.

37.5 Worked Example

A synthetic-but-deliberately-messy predictive maintenance problem, run through the full lifecycle: 2,000 pump sensor readings (vibration, temperature, pressure, runtime_hours), with will_fail generated from a genuine underlying physical mechanism (failure probability rising with vibration and temperature), then corrupted with realistic mess. 7.9% of vibration readings were set to missing (sensor dropout) and 15 pressure readings inflated 5x (sensor glitches), following Procedure 37.1’s requirement that a capstone dataset be messy enough for cleaning to matter. Base failure rate: 9.65% (193 of 2,000): realistic class imbalance for this kind of problem, not a balanced toy dataset.

Model CV recall (mean ± std) Test recall Test precision Failures caught False alarms per correct flag
Logistic Regression (baseline) 0.7241 ± 0.0617 0.7917 0.2568 38 / 48 (79.2%) 2.89
Random Forest 0.3172 ± 0.0402 0.2500 0.2857 12 / 48 (25.0%) 2.50

This is the kind of result Chapter 12’s ensemble chapter already warned against assuming. Random Forest, often the reflexive “stronger” choice, catches barely a quarter of real failures on this dataset, while a simple Logistic Regression baseline with class-weight balancing catches nearly four in five. That’s a genuinely large, measured gap, not a close call decided by noise (the cross-validation standard deviations, 0.06 and 0.04, are far smaller than the 0.41 gap between the two means). For a predictive-maintenance business question, where a missed failure (unplanned downtime, safety risk) is normally far more costly than an unnecessary inspection, Logistic Regression’s higher false-alarm count (2.89 vs. 2.50 per correct flag) is a clearly acceptable trade for catching three times as many real failures. That’s exactly the kind of cost-justified metric choice Procedure 37.1 requires a problem statement to make explicit before modelling starts, not after.

Following Procedure 37.3’s translation requirement, the deployed model’s result in stakeholder language: “Flags pumps likely to fail in the next week, catching roughly 4 out of 5 real failures before they happen, at the cost of about 3 unnecessary inspections for every correct flag.”

Monitoring, in miniature: a Population Stability Index (PSI) check comparing the training distribution against a simulated future batch where the pump fleet has aged and temperatures have drifted up 6 degrees (a plausible seasonal or fleet-ageing shift):

Check PSI value Interpretation (< 0.1 none, 0.1–0.25 moderate, > 0.25 major)
Temperature, drifted +6° batch 0.4704 Major shift: flagged
Vibration, no-drift control batch 0.0482 No significant shift: correctly not flagged

The drift check correctly distinguishes a genuine shift (0.4704, comfortably past the 0.25 “major shift” threshold) from a no-drift control batch drawn from the same distribution as training (0.0482, comfortably below the 0.1 “no shift” threshold). That’s a real, working monitoring stage, not a placeholder, satisfying Exposition’s requirement that deployment and monitoring be more than notebook cells.

A locally-run capstone hitting every lifecycle stage, as this Worked Example does, is sufficient to demonstrate the same competency.

37.7 How This Connects

This chapter builds on every chapter in this book. Chapter 2 and Chapter 10 are the two most directly load-bearing, since they teach how to scope and sequence the rest rather than one specific technique. It is the terminal chapter of Book 2. It enables nothing further in this book, and is meant to be the project pointed to afterward as evidence of the whole book’s outcome. It’s often confused with a portfolio piece pursued for its own sake. A capstone’s purpose here is to prove lifecycle competency to the practitioner themselves, that a project can be run end to end without a chapter number saying what’s next. A strong portfolio artefact is a bonus of that, not the goal.

37.9 Mental Model

Every prior chapter handed a dataset and said “here’s the technique, apply it.” The capstone hands nothing and asks “what’s actually going on here, and what do you do about it?” That’s the entire difference between having learned three dozen techniques and being able to run a project. This chapter’s Worked Example is a demonstration of that difference in miniature. The interesting finding wasn’t a new technique. It was the discovery, only visible by actually measuring both models, that the “obviously stronger” architecture was the wrong choice for this specific, cost-asymmetric problem. The lifecycle from Chapter 10 is the map. A capstone is the first time the practitioner is the one holding it while walking.
