Chapter 39 — The CUDA Programming Model

Key Terms

Term Definition
Kernel A function marked __global__, called from host code, executed on the device by many threads at once
Host / Device Host = CPU and its memory; Device = GPU and its memory. Physically separate address spaces
Block A group of threads (≤1024) that run on one SM, can synchronise (__syncthreads()), and share on-chip shared memory
Grid The full set of blocks launched by one kernel call; blocks run independently, no cross-block synchronisation
threadIdx / blockIdx / blockDim / gridDim Built-in per-thread variables identifying a thread’s position in the block/grid hierarchy
Grid-stride loop Pattern where each thread processes multiple elements, striding by total thread count: decouples launch config from problem size
Pageable memory Ordinary host memory (new/malloc); OS can relocate it, so cudaMemcpy stages it through a pinned buffer first
Pinned (page-locked) memory Host memory allocated with cudaMallocHost; fixed physical address, enables direct DMA transfer, no staging copy

__global__ Device Host (or device, for dynamic parallelism) Kernel entry points — always returns void
__device__ Device Device only Helper functions called from within kernels

Chapter 40 — Memory Hierarchy in Practice

Key Terms

Term Definition
Coalesced access A warp’s 32 threads access consecutive memory addresses, satisfied by one (or few) memory transactions
Strided / scattered access A warp’s threads access widely-separated addresses, requiring many more, smaller memory transactions for the same useful data
Cache line / memory transaction The fixed-size chunk (commonly 128 bytes) DRAM is fetched in, regardless of how much of it you actually need
Shared memory bank One of 32 equal-width physical partitions of shared memory; ideally each of a warp’s 32 threads hits a different bank per access
Bank conflict Two or more threads in a warp access different addresses in the same bank, forcing serialised (not parallel) access
Register spilling When a kernel needs more registers per thread than are available, excess variables spill to slower local memory (physically in global memory)
Occupancy Ratio of active warps to the maximum an SM could support — full treatment in Chapter 43, but register/shared-memory usage per thread directly limits it

Measured Results (This Book’s Reference Rig)

Experiment Configuration Result
Coalesced vs. strided global memory copy 16.7M elements, stride 32 (128 bytes apart) Coalesced: ~1876 GB/s. Strided: ~56 GB/s. ~33.4x slowdown
AoS vs. SoA (sum one field only) 16.7M 16-byte Record{x,y,z,w} structs, sum .x only AoS: ~409 GB/s useful. SoA: ~1044 GB/s. ~2.55x slowdown
Shared memory bank conflicts (tiled transpose) 8192×8192 float matrix (268 MB), tile[32][32] vs tile[32][33] Unpadded: ~1087 GB/s. Padded: ~1250 GB/s. ~1.15x speedup from one line of padding

Re-measure on your own hardware with the companion notebook. The magnitude varies by GPU generation and memory technology. The direction (coalesced/padded is always faster or equal) does not.

The Tiled-Transpose-With-Padding Pattern

#define TILE 32

// Bank-conflict-prone: tile[32][32]
__shared__ float tile[TILE][TILE];

// Conflict-free: tile[32][33]. One extra column shifts
// each row's bank alignment
__shared__ float tile[TILE][TILE + 1];

This single-line pattern (padding the fast/leading dimension of a 2D shared memory array by 1) is one of the most common, highest-value micro-optimisations in CUDA code that uses shared memory tiles — applicable to transposes, tiled matrix multiplication, and any stencil operation that reads shared memory along both dimensions.

Coalescing Checklist

Question If “no,” consider
Do consecutive threadIdx.x values map to consecutive memory addresses? Restructure indexing so they do: often just swapping which index depends on threadIdx.x
Is the data type’s size a “nice” multiple (4/8/16 bytes)? Structs-of-arrays (SoA) generally coalesce better than arrays-of-structs (AoS): each field is contiguous across threads (measured ~2.55x on this book’s reference rig, above)
Are you accessing a 2D array row-major with threadIdx.x on the column? This is usually the coalesced direction; threadIdx.x on the row (with a stride jump per thread) usually isn’t

The Map Kernel Pattern

__global__ void mapKernel(const float* in, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        out[i] = /* per-element operation */;
    }
}

// SAXPY: y = a*x + y
__global__ void saxpy(int n, float a, const float* x, float* y) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) y[i] = a * x[i] + y[i];
}

// Sigmoid activation: out = 1 / (1 + exp(-in))
__global__ void sigmoidKernel(const float* in, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = 1.0f / (1.0f + expf(-in[i]));
}

Benchmarking Decision Checklist

Question Compare against
Does the real workload call this operation once, on host-resident data? GPU round-trip time (H2D + kernel + D2H), single call
Does the real workload call this operation repeatedly on data that can stay resident? GPU amortised time: (1 transfer in, N kernel calls, 1 transfer out) / N

Chapter 42 — Parallel Patterns

Key Terms

Term Definition
Reduction Combining many values into one (sum, max, min, …) via parallel, tree-structured combination rather than a serial pass
Tree reduction Halving the number of active threads each step, each surviving thread combining with a neighbour: log₂(n) steps instead of n
Scan / prefix sum Computing, for every position, the running combination of all elements up to that position
Hillis-Steele scan Simple scan algorithm, log₂(n) steps, O(n log n) total work; easy to implement, not the most work-efficient
Blelloch scan Work-efficient scan algorithm, O(n) total work, more complex (up-sweep/down-sweep); the production-grade choice for large scans
Stencil A kernel pattern where each output element depends on a small fixed neighbourhood of input elements
Halo The extra border of neighbouring elements a tiled stencil kernel loads into shared memory alongside its own block’s data

Reduction Pattern

__global__ void sumTreeReduction(
    const float* in,
    float* result,
    int n
) {
    __shared__ float sdata[256];   // must match blockDim.x
    int tid = threadIdx.x;
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    sdata[tid] = (i < n) ? in[i] : 0.0f;
    __syncthreads();

    for (int s = blockDim.x / 2; s > 0; s >>= 1) {
        if (tid < s) sdata[tid] += sdata[tid + s];
        __syncthreads();
    }
    if (tid == 0) atomicAdd(result, sdata[0]);
}

Stencil (Tiled, With Halo) Pattern

#define RADIUS 3
#define BLOCK 256

__global__ void stencilTiled(const float* in, float* out, int n) {
    __shared__ float tile[BLOCK + 2 * RADIUS];
    int gi = blockIdx.x * blockDim.x + threadIdx.x;
    int li = threadIdx.x + RADIUS;

    tile[li] = (gi < n) ? in[gi] : 0.0f;
    if (threadIdx.x < RADIUS) {
        tile[li - RADIUS] =
            (gi >= RADIUS) ? in[gi - RADIUS] : 0.0f;
        tile[li + BLOCK] =
            (gi + BLOCK < n) ? in[gi + BLOCK] : 0.0f;
    }
    __syncthreads();

    if (gi < RADIUS || gi >= n - RADIUS) return;
    float sum = 0.0f;
    for (int off = -RADIUS; off <= RADIUS; off++)
        sum += tile[li + off];
    out[gi] = sum / (2 * RADIUS + 1);
}

Hillis-Steele Inclusive Scan Pattern

#define N 1024  // single block, one thread per element

__global__ void inclusiveScan(const float* in, float* out, int n) {
    __shared__ float temp[N];
    int tid = threadIdx.x;
    temp[tid] = in[tid];
    __syncthreads();

    for (int offset = 1; offset < n; offset *= 2) {
        float val = 0.0f;
        if (tid >= offset) val = temp[tid - offset];
        __syncthreads();
        temp[tid] += val;
        __syncthreads();
    }
    out[tid] = temp[tid];
}

Note the double __syncthreads(): one after reading the neighbour value (ensuring every thread has read before anyone writes), one after writing (ensuring every thread’s write is visible before the next iteration reads). Dropping either introduces a race condition.

Chapter 43 — Kernel Performance Tuning

Key Terms

Term Definition
Arithmetic intensity FLOPs performed per byte of memory moved; the x-axis of the roofline model
Roofline model Performance ceiling as a function of arithmetic intensity: sloped (bandwidth-limited) at low intensity, flat (compute-limited) at high intensity
Memory-bound Runtime set by memory bandwidth; extra arithmetic is nearly free until the “knee”
Compute-bound Runtime set by FLOPs throughput; more memory bandwidth wouldn’t help
Occupancy Ratio of actually-resident warps on an SM to the hardware maximum it could support

Measured Results (Reference Rig†: RTX 5090, 170 SMs, 1,536 max threads/SM)

Peak memory bandwidth achieved: ~1,986 GB/s. Peak compute achieved: ~118.6 TFLOP/s (FP32, CUDA cores). Ridge point: R=118,600/1,986≈60R = 118{,}600 / 1{,}986 \approx 60R=118,600/1,986≈60 FLOPs/byte. This matches the measured knee between REPEAT=64 (16 FLOPs/byte, memory-bound) and REPEAT=256 (64 FLOPs/byte, past the knee).

Occupancy sweep (200 FMAs/element kernel): block size 512 is the sweet spot band (3 max active blocks/SM, 48 resident warps/SM); block size 1,024 only fits 1 block/SM (32 resident warps) since 2×1,024>1,5362 \times 1{,}024 > 1{,}5362×1,024>1,536.

Achieved vs. theoretical occupancy (ncu --section Occupancy, same six block sizes): achieved is lower than theoretical at every block size, worst at block 64 (100% theoretical vs. 44.00% achieved). Achieved occupancy tracks measured wall-clock ordering more closely than theoretical does, but not perfectly: block 512’s achieved occupancy (85.24%) is the highest of the six, yet block 128 (84.73% achieved) is still the fastest kernel measured.

Rough Roofline Triage

I = total_FLOPs / total_bytes_moved
R = peak_FLOPs / peak_bandwidth

Is I < R?
├── Yes -> memory-bound. Optimise: coalescing, reduce
│          bytes moved, increase reuse (fuse operations),
│          or accept it.
└── No  -> compute-bound. Optimise: reduce redundant
           arithmetic, use Tensor Cores if matmul-shaped,
           reduce precision.

import triton
import triton.language as tl

@triton.jit
def my_kernel(x_ptr, out_ptr, n, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x * 2.0, mask=mask)

from torch.utils.cpp_extension import load_inline

cuda_source = r"""
#include <torch/extension.h>
#include <cuda_runtime.h>

__global__ void my_kernel(const float* x, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = /* your op */;
}

    auto out = torch::empty_like(x);
    int n = x.numel();
    int block = 256, grid = (n + block - 1) / block;

        x.data_ptr<float>(), out.data_ptr<float>(), n
    );
    return out;
}
"""

    cpp_sources=cpp_source,

)

Wiring a Kernel Pair Into Autograd

class MyOp(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        ctx.save_for_backward(x)
        return ext.my_op_fwd(x)

    @staticmethod
    def backward(ctx, grad_output):
        x, = ctx.saved_tensors
        return ext.my_op_bwd(grad_output.contiguous(), x)

def my_op(x):
    return MyOp.apply(x)

backward must return one gradient per forward input. grad_output.contiguous() guards against non-contiguous gradient tensors, which raw pointer access (.data_ptr<float>()) requires.

Squared ReLU Kernel Pair (Full)

__global__ void squared_relu_fwd_kernel(
    const float* x,
    float* out,
    int n
) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        float v = x[i] > 0.0f ? x[i] : 0.0f;
        out[i] = v * v;
    }
}

__global__ void squared_relu_bwd_kernel(
    const float* grad_out,
    const float* x,
    float* grad_in,
    int n
) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        float v = x[i] > 0.0f ? x[i] : 0.0f;
        // d/dx[relu(x)^2] = 2*relu(x)
        grad_in[i] = grad_out[i] * 2.0f * v;
    }
}

Fusion Decision Heuristic

def is_good_fusion_candidate(operations_in_sequence):
    all_memory_bound = all(
        op['arithmetic_intensity'] < op['gpu_ridge_point']
        for op in operations_in_sequence
    )
    shares_data = True
    enough_ops = len(operations_in_sequence) >= 2
    if all_memory_bound and shares_data and enough_ops:
        return 'Good candidate'
    if not all_memory_bound:
        return 'Check first: compute-bound ops may not benefit'
    return 'Marginal: measure both versions'

Verification Checklist

  1. Correctness against a reference implementation (float32 tolerance, ~1e-6)
  2. Kernel launch count via torch.profiler (expect exactly 1 for a fused kernel)
  3. Speed vs. BOTH the naive decomposition AND the vendor-optimised baseline

Correct Benchmarking Pattern

import timeit

def warm_up_and_time(fn, warmup=5, repeat=100):
    for _ in range(warmup):
        fn()
    times = timeit.repeat(fn, number=1, repeat=repeat)
    times.sort()
    return {'min': times[0], 'median': times[len(times)//2],
            'mean': sum(times)/len(times), 'max': times[-1]}

Chapter 49 — CPU Architecture for Performance

Key Terms

Term Definition
Cache line The unit of data (64 bytes on x86-64) fetched into cache on any access
Cache miss A memory access not found in the requested cache level, forcing a fetch from a slower level
Pointer chase A benchmark pattern where each access depends on the value just read, defeating prefetching
Branch prediction The CPU’s speculative guess about which instruction path to execute before a conditional resolves
Loop-carried dependency A dependency where iteration N+1 needs iteration N’s result, blocking concurrent execution
Instruction-level parallelism (ILP) A core’s ability to execute multiple independent instructions per cycle

Measured Results (Reference Rig†: AMD Ryzen 9 5950X, 16C/32T, 32KB L1d, 512KB L2, 32MB L3/CCD)

Cache hierarchy latency (pointer chase): L1d ~1.4ns/access, L2 ~2.1-2.9ns, L3 ~4.9-14.0ns, DRAM ~35-83ns.

Branch prediction (sorted vs. unsorted): Numba @njit (auto-vectorised) shows no real difference (4.98ms vs. 4.80ms); pure CPython shows ~25% slowdown unsorted (12.81ms vs. 16.04ms, branch-misses roughly double).

ILP (single vs. four dependency chains): 3.74x-3.84x speedup in L2/L3-resident working sets, narrowing to 2.30x once DRAM-resident (400MB).

Chapter 53 — Parallelism on CPU

Key Terms

Term Definition
GIL (Global Interpreter Lock) CPython’s lock ensuring only one thread executes Python bytecode at a time per process

Decision Table

Workload type Best tool Why
CPU-bound multiprocessing / ProcessPoolExecutor Only way to get real multi-core parallelism in standard CPython
I/O-bound threading / ThreadPoolExecutor Same scaling as multiprocessing, far less overhead
CPU-bound, need reliability/convenience joblib ~48% overhead vs. raw multiprocessing, better crash-recovery/API

Measured Results (Reference Rig†: AMD Ryzen 9 5950X, 16C/32T)

CPU-bound: threading gives a flat ~1.1x “speedup” regardless of worker count (1-8), while multiprocessing scales close to linearly (1.15x → 8.62x at 8 workers). I/O-bound: both threading and multiprocessing scale close to linearly (~7.95x and ~7.73x at 8 workers respectively). joblib measured 48% slower than raw multiprocessing.Pool on an 8-way CPU-bound task. Pool-creation overhead (tiny task, repeated pool creation every iteration): ~46x slower than reusing one pool.

Key Terms

Term Definition

Chapter 55 — Knowing When to Move to GPU

Key Terms

Term Definition
Arithmetic intensity FLOPs performed per byte of data moved: predicts whether an operation can be compute-bound
Ridge point The intensity threshold, specific to a hardware pair, separating memory-bound from compute-bound
Roofline model Achievable throughput vs. arithmetic intensity, capped by bandwidth (low intensity) or peak compute (high)
Pinned (page-locked) memory Host memory that cannot be paged out, intended to speed DMA transfers to/from GPU

Measured Results (Reference Rig†: AMD Ryzen 9 5950X + NVIDIA RTX 5090)

Pinned vs. pageable memory (100M floats, H2D): 1.08x speedup (27.65ms vs. 29.79ms), real, but far below the commonly-quoted 2-3x.

Elementwise op (x*2+1, constant intensity ~0.25 FLOPs/byte): GPU never wins at any tested size (best case 0.98x at n=100,000, worst 0.11x at n=1,000).

Matmul (intensity grows with n): crossover between n=256 (0.77x) and n=512 (1.08x); peak speedup 3.21x at n=2048.

Decision Formula

arithmetic_intensity = total_FLOPs / total_bytes_moved

if intensity is low AND does not grow with problem size:
    keep on CPU, regardless of data size

if intensity grows with problem size (e.g. O(n) for matmul):
    measure the crossover point on your actual hardware
    move to GPU only past that measured point
