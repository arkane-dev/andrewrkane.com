Chapter 38 — GPU Architecture Fundamentals

Exercise 38.1 [W]. A GPU is throughput-optimised because it uses thousands of simple cores organized into SMs, each issuing one instruction per clock to a whole 32-thread warp, so it finishes millions of largely-uniform pieces of work fast in aggregate. A CPU is latency-optimised because its handful of complex cores (branch prediction, out-of-order execution, deep pipelines) are built to finish one thread of work as fast as possible, even when that thread is branchy or has unpredictable memory accesses.

Exercise 38.2 [W]. Warp divergence is the performance cost that occurs when threads within the same 32-thread warp take different branches of a conditional, forcing the hardware to execute the branches serially (masking off inactive threads) in the classic model. The feature that reduces this cost on Volta-onward GPUs is independent thread scheduling, which lets diverged threads make progress more flexibly than the strict serial-branch model.

Exercise 38.3 [A]. Using Listing 38.3’s formula: bytes_moved = 50_000_000 * 4 * 4 = 800,000,000 bytes = 0.8 GB. achieved_bw = 0.8 / (0.9 / 1000) ≈ 889 GB/s. Against this chapter’s ~1.7 TB/s peak estimate, that is roughly 52% of peak, in the same range as the chapter’s own 55% result, so this kernel also looks memory-bound rather than compute-bound, consistent with an elementwise-style operation.

Exercise 38.4 [A]. Without the warmup=5 loop, the timed run would include one-time CUDA context initialization and kernel JIT compilation costs, both of which are one-off costs unrelated to steady-state performance. The measured time would be dramatically inflated and would not reflect how fast the operation actually runs once “hot.” This effect is worse on the very first run of a notebook specifically because CUDA context creation happens exactly once per process. Any call after that first one, even without an explicit warm-up loop, benefits from the context already existing, so a first-cell measurement without warm-up is the worst-case distortion.

Exercise 38.5 [A]. A naive “170 SMs times some per-core speedup factor” estimate would wildly overshoot the measured 75.4x, because it ignores that the comparison is against a single CPU core (not 170 CPU-core-equivalents’ worth of serial work), that the kernel measured is memory-bandwidth-bound (achieving only ~55% of peak bandwidth) rather than compute-bound, and that not every SM can be kept fully occupied for a workload this size relative to launch overhead. SM count sets an upper bound on parallel capacity, but actual speedup depends on occupancy, memory bandwidth, and how well the specific kernel is able to use all 170 SMs simultaneously, none of which a simple multiplication captures.

Exercise 38.6 [E]. A workload with a data-dependent branch where one side does a slow, scattered global-memory lookup (e.g., a hash-table probe) and the other side does a cheap register-only computation would still diverge expensively on modern hardware. Independent thread scheduling lets threads make progress independently, but it does not eliminate the fact that a warp still has to wait for its slowest-diverged-path threads to finish before the warp can retire or reconverge. A scattered memory access is exactly the kind of high-latency, unpredictable-timing operation that widens that gap far more than the chapter’s cheap-arithmetic branches did.

Exercise 38.7 [E]. The 3.5% figure was measured on a workload where both branches did roughly equal, cheap, register-resident arithmetic. That is close to a best case for modern independent thread scheduling, not a general result. Divergence cost still scales with how unequal and how memory-latency-heavy the branches are, so a kernel with a genuinely expensive branch (a rare-but-slow code path, a scattered load) can still pay a real, large divergence penalty. The right habit is still to measure the actual kernel, not assume either “divergence is free” or “divergence costs 2x,” since this chapter demonstrated both extremes are wrong as universal claims.

Exercise 38.8 [R]. Discussion only, no single answer expected. The Volta whitepaper describes giving each thread its own program counter and call stack, rather than one shared program counter per warp, so threads can diverge and reconverge more flexibly and the scheduler can choose to execute individual threads or subsets of a warp rather than forcing a strict “execute branch A for the whole warp, then branch B for the whole warp” ordering. That per-thread progress state is what lets a warp with cheap, roughly-balanced branches (as in this chapter’s kernels) pay only a small scheduling overhead instead of the full serialized cost the classic model assumes. The 3.5% measured overhead reflects the residual cost of switching between per-thread execution states, not full serial re-execution of both branches.

Chapter 39 — The CUDA Programming Model

Exercise 39.1 [W]. A block is a group of up to 1024 threads that run together on a single SM. Blocks are the unit that can synchronise internally, using __syncthreads(), and can share fast on-chip shared memory. A grid is the full collection of blocks launched by one kernel call. Blocks within a grid run independently, potentially on different SMs and in any order, with no mechanism to synchronise across blocks.

Exercise 39.2 [W]. int global_id = blockIdx.x * blockDim.x + threadIdx.x;. blockIdx.x is the calling thread’s block index within the grid, blockDim.x is the number of threads per block, and threadIdx.x is the calling thread’s index within its own block. Multiplying the block index by the block size and adding the thread’s local index gives a single flat index unique across the whole grid.

Exercise 39.3 [A]. If grid * block < n and the stride loop is replaced with a single if (i < n) check, every thread would compute at most one element, and any element with a flat index i >= grid * block would never be written by any thread at all. The output array would be left partially uninitialised (whatever garbage was in device memory beforehand) for all the “extra” elements beyond the launched thread count. This is a correctness bug, not just a performance regression. The grid-stride while/for loop is what guarantees every element gets processed regardless of how the launch configuration compares to n.

Exercise 39.4 [A]. Bytes moved for one 134.2 MB array: n * 4 bytes = 33,554,432 * 4 = 134,217,728 bytes ≈ 0.1342 GB. Pageable D2H: 0.1342 GB / (54.469 / 1000) s ≈ 2.46 GB/s. Pinned D2H: 0.1342 GB / (9.263 / 1000) s ≈ 14.49 GB/s. Both figures are one to three orders of magnitude below Chapter 38’s roughly 1.7 TB/s on-GPU memory bandwidth estimate. That’s expected, since PCIe host↔︎device transfer is a completely different interconnect from on-die HBM bandwidth, and pageable transfers pay an additional staging-copy tax on top of the PCIe link’s own ceiling. That’s exactly why the pinned number is nearly 6x higher than the pageable one despite moving the identical bytes over the identical physical link.

Exercise 39.5 [A]. Wrap the compute-heavy kernel launch with Listing 39.4 exactly as the H2D/kernel/D2H stages were each individually timed in the Worked Example, then compare the kernel’s elapsed time against the H2D and D2H stage times measured for the same problem size. If the kernel does substantially more arithmetic per element (e.g. a small loop of transcendental functions per element rather than one add), its share of total pipeline time should grow relative to the roughly 1% seen for vector-add. The point is to actually re-measure per-stage rather than assume the same imbalance holds for a different kernel body.

Exercise 39.6 [E]. Pinning every host buffer removes the “which buffers actually matter” decision, but it isn’t free. Pinned memory can’t be swapped to disk, so pinning a large fraction of a training pipeline’s host memory starves the OS and other processes of memory they need, and can even fail outright under memory pressure. The right approach is to pin only the buffers that sit on a frequent, performance-sensitive transfer path, exactly the ones this chapter’s D2H measurement showed benefiting, not every host allocation in the program.

Exercise 39.7 [E]. Unified Memory is reasonable for a fast prototype or research script that moves data between host and device only occasionally and where development speed matters more than shaving milliseconds off transfers, e.g., quickly testing whether an algorithm produces correct results at all. It is clearly the wrong choice for a latency-sensitive production pipeline with frequent, large, predictable transfers on a hot path, exactly this chapter’s vector-add pipeline, where explicit cudaMalloc/cudaMemcpy, plus pinned memory, gives the control and predictability needed to hit a measured performance target.

Exercise 39.8 [R]. Discussion only, no single answer expected. CUDA streams let independent chunks of work (transfers and kernel launches) be queued so that a H2D transfer for one chunk of data can overlap with kernel execution on a previously-transferred chunk, and with a D2H transfer of an even earlier chunk’s results. This turns what this chapter measured as three strictly sequential stages into a pipeline where the GPU’s copy engines and compute units are busy simultaneously. Streams require pinned memory specifically because the DMA engine driving an asynchronous, overlapped transfer needs a stable physical address for the whole transfer’s duration. A pageable buffer could be relocated by the OS mid-transfer, which is exactly why pageable copies are forced through a synchronous staging copy in the first place, and why that staging behavior is incompatible with genuine overlap.

Chapter 40 — Memory Hierarchy in Practice

Exercise 40.1 [W]. An access is coalesced when a warp’s 32 threads request 32 consecutive addresses that fit within one (or a small number of) fixed-size memory bursts, commonly 128 bytes, so the hardware can satisfy the whole warp with a single memory transaction instead of many separate ones for the same amount of useful data.

Exercise 40.2 [W]. A bank conflict occurs when two or more threads in the same warp access different addresses that happen to fall in the same one of shared memory’s 32 physical banks, forcing those accesses to serialise instead of completing in parallel. This chapter’s fix for the tiled-transpose case is a one-line change: declaring the shared-memory tile as tile[32][33] instead of tile[32][32], adding one column of padding so each row’s bank alignment shifts and the transposed access pattern no longer collides onto a single bank.

Exercise 40.3 [A]. (a) data[threadIdx.x]: coalesced. Consecutive threads produce consecutive addresses directly. (b) data[threadIdx.x * 4]: not coalesced. Consecutive threads are 4 elements (16 bytes) apart, so a warp’s 32 threads span a much wider address range than one burst, similar in spirit to Listing 40.1’s stride > 1 case. (c) data[row * width + threadIdx.x] with threadIdx.x on columns: coalesced. For a fixed row, consecutive threadIdx.x values produce consecutive addresses across the warp, the same pattern Listing 40.1’s table marks as the coalesced 2D case.

Exercise 40.4 [A]. Coalesced version: 16,777,216 elements, 4 bytes read + 4 bytes written per element = 8 bytes/element useful traffic, and since each warp’s request is satisfied in one burst, total bytes actually moved is essentially the same as useful bytes: 16,777,216 * 8 ≈ 134.2 MB. Strided version: the same 16,777,216 useful elements are touched, but if each scattered 4-byte access triggers its own full 128-byte transaction (for both the read and the write), total bytes actually moved is 16,777,216 * 128 * 2 ≈ 4.295 GB, roughly 32x more physical traffic than the coalesced version for the identical useful data. That lines up closely with the measured ~33.4x effective-bandwidth slowdown (128/4 = 32, the stride used in the experiment).

Exercise 40.5 [A]. A shared-memory address’s bank index is computed as (address / 4 bytes) mod 32 for 4-byte data. With tile[32][32], row r’s data starts at offset r * 32 floats, so (r * 32) mod 32 = 0 for every row. Every row starts on bank 0, meaning the transposed access tile[threadIdx.x][threadIdx.y] (which varies the row index across the warp) lands every thread on the same bank at a given step. With tile[32][33], row r starts at offset r * 33, and (r * 33) mod 32 = r mod 32: a different bank for every row, so the same transposed access pattern now spreads across all 32 banks.

Exercise 40.6 [E]. The two effects are not comparable in magnitude on this chapter’s own measurements. Uncoalesced global memory access cost 33.4x here, while the unpadded bank conflict cost only about 1.15x, over an order of magnitude apart. Padding every shared-memory tile “just in case” is still low-risk since the fix is nearly free, but treating it as equally urgent to fixing a genuinely uncoalesced global-memory access pattern would be prioritising the wrong problem first. When time is limited, global memory access pattern should be checked before hunting for bank conflicts.

Exercise 40.7 [A]. The two numbers differ because the “distance between consecutive threads’ addresses” differs by a factor of 32 between the two cases. In the AoS case, consecutive threads’ .x fields are 16 bytes apart (one Record), so a warp’s 32 threads span 512 bytes, roughly 4 memory bursts instead of 1, a partial coalescing loss. In the stride-32 case, consecutive threads’ addresses are 128 bytes apart, so a warp’s 32 threads span 4,096 bytes, up to 32 separate bursts instead of 1, a near-total coalescing loss. The AoS case still shares most of each burst’s bytes across two or more threads; the stride-32 case shares almost none of it, which is why 2.55x and 33.4x are both real coalescing losses at very different severities.

Exercise 40.8 [E]. A kernel that is compute-bound rather than memory-bound, for example one that does a long chain of transcendental-function evaluations (sin, exp, log) per element with comparatively little data movement, would see little benefit from fixing an uncoalesced access pattern, because the bottleneck is arithmetic throughput on the SMs, not the memory subsystem. Per this chapter’s Trade-offs section, memory-access optimisations only pay off when memory, not compute, is what the kernel is actually waiting on.

Exercise 40.9 [R]. Discussion only, no single answer expected. The NVIDIA blog’s tiled-transpose example uses the same core pattern this chapter does: a TILE x TILE shared-memory tile, loaded coalesced and written back transposed, padded by one column to remove bank conflicts, and reports a real speedup from padding on the hardware it was measured on at the time. Because that measurement predates this book’s Blackwell-generation reference rig, its reported multiplier is very unlikely to match this chapter’s measured 1.15x exactly. The durable point, consistent across both sources, is that padding never hurts and typically helps by some modest amount, and the specific multiple is a function of GPU generation and cache/bank hardware, not a fixed constant to memorise.

Chapter 41 — Writing Your First Kernels

Exercise 41.1 [W]. A single-shot SAXPY call pays the full host-to-device and device-to-host transfer cost for exactly one kernel launch’s worth of work. SAXPY does only one multiply and one add per element, so the arithmetic is cheap relative to moving the array across PCIe twice. Per Chapter 39’s lesson, the transfer, not the kernel, dominates total time, and no problem size closes that gap because both the transfer cost and the compute cost scale together with n.

Exercise 41.2 [W]. Amortisation is spreading a fixed one-time cost, here, the host-to-device and device-to-host transfer, across many repeated operations so its per-operation share shrinks. The single measurement that changed between the two SAXPY experiments was how many kernel launches occurred per data transfer: one in the single-shot case, one hundred in the amortised case. The kernel code, the GPU, and the per-call problem size were identical in both.

Exercise 41.4 [A]. At n = 10,000,000, single-shot GPU total was 8.6309 ms and single-shot CPU total was 2.1380 ms: the GPU is roughly 4x slower single-shot. With amortised GPU time approaching about 0.1094 ms/call (from the 100-repeated-call measurement) and single-shot CPU at 2.1380 ms as the target to beat, even a single amortised GPU call (0.1094 ms, ignoring the one-time transfer already paid) is far below the CPU’s 2.1380 ms. The crossover happens almost immediately after the transfer is paid once, consistent with the measured 30.2x speedup by 100 calls. The dominant cost being amortised away is the transfer, not the kernel, so the crossover point is set mainly by how large the one-time transfer cost is relative to the ~0.1 ms per-call kernel cost.

Exercise 41.5 [A]. With n_elements=500_000 (not < 100_000) and flops_per_element=1 (< 5), the function returns False. This matches this chapter’s single-shot SAXPY finding. SAXPY does 2 FLOPs/element (one multiply, one add), similarly low arithmetic intensity, and the CPU won at every size tested for exactly the same reason the heuristic flags: too little arithmetic per element to survive a single-shot round trip.

Exercise 41.6 [E]. A function that runs once per user request on a few thousand elements is almost exactly this chapter’s single-shot, small-n case, well under the roughly 100,000-element threshold where GPU overhead alone is likely to dominate, and with no repeated calls to amortise the transfer against. Per this chapter’s measured SAXPY sweep, the CPU should be assumed faster until proven otherwise by an actual benchmark (Procedure 41.2). Porting this to CUDA without measuring first would very likely make it slower, not faster.

Exercise 41.7 [E]. A one-off batch script that loads a CSV, computes a single derived column once, and writes the result back out is a reasonable case where CPU is the right design choice. The data starts and ends on the host, the operation runs exactly once, and there is no repeated-call structure to amortise a transfer against, exactly the single-shot SAXPY shape this chapter measured losing to CPU at every tested size.

Exercise 41.8 [R]. Discussion only, no single answer expected. CUDA streams let a program overlap a kernel’s compute with the next chunk’s transfer, effectively hiding transfer latency behind computation happening concurrently. For an operation as arithmetically cheap as SAXPY, though, the kernel itself takes a tiny fraction of the total pipeline time (Chapter 39’s vector-add pipeline showed the kernel under roughly 1% of total time). There is very little compute to overlap the transfer against, so streams would narrow but not eliminate the gap between single-shot GPU and CPU time for an operation this cheap per element. Streams help more for pipelines with a better balance of transfer and compute time.

Chapter 42 — Parallel Patterns

Exercise 42.1 [W]. The naive atomicAdd-per-thread reduction is slow because every one of the array’s threads writes to the exact same global memory address, and atomics guarantee correctness by serialising those writes. 16.7 million threads all effectively queue behind one memory location. Tree reduction (Listing 42.1) instead has each block combine its own chunk of data locally in shared memory, halving the number of active threads each step, so only one thread per block ever performs a global atomic add: thousands of atomics instead of millions.

Exercise 42.2 [W]. A stencil is a kernel pattern where each output element depends on a small, fixed neighbourhood of input elements (e.g. a blur or finite-difference operation). A halo is the extra border of neighbouring elements a tiled stencil kernel loads into shared memory alongside its own block’s data, so overlapping neighbour reads can be served locally instead of from global memory. This chapter’s measured result: tiling gave no benefit in any of the four variations tested (1D radius 3, 1D radius 32, 1D at a larger size exceeding L2, and 2D). One configuration was even measured very slightly slower with tiling.

Exercise 42.3 [A]. Without __syncthreads() inside the loop, faster threads could race ahead to the next halving step and read sdata[tid + s] before a slower neighbour thread has finished writing its own combined value into that same location from the previous step. This produces a race condition. The final sum would be non-deterministic and, on any given run, very likely wrong (too small, since some additions would be lost or read stale values), a bug that could pass on some runs and fail on others, making it especially hard to catch without deliberately checking.

Exercise 42.4 [A]. With n = 16,777,216 and block size 256, the naive version launches one thread per element, so it performs 16,777,216 individual atomicAdd calls to the shared result address. The tree-reduction version launches 16,777,216 / 256 = 65,536 blocks, and only thread 0 of each block performs one atomicAdd, for 65,536 total atomic calls: 256x fewer atomics, which lines up with the block size itself and roughly tracks the measured 246.2x speedup (not exactly, since atomics contention isn’t the only cost, but it is the dominant one).

Exercise 42.5 [A]. Starting from temp = [1,1,1,1,1,1,1,1]: - After offset=1: temp = [1,2,2,2,2,2,2,2] (each position from index 1 onward adds its immediate left neighbour’s pre-step value) - After offset=2: temp = [1,2,3,4,4,4,4,4] - After offset=4: temp = [1,2,3,4,5,6,7,8]. This is already the final, correct inclusive prefix sum, since log₂(8) = 3 steps exactly suffice for an 8-element scan.

Exercise 42.6 [E]. This chapter’s own measurements are the direct counter-example to that claim. Tree reduction won by 246.2x because it eliminated massive atomic contention on one global address, while tiling a stencil gave no benefit (0.98x) because this GPU’s automatic L1/L2 caching was already serving the “redundant” neighbour reads tiling targets. Shared memory helps specifically when it avoids real, otherwise-necessary traffic, not automatically, and the only way to know which case applies is to measure both versions on the actual target hardware.

Exercise 42.7 [E]. A stencil with a much larger radius, for example a radius of several hundred elements, as in some large-kernel image filters, would likely benefit from tiling even on this GPU. Per Listing 42.3’s triage logic, a radius that large may exceed what a single L1/L2 cache line’s automatic caching can capture efficiently for every thread’s overlapping reads, making the explicit shared-memory halo genuinely reduce redundant global memory traffic rather than duplicate what the cache was already doing.

Exercise 42.8 [R]. Discussion only, no single answer expected. The Harris whitepaper’s further optimisations include unrolling the last warp’s reduction steps (avoiding unnecessary __syncthreads() calls once only one warp remains active, since a single warp executes in lockstep) and using multiple elements per thread during the initial load to reduce the total number of blocks needed. These would likely shave some additional time off this chapter’s 0.0866 ms tree-reduction result, but the dominant win, eliminating per-thread atomic contention, was already captured by the basic tree pattern. The further optimisations would refine, not fundamentally change, the already-large 246.2x speedup.

Chapter 43 — Kernel Performance Tuning

Exercise 43.1 [W]. Arithmetic intensity is the number of floating-point operations performed per byte of memory moved (FLOPs/byte). A kernel with very low arithmetic intensity falls in the memory-bound regime. Its runtime is set by how fast data can be moved, not by how fast the arithmetic can be computed.

Exercise 43.2 [W]. Occupancy is the ratio of actually-resident warps on a streaming multiprocessor to the hardware maximum it could support. This chapter measures it with cudaOccupancyMaxActiveBlocksPerMultiprocessor, rather than guessing from block size alone.

Exercise 43.3 [A]. Intensity I=8 FLOPs/4 bytes=2I = 8 \text{ FLOPs} / 4 \text{ bytes} = 2I=8 FLOPs/4 bytes=2 FLOPs/byte. Ridge point R=118,600/1,986≈60R = 118{,}600 / 1{,}986 \approx 60R=118,600/1,986≈60 FLOPs/byte. Since I=2<R=60I = 2 < R = 60I=2<R=60, the kernel is memory-bound.

Exercise 43.4 [A]. As REPEAT grows, total time grows (more FMAs per element), but the bytes moved per element stay fixed at 8 (one 4-byte read, one 4-byte write). GB/s is bytes-moved divided by time, so as time grows with no corresponding growth in bytes moved, the GB/s figure necessarily falls. The kernel is doing more compute per byte, not moving more bytes faster.

Exercise 43.5 [A]. 1,536/256=61{,}536 / 256 = 61,536/256=6 blocks per SM by the thread-count cap alone. This matches the measured value of 6 max active blocks/SM at block size 256, confirming thread count (not the 24-block architectural cap, which would allow more) is the binding constraint at this block size.

Exercise 43.6 [E]. Larger blocks don’t automatically mean more parallelism. The occupancy sweep shows block size 1,024 fits only 1 block/SM (32 resident warps), fewer than block size 512’s 48 resident warps, because the 1,536-thread-per-SM ceiling caps how many blocks of a given size can be co-resident. “Maximise threads per block” ignores this ceiling. The actual goal is maximising resident warps, which the sweep shows peaks around block size 256-512, not 1,024.

Exercise 43.7 [E]. Reducing redundant arithmetic (this chapter’s compute-bound remedy) would plausibly help, since it directly reduces the FLOPs the compute-bound kernel must perform. Improving memory coalescing (Chapter 40’s remedy) would not help a confirmed compute-bound kernel, since by definition its runtime is set by FLOPs throughput, not memory bandwidth. Chapter 40’s fixes only pay off in the memory-bound regime.

Exercise 43.8 [R]. Discussion only. The roofline paper’s ridge point is architecture-general (peak FLOPs / peak bandwidth), matching this chapter’s own ridge-point calculation closely. Whether the original paper anticipated GPU-specific caps like resident-blocks-per-SM is a fair question to investigate. The paper’s core roofline concept predates modern GPU occupancy constraints becoming a widely-discussed secondary bottleneck, so the occupancy sweep in this chapter likely extends beyond what the original framing directly covers.

Exercise 43.9 [A]. Block 1024 (theoretical 66.67%) is measured slightly faster (0.1209 ms) than block 64 (theoretical 100%, 0.1218 ms), the opposite of what theoretical occupancy alone predicts. Achieved occupancy correctly predicts this ordering: block 1024’s achieved occupancy (61.80%) is higher than block 64’s (44.00%), matching which one actually ran faster. Theoretical occupancy is a resource-based prediction from launch configuration alone; achieved occupancy, measured from the kernel’s real execution via ncu --section Occupancy, is the number that tracks wall-clock time here.

Chapter 44 — Triton for Kernel Authoring

Exercise 44.1 [W]. In CUDA, “one thread” processes one element. In Triton, the equivalent unit is a “program” (one grid instance), which processes an entire BLOCK_SIZE-sized chunk of data at once via vectorised block operations. There is no per-thread-level programming exposed to the author at all.

Exercise 44.2 [W]. Without the mask argument, tl.load would read past the end of the input tensor for the final block whenever the input length isn’t a multiple of BLOCK_SIZE: an out-of-bounds memory access on exactly the trailing elements beyond the tensor’s true length, for that last program instance.

Exercise 44.3 [A]. A layer-norm kernel needs a mean and a variance reduction rather than a max and a sum: compute mean = tl.sum(row, axis=0) / n_cols, then variance = tl.sum((row - mean) ** 2, axis=0) / n_cols, then normalise as (row - mean) / tl.sqrt(variance + eps) in place of softmax’s max-subtraction-then-exp-then-sum-then-divide sequence.

Exercise 44.4 [A]. This is not a bug because vector add is memory-bound. Its runtime is dominated by how fast data moves through memory, not by which specific block size is used, so multiple mid-range block sizes achieve nearly identical throughput. The autotuner’s benchmarking runs are subject to normal system noise (scheduling jitter, thermal state, background load), so which config comes out narrowly “fastest” on a given run can flip between two functionally-equivalent options.

Exercise 44.5 [A]. Adding triton.Config({'BLOCK_SIZE': 8192}, num_warps=16) is straightforward, but this configuration may perform worse because larger blocks increase register/shared-memory pressure per program instance, which can reduce the number of resident programs an SM can run concurrently. For a memory-bound kernel, oversized blocks add scheduling and resource overhead without a corresponding bandwidth benefit.

Exercise 44.6 [E]. A different tensor shape, for example a much smaller row width, where kernel launch overhead dominates over actual compute, might narrow or reverse the ~0.97x gap, since Triton’s and PyTorch’s fixed per-launch overheads would matter proportionally more than the reduction work itself. A much wider row might widen the gap in whichever direction the two implementations differ in memory-access efficiency at scale.

Exercise 44.7 [E]. Discussion, roughly: “Triton’s compiler still needs a hardware model to reason about. Coalescing and occupancy determine why one block size or grid shape outperforms another, and this chapter’s own autotuning results only make sense once you understand blocks compete for finite SM resources. Triton changes what you write, not what actually executes on the hardware.”

Exercise 44.8 [R]. Discussion only. The Triton paper’s stated goals include productivity (writing GPU kernels at a higher level than raw CUDA) and performance competitive with hand-tuned libraries. Both are directly demonstrated by this chapter’s softmax kernel matching torch.softmax’s (cuDNN-backed) performance with far less code. A goal the softmax example does not exercise is Triton’s support for more complex fused, multi-stage kernels (e.g. full attention kernels) where the compiler’s automatic memory-hierarchy management matters far more than in a single-pass elementwise-then-reduce operation like softmax.

Chapter 45 — Custom PyTorch CUDA Extensions

Exercise 45.1 [W]. The three pieces are: (1) the CUDA kernel itself, which does the actual per-element computation on the GPU; (2) a thin C++ wrapper that unpacks PyTorch Tensor objects into raw pointers (via .data_ptr<float>()) and launches the kernel with a grid/block configuration; (3) a Python-side torch.autograd.Function that tells PyTorch how to call the forward kernel and the backward kernel, so gradients flow through the operation during .backward().

Exercise 45.2 [W]. Calling .forward() directly bypasses torch.autograd.Function.apply(), which is the machinery that actually records the operation onto the autograd graph (registering which backward to call and with what saved context). The kernel still runs and produces a numerically correct forward output, since the forward computation itself doesn’t depend on autograd bookkeeping. But because no graph node was recorded, .backward() later has no path back through this operation, so x.grad ends up None (or gradients simply don’t flow past this point), with no error raised at the point of the mistake.

Exercise 47.1 [W]. y = (x - mean(x)) / sqrt(var(x) + eps) * weight + bias. A naive PyTorch decomposition requires 7 separate operations/kernel launches (confirmed via torch.profiler); a fused kernel computes the same result in 1 launch.

Exercise 47.4 [A]. A max absolute error meaningfully larger than float32’s expected rounding-error range (roughly 1e-6 to 1e-5 for operations of this complexity), for example an error in the 1e-2 or larger range, or an error that grows with input magnitude in a way inconsistent with simple rounding, would indicate a genuine formula bug (e.g. a single-pass vs. two-pass variance formula difference, or an off-by-one in the reduction) rather than floating-point noise. Without this check passing first, “the kernel is 7x faster” would not be trustworthy because a kernel could be fast specifically because it’s doing less work than the correct formula requires. Speed and correctness are independent claims, and a wrong-but-fast kernel is worse than a correct-but-slow one, since its wrong answer would silently propagate downstream.

Exercise 47.6 [E]. Exercise 47.7 [R]. The backward pass for a reduction-then-elementwise operation like LayerNorm needs gradients with respect to both the input AND the learnable weight/bias parameters, and because the forward pass’s mean/variance depend on every element in the row, the backward pass’s gradient for any single input element also depends on every other element in that same row. This requires a second, more complex reduction (summing gradient contributions across the row) that the forward pass, which only needs one reduction to compute the shared mean/variance, doesn’t need to handle.

If the answer is no, as it is for both Collatz and tree traversal, vectorization has nothing to exploit, and the right next move is a different kind of optimization entirely (a compiled/JIT’d loop, or restructuring the traversal to be iterative and batchable, not a NumPy wrapper).

Exercise 52.8 [R]. This is the literal hardware mechanism underneath every “vectorized” NumPy operation in this chapter. NumPy/OpenBLAS’s compiled loops emit instructions like this one (or their AVX-512 equivalents) instead of a scalar multiply repeated in a loop.

Chapter 53 — Parallelism on CPU

Exercise 53.1 [W]. The GIL ensures only one thread executes Python bytecode at a time per process; for CPU-bound work, threads spend essentially all their time wanting to execute bytecode, so they end up serialised regardless of thread count, producing the flat ~1.0-1.1x result. Multiprocessing uses separate OS processes, each with its own interpreter and own GIL, so CPU-bound work genuinely runs concurrently across cores, hence the near-linear scaling.

Exercise 53.2 [W]. Threads are indeed lighter-weight to create than processes, but “lighter-weight” only matters for I/O-bound work, where the GIL is released during waits and threads’ low overhead pays off directly (this chapter’s I/O-bound results show threading scaling as well as multiprocessing, with less overhead). For CPU-bound work, the GIL makes threading’s lightness irrelevant. It still caps effective concurrency at ~1x regardless of overhead, so multiprocessing is required despite its heavier cost.

Exercise 53.3 [A]. (a) CPU-bound → multiprocessing/ProcessPoolExecutor. (b) I/O-bound → threading/ThreadPoolExecutor. (c) CPU-bound → multiprocessing/ProcessPoolExecutor. (d) I/O-bound → threading/ThreadPoolExecutor.

Exercise 53.4 [A]. Using the chapter’s measured ~96x pool-creation overhead: creating a fresh pool per batch costs roughly 96x what the real 5ms of work alone would cost, i.e. close to 480ms per batch instead of ~5ms-plus-negligible-reused-pool-overhead. Across 100 batches, that’s roughly (480ms - 5ms) × 100 ≈ 47.5 seconds of pure avoidable overhead eliminated by creating the pool once outside the loop.

Exercise 53.5 [E]. Benchmarking discipline (Chapter 48) requires warm-up and repeated measurement with reported medians, not single runs. Two “honest” measurements can differ this much if one run included cold-start effects, differing background system load, thermal throttling, or a different number of repetitions/warm-up iterations. Without knowing both measurements’ exact benchmarking methodology, an 48%-vs-33% discrepancy is exactly the kind of gap Chapter 48 warns single or poorly-controlled measurements can produce.

Exercise 53.6 [E]. Architecture: use ThreadPoolExecutor for the I/O-bound HTTP-fetching stage (many concurrent requests, GIL released during network waits) feeding results into a ProcessPoolExecutor for the CPU-bound HTML-parsing stage (genuine multi-core parallelism needed since parsing keeps the GIL busy). Threads handle the waiting-dominated stage; processes handle the compute-dominated stage, matching each stage’s bottleneck to the tool built for it.

Exercise 53.7 [R]. Discussion only. PEP 703 proposes making the GIL optional, allowing true multi-threaded parallelism for CPU-bound Python code. Under a no-GIL build, this chapter’s flat ~1.0x threading result for CPU-bound work would NOT be expected to hold. Threads would be able to execute bytecode genuinely concurrently across cores, and threading should scale similarly to multiprocessing for CPU-bound work, without multiprocessing’s process-spawn and serialization overhead.

Exercise 53.8 [R]. Discussion only. GIL contention patterns for threads mixing CPU and I/O work within the same pool is a common topic Beazley’s talk covers that this chapter’s clean CPU-bound/I/O-bound split does not. Real workloads are often a mix, and contention between threads competing for the GIL when some are CPU-heavy can degrade the I/O-bound threads’ apparent scaling too. This would complicate the “prefer threading for I/O-bound work” recommendation whenever I/O-bound threads share a process with any CPU-heavy work, suggesting the clean recommendation applies most cleanly to workloads that are purely one or the other.

Chapter 54 — Memory & I/O Optimization

Exercise 54.1 [W]. Chunk size 1 forces one Python-level read() system call per single byte (~210 million calls for a 210MB file), each carrying fixed system-call overhead, while 1MB chunks need only ~200 calls total. The overhead is paid per-call, so shrinking the number of calls by six orders of magnitude removes almost all of it. The buffering= parameter only adjusts an additional internal buffering layer on top of already-large read() calls, so its effect is marginal once the dominant per-call overhead is already eliminated by chunk size.

Exercise 54.2 [W]. mmap measured slower on a cold pass because the file’s pages aren’t yet resident in memory. The very first access to each page still triggers a page fault, forcing the OS to load it from disk, which is at least as expensive as a direct read() call plus adds mmap’s own setup overhead. mmap’s advantage only appears on repeated/warm access, where already-resident pages are reached with an ordinary memory access instead of a fresh system call.

Exercise 54.3 [A]. At 256KB chunks, a 50MB file needs approximately 50×1024×1024/(256×1024)=20050 \times 1024 \times 1024 / (256 \times 1024) = 20050×1024×1024/(256×1024)=200 read() calls (50MB / 256KB ≈ 200).

Exercise 54.4 [A]. The chapter’s own class used 120 bytes/object regular vs. 88 bytes/object with __slots__ for a two-attribute class (26.7% reduction). A three-float-attribute Point3D would have a somewhat different absolute byte count, but applying the same proportional reduction to 2,000,000 instances at roughly 120 bytes/object regular gives ~240MB regular vs. ~176MB with __slots__, a savings on the order of 60-65MB, scaling with the actual per-object byte counts for a three-attribute class.

Exercise 54.5 [A]. This chapter’s Trade-offs section predicts negligible difference between preallocation and append-growth for a plain Python list (149.1ms vs. 142.4ms measured). CPython’s amortised growth strategy already avoids the repeated-reallocation cost preallocation is meant to prevent. np.append-in-a-loop is a different case: unlike Python lists, np.append creates an entirely new array on every call (no amortised growth), so it should lose badly to a preallocated np.empty(n) filled by index. The “preallocation doesn’t matter” finding is specific to Python lists, not NumPy arrays.

Exercise 54.6 [E]. __slots__ prevents adding arbitrary attributes at runtime. A Config class that user code monkey-patches with extra attributes would break immediately once __slots__ is added, since assigning an attribute not declared in __slots__ raises an AttributeError. Applying __slots__ “for consistency” without checking each class’s actual usage pattern risks breaking legitimate dynamic-attribute use cases for a memory saving that only matters at genuinely large object counts.

Exercise 54.7 [E]. Fixed-size arrays in lower-level languages like C++ (std::vector) or Java (ArrayList) still benefit from preallocation (reserve()), because unlike CPython’s list (whose growth is already amortised at the interpreter level), these containers’ default growth strategies can involve real reallocation-and-copy costs that reserve() explicitly avoids by allocating the final capacity upfront. The difference is which layer already amortises growth by default.

Exercise 54.8 [R]. Discussion only. A write-heavy access pattern (ACCESS_WRITE) would change the cold-pass comparison because mmap writes are typically deferred/lazily flushed by the OS’s page cache, potentially making mmap writes appear faster than they truly are until an explicit flush/sync, while seek()+write() calls involve explicit, more predictable write-through semantics. A fair write-heavy comparison would need to account for when data is actually guaranteed durable on disk, not just when the Python call returns.

Chapter 55 — Knowing When to Move to GPU

Exercise 55.1 [W]. Arithmetic intensity is the number of FLOPs performed per byte of data moved. Of this chapter’s two measured operations, matmul’s intensity grows with problem size (roughly O(n)O(n)O(n)), while the elementwise operation’s stays constant (~0.25 FLOPs/byte) regardless of nnn.

Exercise 55.2 [W]. The elementwise operation’s arithmetic intensity (~0.25 FLOPs/byte) never grows no matter how large nnn gets. It stays fixed by the operation’s structure (2 FLOPs and 8 bytes moved per element). Since it never crosses the ridge point separating memory-bound from compute-bound, the fixed transfer overhead is never amortised away by more compute, so it never becomes worth the GPU round-trip at any size.

Exercise 55.3 [A]. Matrix-vector: 2n22n^22n2 FLOPs over ∼n2×4\sim n^2 \times 4∼n2×4 bytes moved gives intensity ≈2n2/(4n2)=0.5\approx 2n^2 / (4n^2) = 0.5≈2n2/(4n2)=0.5 FLOPs/byte, constant, independent of nnn. Unlike matmul (whose intensity grows as O(n)O(n)O(n) because FLOPs grow as n3n^3n3 but bytes moved only as n2n^2n2), matrix-vector’s FLOPs and bytes-moved both grow as n2n^2n2, so their ratio never changes with nnn. It behaves like the elementwise operation, not like matmul, and is unlikely to ever cross the ridge point either.

Exercise 55.4 [A]. To locate the crossover on different hardware: sweep matrix sizes by powers of two (or finer) around the expected crossover region, measuring CPU time and full GPU time (including transfer) at each size with proper warm-up and repeated timing (Chapter 48’s discipline) and torch.cuda.synchronize() around GPU timing. Hold fixed: data type (float32 vs. float64 changes both compute and transfer cost), whether pinned memory is used, and background system load. The crossover point is specific to the exact CPU/GPU/PCIe/dtype combination being tested, not a universal number.

Exercise 55.5 [A]. The elementwise op never wins at any tested size in this chapter’s own results (GPU speedup ranges 0.11x-0.98x, never exceeding 1.0x). Batching ten calls into one transfer would amortise the fixed transfer overhead across more actual compute, likely pushing the GPU closer to breakeven or slightly past it, since the operation is dominated by transfer overhead rather than compute at any single-call size tested. Whether batching alone is enough to cross 1.0x depends on the batched array’s resulting intensity, but it’s a more promising lever than leaving the calls unbatched.

Exercise 55.6 [E]. “A 10,000-element sum has an arithmetic intensity that doesn’t grow with data being ‘already on GPU.’ Check whether this specific reduction crosses the ridge point on its own merits before moving it, since a low-intensity glue step can still lose to the CPU (or to staying resident on GPU without an extra host round-trip) purely from its own transfer/compute ratio, independent of what the rest of the pipeline does.”

Exercise 55.7 [R]. Discussion only. One plausible factor: PCIe generation/lane configuration or motherboard chipset specifics on this particular reference rig could cap achievable pinned-memory bandwidth gains below the commonly-quoted figures, which are often measured on different (e.g. server-class, more PCIe lanes) hardware. To confirm, one would need to benchmark the same pinned-vs-pageable comparison across multiple different host/GPU/PCIe configurations and see whether the 1.08x figure is specific to this rig or holds more broadly.

Exercise 55.8 [R]. Discussion only. The roofline paper’s original claim that achievable performance is capped by either memory bandwidth or peak compute depending on arithmetic intensity is directly illustrated by this chapter’s two operations landing on opposite sides of that cap. An aspect the two-operation comparison doesn’t exercise is the paper’s fuller model of multiple ceilings for different optimization levels (e.g. with/without SIMD, with/without cache blocking). This chapter treats each operation as a single point rather than sweeping across optimization levels the way the full roofline model does.

Chapter 56 — Profiling Mixed CPU/GPU Pipelines

Exercise 56.1 [W]. import torch (~780ms) and CUDA context initialisation (~185ms), both present identically in both pipeline versions, together roughly 965ms of fixed, one-time cost swamping the ~140ms real difference between the two loops.

Exercise 56.2 [W]. utilisation_pct = gpu_busy_ns / (wall_clock_seconds * 1e9) * 100. gpu_busy_ns is measured from nsys stats reports (cuda_gpu_kern_sum + cuda_gpu_mem_time_sum, summed across all real kernel launches and memory copies); wall_clock_seconds is the isolated loop’s measured wall-clock time (from Procedure 56.2’s instrumentation), not the whole-process time.

Exercise 56.3 [A]. The ~965ms combined fixed overhead was added identically to both versions’ total times: slow pipeline’s real loop time (239.9ms) plus ~965ms fixed cost plus other overhead ≈ 1,599.1ms total; fast pipeline’s real loop time (97.9ms) plus the same ~965ms plus overhead ≈ 1,432.8ms total. Because a large, equal constant is added to both numbers before they’re compared, the ratio between the two totals (1,599.1/1,432.8 ≈ 1.12x) shrinks dramatically toward 1 compared to the ratio of the actual loop times alone (239.9/97.9 ≈ 2.45x). A fixed additive cost compresses any multiplicative difference between two numbers when it dominates both of them.

Exercise 56.4 [A]. The GPU-busy times are essentially identical between versions (0.851ms vs. 0.849ms, a 0.002ms difference, well within measurement noise), direct proof the GPU performed almost exactly the same amount of real work regardless of which preprocessing code ran. Since the utilisation percentage is GPU-busy-time divided by loop wall-clock-time, and the numerator barely changed while the denominator dropped by more than half (239.9ms → 97.9ms), the utilisation increase (0.35% → 0.87%) is arithmetically forced to come entirely from the loop getting faster, not from the GPU doing more work, which is exactly the CPU-side-fix conclusion the chapter draws.

Exercise 56.5 [E]. “Before concluding GPU optimisation isn’t worth it, check whether that 8% figure was measured as whole-process wall-clock time or as an isolated per-iteration/per-epoch measurement. This chapter’s own example showed a naive whole-process comparison reporting only a 1.12x speedup for a change that was actually a genuine 2.45x once import/init overhead was excluded. The real per-iteration effect of your GPU optimisation could be substantially larger than 8% once fixed startup costs are isolated out of the comparison.”

Exercise 56.6 [E]. Evidence that would justify skipping to step 3 (stream overlap) directly: utilisation is already reasonably high after trying steps 1 and 2 (vectorized preprocessing AND a batch size that’s already been increased as far as memory or the problem allows), yet the CPU is still measurably idle-waiting for the GPU or vice versa within each iteration, i.e., steps 1 and 2 have been genuinely exhausted (not just assumed exhausted) and nsys’s timeline still shows serialized, non-overlapping CPU/GPU phases. Without that evidence, as in this chapter’s Worked Example, where vectorization alone (step 1) more than doubled utilisation, jumping to step 3 would be solving a problem steps 1-2 might have already fixed for a fraction of the implementation complexity.

Exercise 56.7 [R]. Overlapping CPU preprocessing of batch N+1 with GPU computation of batch N (using cudaMemcpyAsync and a second CUDA stream) would let the CPU’s preprocessing work happen concurrently with, rather than strictly before, the GPU’s matmul on the previous batch. Instead of the pipeline’s timeline being [CPU preprocess batch N][GPU compute batch N][CPU preprocess batch N+1][GPU compute batch N+1]... serialized end to end, it becomes closer to [CPU preprocess N+1] running alongside [GPU compute N], hiding the CPU-side wait behind GPU compute time (or vice versa) that would otherwise sit idle. This could raise the fast pipeline’s 0.87% GPU utilisation further without any change to batch size, since it addresses the serialization between CPU and GPU phases directly rather than changing how much work either phase does per batch.

Exercise 57.1 [W]. Never guess which fix to apply. Profile first, always. This chapter uses cProfile (on a representative subset) to rank stages by cumulative time before touching any code.

Exercise 57.2 [W]. Load: csv.reader → pandas.read_csv, predicted by the Memory & I/O Optimization chapter’s “let a C parser do the IO” finding. Exercise 57.3 [A]. 443.9 / 3.7 ≈ 120x larger (wall-clock comparison); using the pure-compute figure, 443.9 / 1.923 ≈ 231x larger. This ratio represents the one-time CUDA context initialisation cost. Nearly all of the 443.9ms cold measurement is process/context setup that only happens once per process, not per-call compute. The warm measurement isolates the actual matmul cost, which the cold measurement almost entirely obscures.

Exercise 57.4 [A]. The wall-clock comparison alone (232.1ms CPU-batched vs. 3.7ms warm GPU) already shows GPU winning, but it doesn’t by itself prove why. This distinguishes “batching helped” from “the GPU is just fast,” which the wall-clock number alone cannot.

Exercise 57.6 [E]. The end-to-end number (9,040.8ms → 496.8ms, 18.2x) answers “how much did the whole investigation improve total pipeline time,” the number a stakeholder actually experiences and the one that matters for a go/no-go decision on the whole project. Reporting only the larger, more impressive-sounding one without the other would obscure which fixes (CPU-side batching, 12.5x of the total) versus GPU offload (the remaining increment to 18.2x) actually did the work.

Exercise 57.7 [R]. GPU utilisation (from the prior chapter’s nsys-based measurement, the fraction of wall-clock time the GPU is actually busy) maps directly onto USE’s “Utilization” component: it answers “how much of the available time was this resource doing work.” “Saturation” would add a different question the raw utilisation number can’t answer on its own: whether work is queuing up waiting for the resource even when it isn’t at 100% utilisation, e.g., whether requests are backing up in a queue for GPU time even at, say, 40% utilisation, which would indicate a scheduling or batching problem distinct from “the GPU isn’t busy enough.” Utilisation alone, as this book’s prior chapter showed, can be low (under 1%) with no saturation at all. The GPU simply isn’t given enough work per call, a different diagnosis than a saturated, queued-up resource would imply.
