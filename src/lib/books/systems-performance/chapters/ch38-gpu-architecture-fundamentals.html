Every chapter before this one in the series treated the GPU as an accelerator requested by name, device='cuda', an instance type on a price sheet, and otherwise left as a black box. That abstraction is the right level almost all the time. But it stops working the moment a workload is slow and you need to know why, or you need to choose between instance types on more than price, or you need to write a kernel yourself. None of that is possible without a real model of what a GPU is and why it is built the way it is. This chapter builds that model from first principles. Not “GPUs are fast,” but specifically what they are fast at, what they are bad at, and the vocabulary, SM, warp, occupancy, Tensor Core, that the rest of this book leans on. It ends with real measurements taken on this book’s reference rig, including a genuinely surprising one about how little a classic textbook cost actually costs on modern hardware.

38.1 Motivation

A CPU and a GPU solve the same underlying problem, do arithmetic on data, with opposite design philosophies. A CPU is latency-optimised. A handful of cores (8-64 on typical hardware), each extremely sophisticated, with deep pipelines, aggressive branch prediction, large caches, and out-of-order execution. The goal is to finish one thread of work as fast as possible, including work full of unpredictable branches and dependent memory accesses. A GPU is throughput-optimised. Thousands of much simpler cores, minimal branch prediction, smaller caches, no out-of-order execution. The goal is to finish millions of largely independent, largely uniform pieces of work as fast as possible in aggregate, even if any single piece takes longer than it would on a CPU.

Neither design is “better.” A GPU is superb at “do this same arithmetic operation to every one of these hundred million numbers,” exactly what torch.matmul, attention, and convolution are, and poor at “run this branchy, pointer-chasing, inherently sequential business logic,” exactly what a CPU is for. The rest of this chapter is about how the GPU achieves that throughput.

38.2 Exposition

All measured numbers in this chapter† come from this book’s reference rig. See the preface.

38.2.1 SIMT: Single Instruction, Multiple Threads

A GPU does not schedule threads individually. It groups them into warps of 32 threads (on all current NVIDIA hardware) and issues one instruction per clock to the entire warp. Every thread in the warp executes the same instruction, on its own slice of data, at the same time. This is why the model is called SIMT (Single Instruction, Multiple Threads), a close cousin of the SIMD (Single Instruction, Multiple Data) vector units covered later in this book’s CPU chapters, but implemented at the level of independent hardware threads rather than a single thread’s vector registers.

This has an immediate, important consequence: warp divergence. If threads within the same warp take different branches of an if/else, for instance because the condition depends on thread_id % 2, the hardware historically had to execute both branches serially for the whole warp, masking off the threads that do not apply to each branch. A badly diverged warp could take as long as the sum of all its branches combined, not the max. Modern architectures (Volta, 2017, onward) added independent thread scheduling, which softens this cost considerably. The Worked Example below measures the real overhead on this book’s reference rig, and it is noticeably smaller than the classic worst-case story predicts, though never exactly zero, and it depends heavily on what is inside the branches.

38.2.2 The Streaming Multiprocessor (SM)

The SM is the GPU’s basic execution unit, the rough equivalent of a CPU core, though the comparison undersells it. Each SM contains many CUDA cores, a warp scheduler able to keep several warps “in flight” and switch between them for free when one stalls on a memory access, a register file, and a slice of fast on-chip shared memory (covered in depth in Chapter 40). A modern high-end GPU has on the order of 100+ SMs. This book’s reference rig has 170 SMs†, queried directly in the Worked Example rather than taken from a spec sheet.

The GPU achieves throughput not by making any single warp fast, but by having so many SMs, each juggling so many warps, that memory-access stalls on one warp are hidden by switching to another warp that is ready to compute. This is latency hiding through massive parallelism, and it is the single most important idea in this chapter. A GPU tolerates slow individual memory accesses by having enormous amounts of other work ready to fill the gap. A CPU instead tries to avoid the stall altogether, through branch prediction, prefetching, and big caches. Different problem, different solution.

38.2.3 CUDA Cores vs. Tensor Cores

CUDA cores are general-purpose ALUs: one thread, one core, ordinary scalar arithmetic (add, multiply, fused multiply-add) in FP32/FP64/INT32. This is what the vector-add and elementwise kernels in Chapters 39-43 run on.

Tensor Cores are specialised units that perform an entire small matrix-multiply-accumulate (D = A×B + C, on 4×4 or larger tiles) in a handful of clock cycles, at far higher throughput per watt than the equivalent done on CUDA cores one multiply-add at a time. This matters enormously for this book specifically. The FLOPs formulas from Book 2, Chapter 29’s transformer training math (6ND for training, 2N for inference) are almost entirely matrix multiplications: QKᵀ, softmax(...)V, the feed-forward layers. That means nearly all of an LLM’s compute budget runs on Tensor Cores, not CUDA cores. A GPU’s advertised TFLOPs number for ML workloads is a Tensor Core number, not a CUDA core number, and the two can differ by an order of magnitude on the same chip.

38.2.4 The Memory Hierarchy, at a Glance

Data has to get to the cores to be operated on, and where it lives changes how fast that is by orders of magnitude:

Registers (per-thread, fastest, smallest)
    ↓
Shared memory (per-SM, fast, programmer-managed, tens of KB)
    ↓
L2 cache (chip-wide, shared across all SMs)
    ↓
Global memory / HBM (off-chip, largest, slowest: but
still roughly 1-2 TB/s on modern GPUs)

This is only the map for now. Chapter 40 is entirely about how to use this hierarchy well, and how badly things go when you do not.

38.3 Trade-offs and Limits

GPUs win at massively data-parallel workloads with uniform control flow: matrix multiply, elementwise ops, convolutions, attention. They win at problems where single-operation latency can be traded for aggregate throughput, and at anything dominated by Tensor Core-eligible matrix multiplication, which is essentially all of deep learning. GPUs lose at branchy, data-dependent control flow that differs per thread, where warp divergence eats the throughput advantage. They lose at small problems that cannot fill the GPU with enough parallel work to hide memory latency, since kernel launch overhead alone is often microseconds: trivial for CPUs, real for tiny GPU jobs. And they lose at anything inherently sequential, where one step depends entirely on the previous step’s result.

38.4 Procedures

Procedure 38.1 (Query Your GPU’s Real Specs). When to use: before sizing any workload. Never plan capacity off a spec sheet when the actual card can be queried directly.

Common mistake: assuming every GPU with the same model name performs identically. Clock speeds, power limits, and even SM counts can differ between vendor SKUs, such as an OEM-underclocked card. Always query, never assume.

Procedure 38.2 (Benchmark GPU vs. CPU Correctly). When to use: any time CPU and GPU performance are being compared. The single most common beginner mistake is timing the first GPU call, which includes one-time CUDA context initialisation and kernel JIT compilation costs that have nothing to do with steady-state performance.

warmup discards the first few calls (context init, JIT compile) before timing, typically 3-10 of them. reps sets how many timed repetitions to take the best, least-noisy result from, typically 10-50. torch.cuda.Event gives GPU-side timestamps, the correct tool for timing async CUDA work, since time.perf_counter() around GPU code without a synchronize() call measures almost nothing. Common mistake: using time.perf_counter() around GPU code without calling torch.cuda.synchronize() first. CUDA calls are asynchronous. Python returns immediately after launching the kernel, not after it finishes. So an unsynchronised wall-clock timer measures launch overhead, not execution time.

Procedure 38.3 (Estimate Achieved Memory Bandwidth From a Timing). When to use: to judge whether an elementwise kernel is running near the GPU’s memory-bandwidth ceiling. A first taste of the roofline thinking formalised in Chapter 43.

Common mistake: comparing achieved bandwidth against the GPU’s compute TFLOPs spec instead of its memory bandwidth spec. An elementwise op like this one does far too little arithmetic per byte moved to ever approach peak FLOPs. It is memory-bound by nature, and the right ceiling to compare against is bandwidth in GB/s, not FLOPs. Chapter 43 formalises this distinction.

Next, the notebook computes c = a*a + b over 100 million elements, first on CPU and then on GPU, using Procedure 38.2’s warm-up-then-CUDA-events discipline. The CPU, timed as the best of three runs with time.perf_counter(), takes 96.5 ms†. The GPU, timed as the best of ten runs with CUDA events after five warm-up calls, takes 1.280 ms†: a 75.4x† speedup, with a correctness check (max abs diff CPU vs GPU) of exactly 0.00e+00. That speedup compares one CPU core’s throughput against the whole GPU. A multi-threaded CPU implementation would close some of the gap, but not most of it, since the GPU’s core-count and memory-bandwidth advantage is structural, not a threading artifact.

This produces 938 GB/s† of achieved bandwidth, against a theoretical peak of roughly 1.5-1.8 TB/s for this GDDR7 card: about 55%† of a 1.7 TB/s peak estimate. That is a reasonable result for a simple elementwise kernel, and the first concrete example in this book of a memory-bound workload. Adding more arithmetic per element would be nearly free here, because the bottleneck is moving bytes, not computing on them.

The notebook’s final experiment measures warp divergence directly, using two Triton kernels that do identical arithmetic (a tight loop of tl.where(cond, ..., ...)) but differ in how the condition splits work across a warp. divergent_kernel uses offs % 2 == 0, which alternates every element, splitting every 32-thread warp roughly 16/16 on every iteration. uniform_kernel uses pid % 2 == 0, uniform across a whole block, so each warp takes only one branch:

If warp divergence cost what the classic, pre-Volta SIMT model predicts, divergent_kernel should take roughly twice as long, since the hardware would serially execute both branches for every diverged warp. The measured result, best of 20 runs on 16.7 million elements with 2000 iterations per element: the divergent kernel takes 0.604 ms†, the uniform kernel takes 0.583 ms†, an overhead of 3.5%†, not the roughly 2x the textbook model predicts. This is a genuine, real finding, not an artifact of the experiment. It is the direct, measurable consequence of independent thread scheduling, introduced in the Volta architecture in 2017 and present on this Blackwell-generation reference rig. The lesson is not that divergence does not matter. It is that the classic mental model is a useful first approximation that overstates the cost on modern hardware, that the actual cost depends heavily on what is inside each branch (cheap arithmetic here; a branch containing a slow memory access or very different work per side would diverge more expensively), and that measuring on the actual target hardware beats trusting a rule of thumb, which is the ethos of this entire book.

38.9 Mental Model

A GPU is a factory with hundreds of assembly lines (SMs), each running dozens of identical, synchronised workers (a warp’s 32 threads) who must all perform the same motion at the same time. The factory’s genius is not that any one worker is fast. It is that when one line’s workers are waiting for a part to arrive (a memory access), the foreman instantly switches them to a different line that already has its parts ready, so the factory floor as a whole never sits idle. Feed it uniform, parallel work and it outproduces anything else available. Give it one worker doing a complicated, branching custom job, and it is slower than a single competent craftsman.
