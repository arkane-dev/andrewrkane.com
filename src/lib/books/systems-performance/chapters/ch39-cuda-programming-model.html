Chapter 38 built a model of GPU hardware, SMs, warps, the memory hierarchy, without writing a single line of code that runs on it. This chapter closes that gap. CUDA (Compute Unified Device Architecture) is NVIDIA’s set of extensions to C++ that let a function be written once, called a kernel, and run unmodified on thousands of threads at once. This is the layer directly beneath every .to('cuda') call in the rest of this series: host code that allocates memory, moves data, and launches kernels; device code that computes. The chapter ends with a real measurement that surprises almost everyone the first time they see it. On a genuine vector-add pipeline, the kernel itself is the smallest part of the total time.

39.1 Motivation

A CUDA program is two programs glued together. Host code is ordinary C++ that runs on the CPU. It allocates GPU memory, copies data across, launches kernels, and copies results back. Device code is the kernel itself. It just computes, as fast and as parallel as the hardware allows, on whatever the host handed it. The host is always in charge. The device never decides on its own what to do next. Understanding this split, and specifically the cost of moving data between the two separate memory spaces, is the single most important practical lesson in learning CUDA, more important at first than anything about the kernel body.

39.2 Exposition

All measured numbers in this chapter† come from this book’s reference rig. See the preface.

39.2.1 Threads, Blocks, and Grids

A kernel launch looks unlike ordinary C++:

myKernel<<<grid, block>>>(args...);

The <<<...>>> syntax specifies how many threads to create and how to organise them, not what they do. That’s the kernel body, shared identically by every thread. CUDA organises threads in a two-level hierarchy. A block is a group of up to 1024 threads that run on the same SM, can synchronise with each other via __syncthreads(), and can share fast on-chip shared memory (Chapter 40). A grid is the full collection of blocks a launch creates. Blocks run independently, potentially on different SMs, in any order, with no way to synchronise across blocks. That independence is exactly what lets the hardware scheduler spread blocks across all available SMs.

Inside a kernel, every thread discovers its own identity from four built-in variables: threadIdx (index within its block), blockIdx (its block’s index within the grid), blockDim (threads per block), and gridDim (blocks per grid). The near-universal pattern for turning this into one flat index is:

int global_id = blockIdx.x * blockDim.x + threadIdx.x;

This line is arguably the single most important line of code in CUDA. Nearly every kernel written for the rest of this book starts with some variant of it.

39.2.2 The Grid-Stride Loop

A natural first instinct is to launch exactly as many threads as there are data elements. This works but is brittle. It hardcodes a relationship between problem size and launch configuration, and for very large n it can exceed hardware limits on grid size. The standard, more robust pattern is the grid-stride loop: launch a fixed, hardware-appropriate number of threads, and have each thread process multiple elements, striding forward by the total thread count:

int stride = blockDim.x * gridDim.x;
for (int i = blockIdx.x * blockDim.x + threadIdx.x;
     i < n; i += stride) {
    c[i] = a[i] + b[i];
}

This works correctly for any n, launched with the same grid/block configuration every time. The launch configuration is tuned once per GPU, not per problem size.

39.2.3 Host <-> Device Memory: Two Worlds, One Bus

The CPU and GPU have physically separate memory. Getting data from one to the other means an explicit copy across the PCIe bus:

// allocate on GPU
cudaMalloc(&d_ptr, bytes);
// CPU -> GPU
cudaMemcpy(d_ptr, h_ptr, bytes, cudaMemcpyHostToDevice);
// ... kernel runs on d_ptr ...
// GPU -> CPU
cudaMemcpy(h_ptr, d_ptr, bytes, cudaMemcpyDeviceToHost);
cudaFree(d_ptr);

This transfer is not free, and it is very often the slowest part of the whole pipeline, not the kernel itself. The Worked Example below measures this directly. A vector-add kernel that takes under a millisecond to compute sits inside a pipeline that spends tens of milliseconds just moving data across PCIe. This is why real systems batch work, keep data resident on the GPU across many kernel launches, and overlap transfers with compute wherever possible: a technique called CUDA streams, which this introductory chapter doesn’t cover in depth but is worth knowing the name of.

39.2.4 Pinned Memory: Why the Transfer Speed Isn’t Fixed

Ordinary host memory allocated with new or malloc is pageable. The OS is free to move it around in physical RAM, or swap it to disk. Because cudaMemcpy needs a stable physical address to hand to the DMA engine that actually drives the PCIe transfer, a pageable-memory copy has to be staged through a temporary pinned buffer first, an extra copy the driver performs invisibly, at a real performance cost.

Pinned (page-locked) memory, allocated with cudaMallocHost instead of new, tells the OS “never move this,” so the DMA engine can transfer directly with no staging copy required. The Worked Example measures the real difference on this book’s reference rig. Switching a vector-add pipeline’s host buffers from pageable to pinned memory cuts the device-to-host transfer time by roughly 5.9x, with no other code change. This is one of the highest-value, lowest-effort optimisations in all of CUDA programming.

39.3 Trade-offs and Limits

Explicit memory management, what this chapter teaches, wins at predictable, measurable transfer costs that can be reasoned about and optimised (pinned memory, overlapping transfers), and at giving maximum control over exactly when data moves. It loses at development speed. Unified Memory (cudaMallocManaged, not covered in depth here) lets code skip explicit copies entirely, at some performance cost and less predictability, and is often the right choice for prototyping. It also loses at ergonomics compared to just writing PyTorch and letting the framework manage memory automatically, which is exactly why the overwhelming majority of ML code never touches any of this directly. Pinned memory itself is not free either. It cannot be swapped, so over-pinning large amounts of host memory starves the OS of memory the rest of the system needs. Pin only the buffers that are actually on a performance-sensitive, frequently-used transfer path.

39.4 Procedures

Procedure 39.1 (Write, Compile, and Run a Minimal Kernel). When to use: the very first raw CUDA program. Confirming the whole toolchain (nvcc, driver, GPU) works end to end.

# replace sm_120 with your GPU's compute capability
nvcc -arch=sm_120 hello.cu -o hello
./hello

Common mistake: forgetting cudaDeviceSynchronize() before the program exits. Kernel launches are asynchronous, and device-side printf output is buffered and flushed on synchronisation. Without it, main() can return, and the process exit, before the device has actually printed anything.

Procedure 39.2 (Write a Kernel That Handles Any Problem Size). When to use: any time the data size isn’t known at compile time, or exceeds what’s wanted as a 1:1 thread-per-element mapping.

block (threads per block) is typically 128-256 and must be a multiple of 32, the warp size. grid (blocks) should be enough to keep every SM busy with several blocks. Over-launching relative to n is fine, since the stride loop covers the rest. Common mistake: launching exactly n threads for every kernel (grid = (n + block - 1) / block) and re-deriving this for every different n in a program. It works, but it’s needless coupling. The grid-stride version allows one good launch configuration per GPU, reused everywhere.

Procedure 39.3 (Move Data Between Host and Device, With and Without Pinned Memory). When to use: every CUDA program that isn’t purely synthetic, and any pipeline where transfer time matters. Nearly all of them.

Common mistake: pinning all of a large application’s host memory “just in case.” Pinned memory can’t be swapped, so over-pinning starves the OS of memory it needs for everything else running on the machine. Pin only the buffers actually on a frequent, performance-sensitive transfer path.

Procedure 39.4 (Time CUDA Work Correctly, With Events). When to use: any time host-side or device-side work needs accurate timing. The same principle as torch.cuda.Event from Chapter 38, one level lower, in raw CUDA C++.

Common mistake: wrapping a host-side clock (std::chrono) around a kernel launch without a synchronisation call. Kernel launches are asynchronous. The host resumes immediately after queuing the launch, so an unsynchronised host-side timer measures launch overhead, not execution time.

39.5 Worked Example

The companion notebook compiles and runs raw .cu files with nvcc, targeting this book’s reference rig’s real compute capability (sm_120, queried live rather than hardcoded), and times a grid-stride vector-add pipeline stage by stage using Procedure 39.4’s CUDA events.

With n = 33,554,432 elements (134.2 MB per array) and ordinary pageable host buffers (new float[n]), the pipeline breaks down as:

H2D transfer (pageable):  19.224 ms
Kernel:                    0.529 ms
D2H transfer (pageable):  54.469 ms
Total:                    74.222 ms

The kernel, the actual computation, is a small fraction of the total time. Almost all of the wall-clock time is spent moving 134 MB arrays across the PCIe bus, in both directions. This is the single most common surprise in anyone’s first real CUDA program. The GPU can be extremely fast at compute and still leave a slow pipeline, because the bottleneck moved somewhere else entirely.

Switching only the host buffers to pinned memory (Procedure 39.3), with the identical kernel and identical problem size:

H2D transfer (pinned):   18.562 ms
Kernel:                   0.463 ms
D2H transfer (pinned):    9.263 ms
Total:                   28.287 ms

One line changed, cudaMallocHost in place of new, and the device-to-host transfer dropped from 54.469 ms to 9.263 ms, roughly 5.9x† faster, cutting total pipeline time from 74.222 ms to 28.287 ms, more than 2.6x† overall. The H2D transfer barely moves (19.224 ms to 18.562 ms) because this particular pipeline only pinned the destination buffer used for the D2H copy in a way that most benefits that direction on this measurement. The dominant, unambiguous win is D2H. The result is bit-identical in both runs (hc[i] == 3.0 for every element, verified by the notebook), confirming the optimisation changes nothing about correctness, only about where the wall-clock time goes.

The lesson generalises beyond this one kernel: before optimising a kernel’s arithmetic, check where the time is actually going. Here, no amount of kernel optimisation could have mattered much, because the kernel was never more than about 2% of the pipeline’s total time on either run.

The NVIDIA CUDA C++ Programming Guide, chapters 2-3, is the authoritative and complete reference for the programming model in this chapter. The NVIDIA CUDA C++ Best Practices Guide’s “Data Transfer” chapter goes deeper on pinned memory, streams, and overlapping transfer with compute. “An Easy Introduction to CUDA C and C++,” on the NVIDIA Developer Blog, is a gentler first pass over the same ground. Fregly’s AI Systems Performance Engineering (Fregly 2026), Chapter 6, works through this same launch-parameter tuning in more depth, including why 256 threads per block is a common starting point and how blocksPerGrid is computed from problem size, worth reading once this chapter’s own launch-configuration choices have been made concrete. Cautaerts and Ghorbanfekr’s GPU-Accelerated Computing with Python 3 and CUDA (Cautaerts and Ghorbanfekr 2026), Chapter 3, walks through this identical programming model using Numba-CUDA instead of raw C++, a direct Python-native counterpart worth comparing line by line against this chapter’s kernels.

39.7 How This Connects

This chapter builds on Chapter 38’s SM and warp model. Blocks map onto SMs, and warps are how a block’s threads actually execute in lockstep. It enables Chapter 40 (shared memory is allocated per block, using exactly the block/thread model introduced here), Chapter 41 (writing real first kernels), and Book 3’s later PyTorch CUDA extension chapters, which wrap exactly this launch syntax underneath a Python-callable interface. It is often confused with Triton, covered later in this book, which replaces explicit thread/block indexing with a higher-level block-of-data abstraction. Understanding this raw model first is what makes Triton’s abstraction read as a convenience rather than magic.

39.9 Mental Model

A kernel launch is a phone tree, not a to-do list. You don’t write “do this to element 1, then element 2, …” You write one instruction sheet (the kernel) and specify how many people get a copy of it (<<<grid, block>>>). Every person on the tree runs the identical sheet, but reads their own name off it first (blockIdx, threadIdx) to know which slice of the work is theirs. The data has to physically reach them, though, and that phone call across PCIe is frequently the slowest step of the entire operation, exactly as this chapter’s measurements showed.
