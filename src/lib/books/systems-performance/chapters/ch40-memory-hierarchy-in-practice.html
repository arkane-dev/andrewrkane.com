Chapter 38 sketched the GPU memory hierarchy as a diagram: registers, shared memory, L2, global memory, fastest to slowest. Chapter 39’s vector-add pipeline showed that moving data can dominate total time even when compute is nearly free. This chapter answers the natural next question. Given that memory access is usually the bottleneck, what actually makes one memory access pattern faster than another, when the amount of data moved is identical? The answer, proven here with real measured numbers rather than asserted, is that how a warp’s 32 threads address memory matters as much as how much data they touch.

40.1 Motivation

DRAM, the technology behind a GPU’s global memory (HBM), is fast at reading large contiguous chunks and comparatively slow at reading many small scattered ones. Physically, a memory controller fetches data in fixed-size bursts (a cache line, commonly 128 bytes). If a request only needs 4 bytes out of that burst, the other 124 bytes were fetched for nothing. A warp issues memory requests for all 32 of its threads at once, so whether those 32 requests land in one burst or scatter across 32 is one of the single biggest levers on a memory-bound kernel’s real-world speed, bigger, often, than any change to the arithmetic itself.

40.2 Exposition

All measured numbers in this chapter† come from this book’s reference rig. See the preface.

40.2.1 Coalescing: One Truck, Not Thirty-Two

If a warp’s 32 threads access 32 consecutive 4-byte floats, 128 bytes total, exactly one burst, the hardware satisfies the entire warp with a single memory transaction. This is a coalesced access. If instead those 32 threads access addresses scattered far apart, the hardware may need up to 32 separate transactions to satisfy the same warp, for the identical amount of useful data: dramatically more total memory traffic for no more actual work done.

The general rule that produces coalescing: have consecutive threads (by threadIdx.x) read or write consecutive memory addresses. This falls out naturally for simple elementwise kernels, as in Chapters 39 and 41, but requires deliberate design for anything involving a transpose, a stride, or a non-trivial 2D data layout. It also falls out naturally for the wrong reason whenever data arrives pre-laid-out as an array-of-structs (AoS) and a kernel only needs one field: each thread’s read of that one field is separated from its neighbour’s by the size of the whole struct, not the size of the field, a partial coalescing loss that the Worked Example measures directly below.

40.2.2 Shared Memory Banks and Bank Conflicts

Shared memory has an analogous, smaller-scale version of this problem. It is physically organised into 32 equal-width banks, one per warp lane, so that ideally all 32 threads in a warp can access shared memory in a single cycle, each hitting a different bank. If two or more threads in a warp instead land on the same bank with different addresses, those accesses serialise: a bank conflict. A tiled matrix transpose is the classic case. Loading a TILE x TILE block into shared memory and writing it back transposed causes every thread in a warp to read from the same bank on the transposed step, if the tile is declared tile[32][32]. The fix is a single line: declare the tile as tile[32][33] instead. One extra column of padding shifts each row’s starting bank by one, so the same transposed access pattern that previously collided onto one bank now spreads naturally across all 32.

40.2.3 Vectorized Loads and __restrict__: When the Bottleneck Is Already Bandwidth

Two more techniques are commonly recommended alongside coalescing: vectorized loads, where each thread moves 4 floats (16 bytes) in one float4 instruction instead of one float in four separate instructions, and the __restrict__ qualifier, which tells the compiler that two pointer arguments never alias, unlocking more aggressive instruction scheduling and the read-only data cache path. Both are real techniques, and both matter in the right circumstances. Neither helps this chapter’s own coalesced-copy kernel, and the Worked Example measures that directly rather than assuming it.

The reason is the same access pattern that made coalescing work in the first place. copyCoalesced already issues one 128-byte transaction per warp. The hardware is already moving the maximum useful data per memory request. float4 changes how many instructions a thread issues to request the same bytes, not how many bytes a warp’s request already covers. It has room to help only when the scalar version was leaving transaction width on the table, which a properly coalesced kernel is not doing. __restrict__ similarly has room to help only when pointer-aliasing uncertainty was forcing the compiler into conservative reloads. This kernel’s in and out pointers are already used in the simplest possible way, one read and one write per thread, with nothing for the compiler to be conservative about.

40.2.4 Registers: The Fastest Tier, and Its Limit

Every local variable in a kernel that the compiler can keep in a register lives in the fastest possible storage, effectively free to access. But registers are a strictly limited, per-SM resource shared across every thread resident on that SM. Use too many registers per thread, and fewer threads or blocks fit on the SM simultaneously, reducing occupancy (Chapter 43). This is why aggressively “optimising” a kernel by unrolling loops or introducing many temporary variables can sometimes make it slower. Occupancy is traded for per-thread speed, and more is lost than gained. nvcc --ptxas-options=-v reports register usage per kernel, making this trade-off visible directly.

40.3 Trade-offs and Limits

Optimising for coalescing and conflict-free shared-memory access wins at any memory-bound kernel, which, per this book’s roofline framing (Chapter 43), is most simple elementwise and data-movement kernels, and at cases where the access pattern can be restructured without changing the algorithm’s result, as in the padding fix above. It’s not worth obsessing over when the kernel is compute-bound (Chapter 43), since memory access pattern matters far less when arithmetic, not data movement, is the bottleneck, or when the data volume is small enough that even a “bad” access pattern completes in negligible time relative to everything else in the pipeline. A common confusion is expecting L2/L1 caching to automatically fix bad access patterns. Caching helps with reuse of the same data, but does not turn a scattered single-use access pattern into a coalesced one. The hardware still has to service the original scattered request from somewhere. float4 and __restrict__ are worth trying on a kernel whose access is already coalesced, but expect them to do nothing once the warp is already issuing full 128-byte transactions, as the Worked Example measures directly. They only have room to help when the scalar version was leaving transaction width or compiler aliasing-safety on the table.

40.4 Procedures

Procedure 40.1 (Write a Coalesced-Access Kernel). When to use: any kernel touching global memory. This should be the default indexing pattern unless there is a specific reason to deviate.

Pattern Address seen by thread i Coalesced?
data[i] base + i * sizeof(T) Yes: the default, correct pattern
data[i * stride] base + i * stride * sizeof(T) No, for stride > 1
data[row * width + threadIdx.x] (2D, threadIdx.x on columns) Consecutive across the warp Yes
data[threadIdx.x * width + col] (2D, threadIdx.x on rows) width elements apart across the warp No

Common mistake: transposing a 2D array’s indexing “to make the math read naturally,” for instance putting threadIdx.x on the row instead of the column because that is how the loop would be written on a CPU, without checking whether it broke coalescing. CPU loop order and GPU coalescing order are not the same consideration. Verify explicitly.

Common mistake: assuming float4/__restrict__ are free wins to apply everywhere. Both change how a thread requests bytes it was already free to request efficiently. Neither changes how many bytes a warp’s request covers when the access was already coalesced. The Worked Example below measures this directly, on this kernel, rather than assuming a textbook result carries over unchanged.

Procedure 40.2 (Avoid Shared Memory Bank Conflicts With Padding). When to use: any kernel using a 2D shared-memory tile accessed along both dimensions: transposes, tiled matrix operations, 2D stencils.

Common mistake: padding “just in case” on every shared-memory array, including ones never accessed with a transposed or strided pattern. Padding costs a small amount of shared memory, itself a limited, occupancy-affecting resource (Chapter 43). Apply it where the access pattern actually causes conflicts, not everywhere reflexively.

Procedure 40.3 (Benchmark Access Patterns on Your Own Hardware). When to use: verifying the coalescing/bank-conflict effect on hardware other than this book’s reference rig, since the magnitude of both effects varies meaningfully by GPU generation and memory technology.

Common mistake: benchmarking without a warm-up kernel launch first. The first CUDA kernel launch in a process pays for context initialisation, which makes both variants look artificially slow and can mask the real difference between them. See Chapter 39’s Procedure 39.4 for the correct warm-up-then-events discipline.

40.5 Worked Example

The companion notebook runs two experiments back to back on this book’s reference rig, using Procedure 40.3’s compile-and-run harness.

Coalescing. Both copyCoalesced and copyStrided (Procedure 40.1) copy the identical number of useful float elements, 16.7 million (n = 1 << 24), with copyStrided using stride = 32, placing consecutive threads’ addresses exactly 128 bytes apart, one full cache line. Timed as the mean of 20 runs with CUDA events after a warm-up launch:

Coalesced copy (stride=1):   0.0715 ms, 1876 GB/s effective
Strided copy (stride=32):    2.3911 ms, 56 GB/s effective
Slowdown from striding: 33.4x

The coalesced version reaches 1876 GB/s†, close to this card’s peak HBM bandwidth. The strided version, moving the exact same 16.7 million useful floats, manages only 56 GB/s†: a 33.4x† slowdown. Nothing about the arithmetic changed between these two kernels. The only difference is the address pattern each warp generates. This is the single highest-leverage lesson in this chapter: access pattern, not data volume, is often the dominant factor in memory-bound kernel performance.

Vectorized loads and __restrict__ on the already-coalesced kernel. The same 16.7-million-element copy, now compared three ways, scalar (Procedure 40.1’s baseline), scalar with __restrict__, and vectorized float4 (Procedure 40.1’s second listing), mean of 20 runs after warm-up:

Scalar (no restrict):    0.0705 ms, 1904 GB/s effective
Scalar (__restrict__):   0.0744 ms, 1803 GB/s effective
Vectorized (float4):     0.0732 ms, 1833 GB/s effective
float4 vs. scalar: 0.96x

All three land within about 5%† of each other, run to run: no measurable, repeatable win from either technique on this kernel. This is a genuine null result, not a failed experiment. copyCoalesced was already issuing one 128-byte transaction per warp, the maximum useful bytes per request, so there was no transaction-width headroom for float4 to claim, and no aliasing ambiguity for __restrict__ to resolve. Both techniques are real and both matter elsewhere. A kernel with a more complex indexing expression, where the compiler cannot prove non-aliasing on its own, or a kernel issuing many small sub-word loads, is a different story. On this specific, already-coalesced kernel, the honest result is that the access pattern was already the whole story.

Array-of-structs vs. struct-of-arrays. Coalescing loss doesn’t only come from a deliberately strided access. It shows up naturally whenever data is laid out as an array-of-structs (AoS) and a kernel only needs one field. Summing one float field across 16.7 million 16-byte Record{x,y,z,w} structs, versus summing the identical field stored in its own contiguous array (struct-of-arrays, SoA), mean of 20 runs:

N = 16777216 Records (16 bytes each), reducing one field (.x) only
AoS (Record[4 floats], read 1 of 4 fields): 0.1641 ms, 409 GB/s useful-field bandwidth
SoA (dedicated float array for that field):  0.0643 ms, 1044 GB/s
Speedup (AoS/SoA): 2.55x

AoS costs 2.55x† SoA here, a real but smaller effect than the stride-32 case above. Each thread’s AoS read is only 16 bytes from the next thread’s, not 128 bytes, so a warp’s request is only partially split, not scattered across separate transactions entirely. This is the exact mechanism Chapter 51 measures on CPU (163.1x at n=1,000,000n=1{,}000{,}000n=1,000,000, a bigger number because CPU cache lines and GPU memory transactions have different granularities and cost structures), applied here to the GPU side of the identical layout decision Chapter 51 argues for: reach for SoA whenever a kernel or a hot loop reduces or scans over one field at a time.

Bank conflicts. The tiled transpose experiment (Procedure 40.2) runs on an 8192x8192 float matrix (268.4 MB), comparing an unpadded tile[32][32] against a padded tile[32][33], mean of 20 runs:

Matrix: 8192x8192 floats (268.4 MB)
WITHOUT padding (bank conflicts): 0.4940 ms, 1087 GB/s
WITH padding (conflict-free):     0.4294 ms, 1250 GB/s
Speedup from padding: 1.15x

Padding gives a real, reproducible 1.15x† speedup (1087 to 1250 GB/s) from a single added column. This is a much smaller effect than coalescing produced, and smaller than some older documentation suggests for pre-Ampere hardware. That’s a real, honest finding, not a weaker result to distrust. Bank-conflict severity depends on the specific access pattern and how much other work already dominates the kernel. The right habit is measuring on the actual target hardware and workload, not assuming a fixed textbook multiplier.

A separate correctness run, on a small 256x256 matrix where every output element can be checked by hand against its expected transposed value, confirms out[y][x] == in[x][y] for every element with the padded kernel. The padding optimisation changes only where the wall-clock time goes, never the result.

40.6 History and Further Reading

The NVIDIA CUDA C++ Best Practices Guide’s “Memory Optimizations” chapter is the authoritative treatment of coalescing and shared-memory bank conflicts. “How to Access Global Memory Efficiently,” on the NVIDIA Developer Blog, works through examples very close to this chapter’s coalescing experiment. “Using Shared Memory in CUDA C/C++,” also on the NVIDIA Developer Blog, is the canonical tiled-transpose-with-padding example this chapter’s second experiment is based on. Fregly’s AI Systems Performance Engineering (Fregly 2026), Chapter 7, covers the same coalescing and bank-conflict material in much greater depth, including the identical 32x33-padding fix for a tiled transpose and warp-shuffle intrinsics as a further alternative to shared memory altogether, worth reading once this chapter’s own padding fix has been measured directly. Cautaerts and Ghorbanfekr’s GPU-Accelerated Computing with Python 3 and CUDA (Cautaerts and Ghorbanfekr 2026), Chapter 5, covers the same memory hierarchy, coalescing, and shared-memory material from Numba-CUDA kernels. Farber’s CUDA Application Design and Development (Farber 2011), Chapters 5-6, is an older but still-accurate treatment of the same global-versus-shared-memory trade-off, predating Volta-class hardware but not the underlying mechanism; its Chapter 6 names the same AoS-versus-SoA coalescing loss this chapter now measures directly above, citing a roughly 5x speedup from NVIDIA’s own thrust teaching example. That figure is larger than this chapter’s measured 2.55x, but the two aren’t directly comparable: Farber’s benchmark sorts an 8-byte, 2-field struct across multiple passes, this chapter’s reduces a 16-byte, 4-field struct in one pass, and the underlying hardware is a decade and a half apart, with modern GPUs’ larger caches generally absorbing some of the coalescing penalty older architectures paid in full. The direction agrees on both; the magnitude was never expected to.

40.7 How This Connects

This chapter builds on Chapter 38’s memory hierarchy diagram and Chapter 39’s host-device transfer costs. This chapter is about on-GPU memory costs, the next link in the same chain. It shares a mechanism with Chapter 51’s CPU-side AoS-versus-SoA measurement: both chapters show the identical layout choice mattering for the identical reason, useful data diluted by unneeded data sharing the same transaction or cache line, just at different absolute magnitudes because CPU cache lines and GPU memory transactions are sized and cost differently. It enables Chapter 42 (parallel patterns like reduction and stencil rely heavily on shared memory, and are only fast when this chapter’s lessons are applied) and Chapter 43 (occupancy and the roofline model build directly on the register and memory-bandwidth trade-offs introduced here). It is often confused with the idea that L2/L1 caching automatically fixes bad access patterns. Caching helps with reuse of the same data, but does not turn a scattered single-use access pattern into a coalesced one.

40.9 Mental Model

Global memory coalescing is a delivery truck, not a fleet of couriers. If a warp’s 32 threads ask for 32 consecutive parcels, one truck picks up the whole street’s mail in one pass. If they ask for 32 parcels scattered across 32 different postcodes, up to 32 separate trips are needed: same total mail, vastly more trips. Shared-memory banking is the same idea at a smaller scale: 32 parallel counters at a post office, one per customer, fast only if no two customers queue at the same counter at once.
