Chapter 39 built the launch syntax and the host/device transfer model. Chapter 40 built the memory-access rules that make one kernel fast and an apparently identical one slow. This chapter is where those pieces combine into something recognisable as real GPU programming: a handful of small, genuine kernels, benchmarked honestly against a CPU baseline, including the uncomfortable case where the GPU loses, which turns out to be exactly as instructive as the cases where it wins. Almost every GPU kernel in production ML is a variation on one of a small number of patterns, and the simplest and most common of them, the map (or elementwise) pattern, is this chapter’s subject.

41.1 Motivation

Vector addition (Chapter 39), SAXPY, and elementwise activation functions like sigmoid or ReLU are all instances of one pattern: the same independent operation applied to every element of one or more arrays, with zero communication between elements. Writing the kernel itself is, at this point, nearly mechanical. Chapter 39 already covered the launch syntax and indexing needed. The genuinely useful content in this chapter is a rigorous, measured answer to the question every beginner asks and every ML framework quietly answers on their behalf: when does the GPU actually win?

41.2 Exposition

All measured numbers in this chapter† come from this book’s reference rig. See the preface.

41.2.1 SAXPY: The “Hello World” of Numerical Kernels

SAXPY (y = a·x + y, “Single-precision A·X Plus Y”) is a BLAS Level 1 operation and one of the most benchmarked kernels in computing history. It’s simple enough to write in one line, and representative enough of real elementwise workloads (including, not coincidentally, the parameter-update step inside SGD-family optimisers) to be a meaningful test rather than a toy.

__global__ void saxpy(int n, float a, const float* x, float* y) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) y[i] = a * x[i] + y[i];
}

41.2.2 The Uncomfortable Result: the CPU Can Win

The Worked Example below benchmarks SAXPY end to end, host-to-device transfer, kernel, device-to-host transfer, against a plain CPU loop, across problem sizes from 1,000 to 100,000,000 elements. The CPU wins at every single size tested. This is not a mistake in the experiment. It is the direct, measurable consequence of Chapter 39’s lesson. A single-shot round trip pays the full PCIe transfer cost every time, and SAXPY is cheap enough, one multiply, one add, per element, that transfer cost dominates kernel cost by one to two orders of magnitude, at every size measured. This is also the single most common way beginners misjudge GPU performance: benchmarking a kernel in isolation, transfer included, and being surprised when the “should obviously be faster” GPU version loses.

41.2.3 The Fix Isn’t a Faster Kernel. It’s Amortisation

Running the identical SAXPY kernel 100 times on data transferred to the GPU once, staying resident there, with the result copied back only after all 100 calls, reverses the single-shot result completely, without changing a single line of the kernel itself. This is the real lesson, and it is the reason every serious ML framework works the way it does. PyTorch keeps tensors resident on the GPU across an entire training loop not because any individual operation strictly needs it, but because round-tripping data to the CPU between every operation would make the “faster” GPU version slower overall. That’s precisely what the single-shot experiment demonstrates directly. .to('cuda') once at the start of a training loop, and staying there, is not a stylistic preference. It is load-bearing for the entire performance case for using a GPU at all.

41.2.4 A Second Map Kernel: Sigmoid

To see the map pattern with a slightly more realistic, and directly ML-relevant, body, this chapter also implements a sigmoid activation kernel (1 / (1 + exp(-x))), using expf(), CUDA’s device-side single-precision exponential, in place of a multiply-add:

__global__ void sigmoidKernel(const float* in, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) out[i] = 1.0f / (1.0f + expf(-in[i]));
}

This kernel has exactly the same shape as SAXPY: one thread, one element, one independent computation. Every elementwise activation function inside a neural network’s forward pass, ReLU, GELU, sigmoid, tanh, is this same map pattern. Only the body of the if (i < n) block changes.

41.3 Trade-offs and Limits

The map pattern, and GPUs generally, win decisively at repeated operations on data that stays resident on the device across many calls, at sufficiently large n that per-call overhead (launch plus any transfer) is a small fraction of total work, and at purely elementwise, branch-free computation. They lose at one-shot operations on host-resident data, regardless of size, exactly as this chapter’s SAXPY sweep demonstrates concretely, and at very small n, where kernel launch overhead alone, microseconds, but real, can exceed the entire CPU computation time. The practical implication is a triage question, not a rule of thumb about GPUs being universally fast. Does this exact operation run once on data that starts on the host, or does it run repeatedly on data that can stay resident? The same kernel, unchanged, can be a clear loss or a clear win depending only on the answer.

41.4 Procedures

Procedure 41.1 (Write a Basic Elementwise/Map Kernel). When to use: any operation applied independently to every element of one or more arrays: activations, elementwise arithmetic, type casts, masking.

Common mistake: omitting the bounds check when n isn’t a clean multiple of the block size. The last block’s threads with i >= n will read or write past the end of the allocated buffer: undefined behaviour, sometimes silent, sometimes a crash. Always include if (i < n) unless it has been proven that n divides evenly into the launch configuration.

Procedure 41.2 (Benchmark GPU vs. CPU Correctly for a Real Decision). When to use: before claiming “the GPU version is faster” in any report or design doc. This chapter’s SAXPY result shows how easily this goes wrong by accident.

Common mistake: reporting GPU speedup numbers measured with amortised (data-resident, many-repeated-calls) timing when the actual production use case is single-shot on host data, or the reverse. State plainly which scenario was measured. The two can differ by an order of magnitude or more, in opposite directions, for the exact same kernel.

Procedure 41.3 (Triage Whether an Operation Is Worth a GPU Kernel). When to use: early design-time, before writing any kernel at all.

Common mistake: skipping this triage and reflexively writing a CUDA kernel for every “slow” CPU loop. This chapter’s own SAXPY sweep is a concrete case where the “obvious” GPU port is a net loss at every size tested. A five-line heuristic, or better, an actual measurement, is far cheaper than finding this out after shipping.

CPU total:  330.70 ms (3.3070 ms/call)

Same kernel, same GPU, opposite conclusion: a 30.2x† GPU win once the transfer cost is spread across 100 calls instead of paid once per call. The only thing that changed between the two experiments is how many times the kernel ran per data transfer. Not the kernel’s code, not the GPU, not the problem size per call. This is precisely why PyTorch, and every serious ML framework, keeps tensors resident on the GPU for the duration of a training loop rather than moving them back to the CPU between every single operation.

41.9 Mental Model

A GPU kernel is a specialist hired by the job, not by the hour, and hiring one has a fixed booking fee (the data transfer) that doesn’t depend on how much work is actually handed over. Hire the specialist once for a tiny task, and the booking fee eats the entire budget. That’s the single-shot SAXPY result. Hire the specialist once and hand over a hundred tasks in a row without sending them home in between, and the fixed fee is spread so thin it barely matters. That’s amortisation, and it is the entire reason ML frameworks keep data resident on the GPU across a whole training loop rather than shuttling it back and forth per operation.
