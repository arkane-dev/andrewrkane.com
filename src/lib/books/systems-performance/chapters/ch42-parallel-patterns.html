Every kernel so far in this book, vector add, SAXPY, sigmoid, has been a map: each thread does its own independent work, with zero communication with any other thread. That pattern covers a surprising amount of real code, but not everything. Summing an array, computing a running total, and blurring an image all require threads to combine or share information with each other. This chapter covers the three canonical patterns for that: reduction (combine many values into one), scan (compute a running combination), and stencil (each output depends on a small neighbourhood of inputs). It produces this book’s most dramatic speedup so far, alongside a genuinely surprising null result that corrects a piece of classic CUDA folklore.

42.1 Motivation

Whenever threads need to communicate, the naive approach routes everything through a single shared point in global memory. And the naive approach is usually dramatically slower than a version that structures communication to happen locally, in shared memory within a block, first, paying the cost of global coordination only once. Every pattern in this chapter is a variation on that one idea. The size of the win from applying it turns out to depend heavily on what the hardware was already doing for you before you intervened, which is why this chapter measures rather than assumes, in both directions.

42.2 Exposition

All measured numbers in this chapter† come from this book’s reference rig. See the preface.

42.2.1 Reduction: Don’t Make Every Thread Fight Over One Address

The obvious way to sum an array in parallel is to have every thread execute atomicAdd(&total, my_value). This is correct. Atomics guarantee correctness even with millions of threads writing to the same address. But every one of those millions of writes serialises against every other one, because they are all contending for the same memory location.

The standard fix is tree reduction. Each block first reduces its own chunk of data locally, in shared memory, using a halving pattern: half the active threads add a neighbour’s value, then half of those continue, and so on, log₂(block size) steps instead of block size sequential adds. Only the final, single per-block result is committed to global memory with an atomic add: one atomic operation per block, not per thread.

__global__ void sumTreeReduction(
    const float* in,
    float* result,
    int n
) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    sdata[tid] = (i < n) ? in[i] : 0.0f;
    __syncthreads();

    for (int s = blockDim.x / 2; s > 0; s >>= 1) {
        if (tid < s) sdata[tid] += sdata[tid + s];
        __syncthreads();
    }
    if (tid == 0) atomicAdd(result, sdata[0]);
}

42.2.2 Warp-Shuffle Reduction: One Step Further Than Shared Memory

Tree reduction already removed the bottleneck of one global address shared by every thread. A further step removes shared memory from the reduction’s first stage entirely. Warp-shuffle intrinsics let threads within the same warp exchange register values directly, without going through shared memory and without a __syncthreads() call. __shfl_down_sync(mask, val, offset) reads val from the lane offset positions higher in the warp. Applying the same halving pattern as tree reduction, but with shuffles instead of shared-memory reads and writes, reduces all 32 lanes of a warp to a single value in log₂(32) = 5 steps, entirely in registers.

A 256-thread block still needs to combine its 8 warps’ partial sums, so a small second stage remains: each warp’s lane 0 writes its partial into an 8-element shared-memory array, one __syncthreads(), then the first warp shuffle-reduces those 8 values the same way. The result is a reduction with far fewer shared-memory reads and writes and fewer __syncthreads() barriers than the pure tree-reduction version, while producing the identical numerical result.

__global__ void sumWarpShuffle(const float* in, float* result, int n) {
    int tid = threadIdx.x;
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    float val = (i < n) ? in[i] : 0.0f;

    // Intra-warp reduction via register shuffle: no shared
    // memory, no __syncthreads()
    for (int offset = 16; offset > 0; offset >>= 1)
        val += __shfl_down_sync(0xffffffff, val, offset);

    __shared__ float warpSums[8];   // 256 threads / 32 = 8 warps
    int warpId = tid / 32, lane = tid % 32;
    if (lane == 0) warpSums[warpId] = val;
    __syncthreads();

    if (warpId == 0) {
        float v = (lane < 8) ? warpSums[lane] : 0.0f;
        for (int offset = 4; offset > 0; offset >>= 1)
            v += __shfl_down_sync(0xffffffff, v, offset);
        if (lane == 0) atomicAdd(result, v);
    }
}

42.2.3 Stencil: a Genuinely Surprising, Honest Result

The classic CUDA optimisation literature teaches that stencil operations, where each output depends on a small neighbourhood, as in a blur, a finite-difference PDE solver, or a convolution, benefit substantially from loading a “tile plus halo” into shared memory once, so overlapping neighbour reads between adjacent threads are served from fast shared memory instead of redundant trips to global memory. This chapter’s Worked Example tests that claim directly, across four variations, and finds no measurable benefit from tiling in any of them on this book’s reference rig. Several results land within a percent or two of the naive version, one even a hair slower. This is a real, reproducible result, not a mistake. Modern NVIDIA architectures (Volta onward) automatically cache global memory reads in an L1 data cache, and this GPU’s 96 MB L2 cache is large enough to hold the entire test array in every variation tested. The “redundant” neighbour reads the classic technique optimises away were already being served from cache. Manual shared-memory tiling was solving a problem the hardware had already solved.

This does not mean shared-memory tiling is generally useless. Chapter 40’s transpose experiment showed a real, if modest, benefit from a related shared-memory technique (bank-conflict padding), and this chapter’s own reduction result shows shared memory delivering the single largest speedup measured anywhere in this book so far. What the stencil result specifically shows is that manual caching of read-only, naturally-overlapping neighbour data is a technique whose value has shrunk as GPU caches have grown. The only way to know whether it helps on a given workload and piece of hardware is to measure, exactly as this chapter did, reporting a null result honestly rather than a fabricated win.

42.2.4 Scan: a Running Combination

A scan (or prefix sum) computes, for each position i, the combination, typically sum, of all elements up to and including i: [1,1,1,1] becomes [1,2,3,4] for an inclusive sum-scan. This underlies cumulative sums directly, but also less obvious operations: stream compaction (removing filtered-out elements while preserving order), and the parallel algorithms behind sorting and building histograms.

This chapter implements the classic Hillis-Steele scan: log₂(n) steps, where at each step every thread adds a value from offset positions back, with offset doubling each step (1, 2, 4, 8, …). It is simple and instructive, though not the most work-efficient algorithm. The Blelloch work-efficient scan does the same job with less total work, at the cost of more implementation complexity, and is worth knowing by name even though it is out of scope for this introduction.

#define N 1024  // single block, one thread per element

__global__ void inclusiveScan(const float* in, float* out, int n) {
    __shared__ float temp[N];
    int tid = threadIdx.x;
    temp[tid] = in[tid];
    __syncthreads();

    for (int offset = 1; offset < n; offset *= 2) {
        float val = 0.0f;
        if (tid >= offset) val = temp[tid - offset];
        __syncthreads();
        temp[tid] += val;
        __syncthreads();
    }
    out[tid] = temp[tid];
}

Note the double __syncthreads(): one after reading a neighbour’s value (ensuring every thread has read before anyone writes), one after writing (ensuring every thread’s write is visible before the next iteration reads). Dropping either introduces a race condition.

42.3 Trade-offs and Limits

Tree reduction wins decisively, close to a strict no-downside upgrade over naive per-thread atomics, at any large-scale aggregation (sum, max, min, mean) whenever the block size divides evenly and shared memory can be spared. Warp-shuffle reduction is worth reaching for on top of tree reduction whenever the aggregation itself, not memory bandwidth, is the bottleneck. It gave a real, repeatable 1.02x further win here, small compared to tree reduction’s own 246.2x, which is the expected shape. The first fix removes the dominant cost. The second trims what is left. Manual stencil tiling is worth trying, not assuming. On hardware with small caches, or with a per-thread neighbourhood large enough to exceed cache reach, tiling can still help substantially. But on modern GPUs with large L1/L2 caches and modest radii, this chapter found no benefit at all, in four separate configurations. Scan wins at any cumulative or order-preserving parallel operation, but the simple Hillis-Steele version used here does O(n log n) total work versus O(n) for a sequential scan, fine at the block sizes shown here, worth revisiting the work-efficient Blelloch variant for very large scans. A common confusion this chapter directly corrects: “shared memory always helps.” It helps when it avoids work the cache would not otherwise do, and no more than that, as the stencil result shows in stark, measured contrast to the reduction result.

42.4 Procedures

Procedure 42.1 (Sum a Large Array Efficiently With Tree Reduction). When to use: any aggregation (sum, max, min) over a large array. Close to a strict upgrade over naive per-thread atomics.

Common mistake: forgetting __syncthreads() inside the reduction loop. Without it, faster threads race ahead to the next iteration and read a neighbour’s value before that neighbour has finished writing. This is a silent, non-deterministic correctness bug, often maddening to debug because it frequently “mostly” produces the right answer.

Common mistake: using a partial warp mask (anything other than 0xffffffff) when every lane in the warp is actually active. __shfl_down_sync needs a mask naming every participating lane. Getting it wrong either hangs the warp or silently reads garbage from an inactive lane.

Procedure 42.2 (Decide Whether Shared-Memory Tiling Will Help a Stencil). When to use: before investing time implementing the more complex tiled-with-halo version of a stencil kernel.

Common mistake: implementing the tiled version reflexively “because that’s what the textbook says to do for stencils,” without first benchmarking the simpler naive version. This chapter’s own measurements found the naive version equal to or faster than the tiled version in every configuration tested. Always benchmark both before committing to the more complex code.

Procedure 42.3 (Write a Block-Level Parallel Scan). When to use: cumulative sums, stream compaction, or any “running combination” computed in parallel, for data that fits in one block. Multi-block scans need an additional combination pass, out of scope here.

Common mistake: using this Hillis-Steele version for very large arrays without realising it does O(n log n) total work, not O(n). Fine at n = 1024; for large-scale production scans over millions of elements, the work-efficient Blelloch algorithm does meaningfully less total work.

A 246.2x† speedup for the mathematically identical result, the largest measured speedup anywhere in this book so far. Both kernels compute the exact same sum. The only difference is whether every one of 16.7 million threads contends for one global memory address, or each block quietly resolves its own contention first, so that only one thread per block ever touches global memory.

Warp-shuffle reduction (Listing 42.2), same array, mean of 20 runs:

Tree reduction (shared):   0.0862 ms, result = 16777216.0 (correct)
Warp-shuffle reduction:    0.0844 ms, result = 16777216.0 (correct)
Speedup from warp shuffle over tree reduction: 1.02x

A real, reproducible† but modest further win: 1.02x, consistent across repeated runs, not noise. This is a much smaller jump than tree reduction’s 246.2x over the naive version, and that is expected. Tree reduction already removed the dominant cost (millions of threads serialising on one address). Warp-shuffle removes a second, smaller cost on top of that: shared-memory traffic and __syncthreads() barrier overhead during the intra-warp stage. Both kernels compute the identical sum. The remaining difference is instruction count and synchronisation overhead, not memory-access pattern.

Tiling is very slightly slower here (0.98x†): a real, honest null result, not noise below measurement resolution. If this result reproduces on your own hardware, that is expected, not a bug. This book’s reference rig automatically caches global memory reads (L1 caching since Volta, plus a 96 MB L2 cache), which already captures the “redundant” neighbour reads the manual tiling technique targets. The lesson is not “tiling is useless.” It is that the classic CUDA optimisation literature was written for hardware with much smaller or no automatic caching of global loads, and claims like this one must be re-measured on the actual target hardware rather than trusted by default.

42.6 History and Further Reading

Harris’s “Optimizing Parallel Reduction in CUDA” (Harris 2007) is the canonical, deeper treatment of reduction, including further optimisations beyond the tree pattern shown here. Blelloch’s “Prefix Sums and Their Applications” (Blelloch 1990) is the original source for the work-efficient scan algorithm named but not implemented in this chapter. Harris, Sengupta, and Owens’s “Parallel Prefix Sum (Scan) with CUDA,” Chapter 39 of GPU Gems 3 (Harris et al. 2007), is a classic reference covering both the Hillis-Steele and Blelloch scans in depth. The “Global Memory” section of the NVIDIA CUDA C++ Programming Guide explains the automatic L1/L2 caching behaviour behind this chapter’s stencil result. Fregly’s AI Systems Performance Engineering (Fregly 2026), Chapter 9, extends this chapter’s tree-reduction pattern into a single fused kernel, computing a per-row L2 norm as a block-level reduction and writing the normalised result in one pass rather than three, worth reading as a preview of the fusion technique this book’s capstone builds on. Farber’s CUDA Application Design and Development (Farber 2011), Chapter 6, covers this same family of parallel patterns (reduction, tiling, stencils) plus the structure-of-arrays-versus-array-of-structures layout choice this book’s Chapter 51 measures on CPU; the specific hardware it targets predates Volta, but the patterns themselves haven’t changed.

42.9 Mental Model

Reduction, scan, and stencil are all instances of one question: when threads need each other’s answers, do they ask a crowded central desk (global memory, atomics) or hold a local team huddle first (shared memory, block-local computation)? The huddle almost always wins when the central desk would otherwise be hit by every single thread: reduction’s atomics, and this chapter’s most dramatic number. It does not automatically win when the hardware was already quietly running an equivalent huddle on your behalf: the stencil’s null result. The only way to know which situation applies is to measure, in both directions, exactly as this chapter did.
