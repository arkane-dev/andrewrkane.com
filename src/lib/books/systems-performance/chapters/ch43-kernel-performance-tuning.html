Every experiment so far in this book’s kernel chapters has produced a number, a speedup, a bandwidth figure, an honest null result, without a unifying framework for predicting which kind of result to expect before measuring. This chapter supplies that framework: the roofline model, which tells you in advance whether a kernel’s ceiling is set by memory bandwidth or by compute throughput, and occupancy, which explains why a functionally identical kernel can run at wildly different speeds depending on launch configuration alone. Every prior chapter’s result, Chapter 40’s large coalescing effect and small bank-conflict effect, Chapter 42’s dramatic reduction speedup and its stencil null result, is an instance of the one curve this chapter makes explicit.

43.1 Motivation

Every kernel has an arithmetic intensity: the ratio of floating-point operations performed to bytes of memory moved, in FLOPs/byte. A kernel with low intensity, little computation per byte, like the elementwise operations in Chapter 41, is memory-bound. Its runtime is set by how fast bytes can move, and doing more arithmetic per byte is nearly free until intensity gets high. A kernel with high intensity, lots of computation reusing the same bytes, like the reduction in Chapter 42, or dense matrix multiplication, is compute-bound. Its runtime is set by the GPU’s FLOPs throughput, and moving more bytes stops being the bottleneck. The roofline model plots achievable performance (GFLOP/s) against arithmetic intensity: a sloped line (the memory-bandwidth ceiling) at low intensity, a flat line (the compute-throughput ceiling) at high intensity, meeting at a knee: the intensity at which a kernel transitions from one regime to the other.

43.2 Exposition

All measured numbers in this chapter† come from this book’s reference rig. See the preface.

43.2.1 The Roofline, Measured Directly

A single kernel, read one element, apply REPEAT fused multiply-adds, write one element, sweeping REPEAT from 1 to 65,536 controls arithmetic intensity directly. More FMAs per element, the same two memory operations (one read, one write), so intensity scales linearly with REPEAT. The Worked Example below traces this curve almost exactly as the model predicts. At low REPEAT, achieved bandwidth stays flat near this card’s peak HBM bandwidth while GFLOP/s climbs: the memory-bound region, where adding more arithmetic is nearly free because the GPU is waiting on memory either way. Around REPEAT in the low hundreds, the curve bends: the knee, where compute time and memory time become comparable. At high REPEAT, achieved GFLOP/s plateaus regardless of further intensity increases: the compute-bound region, at a ceiling set by this GPU’s FP32 CUDA-core peak throughput, not by memory at all.

43.2.2 Occupancy: Why Launch Configuration Alone Changes Performance

Occupancy is the ratio of actually-resident warps on an SM to the maximum the hardware could support. Low occupancy means an SM has fewer warps available to switch to when one stalls on a memory access (Chapter 38’s latency-hiding argument). The SM idles more often, waiting. Sweeping block size (32 to 1,024 threads) for an identical compute-heavy kernel, measuring both real wall-clock time and actual occupancy via cudaOccupancyMaxActiveBlocksPerMultiprocessor (a genuine CUDA runtime query, not a guess), traces out a clean U-shape. Very small blocks waste an architectural cap on resident blocks per SM. Very large blocks waste this GPU’s cap on resident threads per SM, because too few blocks fit simultaneously. A middle band satisfies both caps at once and wins. Both ends of this curve are real, measured architectural limits on this specific GPU, queried directly rather than estimated: a maximum of 1,536 threads per SM, and an implied cap of 24 resident blocks per SM. Register usage was checked and ruled out as the limiting factor. Only 8 registers/thread, nowhere near enough to explain the slowdown at the largest block size. The lesson: the same kernel, completely unchanged, can run meaningfully slower purely from a launch configuration that under- or over-commits the SM’s resident-thread budget.

43.2.3 Instruction-Level Parallelism: A Third, Independent Lever

Occupancy answers “does an SM have enough warps to switch to when one stalls?” A question about thread-level parallelism, hiding one warp’s stall behind another warp’s work. A separate question remains even at fixed, already-good occupancy. Does a single thread have enough independent work in flight that the SM’s execution units stay fed between one instruction issuing and its result being needed? This is instruction-level parallelism (ILP), and it is the answer to a question ch43’s own occupancy sweep sets up but does not resolve. Block size 128 already hits full occupancy. What is left to tune once occupancy is fixed?

A kernel with 200 sequential fused-multiply-adds, each depending on the previous FMA’s result (acc = acc * a + b, repeated), forces the hardware to wait for each FMA’s latency before issuing the next: a dependency chain. The identical total arithmetic, split across four independent accumulators with no dependency between them, lets the SM keep multiple FMAs in flight simultaneously. While one accumulator’s FMA is still completing, another accumulator’s FMA can already issue. Same FLOP count, same block size, same occupancy. The only difference is whether the compiler and hardware have independent work to overlap.

43.3 Trade-offs and Limits

Optimising arithmetic intensity, moving a kernel rightward on the roofline, helps when a kernel is confirmed memory-bound and there is slack compute capacity to exploit, for instance by fusing multiple elementwise operations into one kernel (Chapter 47’s capstone) so several operations share one memory round trip. It is wasted effort when the kernel is already compute-bound. Chapter 42’s reduction result shows that adding a memory optimisation to an already-fast, compute-appropriate kernel yields nothing, because memory was never the bottleneck for that kernel. Tuning occupancy via block size helps whenever a kernel has enough independent work per thread that latency hiding matters, compute-heavy kernels, as tested here, and matters far less for kernels that are already deeply memory-bound and bandwidth-saturated at almost any reasonable block size, as Chapters 39-41’s elementwise kernels showed, running near-peak bandwidth even at a default 256-thread block. A common confusion this chapter directly corrects: “more threads is always better,” or “more shared memory is always better.” Both this chapter’s block-size sweep and Chapter 42’s stencil result are concrete counter-examples. Past a hardware-specific point, more of either resource reduces achievable parallelism rather than increasing it. Restructuring for ILP helps once occupancy is already at its sweet spot and a kernel still has a long sequential dependency chain per thread. It does nothing for a kernel that is already occupancy-limited or memory-bound, since neither of those bottlenecks is about how independent one thread’s own instructions are.

43.4 Procedures

Procedure 43.1 (Classify a Kernel as Memory-Bound or Compute-Bound). When to use: before choosing any optimisation strategy. The right fix is completely different depending on the answer.

Common mistake: optimising memory access patterns (Chapter 40’s coalescing, tiling) on a kernel that is actually compute-bound. Chapter 42’s stencil result is the concrete proof this does not help. Always classify first.

Procedure 43.2 (Sweep Block Size to Find the Occupancy Sweet Spot). When to use: tuning a new kernel’s launch configuration, rather than assuming the “obvious” choice (e.g. always 256) is right for a specific kernel and GPU.

Common mistake: assuming higher occupancy always means faster. It is a necessary condition for hiding memory latency, not a sufficient one. A compute-bound kernel already saturating the SMs’ ALUs will not speed up further from more occupancy. Measure wall-clock time, not just occupancy, to confirm.

A second, sharper common mistake: trusting cudaOccupancyMaxActiveBlocksPerMultiprocessor’s number as what actually happened at runtime. It is a resource-based prediction from launch configuration alone, computed before the kernel ever runs. ncu --section Occupancy ./yourprogram reports Achieved Occupancy alongside Theoretical Occupancy for comparison, measured from the kernel’s real execution rather than calculated from its resource footprint. The Worked Example below measures both across the same six block sizes and finds achieved consistently below theoretical, sometimes by more than half.

Procedure 43.3 (Check Register and Shared-Memory Usage Per Kernel). When to use: diagnosing why a kernel’s occupancy is lower than expected.

Common mistake: seeing “spill stores/loads” in the ptxas output and ignoring it. Register spilling means the compiler ran out of fast register space and is using much slower local memory (physically global memory) instead. It is a correctness-neutral but performance-significant regression, easy to miss if only compile errors are checked.

Procedure 43.4 (Break a Long Dependency Chain Into Independent Accumulators). When to use: a compute-heavy kernel is already at its occupancy sweet spot (Procedure 43.2) and still spends most of its time in one long sequential chain of dependent instructions per thread.

Common mistake: adding more accumulators (or unrolling further) without checking register usage against Procedure 43.3. More independent state means more live registers; past some point, extra accumulators push a kernel into the same register-pressure-reduces-occupancy trap this chapter’s occupancy section warns about, trading one bottleneck for another instead of removing it.

43.5 Worked Example

The companion notebook runs both sweeps on this book’s reference rig (170 SMs, 1,536 max threads/SM), using the same nvcc-compile-and-run harness as Chapters 40-42.

Roofline sweep (read one element, REPEAT FMAs, write one element, n = 1 << 24):

REPEAT   time(ms)   GFLOP/s      GB/s  FLOPs/byte
     1     0.0671     499.7    1998.9        0.25
     4     0.0676    1984.7    1984.7        1.00
    16     0.0850    6313.6    1578.4        4.00
    64     0.0753   28537.5    1783.6       16.00
   256     0.1009   85163.5    1330.7       64.00
  1024     0.2985  115093.5     449.6      256.00
  4096     1.1830  116174.7     113.5     1024.00
 16384     4.6439  118383.1      28.9     4096.00
 65536    18.3400  119903.0       7.3    16384.00

Read left to right, this table is the roofline model, measured rather than drawn. GB/s starts near this GPU’s peak memory bandwidth (1998.9 GB/s† at REPEAT=1) and stays roughly flat through REPEAT=64 while GFLOP/s climbs: more computation “for free” out of the same memory traffic. Past the knee, around REPEAT=256, GFLOP/s plateaus near this GPU’s compute ceiling (119,903 GFLOP/s†, about 120 TFLOP/s, at REPEAT=65536) while GB/s falls. The arithmetic itself is now the bottleneck, and no amount of memory optimisation would help further. The theoretical ridge point, 118,600 GFLOP/s / 1,986 GB/s ≈ 60 FLOPs/byte, lines up closely with the measured knee between REPEAT=64 (16 FLOPs/byte, still memory-bound) and REPEAT=256 (64 FLOPs/byte, just past the knee).

Occupancy sweep (compute-heavy kernel, 200 FMAs/element, six block sizes):

     block       time(ms)    max active blk/SM       warps/SM
        32         0.2610                   24             24
        64         0.1218                   24             48
       128         0.0868                   12             48
       256         0.0897                    6             48
       512         0.0918                    3             48
      1024         0.1209                    1             32

The U-shape is direct and measured. Block size 32 is slowest at 0.2610 ms, limited by an architectural cap of 24 resident blocks/SM before warp capacity (48 warps/SM) is reached. Block size 128 is fastest at 0.0868 ms†, where the thread-count cap (1536/128 = 12 blocks) exactly saturates 48 warps/SM. Block size 1,024 slows back down to 0.1209 ms because this GPU’s 1,536-max-threads-per-SM limit allows only one block of 1,024 threads to be resident, wasting 512 threads of headroom. Querying this book’s reference rig directly confirms the mechanism: max_threads_per_multi_processor = 1536, so 1536 // 512 = 3 blocks/SM fit exactly at the sweet spot, while 1536 // 1024 = 1 block/SM fits at the worst-measured size, wasting 1536 % 1024 = 512 threads. A --ptxas-options=-v check confirms this kernel uses only 8 registers/thread with zero spill. Register pressure is ruled out as a cause, leaving the block/thread occupancy caps as the entire explanation for the roughly 40% swing between the fastest and slowest block sizes tested, on the exact same kernel logic.

Theoretical vs. achieved occupancy. Everything above comes from cudaOccupancyMaxActiveBlocksPerMultiprocessor, a resource-based calculation from launch configuration alone: a prediction, not a runtime measurement. ncu --section Occupancy measures what actually happened, on the identical kernel and identical six block sizes:

     block   theoretical %    achieved %
        32              50         18.44
        64             100         44.00
       128             100         84.73
       256             100         84.03
       512             100         85.24
      1024           66.67         61.80

Achieved occupancy is lower than theoretical at every single block size†, sometimes drastically: block 64 is predicted at a perfect 100% but only reaches 44.00%. This is real, not a rounding artefact: theoretical occupancy answers “how many warps could be resident, given this kernel’s resource footprint,” while achieved occupancy answers “how many warps actually were resident, on average, across the kernel’s real, imperfect launch and completion tail.” The two numbers also rank block sizes differently than expected. Block 64’s theoretical occupancy (100%) beats block 1024’s (66.67%), but block 64’s achieved occupancy (44.00%) is lower than block 1024’s (61.80%), and block 64’s measured wall-clock time (0.1218 ms) is in fact slightly slower than block 1024’s (0.1209 ms), the opposite of what theoretical occupancy alone would predict. Achieved occupancy is the better predictor of the two here, but still not a perfect one: block 512 has the single highest achieved occupancy of the six (85.24%), yet block 128, at 84.73%, is still the fastest kernel measured. Occupancy, of either kind, is one real, measured factor among several, not the entire story on its own, exactly Procedure 43.2’s original warning, now with the runtime-measured number to back it up rather than only the resource-calculated one.

ILP sweep (Procedure 43.4’s two kernels, both at block size 128, the occupancy sweet spot found above, held fixed):

block=128, 200 FMAs/thread, n=16777216
Single dependency chain:   0.0873 ms, 76908.9 GFLOP/s
Four independent chains:   0.0723 ms, 92784.1 GFLOP/s
Speedup from ILP (4 chains vs 1): 1.21x

A real, repeatable 1.21x† speedup from restructuring the same total arithmetic into independent work, at identical occupancy: block size 128 for both kernels, both already at this GPU’s 48-warps/SM ceiling. --ptxas-options=-v confirms occupancy genuinely was held constant, not accidentally changed: the single-chain kernel uses 8 registers/thread, the four-chain kernel 10, both far below any register-count occupancy limit on this GPU. This isolates the effect Procedure 43.2’s sweep could not show on its own: occupancy determines whether an SM has other warps to switch to. ILP determines whether one warp’s own instruction stream keeps the SM’s execution units busy while any single instruction’s result is still in flight. Both matter, and they are independent levers, not the same lever measured two ways.

43.9 Mental Model

The roofline model is a speed limit sign with two different limits depending on the road. On the open highway, low arithmetic intensity, plenty of “road” (memory bandwidth) relative to how much “driving” (compute) is being done, speed is capped by how fast data can safely travel, the memory bandwidth ceiling. In a school zone, high arithmetic intensity, lots of compute crammed into every byte moved, speed is capped by the work itself, not the road, the compute ceiling. Occupancy is a separate question entirely: how many lanes of that highway are actually open. Close too many lanes (too few resident warps) and traffic backs up even below the speed limit. Try to cram too many oversized vehicles into too few lanes (blocks too large for the SM’s capacity) and the same result appears from the other direction.
