Every CUDA kernel written so far in this book has demanded C++, manual memory management, a separate nvcc compile step, and hand-tuned launch configuration swept by brute force. That is a real barrier: most ML engineers who need one fused operation that doesn’t exist in PyTorch are not C++ systems programmers and shouldn’t have to become one to get it. Triton, originally from OpenAI, now the kernel-authoring language underneath PyTorch’s torch.compile, vLLM, and most modern LLM inference engines, solves this by letting you write a kernel in a Python-embedded DSL at a higher level of abstraction than raw CUDA, while its compiler generates GPU code competitive with hand-tuned CUDA on real workloads. This chapter builds a numerically-stable softmax kernel from scratch and shows it matching PyTorch’s native implementation, then automates launch-configuration tuning with @triton.autotune, turning the previous chapter’s manual sweep into a one-line decorator.

44.1 Motivation

The single biggest conceptual shift from CUDA to Triton is this: CUDA programs in terms of individual threads; Triton programs in terms of blocks of data. In CUDA, you write the body of what one thread does and reason explicitly about threadIdx, warps, and per-thread register usage. In Triton, you write the body of what happens to one block (a BLOCK_SIZE-sized chunk) at a time, using operations like tl.load, tl.sum, and tl.max that act on the whole block at once. Triton’s compiler handles the mapping onto individual threads, register allocation, and much of the memory-coalescing work automatically.

This does not mean the hardware model from earlier chapters stops applying. It is still SMs, warps, shared memory, and the roofline underneath. It means Triton takes over a layer of the mechanical work of expressing that model against real hardware, freeing you to focus on the algorithm rather than the plumbing.

44.2 Exposition

44.2.1 A Familiar Kernel, at a Higher Level

A vector-add kernel makes the shift concrete:

@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask)

Compare this to the raw-CUDA equivalent from earlier chapters. The shape is recognisably the same: a program_id/blockIdx for identity, an offset computation, a bounds mask, load-compute-store. But tl.arange(0, BLOCK_SIZE) and the vectorised tl.load/tl.store operate on an entire block of BLOCK_SIZE elements as a single operation, not one element per thread. Triton’s compiler decides how to map that block-level operation onto actual warps and threads, including memory coalescing, and you get much of that optimisation for free for patterns Triton’s compiler recognises well.

44.2.2 A Real, Non-Trivial Kernel: Softmax

A numerically-stable row-wise softmax, subtracting the row max before exponentiating, the standard trick to prevent overflow, can be written using tl.max, tl.exp, and tl.sum as block-level reductions, with no explicit shared-memory tree reduction required. Triton generates that from the block-level tl.max/tl.sum calls itself.

All measured numbers in this chapter† come from this book’s reference rig. See the preface. Measured on that hardware, a hand-written Triton softmax kernel matched PyTorch’s native torch.softmax: 0.0727 ms† versus 0.0735 ms†, a ratio of 0.99x† (Triton fractionally faster), a genuinely notable result for an introductory kernel. This is exactly why Triton has become the standard tool for writing custom fused operations in modern ML systems: the abstraction cost is low enough that hand-written kernels can compete with vendor-optimised libraries on real workloads.

44.2.3 Autotuning: Automating the Manual Sweep

The previous chapter swept block sizes by hand: launching, timing, and comparing manually. Triton automates exactly this with the @triton.autotune decorator:

@triton.autotune(
    configs=[
        triton.Config({'BLOCK_SIZE': 256}, num_warps=2),
        triton.Config({'BLOCK_SIZE': 1024}, num_warps=4),
        triton.Config({'BLOCK_SIZE': 4096}, num_warps=8),
        # ...
    ],
    key=['n_elements'],
)
@triton.jit
def add_kernel_autotuned(...):
    ...

The first time the kernel runs for a given value of the key parameters (here, n_elements), Triton actually benchmarks every listed configuration and caches the winner. Subsequent calls with the same key skip straight to the fastest configuration found. This is the same kind of search the previous chapter did by hand, done automatically, and re-done automatically if hardware or input size changes.

44.3 Trade-offs and Limits

Triton wins at custom fused operations not available in PyTorch or cuDNN, especially elementwise-plus-reduction patterns like normalisation, softmax, and activation-fused-with-something-else, at rapid iteration (no separate C++ compile step, ordinary Python debugging tools mostly work), and at portability across NVIDIA and AMD GPUs from the same source (not exercised on this book’s NVIDIA-only reference rig, but a real Triton advantage). Raw CUDA still wins at maximum control over every hardware detail, specific shared-memory bank layouts, warp-level primitives Triton doesn’t expose, at kernels Triton’s compiler doesn’t schedule well, typically highly irregular, non-block-structured algorithms, and in situations that need to call vendor libraries or hardware features with no Triton binding yet. Neither tool subsumes the other. The choice is a function of how regular the access pattern is and how much manual control the specific optimisation needs.

44.4 Procedures

Procedure 44.1 (Write and Launch a Basic Triton Kernel). When to use: any elementwise or simple block-parallel operation you’d otherwise write in raw CUDA.

Common mistake: forgetting the mask argument to tl.load/tl.store. Unlike raw CUDA, where you write an explicit if (i < n) per thread, Triton’s block-level tl.load will read past the array boundary for the last block unless masked. This is usually a silent correctness bug (reading garbage or another array’s memory), not a crash.

Procedure 44.2 (Write a Row-Wise Reduction Kernel). When to use: any operation that reduces across one dimension per row: softmax, layer norm, any per-row normalisation.

Common mistake: skipping the max-subtraction step. exp() of a large positive number overflows to inf in float32 well before you’d expect: exp(89) already overflows fp32, and real model logits can exceed that range. The “obvious” direct-exponentiate softmax is a genuine, easy-to-hit numerical bug, not just a theoretical concern.

Procedure 44.3 (Autotune a Kernel’s Launch Configuration). When to use: any kernel where the best BLOCK_SIZE/num_warps isn’t obvious, or varies by input size or hardware.

Common mistake: using a fixed-size grid tuple (e.g. grid = (64,)) with an autotuned kernel. Since BLOCK_SIZE changes between configs, the grid size needed also changes. Always use a lambda that recomputes grid size from meta['BLOCK_SIZE'] for autotuned kernels.

44.6 History and Further Reading

Triton originates from Tillet, Kung, and Cox’s paper, “Triton: An Intermediate Language and Compiler for Tiled Neural Network Computations” (Tillet et al. 2019), which introduced the tile-based programming model this chapter’s block-level operations are built on. The official Triton tutorials at triton-lang.org cover the softmax and matrix-multiplication kernels this chapter’s softmax example is based on, in more depth. PyTorch’s torch.compile documentation explains how Triton is invoked automatically inside modern PyTorch, which is worth reading against this chapter’s hand-written approach. For a sense of what production Triton kernels look like at scale, the attention kernels in vLLM’s source tree (vllm/attention) are a genuinely useful, if advanced, reference. Fregly’s AI Systems Performance Engineering (Fregly 2026), Chapter 14, covers Triton’s programming model in the context of torch.compile and TorchInductor, including torch.library.triton_op for registering a hand-written Triton kernel so the compiler can fuse it with surrounding operations, worth reading once this chapter’s own softmax kernel has been written and benchmarked directly.

44.7 How This Connects

This chapter builds on every prior chapter in this book’s GPU-kernels sequence. Triton doesn’t replace the hardware model of SMs, warps, and memory coalescing. It’s a different way of expressing programs against that same model. It enables Chapter 45 (custom PyTorch CUDA extensions are the alternative path to a custom PyTorch op: these two chapters present competing answers to the same problem) and Chapter 47 (the capstone fused kernel is written in Triton). It is often confused with torch.compile: torch.compile can generate Triton kernels automatically from ordinary PyTorch code, whereas this chapter is about writing Triton kernels by hand for cases automatic generation doesn’t reach: novel fusions, algorithms torch.compile doesn’t recognise.

44.9 Mental Model

CUDA hands you a box of individual bricks and asks you to describe what one brick does. Triton hands you a pallet of bricks already organised into blocks and asks what happens to one pallet at a time. The same wall gets built, but you’re reasoning at the level the wall actually needs, and the compiler handles the brick-by-brick logistics of laying it down efficiently.
