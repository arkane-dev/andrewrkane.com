Chapter 44 covered Triton, the modern Python-first way to write custom GPU kernels. This chapter covers the other real path: writing raw CUDA in the style of Chapters 39-43, and wiring it into PyTorch as a first-class operation, complete with autograd support, so it works inside .backward() calls exactly like any built-in torch function. This is the path most existing custom CUDA operations in the PyTorch ecosystem actually use, including many inside PyTorch itself, and it gives full, unrestricted access to CUDA. Anything the earlier hand-written-kernel chapters could express, this chapter lets you plug directly into a training loop.

45.1 Motivation

A PyTorch CUDA extension has three pieces: the CUDA kernel itself (unchanged from earlier chapters), a thin C++ wrapper that unpacks PyTorch Tensor objects into raw pointers the kernel can use, and a Python-side torch.autograd.Function that tells PyTorch how to call the forward kernel and, critically, the backward kernel, so gradients flow through the custom operation correctly during training. torch.utils.cpp_extension.load_inline is the fastest way to build this: pass CUDA and C++ source as Python strings, and PyTorch compiles them just-in-time via nvcc and the system C++ compiler, coordinated by ninja, caching the compiled .so for subsequent runs.

45.2 Exposition

45.2.1 Wiring a Kernel Into Autograd

The Worked Example below implements Squared ReLU (f(x) = relu(x)^2), an activation function used in some transformer feed-forward variants. It needs both directions: the forward pass, y = relu(x)^2, and the backward pass, dy/dx = 2*relu(x) (zero for x <= 0, 2x for x > 0), the ordinary calculus derivative, computed in a second CUDA kernel.

ctx.save_for_backward is how information crosses from forward to backward. Without it, the backward pass would have no way to know what x was. A trustworthy custom op has to clear two correctness bars before it belongs in a real training loop: the forward output must match the native expression exactly, and the gradient must match PyTorch’s own autograd-computed gradient on that same native expression exactly. A subtly wrong gradient can silently degrade training for weeks before anyone notices, with no error thrown at any point.

45.2.2 The Real Payoff: Fusion

Computing relu(x) ** 2 in native PyTorch is two separate kernel launches, one for relu, one for the square, with the intermediate relu(x) result written to and then read back from global memory between them. The custom kernel does both in one launch, one memory pass: read x once, compute both operations while the value is already in a register, write the result once. This is Chapter 43’s roofline model in action: fusing two memory-bound operations into one halves the memory traffic for the same total compute, and because both operations were memory-bound, that translates almost directly into a real speedup. This is the mechanism behind Chapter 47’s capstone, and behind why real ML systems (fused attention kernels, fused optimizer steps) invest in custom kernels specifically for fusion rather than raw compute.

45.2.3 A Real Toolchain Lesson

Building an extension of this kind on a very new Linux distribution with a bleeding-edge GCC compiler can trigger a genuine compile error inside PyTorch’s own headers: a template-handling incompatibility between PyTorch’s C++ code and a newer GCC than PyTorch’s headers were tested against. This is a real, documented class of problem with JIT-compiled PyTorch extensions. The compilation happens against the system’s C++ toolchain, not a toolchain PyTorch controls, so version mismatches between what PyTorch’s headers assume and what the compiler actually enforces are a genuine occupational hazard of this technique. On this book’s reference rig, this surfaced as a compile error inside ATen/core/List_inl.h, error: need 'typename' before 'decltype(...)::difference_type', because the header’s decltype(impl_->list) expression is syntactically dependent (it involves this, whose type depends on a template parameter) even though impl_->list always resolves to the same concrete type, std::vector<c10::IValue>. A newer GCC’s stricter two-phase-lookup checking flags this in a way older GCC versions tolerated. The fix was a targeted, minimal patch to the one offending header line, isolated to the project’s own virtual environment rather than a system-wide change. It’s worth knowing this class of problem exists before assuming a compile failure inside torch/include/ means the kernel code itself is at fault.

45.3 Trade-offs and Limits

Custom CUDA extensions win at needing autograd-compatible custom operations with full control over both forward and backward CUDA code, at fusing multiple operations to eliminate intermediate memory traffic, and at situations needing CUDA features or libraries without a Triton binding. Triton wins at faster iteration (no C++/toolchain compilation step, no ninja, no host-compiler version sensitivity), at cross-vendor portability, and at most elementwise/reduction fusion patterns, where Triton’s compiler already gets close to hand-written CUDA performance, as Chapter 44’s softmax result showed. Neither approach subsumes the other. A Triton kernel called from PyTorch and a full C++/CUDA extension both end up callable as ordinary PyTorch operations, so the choice is about how the kernel itself needs to be authored and compiled, not about what it looks like from the calling code.

45.4 Procedures

Procedure 45.1 (Build and Call a Custom CUDA Extension). When to use: there is a CUDA kernel in the style of earlier chapters and a need to call it from ordinary PyTorch code.

Common mistake: forgetting that x.data_ptr<float>() requires x to be contiguous and of the matching dtype. Calling the extension on a non-contiguous tensor (e.g. after a .transpose()) or a float64 tensor when the kernel assumes float32 produces silently wrong results or a crash, not a helpful error message. Validate dtype and contiguity explicitly for production code.

Procedure 45.2 (Wire a Kernel Into Autograd, Forward and Backward). When to use: the custom operation needs to work inside a training loop, i.e. support .backward().

Common mistake: calling MyOp.forward(x) directly instead of MyOp.apply(x). Calling .forward() directly bypasses autograd’s bookkeeping entirely. The operation computes a correct result but silently produces no gradient, a bug that only surfaces later as “loss isn’t decreasing” or “gradients are None,” far from the actual mistake.

Procedure 45.3 (Verify a Custom Op’s Gradient Is Correct). When to use: before trusting a custom backward kernel in a real training run. A wrong gradient can silently degrade training without ever throwing an error.

Common mistake: only checking forward correctness and assuming backward is “probably fine” because the math looks right on paper. A transcription error in the derivative, a dropped factor of 2, a wrong sign, forgetting the ReLU gate, is easy to make and easy to miss without an explicit check. Always verify both directions. torch.autograd.gradcheck is the more rigorous, numerical-differentiation-based version of this same check, and the standard tool for production custom ops.

45.6 History and Further Reading

The official PyTorch documentation’s “Custom C++ and CUDA Extensions” tutorial is the canonical walkthrough this chapter’s pattern follows, and is worth reading end to end before writing a production extension. The torch.autograd.Function and torch.autograd.gradcheck API documentation cover the full mechanics of forward/backward/ctx and the rigorous numerical-gradient-checking approach only sketched in Procedure 45.3. For the toolchain-incompatibility class of problem this chapter’s Exposition describes, searching PyTorch’s GitHub issues for the exact error text (in this case, referencing List_inl.h and typename) is generally the fastest way to find out whether a newer PyTorch release already fixes it, before patching a header by hand. Fregly’s AI Systems Performance Engineering (Fregly 2026), Chapter 13, works through the same compiling-versus-custom-kernel decision in more depth, framing torch.compile as the first resort and a hand-written extension like this chapter’s as the fallback once a novel operation falls outside what TorchInductor’s automatic fusion can capture, worth reading once this chapter’s own extension has been wired into autograd.

45.7 How This Connects

This chapter builds on Chapter 39 (the raw CUDA kernel) and Chapter 43 (fusion as an application of the roofline model), and on Chapter 44, which presents Triton as the alternative path to a custom PyTorch operation. These two chapters are competing answers to the same problem, and both end up callable as ordinary PyTorch operations. It enables Chapter 47, whose capstone fused kernel can legitimately be built either as a Triton kernel or as a custom extension of the kind built here, with this chapter’s fusion result serving as direct evidence for why the capstone is worth doing at all. It is often confused with a Triton kernel called from PyTorch: the difference is entirely in how the kernel itself is authored and compiled, not in how it’s called once it exists.

45.9 Mental Model

A raw CUDA kernel from earlier chapters is a specialist tool sitting outside the workshop. A PyTorch CUDA extension is that same tool, fitted with a standard-issue handle, torch.autograd.Function, so it slots into the same toolbelt as every other PyTorch operation: usable in a training loop, differentiable, indistinguishable from a built-in op to the rest of the code, while still being exactly the hand-written kernel built underneath.
