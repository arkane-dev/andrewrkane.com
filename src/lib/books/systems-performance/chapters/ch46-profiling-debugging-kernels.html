Every measurement in this book’s GPU-kernels chapters so far came from hand-rolled cudaEvent_t timing wrapped around individual kernels already known to be suspect. Real GPU programs have many kernels, and the one that’s actually slow is often not the one intuition would pick. Real GPU bugs, out-of-bounds memory access, race conditions, frequently produce no visible symptom at all. The wrong answer looks plausible, or the corruption doesn’t crash anything until much later, in an unrelated part of the program. This chapter covers nvidia-smi, the free glance that costs nothing and comes before any other tool; torch.profiler, the natural starting point for a PyTorch pipeline; and the three standard NVIDIA tools that replace guessing with measurement below the PyTorch level: Nsight Systems, which shows where time goes across a whole program; Nsight Compute, which shows why one specific kernel is slow, in hardware-counter detail; and compute-sanitizer, which checks whether a kernel is even correct in the first place.

46.1 Motivation

These three tools answer three different questions, and reaching for the wrong one wastes time. “Which kernel is the bottleneck?” is answered by Nsight Systems (nsys), a timeline-and-summary profiler across the whole program. “Why is this specific kernel slow?” is answered by Nsight Compute (ncu), which reports deep per-kernel hardware counters: occupancy, memory throughput, warp stall reasons. “Is this kernel’s output actually correct, or does it have a memory bug?” is answered by compute-sanitizer, a correctness checker, not a performance tool at all. Using ncu before nsys has found the actual bottleneck kernel wastes its far higher per-kernel profiling overhead on a kernel that might not matter. Assuming an algorithm is wrong before ruling out a memory bug with compute-sanitizer can cost days of misdirected debugging on a problem that turns out to be one off-by-one comparison.

46.2 Exposition

46.2.1 nvidia-smi: The Free Glance Before Any of the Above

Before torch.profiler, nsys, ncu, or compute-sanitizer, there’s a zero-cost, zero-code-change step: watching the GPU while the program runs. nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv is scriptable, ships with every CUDA install, and answers one question none of this chapter’s other four tools answer as cheaply: is the GPU doing anything at all, right now? It won’t say why a kernel is slow, only whether one is currently running. That’s still useful, and it’s the right first move for a program that looks like it’s hanging: confirm whether the GPU is idle (the problem is upstream, on the CPU side, before any kernel launch) or pegged at 100% (the problem is a real, running kernel, and the next four tools are what to reach for). Terminal-UI tools in this same category (nvtop, nvitop, gpustat) give a live, human-readable view but need a separate install and don’t capture cleanly in an automated script or notebook; nvidia-smi’s scriptable query flags do both jobs from one already-installed tool.

46.2.2 torch.profiler: The PyTorch-Level Starting Point

Every kernel measured so far in this book’s GPU-kernels chapters was hand-written CUDA, compiled and run directly with nvcc. Most real GPU work happens inside PyTorch, where the actual CUDA kernels a line of Python calls are not visible from the Python source at all. torch.matmul(a, b) might dispatch to a cuBLAS or CUTLASS kernel with a name nothing like matmul. torch.profiler answers the same “which operation dominates?” question as nsys, but at the PyTorch-op level, with zero extra tooling beyond the torch import already in the program: wrap the code under investigation in with torch.profiler.profile(activities=[...]) as prof:, then call prof.key_averages().table(sort_by='cuda_time_total') afterwards. It is the natural first tool for a PyTorch pipeline, before dropping down to nsys/ncu for compiled-kernel or hardware-counter detail torch.profiler cannot see inside.

46.2.3 Nsight Systems: Finding the Bottleneck, Not Guessing It

nsys profile records a timeline of everything a program does on the CPU and GPU. nsys stats --report cuda_gpu_kern_sum summarizes that timeline into a per-kernel breakdown of total time, instance count, and average time per launch. The workflow is always the same: profile the whole program first, then look at which kernel actually dominates, before deciding what to optimize.

46.2.4 Nsight Compute: Going Deeper on One Kernel

Once nsys has identified which kernel matters, ncu explains why it runs at the speed it does: achieved occupancy (Chapter 43), memory throughput as a percentage of peak, warp stall reasons, register usage, and dozens of other hardware counters, all scoped to one specific kernel launch. Collecting these detailed hardware counters requires elevated permissions on most Linux NVIDIA driver installs. Running ncu as a normal user commonly produces ERR_NVGPUCTRPERM: The user does not have permission to access NVIDIA GPU Performance Counters on the target device 0. This is not specific to any one environment or a misconfiguration to be embarrassed about. It is the NVIDIA driver’s default security posture (NVreg_RestrictProfilingToAdminUsers) on most modern Linux distributions, adopted because unrestricted performance-counter access has historically been usable as a side-channel. The fix is either running ncu with sudo, or, for a persistent fix, a driver-level permission change requiring a reboot. Knowing this is a normal, expected speed bump rather than a sign of a broken kernel or setup is itself worth knowing before hitting it for the first time.

46.2.5 compute-sanitizer: Catching What Doesn’t Crash

A classic, realistic bug, an off-by-one bounds check, i <= n instead of i < n, illustrates exactly why correctness tooling exists separately from performance tooling. Running the buggy kernel normally produces cudaGetLastError: no error. The kernel launch “succeeds” from CUDA’s own error-checking perspective, because cudaGetLastError() only checks whether the launch itself was rejected (bad grid/block dimensions, resource limits exceeded), not whether the kernel’s individual memory accesses were valid. An out-of-bounds write into unrelated device memory can corrupt data used elsewhere in a program, non-deterministically, without CUDA itself ever flagging that anything went wrong. Running the identical binary under compute-sanitizer --tool memcheck instead reports the exact source line, the exact offending thread and block, and confirms the access lands exactly one element past the allocation boundary, turning a silent, non-deterministic corruption into a precisely located bug.

46.3 Trade-offs and Limits

Reach for torch.profiler first, when the code under investigation is PyTorch. It needs no separate tool invocation and gives an op-level breakdown immediately. Reach for nsys when the code is hand-written CUDA, or once torch.profiler has identified a suspect PyTorch op and its actual compiled kernel needs to be seen in a whole-program timeline. It has no special permission requirements and comparatively low overhead. Reach for ncu once nsys has identified one specific kernel and hardware-counter-level detail is needed to know what to fix about it, accepting both its higher per-kernel overhead and the permissions speed bump. Reach for compute-sanitizer whenever output is wrong, inconsistent across runs, or crashes unpredictably, before assuming the algorithm itself is wrong, since ruling out a memory bug is often faster once a tool finds it than any amount of manual code review. None of the three substitutes for another: nsys will not explain why a kernel is slow in hardware terms, ncu will not tell you a kernel is memory-unsafe, and compute-sanitizer will not catch a pure logic error that never touches invalid memory. It only catches the memory/race/sync classes of bug, so a wrong answer with no sanitizer output still needs the algorithm’s math checked independently.

46.4 Procedures

Procedure 46.1 (Find the Bottleneck Kernel in a Multi-Kernel Program). When to use: a program has several kernels and it isn’t yet known which one is worth optimizing. Always the first profiling step, never guess.

The Time (%) column gives the share of total GPU kernel time. Sort by this to find the bottleneck. Instances shows how many times a kernel was launched: a kernel launched many times can dominate even if each individual call is fast. Avg (ns) gives the per-launch average time, useful for distinguishing a cost that’s per-call from one that’s driven by call count. Common mistake: assuming the kernel that “sounds” most expensive, a transcendental-function-heavy kernel, say, is the bottleneck without checking. The Worked Example below found the opposite.

Procedure 46.2 (Catch Memory Bugs Before They Cause Silent Corruption). When to use: output is wrong, inconsistent between runs, or “mostly right but sometimes not,” before spending time debugging the algorithm itself.

Invalid __global__ read/write of size N bytes reports the access type and size that violated bounds. at kernelName(...)+0xNN in file.cu:LINE gives the exact kernel and source line. This only resolves to a real file:line reference, rather than a bare address, if the binary was compiled with nvcc -lineinfo. by thread (x,y,z) in block (x,y,z) identifies exactly which thread triggered the fault, useful for reasoning about which index computation is wrong. N bytes after/before the nearest allocation confirms whether it’s an overrun or underrun, and by how much. Common mistake: compiling without -lineinfo and then trying to debug from raw addresses alone. It costs nothing at runtime and turns opaque offsets into actual source references.

Procedure 46.3 (Choose Which Tool to Reach For First). When to use: at the start of any performance or correctness investigation, before running anything.

Common mistake: reaching for ncu’s deep hardware counters before establishing, via nsys, that the kernel about to be deep-dived on is actually the one that matters. ncu’s per-kernel profiling overhead is much higher than nsys’s, so it’s worth spending only on a kernel already confirmed to matter.

Procedure 46.4 (Get an Op-Level Breakdown of a PyTorch Pipeline). When to use: the code under investigation is PyTorch, not hand-written CUDA. The natural first step, before nsys/ncu.

Common mistake: profiling without a warm-up call first, or without torch.cuda.synchronize() before reading results. CUDA kernel launches are asynchronous from Python’s perspective. Timings taken without a synchronize point can attribute one op’s actual execution time to whatever op happened to be running on the CPU when the clock was read.

Procedure 46.5 (Check Whether the GPU Is Doing Anything Before Reaching for Any Profiler). When to use: the very first step, even before Procedure 46.3’s decision tree, whenever a program looks stuck or its behaviour is unclear.

Common mistake: treating a 0% reading as proof a kernel is slow. It only proves the GPU isn’t running anything at this instant: a fast kernel launched in a tight loop can be idle between launches even while the overall pipeline is GPU-bound, and a program stuck on a CPU-side lock or blocked I/O call will also read 0% forever, for a completely different reason nvidia-smi alone cannot distinguish. Poll repeatedly across the program’s runtime, not once.

46.5 Worked Example

All measured numbers in this chapter† come from this book’s reference rig. See the preface.

nvidia-smi, the free glance. A single deliberately GPU-bound kernel, polled with Listing 46.5 every 0.5 seconds while it runs, following Procedure 46.5:

Before launch:    4 %, 937 MiB

While busyKernel ran:
  t=0.00s  4 %, 937 MiB
  t=0.53s  100 %, 1457 MiB
  t=1.05s  100 %, 1457 MiB
  t=1.57s  100 %, 1457 MiB
  t=2.08s  100 %, 1457 MiB
  t=2.60s  100 %, 1457 MiB

After completion: 1 %, 937 MiB

Idle before, pegged at 100%† for the entire runtime, idle again afterward: exactly the signature that confirms real GPU work is happening, and roughly when it starts and stops, all from one already-installed tool, no code instrumentation, no separate profiler run. This is a coarse signal on purpose: it says nothing about which kernel, or why. But it costs nothing to check first, and it’s the fastest way to rule in or rule out “is the GPU even doing anything” before spending time on any of the tools below.

torch.profiler, PyTorch-level. A three-op PyTorch pipeline, a 4096x4096 matrix multiply, then sigmoid, then sum, run five times, following Listing 46.4:

Name                  CUDA total (us)       %   Calls
cutlass matmul kernel          10285.2   96.8%       5
sigmoid kernel                   252.0    2.4%       5
sum/reduce kernel                 81.4    0.8%       5

Total CUDA time: 10.622 ms

Here the intuitive guess turns out right. The matmul dominates at 96.8%† of total GPU time, with sigmoid and sum both comparatively cheap. That is worth noting alongside the nsys result immediately below: sometimes intuition matches the measurement, sometimes it does not, and the entire point of profiling is finding out which, not assuming either direction. torch.profiler found this without leaving Python or invoking a separate tool, the natural first step for a PyTorch pipeline, before nsys/ncu are needed for compiled-kernel-level or hardware-counter detail.

nsys, hand-written CUDA. The pipeline under test is three kernels run five times each: vecAdd, then sigmoidKernel (using expf()), then sumTreeReduction (Chapter 42’s tree-reduction pattern), over 1 << 22 elements. Before running anything, a reasonable guess is that sigmoidKernel, the one doing an expensive-looking transcendental function, dominates. Following Listing 46.1:

The guess was wrong. sumTreeReduction took 56.3%† of total GPU time, more than vecAdd and sigmoidKernel combined, despite looking like the “simplest” operation in the pipeline. The cost comes from the reduction’s __syncthreads() barriers and final atomicAdd (Chapter 42), not from arithmetic complexity. expf() is comparatively cheap by contrast. This is the entire point of profiling instead of guessing, and it echoes Chapter 41’s stencil-tiling null result and Chapter 43’s occupancy curve: real measured answers are frequently not what intuition predicts.

The correctness half of the Worked Example deliberately introduces the off-by-one bug from this chapter’s Exposition, in a kernel launched with grid * block = 1024 threads over n = 1000 elements, so 24 threads have i >= n. Run normally:

Running BUGGY kernel (off-by-one bounds check)...
cudaGetLastError: no error

No error is reported. The launch “succeeded.” The same binary under compute-sanitizer --tool memcheck:

========= Invalid __global__ read of size 4 bytes
=========     at addOneBuggy(float *, int)+0xb0 in buggy.cu:8
=========     by thread (232,0,0) in block (3,0,0)
=========     Access to 0x7f7412400fa0 is out of bounds
=========     and is 1 bytes after the nearest allocation
=========     at 0x7f7412400000 of size 4,000 bytes

This pinpoints the exact source line, the exact thread (232 in block 3, global index 1000, precisely the first out-of-bounds index), and confirms the access lands exactly one byte after a 4,000-byte (1,000-float) allocation: precisely the bug. Compute-sanitizer’s instrumentation also surfaces a cudaErrorLaunchFailure on the subsequent cudaDeviceSynchronize() call, something the uninstrumented run never revealed. The fixed kernel, run through the same tool, reports ERROR SUMMARY: 0 errors.

Finally, running ncu --set basic on this reference rig without elevated permissions reproduces the exact permission error described in the Exposition:

==PROF== Connected to process ...
==ERROR== ERR_NVGPUCTRPERM - The user does not have
permission to access NVIDIA GPU
Performance Counters on the target device 0.

nsys and compute-sanitizer are both unaffected by this restriction and remain usable without elevated access. On a shared cluster without root, they are the primary tools available.

46.6 History and Further Reading

NVIDIA’s Nsight Systems documentation is the full CLI and GUI reference, and covers how to read the timeline view that nsys stats output summarizes numerically. NVIDIA’s Nsight Compute documentation covers the full metric reference, hundreds of countable hardware events, once permission to collect them is available, and the NVIDIA Developer Blog’s Nsight Compute profiling guide walks through worked examples of the occupancy and memory-throughput metrics this chapter refers back to from Chapter 43. The compute-sanitizer documentation’s “Memcheck Tool” section also covers the sanitizer tools not exercised in this chapter’s Worked Example: racecheck for shared-memory data races, initcheck for reads of uninitialized device memory, and synccheck for invalid __syncthreads() usage such as calls inside divergent branches. Fregly’s AI Systems Performance Engineering (Fregly 2026), Chapter 8, covers Nsight Systems and Nsight Compute in much greater depth, including the achieved-occupancy and occupancy-limiter metrics this chapter reports back to Chapter 43, worth reading once this chapter’s own nsys-then-ncu workflow has been run directly. Cautaerts and Ghorbanfekr’s GPU-Accelerated Computing with Python 3 and CUDA (Cautaerts and Ghorbanfekr 2026), Chapter 4, covers the same Nsight Systems and Nsight Compute workflow from Numba-CUDA kernels, plus print-statement and CPU-emulation debugging techniques this chapter’s compute-sanitizer coverage doesn’t touch.

46.7 How This Connects

This chapter builds on every prior chapter in this book’s GPU-kernels sequence. It is the tooling that would have let earlier results be observed directly rather than inferred, such as seeing memory-bandwidth-bound versus compute-bound behavior in ncu’s output rather than deriving it from timing sweeps in Chapter 43. It enables Chapter 47, whose capstone fused kernel is profiled with these same tools to confirm its expected win rather than trusting timing alone. It is often confused with cudaGetLastError()/cudaPeekAtLastError() as a substitute for correctness checking: those catch launch configuration errors (invalid grid or block dimensions, resource limits exceeded), not out-of-bounds memory access or races, which is exactly what this chapter’s bug demonstrated slipping through silently.

46.9 Mental Model

nsys is a building’s master electrician checking which floor is drawing too much power. ncu is that electrician opening the breaker panel on the one floor that’s a problem, testing individual circuits. compute-sanitizer is a structural inspector who doesn’t care about power usage at all, only whether the wiring is actually safe, because a fire, like a memory bug, doesn’t announce itself as a symptom the electrician would ever have measured.
