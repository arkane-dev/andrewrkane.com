Chapter 48 established that you must measure before optimizing, but “measure” so far has meant timing a function already suspected of being slow. Real code is rarely that simple: a program has dozens or hundreds of functions, and intuition about which one dominates runtime is frequently wrong. Profiling is the discipline of finding out where time actually goes, with evidence, rather than guessing from how a function “looks”: how much code it has, how many objects it allocates, how clever or naive it seems.

50.1 Motivation

Two distinct profiling techniques anchor this chapter, and both are used here because they arrive at the same answer independently. Deterministic profiling (cProfile) instruments every function call, recording exact counts and cumulative time per function. Complete and precise, at the cost of some overhead and function-level (not always line-level) granularity. Statistical/sampling profiling (py-spy) periodically interrupts the running process and records the current call stack, without instrumenting anything. Lower overhead, works on unmodified running processes, and, for py-spy specifically, resolves all the way down to the exact source line. A third tool, perf (introduced in Chapter 49), profiles at the hardware/native-instruction level: the right tool for cache and branch questions, and, as this chapter shows directly, the wrong tool for “which Python function is slow.” A fourth, bpftrace, sits a tier below all three: it doesn’t see Python frames or native instructions at all, only whether the process is asking the kernel for anything, and it measures that directly, from a running system, with the lowest overhead of the four.

50.2 Exposition

The measured numbers in this chapter† come from a small deliberately-non-obvious demo program run on this book’s reference rig. See the preface.

50.2.1 Intuition Is Not Evidence: A Concrete Miss

A small program has two functions: parse_records, which allocates 40,000 dictionary objects, and dedupe_slow, which removes duplicates from a list using if item not in seen, checking membership against a plain Python list, not a set. Before measuring, parse_records looks like the more expensive step. It performs 40,000 real object allocations, while dedupe_slow is “just” checking membership.

cProfile found the opposite:

Function tottime cumtime Share of total
dedupe_slow 0.700s 0.701s 97.9%
parse_records 0.008s 0.011s 1.1%
(total program) — 0.715s 100%

The mechanism, Chapter 51’s territory, is that if item not in seen on a growing list is an O(n)O(n)O(n) scan, repeated nnn times as the list grows: an accidentally quadratic algorithm hiding behind three lines of completely ordinary-looking code, while parse_records’s dict allocations are each fast, constant-time operations that simply don’t add up to much even 40,000 times over.

50.2.2 Two Independent Techniques, One Answer

Running py-spy record against the identical program, sampling the call stack 300 times per second, found 226 of 227 samples (~99.6%) landed inside dedupe_slow, specifically at the if item not in seen: line, not just the same function cProfile found, but the exact source line, and via a completely different mechanism: instead of instrumenting every function call, py-spy interrupts the running process at a fixed rate and records whatever the call stack happens to be at that instant. Two independent techniques agreeing this precisely is strong confirmation the finding is real, not an artifact of either measurement method, the same “trust but verify with an independent method” principle that recurs throughout this book.

50.2.3 A Real Permissions Gotcha: ptrace_scope

The first attempt to use py-spy, launching the target program separately, then attaching py-spy dump --pid <pid> to the already-running process, fails with Permission Denied. This is not a broken installation. Linux’s yama security module restricts which processes may inspect another process’s memory via ptrace (the same low-level mechanism debuggers use), controlled by /proc/sys/kernel/yama/ptrace_scope. At a setting of 1 (a common default), a process may only be ptraced by its own direct parent. The fix: let py-spy launch the target program itself (py-spy record -- python script.py), so py-spy is the parent process, and the restriction no longer applies. This is a real, common gotcha in containerized and sandboxed environments specifically, not a py-spy quirk. It’s worth knowing before assuming a profiler installation is broken.

50.2.4 Why perf Can’t Answer This Question

Running perf stat against the same program gives entirely real, accurate numbers (3,392,566,509 cycles, 14,496,828,974 instructions, 3,945,942 cache-misses) but nothing that says which Python function they belong to. perf operates below the Python interpreter: it sees native CPU instructions, and in a standard, non-specially-instrumented CPython build, the overwhelming majority of those instructions are inside _PyEval_EvalFrameDefault (the interpreter’s core bytecode dispatch loop), regardless of which Python-level function is logically executing. perf answers “how is the CPU spending cycles at the hardware level” (Chapter 49’s question). It cannot answer “which Python function is slow” (this chapter’s question). That requires a tool that understands Python’s own call-frame structure, which is exactly what cProfile and py-spy are built to do.

50.2.5 One Tier Below Both: bpftrace and Kernel-Level Tracing

cProfile and py-spy both answer questions inside the Python interpreter: which function, which line. There’s a tier below both of them, and below perf too: the kernel itself. bpftrace, built on eBPF (extended Berkeley Packet Filter), attaches lightweight programs directly to kernel tracepoints, syscall entry/exit points, scheduler events, so it can answer a different class of question neither Python-level tool touches: not “which Python function is slow,” but “is this program, whatever language it’s written in, actually asking the kernel for anything at all?” A single bpftrace one-liner can count every read, write, openat, mmap, or futex call a specific process makes, system-wide, with overhead low enough to run in production continuously, something neither cProfile’s instrumentation nor py-spy’s repeated sampling is built for at that scale. It answers a question this chapter’s other three tools cannot: is the bottleneck even inside this process’s own compute at all, or is it waiting on the kernel for something?

50.3 Trade-offs and Limits

Use cProfile when the program’s invocation can be modified (adding -m cProfile, or wrapping the call in code), when exact call counts and cumulative or per-call time broken down by function are needed, and when some profiling overhead (typically 2-5x slowdown from instrumentation) is acceptable. Use py-spy when the running process cannot or should not be modified, a live production service, when line-level granularity with minimal overhead is needed, and remember the ptrace_scope gotcha above if attaching to an already-running process. Use perf when the question is about hardware-level behavior (cache misses, branch mispredictions, IPC, Chapter 49), not “which Python function,” and when profiling native extensions, C libraries, or non-Python processes with no Python frame structure to resolve in the first place. Use bpftrace when the question is “is this process touching the kernel at all,” or when a production system needs continuous, always-on, near-zero-overhead observation that neither cProfile’s instrumentation nor py-spy’s repeated sampling is cheap enough to run forever. It requires root or CAP_BPF/CAP_PERFMON, same permissions class as ncu in Chapter 46, and it answers a different question than the other three tools entirely: not which function is slow, but whether the process is even asking the kernel for anything while it runs.

50.4 Procedures

Procedure 50.1 (Profile a Script With cProfile). When to use: a script or entry point that can be invoked directly, needing an exact, function-level breakdown of where time goes.

tottime is time spent in the function itself, excluding calls to other functions; cumtime is tottime plus all functions it called. For finding a hotspot, sort by cumulative first. The function with the highest cumtime at the top of the call chain shows where to look. The deepest function with a high tottime shows exactly what to fix. Common mistake: sorting by tottime only and missing a function that’s expensive purely because of what it calls (high cumtime, low tottime). Start with cumulative, then drill into tottime for the specific function actually doing the work.

Procedure 50.2 (Profile an Already-Running Process With py-spy). When to use: a long-running service or process that shouldn’t (or can’t) be restarted with different invocation flags.

Common mistake: attaching to a process py-spy did not itself launch, and getting Permission Denied. A ptrace_scope setting of 1 or higher restricts ptrace access to direct parent processes. If the target’s launch can be controlled, prefer launching it through py-spy instead, as shown above; changing ptrace_scope itself requires root and is a system-wide security-relevant setting, not something to flip casually in a shared or production environment.

Procedure 50.3 (Read py-spy’s Raw Output Format). When to use: parsing py-spy record -f raw output programmatically, or understanding a flamegraph SVG’s underlying data.

Each line is stack_frame;stack_frame;...;stack_frame COUNT: an entire call stack, outermost frame first, with a count of how many samples observed exactly that stack. A single dominant line with a count close to the total sample count means one code path accounts for nearly all the time; a spread of many different lines with similar counts means time is genuinely distributed across many call paths. Common mistake: interpreting sample count as exact time. With sampling profilers, the count is a statistical estimate, accurate for finding where time goes with enough samples, but not a precise timer the way cProfile’s instrumented counts are.

Procedure 50.4 (Decide Whether perf, cProfile, or py-spy Is the Right Tool). When to use: before reaching for a profiler, confirm it’s the one that can actually answer the question at hand.

Question Right tool
Which Python function/line is slow? cProfile (if invocation can be modified) or py-spy (if not, or lower overhead is needed)
Is this slow because of cache misses / branch mispredictions? perf (Chapter 49), but confirm which function first via cProfile/py-spy, then investigate that function’s hardware behavior with perf
How much total CPU/memory/cache traffic did the whole program use? perf stat for a whole-process summary
Is the process even talking to the kernel, or is the time genuinely all in-process compute? bpftrace, tracing syscall tracepoints for the specific PID (Procedure 50.5)

Common mistake: running perf stat or perf record on Python code expecting Python-level function names in the output. On a standard CPython build, perf sees mostly _PyEval_EvalFrameDefault regardless of which Python function is running. It cannot resolve Python source lines without specialized support. Use cProfile/py-spy to find the Python-level hotspot first, then reach for perf only to understand why that specific hotspot is slow at the hardware level.

Procedure 50.5 (Trace a Specific Process’s Syscalls With bpftrace). When to use: confirming whether a process is doing kernel-visible work (I/O, memory mapping, lock contention) at all, independent of and below the level of any Python-aware profiler.

Common mistake: requiring root, then giving up on bpftrace entirely after the first EPERM-style failure. Like ncu in Chapter 46, this is standard, expected default-permissions behaviour, not a broken setup; run with sudo or grant CAP_BPF/CAP_PERFMON. A second common mistake: treating an empty result (no syscall counts printed) as a tool failure. bpftrace only prints a map entry for syscalls that actually occurred. Zero entries is a real, valid measurement: it means none of the traced syscalls fired during the observation window, not that the trace didn’t work.

50.6 History and Further Reading

The Python cProfile and pstats standard library documentation is the authoritative reference for sort keys, output columns, and programmatic use of profiling data beyond what this chapter covers. The py-spy GitHub repository (benfred/py-spy) documents the dump, record, and top subcommands in more depth, including the ptrace_scope permissions notes this chapter hit directly. man 2 ptrace and the Linux kernel’s yama documentation describe the actual security mechanism behind the permissions gotcha. Gregg’s “Flame Graphs” (brendangregg.com) is the reference for the visual format py-spy record’s default (non-raw) output produces, and for reading one once this chapter’s raw-format output has been seen directly. Rotem’s Software Performance Engineering (Rotem 2025), Chapter 9, covers static-versus-dynamic profiling and sampling-versus-instrumentation as general concepts, above the specific tools this chapter applies them with, useful context for judging when cProfile’s deterministic instrumentation versus py-spy’s sampling is the right choice for a given problem; its section on Linux kernel profiling with eBPF is the direct source for this chapter’s bpftrace material. The bpftrace project’s own reference guide (github.com/bpftrace/bpftrace) documents the full tracepoint, kprobe, and USDT probe types beyond the syscall tracepoints this chapter uses. Gregg’s Systems Performance (Gregg 2020), already cited in Chapter 57 for its profile-locate-fix-verify methodology, is also the standard reference for BPF-based tracing specifically: Gregg is one of the tool’s principal real-world popularizers, and the book’s BPF chapter is worth reading once this chapter’s own zero-syscall result has been seen directly.

50.7 How This Connects

This chapter builds on Chapter 48’s “measure before you fix” discipline, applied here to locating the thing to fix rather than just timing something already suspected, and on Chapter 49’s perf tool, reused here to show its limits for this specific question. It enables Chapter 51, which explains why the hotspot this chapter found, an O(n)O(n)O(n) scan repeated nnn times, is slow, and how to fix it with the right data structure. This chapter was deliberately scoped to finding the problem, not fixing it. It is often confused with guessing from code review alone (“this loop looks expensive”). This chapter’s entire first section is a concrete demonstration of why that instinct, however experienced the reader, can be simply wrong, and profiling is how to find out before spending effort optimizing the wrong function.

50.9 Mental Model

Profiling a program by reading its code and guessing the hotspot is like guessing which pipe in a building is leaking by looking at the blueprint: plausible-sounding, and frequently wrong. cProfile is turning on a flow meter at every valve simultaneously; py-spy is walking the building at a fixed interval and noting which room currently has someone frantically mopping. Both approaches find the actual leak; neither requires trusting the blueprint’s implied story about where problems “should” be.
