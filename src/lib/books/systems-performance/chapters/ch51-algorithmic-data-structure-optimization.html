Once profiling has pointed at a specific slow function, the discipline of Chapter 50, the fix is very often not “make this faster” in some vague, effortful sense, but “you’re using the wrong algorithm or the wrong data structure for this access pattern.” This is the cheapest class of optimization available: no new hardware, no parallelism, often a one-line change, and the effect can dwarf anything Chapter 53’s parallelism or Chapter 55’s GPU offload can offer on the same workload. This chapter separates two effects that are easy to conflate under the umbrella of “choosing the right data structure”: algorithmic complexity, the textbook Big-O story of how cost scales with input size, and memory layout, how a fixed amount of work is arranged in memory, something Big-O says nothing about at all. Both are demonstrated with real measurements, not asymptotic argument alone.

51.1 Motivation

Three ideas organize this chapter, in increasing order of how invisible they are to someone who has only learned Big-O from a textbook. First, asymptotic complexity is real and matters enormously at scale, O(n)O(n)O(n) versus O(1)O(1)O(1), O(n2)O(n^2)O(n2) versus O(n)O(n)O(n), but the crossover point where it starts mattering in wall-clock terms is an empirical question, not a theoretical one. Second, memory layout affects real performance at a fixed Big-O complexity: two implementations of “sum one field across nnn records” can both be O(n)O(n)O(n) and differ by two orders of magnitude, because one streams through contiguous memory and the other chases pointers. Third, the “obvious” choice is often the wrong one, not because the right choice is exotic, but because Python’s most familiar general-purpose container, list, is rarely the asymptotically best choice for any specific access pattern (membership testing, FIFO queues). It’s a reasonable default, not a correct-by-default one.

51.2 Exposition

All measured numbers in this chapter† come from this book’s reference rig. See the preface. The CPU side of that rig, the AMD Ryzen 9 5950X, is what every timing below was collected on.

51.2.1 Membership Testing: O(n) vs O(1), Measured

A Python list’s in operator scans element by element until it finds a match or exhausts the list: O(n)O(n)O(n). A set or dict’s in operator computes a hash of the query value and jumps directly to the bucket that would contain it: O(1)O(1)O(1), independent of how many elements are already stored. Measuring worst-case membership (an absent value, forcing the list to scan everything) at five scales:

n list (min) set (min) ratio
100 0.00077 ms† 0.00010 ms 7.7x
1,000 0.00677 ms 0.00011 ms 61.5x
10,000 0.06611 ms 0.00010 ms 661.1x
100,000 0.44828 ms 0.00006 ms 7,471.4x
1,000,000 4.57576 ms 0.00006 ms 76,262.9x

The ratio itself grows with nnn. That growth is the entire point. The set’s absolute time barely changes across five orders of magnitude of nnn (it’s dominated by hashing the query value, not by how many elements are already stored); the list’s time grows linearly, exactly as O(n)O(n)O(n) predicts. At n=100n=100n=100 the difference is real but easy to shrug off (7.7x of a fraction of a microsecond); at n=1,000,000n=1{,}000{,}000n=1,000,000 it’s a five-figure multiplier. The crossover where this becomes a genuine production concern is empirical, not something knowable in advance from the complexity class alone. Chapter 50’s “measure it” discipline applies here too, not just to whole-program timing.

51.2.2 Cache Layout: The Effect Big-O Cannot See

Array-of-structs (AoS) stores each record as a single object with all its fields together ([(x0,y0,z0,w0), (x1,y1,z1,w1), ...]). Struct-of-arrays (SoA) stores each field in its own contiguous array (xs = [x0, x1, ...], ys = [y0, y1, ...], and so on). “Sum every x value across nnn records” is O(n)O(n)O(n) either way. Big-O treats them as identical. Measured summing one field across nnn records:

n AoS (min) SoA (min) speedup
10,000 0.1910 ms 0.0023 ms 82.0x
100,000 1.9550 ms 0.0158 ms 123.7x
1,000,000 21.1580 ms 0.1297 ms 163.1x
5,000,000 106.3220 ms 1.2449 ms 85.4x

Two O(n)O(n)O(n) algorithms, 80-160x apart. The mechanism is entirely about what the CPU pulls into cache per memory access, a preview of Chapter 49’s cache-hierarchy material, which explains why a cache line is 64 bytes and what a miss costs. The SoA sum streams through one contiguous block of float64s, and every 64-byte cache line fetched is 100% useful data for the operation being performed. The AoS sum has to follow a pointer to a Python tuple object, read one field out of four, and discard the rest. The same cache line brings in y, z, w too, but the sum-over-x operation never uses them before that line is evicted to make room for the next record’s line. This is real, and it is invisible to complexity analysis entirely. It’s a statement about memory traffic, not operation count.

51.2.3 Queue Draining: O(n) vs O(n²)-to-Drain

A Python list is a dynamic array. Removing the first element (list.pop(0)) requires shifting every remaining element down one slot: O(n)O(n)O(n) per pop, so draining a queue of nnn items via repeated pop(0) costs O(n2)O(n^2)O(n2) overall. A collections.deque is implemented as a doubly-linked list of fixed-size blocks, so popping from either end is O(1)O(1)O(1) regardless of size.

n list.pop(0) deque.popleft() speedup
1,000 0.057 ms 0.023 ms 2.5x
5,000 0.870 ms 0.112 ms 7.7x
20,000 16.606 ms 0.454 ms 36.5x

The speedup itself grows with nnn, the visible signature of comparing an operation that costs O(n2)O(n^2)O(n2) overall against one that costs O(n)O(n)O(n) overall. At small nnn the difference is a rounding error; by n=20,000n=20{,}000n=20,000 it’s a 36x gap, and the gap keeps widening the larger nnn gets. This is arguably the single most common avoidable data-structure mistake in Python code: reaching for list as a FIFO queue because it’s the container everyone learns first, not because it’s the right one for this access pattern.

51.3 Trade-offs and Limits

Reach for set/dict over list for membership testing when the container will be checked more than a handful of times, or is large (the crossover is empirical, so profile if it matters, Chapter 50), and when element order doesn’t need to be preserved, or a separate ordered structure can be kept alongside. A list is still the right choice when positional/order-preserving access is needed, or the container is small and checked rarely: the constant-factor overhead of hashing isn’t free either, just much smaller than O(n)O(n)O(n) scanning at any real scale.

Reach for struct-of-arrays over array-of-structs when scanning or reducing over one field at a time across many records, exactly NumPy’s whole design philosophy, and precisely the layout GPU kernels want too (Chapter 40’s memory-coalescing material is the same principle one level lower). Array-of-structs is still reasonable when typically accessing all fields of one record together (processing one customer’s full record at a time, say). Then AoS keeps the record’s fields on the same cache line, which is the layout that pattern actually wants.

Reach for deque over list for queue-style access whenever adding or removing from either end repeatedly (FIFO, or mixed LIFO+FIFO). deque is a strict improvement here with no downside. The one place list beats deque is frequent random-index access into the middle, which is O(n)O(n)O(n) for a deque and O(1)O(1)O(1) for a list. Match the container to the actual access pattern, not to which one sounds more sophisticated.

51.4 Procedures

Procedure 51.1 (Replace O(n) Membership Checks with O(1) Ones). When to use: code doing if x in some_list: inside a loop, or repeatedly checking membership against the same collection.

Use set when only membership is needed, with no associated value and no ordering requirement. Use dict when membership and an associated value are needed (id -> record). Keep list when the collection is small, checked rarely, or when order and duplicates matter and membership isn’t checked in a hot loop. Common mistake: building the set or dict inside the loop that checks membership, which pays the O(n)O(n)O(n) construction cost on every iteration and can end up slower than just using a list. Build it once, outside the loop, then check membership repeatedly against it.

Procedure 51.2 (Detect and Fix an Array-of-Structs Cache Problem). When to use: processing a large collection of multi-field records (rows, points, particles) with a reduction (sum, mean, filter) over just one field at a time, and it’s slower than it feels like it should be.

Before converting, ask three diagnostic questions: do most operations scan or reduce over one field across many records (convert to SoA); do most operations process all fields of one record together (stay AoS, or use a NumPy structured array as a middle ground); is nnn small, in the thousands rather than millions (the conversion may not be worth the added code complexity, measure first). Common mistake: converting to SoA and then still processing “one record” at a time by indexing into all four arrays at the same index (xs[i], ys[i], zs[i]). This throws away the entire benefit, since access is back to non-contiguous, one-value-at-a-time, with extra bookkeeping on top. SoA only wins when the operations are also structured field-at-a-time, ideally as vectorized NumPy calls (Chapter 52).

Procedure 51.3 (Replace an O(n²)-to-Drain Queue with an O(n) One). When to use: code that repeatedly does list.append(x) and list.pop(0) (or list.insert(0, x)) to implement a FIFO queue.

deque supports append/appendleft/pop/popleft, all O(1)O(1)O(1); random access by index (d[i]) is O(n)O(n)O(n), so deque is not a good fit when frequent random indexing is required. Common mistake: assuming deque is a strict upgrade for every use of list. If code needs frequent random-index access (d[len(d)//2]), a list is faster for that specific operation. deque only wins for append/pop at the ends.

Procedure 51.4 (Decide Which Fix Category Applies to a Slow Function). When to use: a hot function has been found through profiling (Chapter 50), but it isn’t yet clear which fix category applies. Walk through, in order: does it do x in some_collection inside a loop (membership check, consider set/dict); does it reduce over one field of many multi-field records (layout check, consider SoA); does it .pop(0) or .insert(0, ...) on a list repeatedly (queue pattern, use deque). Common mistake: reaching for parallelism (Chapter 53) or GPU offload (Chapter 55) before checking whether a data-structure fix removes the bottleneck entirely at a fraction of the engineering cost. A 76,000x algorithmic fix (this chapter’s membership result at n=1,000,000n=1{,}000{,}000n=1,000,000) will always beat whatever a few extra cores or a GPU can add on top of the wrong data structure.

51.6 History and Further Reading

The measured effects in this chapter trace back to two well-documented pieces of the CPython implementation: Objects/listobject.c, which implements list.pop(0)’s element-shifting behavior directly, and Objects/setobject.c, which implements set and dict hashing and open addressing. Ulrich Drepper’s “What Every Programmer Should Know About Memory” (Drepper 2007) remains the canonical deep treatment of cache behavior and layout effects on real hardware, and is worth reading in full once the SoA-versus-AoS result here has been felt on real data rather than just read about. Burkov’s discussion of algorithmic considerations in feature engineering pipelines touches on similar ground from the modeling side (Burkov 2019).

51.9 Mental Model

Big-O is the shape of the road: does it get steeper as more cargo is added, or stay flat, genuinely important, and the first thing to check. But two trucks can drive the exact same flat road and one still arrives 100x slower, because one has its cargo pre-sorted into the right compartments (SoA) and the other has it scattered loose in the back, forcing the driver to dig through everything to find each item (AoS). The road’s shape never captures that difference at all.
