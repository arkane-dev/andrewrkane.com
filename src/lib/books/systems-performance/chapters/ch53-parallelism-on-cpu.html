Chapter 48 measured Amdahl’s Law’s ceiling using multiprocessing, without asking why multiprocessing rather than threading. This chapter answers that directly: Python has a specific, well-known constraint, the Global Interpreter Lock (GIL), that determines which of threading, multiprocessing, or asyncio-style concurrency actually helps for a given workload, and getting this choice wrong is one of the most common ways to add real complexity for zero real speedup.

53.1 Motivation

One mechanism explains almost the entire decision this chapter is built around: the GIL allows only one thread to execute Python bytecode at a time per process, but it is released during I/O waits and some C-extension calls. This single fact splits all workloads into two categories with opposite correct answers. CPU-bound work (arithmetic, data processing, anything that keeps the interpreter busy executing Python bytecode) gets essentially no speedup from threading, because the GIL serializes the actual work regardless of thread count. multiprocessing is the correct tool, since each process gets its own interpreter and its own GIL. I/O-bound work (network calls, disk reads, anything spending most of its time waiting rather than computing) works well with threading, because the GIL is released during the wait, letting other threads run. multiprocessing also works for I/O-bound work, but with unnecessary overhead (process-spawn cost, inter-process data serialization) that threading avoids.

53.2 Exposition

This chapter’s measured numbers† come from this book’s reference rig (see the preface): its AMD Ryzen 9 5950X, 16C/32T.

53.2.1 CPU-Bound: The GIL Makes Threading Flat, Multiprocessing Scale

An identical CPU-bound function (summing squares over 10,000,000 iterations) run across 1, 2, 4, and 8 workers, once with threading.Thread and once with multiprocessing.Pool, each speedup measured against the ideal (N×N \timesN× the 1-worker baseline):

Workers Threads (speedup vs. ideal) Processes (speedup vs. ideal)
1 1.04x 1.00x
2 1.00x 1.97x
4 1.01x 3.82x
8 1.00x 7.24x†

Threads plateau at roughly 1.0x no matter how many are added. That flat line, not a gradual decline, is the GIL’s signature. It isn’t that threading gets less effective with more threads. It’s that threading was never providing real CPU parallelism in the first place, at any count. Processes, in contrast, scale close to linearly with worker count, because each process runs its own independent Python interpreter with its own GIL, genuinely executing on separate CPU cores simultaneously.

53.2.2 I/O-Bound: The Opposite Result, Equally Real

Repeating the comparison with an I/O-bound function (time.sleep(0.2), standing in for a network call or disk read) across ThreadPoolExecutor and ProcessPoolExecutor, against a serial (8 x 0.2s) baseline of 1.601s:

Workers ThreadPoolExecutor speedup ProcessPoolExecutor speedup
2 2.00x 1.98x
4 3.99x 3.90x
8 7.95x 7.37x

Both scale almost perfectly linearly, and threads and processes are close to indistinguishable. time.sleep() releases the GIL for the duration of the wait, exactly like a real network socket read or disk I/O call, which also release the GIL while blocked in the underlying system call. With the GIL released, multiple threads genuinely overlap their waiting periods. Since threads avoid the process-spawn and inter-process-communication overhead that processes carry, threading is the better default for I/O-bound work specifically because it gets the same scaling for less cost, not because it’s “faster” in some general sense.

53.2.3 joblib: A Real Convenience/Overhead Trade-Off

Running the same 8-way CPU-bound workload through raw multiprocessing.Pool versus joblib.Parallel, both using 8 workers:

Approach Time
Raw multiprocessing.Pool(8) 0.387s
joblib.Parallel(n_jobs=8) 0.515s (33% slower)

This is a genuine cost, not a measurement artifact. joblib’s default loky backend adds process-management robustness (automatic worker recycling, better cross-platform behavior, more graceful handling of crashed workers) on top of what raw multiprocessing provides. For a performance-critical hot path where the environment is fully controlled, that overhead may not be worth paying; for a production data pipeline where reliability matters more than shaving milliseconds, it usually is.

53.2.4 Pool Creation Overhead: A Real, Large Number

Creating a fresh 4-worker pool, running four tiny tasks (1,000 iterations each), and tearing the pool down, repeated 20 times, took 11.3 ms per iteration. Running the identical tiny tasks serially, with no pool at all, took 0.12 ms per iteration. Creating a pool for trivial work was 96x slower than not parallelizing at all.

Process creation has a genuine fixed cost (forking or spawning a new OS process, starting a fresh Python interpreter inside it, tearing it down afterward) that is completely independent of how much work the pool actually does. For a small enough task, that fixed cost dwarfs any benefit from spreading the work across cores. Chapter 48’s troubleshooting guidance already flagged “creating a new Pool inside the timed region” as a common mistake in the abstract. This measurement puts a concrete, large number on exactly how costly that mistake is.

53.3 Trade-offs and Limits

Use multiprocessing (or ProcessPoolExecutor) when the workload is CPU-bound (real computation, not waiting), since this is the only way to get genuine multi-core speedup for such work in standard CPython, and when the per-task work is large enough to amortize process-spawn overhead (create the pool once, reuse it for many tasks, never inside a hot loop). Use threading (or ThreadPoolExecutor) when the workload is I/O-bound (network, disk, waiting on external resources) to get the same scaling as multiprocessing with far less overhead, and when shared in-memory state between workers is needed without the serialization cost of passing data between processes. Use joblib when multiprocessing’s CPU-bound benefits are wanted alongside better reliability, crash-recovery, and a more convenient API, and the roughly 30-50% overhead versus the rawest possible approach can be afforded, or when already inside a data-science stack where joblib is a standard dependency, such as scikit-learn, which uses it internally.

53.4 Procedures

Procedure 53.1 (Decide Between Threading and Multiprocessing). When to use: before writing any concurrent code. Get this decision right first, since the wrong choice can mean zero benefit for real added complexity.

Common mistake: reaching for threading to speed up a CPU-bound Python function. This chapter’s own measurement shows this gives a flat ~1.0x “speedup” regardless of thread count (1 through 8). The GIL fully serializes CPU-bound bytecode execution, so more threads simply queue up rather than run concurrently.

Procedure 53.2 (Parallelize CPU-Bound Work Correctly). When to use: a profiled (Chapter 50), genuinely CPU-bound function needs to process many independent items faster.

Common mistake: creating a new Pool for every batch of work inside a loop. This chapter’s own measurement found this costs ~96x more than not parallelizing at all for small tasks. Process creation has a real, fixed cost independent of task size. Create the pool once, submit all the work through it, and only tear it down once all of it is done.

Procedure 53.3 (Parallelize I/O-Bound Work Correctly). When to use: fetching many URLs, querying a database repeatedly, or reading many files: anything spending most of its time waiting, not computing.

Common mistake: limiting thread count to the CPU core count for I/O-bound work. Since threads are mostly waiting, not computing, far more threads than CPU cores can profitably be run. The bottleneck is the external resource (network latency, disk), not CPU availability. Chapter 55 covers the analogous mistake in the CPU/GPU context: assuming CPU core count is always the right concurrency limit.

Procedure 53.4 (Choose Between joblib and Raw multiprocessing). When to use: deciding how much reliability/convenience overhead is worth paying for a given parallel workload.

Common mistake: assuming joblib and raw multiprocessing.Pool are interchangeable with identical performance. This chapter measured joblib at roughly 33% slower than raw multiprocessing.Pool for an identical CPU-bound workload, real overhead from joblib’s loky backend’s extra process-management machinery. Use joblib when its convenience and crash-recovery robustness matter, or when already using it via scikit-learn; use raw multiprocessing when squeezing out the last bit of performance in a fully-controlled environment matters more.

53.6 History and Further Reading

Beazley’s 2010 talk “Understanding the Python GIL” remains the classic, still-relevant deep explanation of what the GIL actually does and doesn’t serialize, and is worth watching once this chapter’s flat-threading result has been measured directly rather than just read about. The Python multiprocessing and concurrent.futures standard library documentation is the authoritative API reference and the standard library’s own guidance on process versus thread pools. The joblib documentation’s “Embarrassingly parallel for loops” page gives the library’s own framing of when its overhead is and isn’t worth paying. PEP 703, “Making the Global Interpreter Lock Optional,” documents the in-progress CPython effort toward a no-GIL build. It’s worth knowing this constraint is actively being relaxed in future Python versions, even though it applies in full to the environment this chapter’s numbers were measured on. Rotem’s Software Performance Engineering (Rotem 2025), Chapter 6, names the GIL specifically as a “performance antipattern,” alongside other language- and process-level antipatterns (premature optimization, tight coupling, busy waiting); confirmation this chapter’s flat-threading result is a recognised class of failure in the wider field, not a quirk specific to this chapter’s benchmark.

53.7 How This Connects

This chapter builds on Chapter 48’s Amdahl’s Law measurement (that chapter’s multiprocessing.Pool choice is now explained, not just asserted) and on Chapter 48’s benchmarking discipline, used throughout for every number above. It enables Chapter 55’s “should this move to GPU” question, which partly asks whether CPU parallelism (this chapter) has already been exhausted first. GPU offload is a much bigger step than adding worker processes, and is only worth taking once the cheaper lever has been tried. It is often confused with asyncio, a third concurrency model, best for very high volumes of I/O-bound work with a single thread using cooperative scheduling instead of OS threads. asyncio solves the same class of problem as threading for I/O-bound work but with different trade-offs: no OS thread-switching overhead, but it requires async/await-aware libraries throughout, and is not covered in depth in this book.

53.9 Mental Model

Threads sharing one Python interpreter are like several cashiers sharing a single cash register key. Only one can actually ring up a sale at a time, no matter how many cashiers are standing at the counter, so adding more cashiers to this specific task doesn’t speed up the ringing up part at all. But if the register key is handed over willingly during a wait, a customer digging for exact change, the I/O wait, other cashiers can use it in the meantime, and having several on hand genuinely speeds up serving many customers with a lot of that kind of wait. Processes are separate stores entirely, each with its own register key, genuinely serving customers in parallel, at the real cost of opening and staffing an entire additional store.
