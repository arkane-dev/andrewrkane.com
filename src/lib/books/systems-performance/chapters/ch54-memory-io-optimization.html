Every chapter so far in this track has assumed data is already resident in memory, ready to compute on. Real workloads spend real time getting data into memory in the first place: reading files, allocating objects to hold what was parsed, managing buffers, and that stage has its own failure modes, independent of anything CPU-bound covered previously. This chapter covers three of the most common: reading a file in the wrong chunk size, choosing the wrong access pattern for a large file, and paying avoidable per-object memory overhead at scale. One of the four results below is a debunked myth, included deliberately: not every “optimization” habit that sounds plausible turns out to be real once it’s measured.

54.1 Motivation

Three mechanisms, each with a measured signature on this book’s reference rig. First, every I/O operation carries a fixed per-call cost (Python function dispatch, a kernel system call, buffer bookkeeping) independent of how much data that call actually moves. Calling read() too many times for too little data each time can dominate total runtime completely. Second, memory-mapped files (mmap) trade a page-fault cost on first access for zero system-call cost on every subsequent access to the same page: a clear win for repeated or random access to data that stays cached, and no better (sometimes measurably worse) for a single sequential pass. Third, Python object memory layout has real, measurable overhead, a per-instance __dict__ by default, that __slots__ can remove. But some “common knowledge” optimizations turn out to already be handled by the interpreter itself, adding nothing.

54.2 Exposition

54.2.1 Read Chunk Size: The Dominant, First-Order Effect

Every read() call pays fixed overhead regardless of how many bytes it returns: a Python-level function call, a transition into kernel space for the underlying system call, and buffer management on both sides. At chunk size 1, that fixed cost is paid once per byte; at chunk size 1MB, it’s paid once per megabyte-plus. This is the same shape of lesson as Chapter 53’s process-pool-creation finding, fixed per-operation overhead dominating when the operation is called far more often than the work justifies, applied here to file I/O instead of process spawning.

54.2.2 OS-Level Buffering: A Real, Much Smaller, Sometimes Negative Effect

Holding the application-level read chunk fixed and varying only the OS-level read-ahead buffer (Python’s buffering= parameter) is a genuinely different lever from application-level chunk size, and a much weaker one. Once the application is already requesting data in reasonably large chunks, the OS’s own read-ahead buffer has little additional overhead left to amortize. At an extreme buffer size, the cost of allocating and managing that large a buffer on every file open can outweigh any remaining benefit. The practical ordering of effort: fix application-level chunk size first. Only consider tuning OS-level buffering after that, and verify it actually helps rather than assuming bigger is always better.

54.2.3 Memory-Mapped Files: A Genuine Win, With an Honest Asterisk

mmap maps a file’s pages directly into a process’s own virtual address space. The very first access to any page still pays a real page-fault cost either way. mmap doesn’t avoid that, and constructing a Python bytes object from an mmap slice has its own overhead that a direct read() call doesn’t. So on a single cold pass over a file, mmap is not automatically faster, and can measure slightly slower than a well-chunked seek()+read() loop. The advantage shows up specifically on repeated access to already-cached pages: seek()+read() issues a real system call on every single access, even when the requested data is already sitting in the OS page cache, paying that kernel-transition cost every time regardless of caching. mmap, once a page is resident, turns a read into an ordinary memory access with no system call at all. The complete, honest picture: mmap’s advantage is specifically for repeated or random access to data that stays resident in cache. For a single sequential pass over a file, a well-chunked regular read is simpler to write and just as fast.

54.2.4 __slots__: A Real, Measurable Memory Win

A regular Python object stores its attributes in a per-instance __dict__, flexible, since attributes can be added dynamically at any time, but carrying real memory overhead per instance. __slots__ tells Python to allocate fixed, dictionary-free storage for exactly the declared attributes instead, at the cost of that flexibility. For a program holding millions of small objects, parsed records, graph nodes, particles in a simulation, this is not an academic difference. It can decide whether a dataset fits in RAM at all.

54.2.5 A Debunked Myth: List Preallocation

A widely repeated piece of Python performance folklore holds that preallocating a list ([None] * n, then filling by index) should beat growing it with repeated .append() calls, by analogy with how C or C++ arrays are typically handled. This turns out to be false for CPython specifically: CPython’s list already over-allocates its backing array internally, growing it in chunks larger than strictly needed so that .append()’s occasional resize cost is amortized across many calls, precisely the manual optimization the “preallocate first” habit is trying to hand-roll, already done for you by the interpreter. This does not generalize to every container or every language: a NumPy array, or a language without CPython’s amortized-growth strategy, would show a real, large gap between the two approaches.

54.3 Trade-offs and Limits

Optimize read chunk size first, always. It is the single largest, most reliable lever in an I/O-bound pipeline, and should be checked before anything else. Reach for mmap when access to a large file is repeated and/or random, and the working set fits in available RAM or page cache; not for a single sequential pass, where plain buffered reads are simpler and equally fast. Reach for __slots__ when holding large numbers, thousands to millions, of instances of a simple, fixed-attribute class; skip it for a handful of objects, or for classes that genuinely need dynamic attribute assignment. Don’t bother hand-optimizing list growth in pure Python. CPython’s amortized list growth already does this. Spend the effort instead on the algorithm or data-structure choice (Chapter 51), or reach for NumPy (Chapter 52) if the container really is large and numeric, since np.append in a loop is genuinely slow and preallocating a NumPy array is a real, large win there.

54.4 Procedures

Procedure 54.1 (Choose a Read Chunk Size). When to use: reading a large file and unsure what chunk size to use. The default, first-line answer for any new I/O-bound routine.

Common mistake: reading line-by-line or byte-by-byte on a large binary or high-throughput file “to save memory,” then being surprised at the runtime. If memory is genuinely a constraint, use a moderate chunk size (64KB-1MB) rather than the smallest possible one. The memory savings from going smaller are marginal while the per-call overhead cost is severe.

Procedure 54.2 (Decide Whether mmap Will Help an Access Pattern). When to use: before reaching for mmap as a general “faster file access” fix, rather than after.

Ask first: is the access pattern repeated or random over the same region of a large file? If yes, mmap is likely to help. If the access is a single sequential pass over the whole file, a plain buffered read() loop (Listing 54.1) is simpler to write and measures just as fast. Common mistake: expecting mmap to be faster on the very first access to a large file. The first touch of any page pays a real page-fault cost regardless of access method; mmap’s advantage only shows up once pages are already resident in the OS page cache from a prior access.

Procedure 54.3 (Reduce Memory Overhead for Large Collections of Small Objects). When to use: holding millions of instances of a simple class with a fixed, known set of attributes.

Common mistake: adding __slots__ to a class that needs dynamic attribute assignment, or that participates in multiple inheritance with non-__slots__ base classes in a way that breaks. Check that every attribute the class will ever need is declared, and that __slots__ doesn’t conflict with a parent class’s __dict__. For simple, fixed-shape “record” classes, it’s a safe, meaningful win.

Procedure 54.4 (Check Whether “Preallocate for Performance” Actually Helps, Before Assuming It Does). When to use: deciding whether to preallocate a list before filling it, versus just appending.

Common mistake: assuming preallocation habits from C/C++ transfer directly to Python’s list. They don’t. CPython’s list already over-allocates its backing array internally, amortizing .append()’s occasional resize cost. This does not apply to NumPy arrays: preallocating a NumPy array (np.empty(n), then filling by index) is a real, large win there. Know which container is in use before applying, or dismissing, this habit.

54.5 Worked Example

All measured numbers in this chapter† come from this book’s reference rig. See the preface. The companion notebook builds a 210MB test file and reads it in chunks of 1, 64, 4,096, and 1,048,576 bytes. Chunk size 1 took 8,322.8 ms† (25.2 MB/s, roughly 210 million read() calls); chunk size 1MB took 13.7 ms† (15,258.4 MB/s, roughly 200 calls), a greater than 600x difference for moving the exact same bytes, purely from how many bytes were requested per call. The intermediate points confirm the trend is smooth, not a two-point artifact: 64 bytes took 217.0 ms, 4,096 bytes took 55.0 ms.

Holding the application-level chunk fixed at 1MB and varying only buffering=: unbuffered (0), default-ish (4KB), and 1MB all measured within noise of each other (12.9-13.1 ms). 16MB buffering measured slower, 66.4 ms, roughly 5x worse than the smaller settings, a genuine negative result from over-tuning a second-order lever once the first-order one (chunk size) was already fixed.

A single cold pass over 50,000 random 64-byte reads from a 500MB file measured seek()+read() at 77.0 ms against mmap at 94.4 ms, mmap actually slightly slower, ratio 0.82x, an honest unforced negative result rather than a mistake. Repeating the identical 50,000 reads after warming the page cache with one throwaway pass flipped the comparison entirely: seek()+read() took 90.3 ms (1.81µs/read); mmap took 7.2 ms (0.14µs/read), a genuine 12.5x speedup, entirely attributable to mmap eliminating a system call per access once the data is already cached.

Creating 100,000 instances of an ordinary Python class used 12.02 MB (120 bytes/object); the identical class with __slots__ = ('x', 'y') used 8.81 MB (88 bytes/object), a 26.7% memory reduction with no other code changes. Finally, timing three ways of building a 5,000,000-element list: append-growth took 149.1 ms, preallocate-then-fill took 142.4 ms, statistically indistinguishable, and a plain list comprehension was fastest at 135.9 ms, for the unrelated reason of avoiding repeated .append method-lookup overhead via dedicated bytecode, not any allocation difference. The preallocation myth is genuinely false for CPython specifically, not merely overstated.

54.6 History and Further Reading

The Python io module documentation is the authoritative reference on buffering modes and the actual semantics of the buffering= parameter used in this chapter’s second Exposition section. The mmap module documentation, alongside man 2 mmap, covers the underlying system call mmap wraps and its page-fault and caching behavior in more depth than this chapter’s summary. The Python data model documentation’s section on __slots__ gives the authoritative explanation of the __dict__-versus-__slots__ memory trade-off. For readers who want to see the amortized-growth strategy behind this chapter’s list-preallocation finding in the actual source, CPython’s Objects/listobject.c implements it directly. Fregly’s AI Systems Performance Engineering (Fregly 2026), Chapter 5, covers the same read-chunk-size mechanism at the scale of feeding GPU clusters from network or NVMe storage, 1MB reads beating 4KB reads for the identical per-call-overhead reason this chapter measures locally, worth reading once this chapter’s single-machine chunk-size result has been seen directly.

54.9 Mental Model

Reading a file one byte at a time is like moving a house one book at a time, walking back to the truck after each one. The truck’s capacity is irrelevant if you never load more than one book per trip. mmap is arranging for the boxes to already be sitting in the room you need them in, so grabbing one is just reaching over rather than a whole round trip, genuinely faster once the boxes are actually there, but no help at all for the very first trip that has to fetch them from the truck in the first place.
