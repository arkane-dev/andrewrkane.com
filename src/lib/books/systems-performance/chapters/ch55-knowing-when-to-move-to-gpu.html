Chapters 48 through 54 exhausted the CPU-side levers this track has to offer: cache locality, profiling discipline, algorithmic and data-structure choice, vectorization, parallelism, memory and I/O. This chapter asks the question those chapters deliberately deferred: when has “make the CPU version faster” stopped being the right lever, and “move this to GPU” become the correct next step? The honest answer is not “always” or “for anything big enough.” It is a specific, computable property of the operation itself, and this chapter measures both a case where GPU offload never helps, at any size tested, and a case where it clearly does, on the same real hardware, so the comparison is not hypothetical.

55.1 Motivation

Two mechanisms determine the answer, together. First, every GPU offload pays a fixed transfer cost, moving data across PCIe to the GPU’s own memory, and back, that has nothing to do with how fast the GPU itself computes. Second, arithmetic intensity (FLOPs performed per byte of data moved) determines whether an operation can ever amortize that transfer cost. Low, size-independent intensity means transfer cost dominates forever, no matter how large the problem gets; intensity that grows with problem size means there is a real crossover point past which the GPU’s much larger raw compute throughput wins decisively. Knowing which regime an operation is in, before writing a single line of GPU code, is the actual skill this chapter teaches.

55.2 Exposition

55.2.1 Transfer Overhead Is Real, and Textbook Mitigations Aren’t Guaranteed

Moving data across PCIe is a much narrower pipe than either the CPU’s own memory bus or the GPU’s on-board HBM bandwidth. A round-trip host-to-device-to-host transfer implies bandwidth far below either side’s own internal memory bandwidth, because the transfer is specifically limited by the interconnect between them, not by either processor’s own memory subsystem. Small transfers fare worse proportionally still: at the smallest sizes, fixed per-call overhead (driver and API call cost, DMA setup) dominates almost completely over the actual (negligible) data volume being moved, the same fixed-cost-per-operation shape Chapter 54 found for read() calls, now recurring at the PCIe level instead of the filesystem level.

The standard textbook mitigation for transfer cost is pinned (page-locked) host memory, which is supposed to avoid an intermediate staging copy and speed up DMA transfers meaningfully. Measured directly on this book’s reference rig, pinned memory gave only a modest improvement over ordinary pageable memory, real, but far below the two-to-three-times improvement sometimes quoted in general guidance. This is an honest, measured result, not a failed demo. It is a direct instance of this track’s recurring “verify, don’t assume a textbook effect transfers unchanged to your stack” lesson, applied here to a GPU-specific optimization instead of a CPU one.

55.2.2 A Memory-Bound Operation: GPU Never Wins

Consider x * 2.0 + 1.0: 2 FLOPs and 2 memory accesses (one read, one write) per element. Timed on CPU versus GPU-including-transfer, across sizes from 1,000 to 100,000,000 elements, GPU’s best result on this hardware was a near-tie at a middle size, falling to a clear loss everywhere else, including the very largest size tested. This operation’s arithmetic intensity is a constant 0.25 FLOPs/byte, completely independent of n. Doubling the array doubles both the compute and the data moved in lockstep, so there is no way to “grow into” a regime where compute dominates transfer. No array size makes this operation worth offloading on this hardware, full stop, not because GPUs are slow, but because this operation’s fundamental shape never lets the GPU’s raw compute advantage show up before the transfer cost has already lost the race.

55.2.3 A Compute-Bound Operation: A Real, Computable Crossover

Timing matrix multiplication (A @ B) the same way, across n from 64 to 4096, produces a genuine, hardware-measured crossover. GPU loses at the smaller sizes and wins decisively past a specific size, rising to a peak speedup before settling to a still-substantial win at the largest size tested, not perfectly monotonic (real measurements rarely are) but decisively favoring GPU past the crossover point. The mechanism: matmul’s arithmetic intensity is 2n³ FLOPs over roughly 3n² float32 elements moved, which grows linearly with problem size. Computed directly for the sizes in this chapter’s Worked Example, intensity rises by roughly two orders of magnitude from the smallest matrix tested to the largest. Past a certain intensity, the operation is no longer limited by how fast data can be shipped across PCIe. It is limited by how fast the processor can compute, and a GPU’s peak compute throughput vastly exceeds a CPU’s, Chapter 52’s SIMD story, at a much larger scale, so the crossover, once intensity is high enough, tips decisively toward GPU.

55.2.4 The Roofline Model: Why These Two Cases Diverge

The roofline model plots achievable performance against arithmetic intensity: below a hardware-specific “ridge point,” performance is capped by memory bandwidth (more compute doesn’t help, because the processor is waiting on data, not arithmetic); above it, performance is capped by the processor’s peak compute throughput. Elementwise operations sit permanently to the left of the ridge, at a fixed intensity that never changes with n. There is no path to the compute-bound region no matter how big the problem grows, which is exactly why the elementwise result above held across six orders of magnitude. Matmul’s intensity climbs with n, eventually crossing the ridge into the compute-bound region, exactly where the matmul crossover happened. This gives a real, computable answer to “should this move to GPU”: compute the operation’s arithmetic intensity (FLOPs divided by bytes moved) and check whether, and at what size, it crosses this hardware’s ridge point, rather than guessing from how large the array “feels.”

55.3 Trade-offs and Limits

Move an operation to GPU when its arithmetic intensity is high, or grows with problem size (matrix multiplication, convolutions, most dense linear algebra, the operations underlying deep learning, which is exactly why GPUs took over that field) and the problem size is large enough to be past this hardware’s measured crossover point, computed rather than assumed. Keep an operation on CPU when arithmetic intensity is low and size-independent (elementwise operations, simple reductions, most “glue” code in a data pipeline) or when the CPU-side levers of Chapters 48 through 54 haven’t been exhausted yet. GPU offload is a much bigger architectural step than adding vectorization or parallelism, and shouldn’t be reached for before the cheaper options are tried. Watch for transfer overhead swamping a genuine per-call GPU compute win on small or frequent operations. Batch work to amortize transfer cost, exactly like Chapter 53’s pool-reuse lesson and Chapter 54’s chunk-size lesson, and watch for assuming a textbook GPU optimization like pinned memory transfers unchanged to a specific hardware and software stack, when it should be measured instead.

55.4 Procedures

Procedure 55.1 (Compute an Operation’s Arithmetic Intensity). When to use: before deciding whether an operation is a GPU-offload candidate at all. The first, cheapest step, requiring no benchmarking.

Common mistake: judging GPU-worthiness by total data size alone (“it’s a big array, GPU should help”). This chapter’s Worked Example measured a 100-million-element elementwise operation that was still slower on GPU, including transfer, than on CPU. Size alone doesn’t determine intensity. The ratio of compute to data movement does, and that ratio can stay flat regardless of how large the array gets.

Procedure 55.2 (Measure a Hardware’s Own CPU/GPU Crossover Point). When to use: deciding whether a specific operation, at actual production data size, belongs on CPU or GPU. Never assume a crossover point from a different machine.

Common mistake: benchmarking GPU compute time alone, without the transfer, and concluding “GPU is N times faster.” The honest number, the one that determines whether offloading is actually worth it in a real pipeline, must include the round trip. Always call torch.cuda.synchronize() before and after timing; CUDA operations are asynchronous by default, and omitting synchronization will silently under-report GPU time.

Procedure 55.3 (Decide: Keep This on CPU, or Move It to GPU?). When to use: a concrete decision checklist for a specific operation and data size, before writing any GPU-specific code.

  1. Have Chapters 48 through 54’s CPU-side levers already been applied: vectorization, parallelism, cache-friendly layout? If not, try those first; they’re cheaper than a GPU port, and this chapter’s own elementwise result shows a well-vectorized CPU op can beat a naive GPU port outright.
  2. Compute the operation’s arithmetic intensity (Listing 55.1). Does it grow with problem size, like matmul, or stay flat, like elementwise ops? Flat-and-low intensity means GPU offload is unlikely to ever pay off, regardless of size.
  3. If intensity does grow with size, measure the actual crossover point on the target hardware (Listing 55.2). Don’t assume a number from a different GPU, PyTorch version, or PCIe generation transfers unchanged.
  4. If moving to GPU, check whether the same data will be reused across multiple GPU operations before transferring back. Amortizing one transfer cost across many GPU-side operations changes the calculus significantly compared to a single transfer-compute-transfer round trip.

Common mistake: making this decision once for an operation and never revisiting it. Data sizes, batch sizes, and hardware change. A decision that correctly kept an operation on CPU at last year’s data volume may no longer hold; re-measure rather than assume the old conclusion still applies.

55.5 Worked Example

All measured numbers in this chapter† come from this book’s reference rig. See the preface. Round-trip host-to-device-to-host transfer, measured at several sizes: a 1,000-element transfer took 0.025 ms†, implying only 0.32 GB/s, dominated almost entirely by fixed per-call overhead rather than the negligible actual data volume. A 100,000,000-element transfer (800MB total) took 203.23 ms†, implying roughly 3.94 GB/s, real bandwidth at last, but nowhere near either side’s own internal memory bandwidth, because this is specifically the PCIe interconnect, a much narrower pipe. Testing pinned versus pageable host memory on a 100,000,000-float host-to-device transfer: pageable took 29.79 ms (13.43 GB/s); pinned took 27.65 ms (14.47 GB/s), a 1.08x† improvement, real but far below textbook expectations on this exact hardware/driver/PyTorch combination.

The elementwise operation x * 2.0 + 1.0, timed CPU versus GPU-including-transfer from n=1,000 to n=100,000,000: GPU’s best result was 0.98x† at n=100,000, essentially a tie, still not a genuine win, falling to 0.3-0.6x everywhere else, including the very largest size tested (0.39x at n=100,000,000). GPU never wins for this operation, at any tested size, across six orders of magnitude.

Matrix multiplication, timed the same way from n=64 to n=4096: GPU lost at n=256 (0.77x) and won starting at n=512 (1.08x, the crossover), rising to a 3.21x peak at n=2048 before settling to 2.52x at n=4096. Computed arithmetic intensity over the same range rises from 10.7 FLOPs/byte at n=64 to 682.7 FLOPs/byte at n=4096, a genuinely computable property that predicts the crossover directly, rather than requiring it to be discovered by trial and error each time.

55.9 Mental Model

Moving work to a GPU is like sending a job to a distant, extremely fast specialist workshop. The workshop can do far more work per hour than a local shop, but every job has to be physically couriered there and the finished piece couriered back, and that round trip has a real, roughly fixed cost regardless of how small the job is. A quick, simple job, the elementwise operation, never earns back the courier cost, no matter how many times it’s sent. Cheaper to just do it locally. A large, intricate job, a big matmul, easily earns back the courier cost many times over, because the specialist workshop finishes it so much faster than the local shop could.
