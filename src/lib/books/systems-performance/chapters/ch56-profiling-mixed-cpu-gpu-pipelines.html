Chapter 55 decided, for a single isolated operation, whether CPU or GPU was the right home. Real pipelines are rarely a single operation. They interleave CPU-side work (data loading, preprocessing, control flow) with GPU-side compute, and the question “which side is the bottleneck” can only be answered by measuring the whole pipeline together, not either side in isolation. This chapter uses Nsight Systems (nsys), a real system-level profiler that records both CPU and GPU activity on a shared timeline, to answer that question with evidence rather than assumption.

56.1 Motivation

Two lessons compound in this chapter: naive whole-process timing can be dominated by one-time fixed costs (here, import torch and CUDA context initialisation) that have nothing to do with the pipeline logic actually being measured. This is Chapter 48’s “isolate the region you care about” discipline, resurfacing at the process level. And GPU utilisation, the fraction of wall-clock time the GPU is actually busy, is the real, measurable answer to “is the GPU the bottleneck,” and nsys gives it directly from real kernel and memory-copy records, rather than requiring it to be inferred indirectly from timing differences alone. Worked Example 56 below measures both effects on the same small CPU-preprocess-then-GPU-matmul pipeline.

56.2 Exposition

56.2.1 The Naive Comparison Lies About the Size of the Fix

Comparing two versions of a small pipeline, identical except one preprocessing step is a slow Python loop, the other a vectorized expression, by timing the whole process end to end gives an unimpressive apparent speedup, because import torch alone takes several hundred milliseconds and CUDA context initialisation adds more, as fixed, one-time costs present in both versions that swamp whatever the actual loop is doing. This is exactly the single-naive-measurement trap from Chapter 48, recurring at the scale of an entire process invocation rather than a single function call.

56.2.2 Isolating the Loop Reveals the Real Effect

Instrumenting the script to report import time, CUDA-init time, and loop time separately reveals the genuine per-iteration effect, hidden entirely by whole-process timing. The lesson isn’t new. Chapter 48 established it. But the failure mode recurs at every scale, here at the level of comparing two entire program runs rather than two function calls.

56.2.3 nsys Measures GPU Busy Time Directly, Not by Inference

Profiling both versions with nsys profile and summarising with nsys stats --report cuda_gpu_kern_sum --report cuda_gpu_mem_time_sum gives exact, measured totals for every CUDA kernel launch and every host-device memory copy across the whole run, the direct, measured confirmation of what timing numbers alone can only imply indirectly.

56.2.4 NVTX Ranges: Labelling Which Phase the Time Belongs To

The previous section’s nsys totals answer “how much GPU work happened,” summed across the whole run. They don’t say which part of the per-batch loop each nanosecond belongs to. NVTX ranges close that gap: torch.cuda.nvtx.range_push('label') and range_pop(), wrapped around a specific region of code, tag every kernel launch and CPU-side interval inside that region with the label. nsys stats --report nvtx_sum then reports total and per-instance time per label, directly, rather than requiring the two-pipeline-comparison trick this chapter has used so far to infer where time went. This turns “the CPU-side fix helped” (inferred from comparing two whole runs) into “the preprocess range took this many milliseconds, the matmul range took this many” (measured directly, from one run).

56.2.5 GPU Utilisation: The Real Bottleneck, Quantified

Dividing GPU-busy time by isolated loop wall-clock time gives real GPU utilisation. A low number for a small-batch toy pipeline is an honest, important finding, not a flaw in the method: a single small matmul per batch is simply too small a GPU task to keep even a modest GPU consistently busy. The comparison between two pipeline versions is the useful result. Vectorizing CPU preprocessing can roughly double the fraction of time the GPU spends doing anything at all, by shrinking the CPU-side wait it was starved behind. Real production pipelines address low GPU utilisation specifically by using much larger batch sizes. A single large batch keeps the GPU busy for a proportionally larger slice of each iteration’s wall-clock time, the same “amortise fixed cost across more useful work” principle recurring throughout this book (pool reuse, chunk sizing, transfer-overhead amortisation).

56.3 Trade-offs and Limits

Profile the whole pipeline with nsys, not just isolated operations, when CPU and GPU work is interleaved and it’s unclear which side actually limits throughput, or when a wall-clock speedup from a CPU-side or GPU-side fix seems smaller than expected. One-time process overhead may be masking the real per-iteration effect. Isolate the code region of interest from process-level fixed costs whenever comparing two script versions by running each as a whole process. import and initialisation time can dominate short workloads and hide real per-iteration differences. Increase batch size, or otherwise give the GPU more work per CPU-GPU round trip, when nsys reveals low GPU utilisation and the workload’s arithmetic intensity (Chapter 55) suggests GPU offload should be worthwhile in principle. The gap is often that each individual GPU call is too small, not that GPU offload was the wrong call in the first place.

56.4 Procedures

Procedure 56.1 (Profile a Mixed CPU/GPU Script with Nsight Systems). When to use: any script using the GPU where CPU and GPU activity need to be seen together on one timeline.

Common mistake: profiling only a single iteration or a very short run. nsys needs enough activity for a statistically meaningful picture; profile a representative number of iterations, not just one.

Procedure 56.2 (Avoid the Whole-Process Timing Trap). When to use: comparing two script versions as separate process runs and getting a suspiciously small difference.

Common mistake: timing two script variants with a shell time command or a wrapper subprocess call and comparing those numbers directly. Always instrument the script to report the specific region of interest separately from one-time startup costs.

Procedure 56.3 (Compute GPU Utilisation from nsys Output). When to use: deciding whether a pipeline’s bottleneck is really the GPU, or the GPU is sitting idle waiting on something else.

Common mistake: assuming a slow pipeline with GPU code in it is “GPU-bound” without checking utilisation. Low GPU utilisation is a clear, actionable signal to look at the CPU side (or increase batch size), rather than optimising GPU kernels that are barely running.

Procedure 56.4 (Fix Low GPU Utilisation). When to use: nsys confirms the GPU is mostly idle.

Common mistake: jumping straight to multi-stream overlap before trying the simpler fixes. Check the cheaper options first, the same “measure before you architect a complex solution” discipline running throughout this book.

Procedure 56.5 (Label Pipeline Phases With NVTX Ranges). When to use: a pipeline has more than one distinct phase per iteration and it’s unclear which phase, specifically, dominates. The direct alternative to inferring this by comparing two whole-pipeline runs.

Common mistake: profiling without --trace=cuda,nvtx explicitly. Some nsys invocations trace CUDA activity by default but not NVTX ranges, and a script with range_push/range_pop calls that were never captured produces an empty or misleading nvtx_sum report with no indication anything was skipped.

56.5 Worked Example

Two versions of a 20-batch CPU-preprocess-then-GPU-matmul pipeline, identical except one preprocessing step is a slow Python loop, the other a vectorized expression, measured on this book’s reference rig†, three separate ways.

Whole-process timing (the naive, misleading comparison): slow pipeline 1,599.1ms† versus fast pipeline 1,432.8ms†, an unimpressive apparent 1.12x speedup for what should be a much larger fix.

Isolated-loop timing (Procedure 56.2, excluding import torch’s ~780ms† and CUDA init’s ~185ms†, identical fixed costs in both versions):

Pipeline 20-batch loop time Per-batch time
Slow (Python-loop preprocessing) 239.9ms† 12.00ms/batch
Fast (vectorized preprocessing) 97.9ms† 4.90ms/batch

A genuine 2.45x speedup, more than double what the naive whole-process comparison suggested, entirely attributable to the one changed line of code. This is Exposition’s claim measured directly: over 1,100ms of shared fixed cost, invisible to the loop logic, was masking most of the real effect.

nsys-measured GPU busy time (Procedure 56.1, confirming the fix was CPU-side, not GPU-side):

Slow pipeline’s total GPU-side work: 0.851ms†. Fast pipeline’s total GPU-side work: 0.849ms†, essentially identical, exactly as expected, since only the CPU-side preprocessing code changed between versions. This is the direct, measured confirmation of what the timing numbers already implied indirectly: the GPU did almost exactly the same amount of real work in both cases.

GPU utilisation (Procedure 56.3, dividing GPU-busy time by isolated loop time):

Pipeline GPU busy / loop time Utilisation
Slow 0.851ms / 239.9ms ~0.35%†
Fast 0.849ms / 97.9ms ~0.87%†

NVTX-labelled per-phase breakdown (Procedure 56.5, direct attribution rather than inferred from comparing two runs):

Slow pipeline, nsys stats --report nvtx_sum:
  preprocess:  70.1% of ranged time, median 6.855ms/batch
  matmul:      29.9% of ranged time, median 0.222ms/batch

Fast pipeline, nsys stats --report nvtx_sum:
  matmul:      95.7% of ranged time, median 0.149ms/batch
  preprocess:   4.3% of ranged time, median 0.081ms/batch

This is the same conclusion the isolated-loop timing and the GPU-utilisation calculation above both already pointed to, now measured directly rather than inferred: in the slow pipeline, preprocess consumes more than two-thirds of every batch’s time, dwarfing matmul; in the fast pipeline, the relationship flips, and matmul dominates instead, exactly as expected once the CPU-side bottleneck is removed. (The reported nsys stats --report nvtx_sum output also includes a mean and standard deviation per range, both dominated by a single first-iteration outlier, CUDA’s lazy kernel-cache warm-up on the very first launch, which is why the median, not the mean, is the number to trust here; a real, common profiling nuance worth knowing before it causes confusion on a real run.) Where the earlier GPU-utilisation numbers required running the pipeline twice and comparing, NVTX ranges answer “which phase dominates” from a single profiled run, with the phase boundaries drawn exactly where the code says they are.

Both numbers are low, and that’s an honest, important finding, not a flaw in the method: this toy pipeline’s single 256×256 matmul per batch is too small a GPU task to keep even a modest GPU consistently busy, let alone the reference rig’s RTX 5090. The comparison between the two versions is the useful result. Vectorizing the CPU preprocessing roughly doubled the fraction of time the GPU spent doing anything at all (0.35% → 0.87%), by shrinking the CPU-side wait it was starved behind, not by changing GPU work at all (confirmed above: 0.851ms vs. 0.849ms, essentially unchanged). Per Procedure 56.4, the next lever beyond this fix would be increasing batch size, giving the GPU proportionally more work per round trip.

AWS SageMaker Notes

This chapter’s whole-process-timing trap has a direct SageMaker analogue: comparing two SageMaker Training Job configurations by their reported total job duration can be similarly misled by fixed container-startup and model-loading overhead that has nothing to do with the per-epoch training loop being optimised. CloudWatch’s per-step or per-epoch custom metrics (logged from inside the training script, the same way Procedure 56.2 instruments import/loop time separately) avoid this trap the same way this chapter’s isolated-loop timing does. Always compare the specific region of interest, not total job wall-clock time, when evaluating a training-loop optimisation on SageMaker.

This chapter builds on Chapter 48’s benchmarking discipline (isolating the region actually being measured) applied at whole-process scale, and on Chapter 55’s arithmetic-intensity framework, which this chapter’s low-utilisation finding directly explains the practical consequence of. 56.9 Mental Model

A wall-clock stopwatch on the whole kitchen says dinner took an hour. It doesn’t say the oven (the GPU) was only actually cooking for two minutes of that hour, with the rest spent waiting on someone chopping vegetables by hand (the CPU preprocessing). nsys is a timer on the oven itself, alongside the kitchen’s overall clock. Only with both is it clear whether a faster oven would help at all, or whether the chopping is the real thing to fix. This chapter’s Worked Example measured exactly that distinction: nearly identical GPU work (0.851ms vs. 0.849ms) in both pipeline versions, with the entire real speedup (2.45x) coming from the chopping, not the oven.
